# Front-end end-to-end tests

The specs in this directory run the built app (`next build && next start`) against a **mock CMS**, a small Node server in `mock-cms/` that answers the WordPress REST routes the front end reads. Front-end e2e never uses wp-env, Docker or the hosted CMS: the mock needs nothing but Node, so the same run works on a laptop and in CI, and a spec can change the CMS's data mid-test without touching a WordPress install.

## Running

From the repository root:

```sh
pnpm web:test:e2e
```

Playwright starts the mock first, then builds and starts the app with `WP_API_URL` pointing at the mock (`playwright.config.ts`); the order matters, since the build prerenders from the mock. Chromium must be installed once: `pnpm exec playwright install chromium` in `apps/web`.

By default both servers are started fresh, and a port that is already taken fails the run rather than testing whatever answers on it. To iterate on a spec without rebuilding, opt in to reuse with `RH_E2E_REUSE=1`: leave `node e2e/mock-cms/main.mts` and `next start` running (with the same ports and environment the config would give them) and re-run `RH_E2E_REUSE=1 pnpm exec playwright test`. Reuse is never on in CI. A reused mock can be recognised: `GET /__mock/health` answers `{ ok, dir, build, pid, origin }`, where `dir` is the absolute path of the `mock-cms/` directory it runs from and `build` a SHA-256 of every file in that directory, its code and fixtures, read when the process started (`mock-cms/identity.mts`). `harness.spec.ts` fails when `dir` is not this checkout's, and when `build` differs from the files on disk now, which means the mock was started before its code last changed: stop it and run again. A reused app is checked the same way: `GET /fixtures/app-identity/` (a fixture route) answers `{ dir, pid, startedAt, stamp }`, the directory `next start` runs from, its process ID, when the process started and the build stamp it read from `.next/rh-e2e-build.json` (`build-stamp.mts`). `harness.spec.ts` fails, naming the process, when `dir` is not this checkout's app, when the build in `.next` is not the harness's build of the commit checked out now for these ports (`node e2e/build-stamp.mts verify`, the test a prebuilt run makes), when the server read another stamp than the one in `.next` now, and when the server started before `.next/BUILD_ID` was written, which means something rebuilt the app after it started: stop it and run again. Uncommitted edits since the build are not caught, as for a prebuilt run.

`RH_E2E_PREBUILT=1` skips the build and starts the app already in `.next`, which must be a build from this harness (`RH_FIXTURES=1`, the mock's `WP_API_URL`, the same ports). Every harness build writes a stamp, `.next/rh-e2e-build.json`, with the build's ID, the git commit checked out and the variables that change the build's output (`RH_FIXTURES`, `WP_API_URL`, `WP_MEDIA_ORIGIN`, `SITE_URL`; `build-stamp.mts`), and a prebuilt run checks it before it starts anything, so a production build from `pnpm web:build`, a build for other ports, one from another commit or a missing one fails with the reason rather than as a 404 later. Uncommitted edits since the build are not caught: after changing files, run without `RH_E2E_PREBUILT`. `test/build-stamp.test.ts` covers each case. CI sets it for the screenshot and Lighthouse runs that follow the end-to-end run, so the job builds the fixture app once.

Specs run in one worker, one file at a time (`workers: 1`, `fullyParallel: false`), because they all share one mock process and one app.

The mock's self-check, which proves every response passes the front end's reader schemas, is a unit test: `test/mock-cms.test.ts`, run by `pnpm web:test`.

## Ports and environment

| What | Default | Override |
| --- | --- | --- |
| The app under test (`next start`) | `3310` | `RH_WEB_PORT` |
| The mock CMS | `4010` | `RH_MOCK_CMS_PORT` |

The mock binds to `127.0.0.1` and names itself `http://127.0.0.1:4010` in every URL it emits; the app is started with `WP_API_URL=http://127.0.0.1:4010/wp-json`, `RH_FIXTURES=1` (the test-only pages under `app/fixtures/`), `WP_MEDIA_ORIGIN` set empty, which the app reads as unset, so `/media/` maps to the mock through `WP_API_URL` whatever the shell or `.env.local` holds, `REVALIDATE_SECRET` set to the fixed test value in `mock-cms/config.mts` (`E2E_REVALIDATE_SECRET`), which `e2e/revalidate.spec.ts` sends as its bearer, and `SITE_URL=http://localhost:3310` (`appSiteOrigin`, the same origin as Playwright's `baseURL`), so the canonical and `og:url` are absolute. The site's origin is `localhost` rather than the mock's `127.0.0.1` so that a check for `127.0.0.1:` in a page still means the CMS's host. All of these come from `mock-cms/config.mts`, which the config, the specs and the mock share. The build reads the mock: Playwright starts the mock before the app's web server command runs `next build`, and the build prerenders the library, each type's first page, the root and every seeded resource from the seed (ADR 0043; `lib/prerender.ts`), so those pages are route-cache hits on their first request of a run and `prefetch.spec.ts` checks the files the build wrote. A build with no CMS answering (the production build in CI, with its placeholder `WP_API_URL`) prerenders none of them, with one warning per route, and is otherwise the same build.

## The design gates

Four checks measure the design rather than behaviour, and every design change shows its cost in them. Three read the same list of URLs, `sampled-urls.mts`, picked from the seed: the welcome page at `/`, a CMS page, the library, a type listing, a topic listing, a type within a topic with resources and one without (the empty state), the library's page 2, the long-form resource, and both kinds of 404: a path no CMS page has, which the root catch-all answers with `DataNotFound`, and a path the proxy rewrites to the prerendered not-found page without asking the CMS. The file says what is not sampled (a CMS page as the static front page, a paginated filtered listing, a listing's or resource's own `DataNotFound`, a resource without an image or a body). A route or a state that renders differently adds a URL; new content adds nothing.

- **axe** (`a11y.spec.ts`, in the normal suite): `@axe-core/playwright` with every WCAG 2.0, 2.1 and 2.2 level A and AA rule (`axe.mts`), on every sampled URL in the emulated light and dark schemes. Zero violations.
- **Document size** (`document-size.spec.ts`, in the normal suite): two checks on the sampled URLs whose LCP is an image (`imageLed`: the CMS page, the library and the resource), both against 14,600 bytes, the ten 1,460-byte segments a connection's first round trip carries in Lighthouse's simulation. The **whole-document check**, on every image-led page the owner has not exempted, holds the HTML's transfer size as Chromium counts it, headers and gzipped body, to that limit: Lighthouse's simulator starts the requests a document names only once the whole document has arrived, so a page over it pays a second 150 ms round trip on FCP and LCP, which the Lighthouse budget has room for, so only this notices. A page may be exempted from it (`wholeDocumentGuard: false` in `sampled-urls.mts`) only by the owner's decision (2026-11-08, issue #85), when its size is the cost of content that is wanted; it is then held to a **ceiling** of 43,800 bytes, Lantern's first two round trips, and otherwise guarded in the lab only by the discovery check and the Lighthouse LCP budget, a warning until issue #76. The resource page is exempt, for its related section (the spec's docblock). The **discovery check**, on the library and the resource page, holds the bytes up to the end of the LCP image's `<link rel="preload" as="image">` to the same limit, and checks, as canaries, that the font preload comes before it and both come before the first `<style>`, `<script>` and stylesheet link. That is what decides when a real browser, whose preload scanner reads each chunk as it arrives, starts the image. It guards the `<head>`'s order, not CSS growth: React hoists the preloads ahead of the inlined CSS. The CMS page is exempt (`discoveryGuard: false`) because its LCP image is lazy and has no preload, until #86 makes the first body image eager; then drop `discoveryGuard: false`. The spec's docblock has the reasons and the exact byte method; the measurements are in [`../README.md`](../README.md#images), "Images".
- **Screenshots** (`specimen.screenshot.ts`, the `screenshots` project): full-page baselines of the specimen page at 360 and 1280 px, light and dark, with reduced motion, its states link focused and the footer's theme control hydrated, and for each a crop of that focused link and its ring, in `__screenshots__/`. Every comparison uses `threshold: 0` (any colour change counts a pixel as different). The full-page shots mask the three images Next.js's optimiser serves, the lead's and the resource's featured image and the figure in the resource sample's body (`img[src^="/_next/image"]`, as AVIF in Chromium): while the page is captured, each draws none of its own pixels and fills its own box with flat `#ff00ff`, Playwright's mask colour, so its size, position and rounded corners (`--rh-radius`) are still compared at the same tolerance as the rest. The gate checks the tokens and the components, not image codecs: in CI run 42337676741 (2026-11-07 UTC) the same AVIFs decoded 6,308 pixels apart at 360 px and 28,518 at 1280 px between the emulated run that made the baselines and CI's native amd64, every one of them at the edges of those two images. The mask is a stylesheet, `specimen-mask.css`, applied through `toHaveScreenshot`'s `stylePath` while the page is captured, rather than Playwright's `mask` option, which paints a plain rectangle over the element's bounding box and would hide the corners. The committed brand PNGs on the specimen are served unoptimised and stay compared, and the spec fails if the selector stops matching exactly those three images. A full page may differ in at most 50 pixels (`maxDiffPixels`), a count rather than a ratio so it does not grow with the page, which runs to millions of pixels (the baselines in `__screenshots__/` hold the current sizes; a ratio such as 0.1% would allow thousands); the crop may differ in at most 10, room for anti-aliasing at a glyph's edge or the ring's corner and far under the 440 a ring one pixel narrower moves. The project never retries (`retries: 0`, CI included), so a difference that comes and goes fails. The noise floor, measured on 2026-11-06 in six runs of every shot under emulation on Apple silicon, was zero; the 50 is headroom for anti-aliasing landing a pixel apart between that emulation and CI's native amd64. Measured the same day, on the palette before Figtree and Colbination's colours, each change failed every shot it touched: the light accent from `#1f4f8f` to `#2a5a9a`, 35,741 and 26,093 pixels on the light pages at 360 and 1280 px; `--rh-focus-width` from 3 to 2 px, 732 pixels on every page and 440 on every crop; and the light `--rh-color-focus` one step, `#1f4f8f` to `#1f4f90`, 22,340 and 12,792 pixels on the light pages and 1,296 on each light crop. The full-page check is soft, so the crop is compared and its diff written even when the page fails.

  `pnpm web:test:screenshots` (check) and `pnpm web:test:screenshots:update` (rewrite) run `screenshots.mts`, which starts a browser server in Playwright's image (`browser-container.mts`), pinned by digest in `playwright-image.mts` (its comment says how to move the version and the digest together), on `linux/amd64` (emulated on Apple silicon, native in CI), and runs the project against it; the mock and the app stay on the host, and the container's browser reaches the app's port, and nothing else on the host, through the connection (`exposeNetwork: localhost:{RH_WEB_PORT}`). The server is the repository's installed `playwright-core`, mounted read-only into the container, so a run downloads nothing but the pinned image. It listens on a port published to the host's loopback only, at a random endpoint path: unguessable, not secret. The path is passed to Docker through the environment rather than its command line, and the script redacts it from what it prints itself (Docker's errors, the container's log), but Playwright's own connection errors in the runner's output may include it, and the test runner's environment, `docker inspect` and, on a Linux host, the server process's own arguments in `ps` carry it, and a local user who reads it there can use the server while the run lasts. That is why the container is locked down and lives only for the run. The container runs with every capability dropped, `no-new-privileges`, a 1,024-process and 3 GB memory limit and a 1 GB `/dev/shm`. It runs with `--unsafe`, which lets a client pass Chromium arguments, because that is the only way to give its browser `--no-zygote`, without which Chromium's renderers crash under QEMU (`launch-server` takes arguments but cannot serve `exposeNetwork`); the flag is set everywhere for parity. The runner is started with Node directly, in a process group of its own; on Ctrl-C, `SIGTERM` or `SIGHUP` the script passes the signal on once (a hang-up as `SIGTERM`), waits up to 15 s for Playwright to stop the mock and the app, and kills the runner's group if it has not exited. Playwright starts the mock and the app in process groups of their own, so killing the runner does not stop them: after the runner has gone, however it ended, the script stops whatever still listens on either harness port that was free when the run began (found with `lsof`, killed with its process group), and only then stops its container. A port that was already taken, such as a server reused with `RH_E2E_REUSE=1`, is never touched. An `exit` handler runs the same cleanup if the script ends any other way. The project exists only when `RH_PW_REMOTE_WS` names that server, so `playwright test` alone never takes a screenshot with the host's browser and fonts. The spec takes one capture before asserting, because the image's Chromium resolves `monospace` to a different font for the first layout than after (the spec's comment has the measurement). Docker must be running; the script stops only the container it started.

  The same run checks the committed brand images first (`packages/ui/DESIGN.md`, "Brand"): with the same browser it renders `app/apple-icon.png`, `app/icon.png`, `app/favicon.ico` and `app/opengraph-image.png` again in memory (`scripts/render-brand-images.mts`, whose `--check` does the same on its own), decodes each and the committed file in the browser and compares their pixels, as RGBA, with any change in a channel counting. At most 50 pixels may differ in the share image, 10 in the apple icon and 4 in each 32 px icon, room for anti-aliasing as above. Measured on 2026-11-06: a fresh render matched every file pixel for pixel; the light `--rh-color-text-muted` one step, `#5c5962` to `#5c5963`, failed the share image in 4,170 pixels; and the share image as first rendered with the host's Chromium on macOS differed from the container's in 8,934. A stale file fails the run, whatever the screenshots did, with the file and what to run (`pnpm --filter resource-hub-web brand:images`, which writes the files from the same image); the check never writes, in either mode.

  The project writes its results to `test-results-screenshots/`, not `test-results/`, because Playwright empties a project's output directory when its run starts and in CI this run follows the end-to-end run, whose failure traces must survive for the upload; CI uploads both directories on a failure. A change to a token or a component fails here; review the diff images in `test-results-screenshots/`, then rewrite the baselines and commit them with the change.

  The baselines were made under emulation and have not yet been compared on a native amd64 runner. If the first CI run fails with a small difference that no change explains, the runner's render is the reference: take its actual images from the failed run's `web-playwright-traces` artifact (`test-results-screenshots/`), look at them, and commit them as the baselines, or, once this branch has merged, run the **Screenshot baselines** workflow (`.github/workflows/screenshot-baselines.yml`, manual). GitHub can dispatch a manual workflow only once its file is on the default branch, so that workflow cannot run before it reaches `main`; from then on it runs against any branch chosen when dispatching it, regenerates every baseline on a GitHub runner and uploads them as the private `screenshot-baselines` artifact, to look at and commit. A difference on CI in more than a handful of pixels is a real one, never a reason to raise the tolerance.
- **Lighthouse CI** (`lighthouserc.cjs`): `pnpm web:test:lighthouse` runs `lighthouse.mts`, which starts the mock on the harness's port first, then builds (unless `RH_E2E_PREBUILT=1`), since the build prerenders from the mock (ADR 0043), then `next start` on the harness's port (and stops at once if either server exits before answering), requests each URL once, and runs `lhci collect`, `upload` and `assert` with Playwright's Chromium: mobile (Lighthouse's default, with its fixed 4x CPU slowdown), five runs per URL, the medians asserted against performance ≥ 0.95, accessibility = 1, LCP ≤ 2500 ms, CLS ≤ 0.05 and TBT ≤ 200 ms. Every sampled URL but the two 404s, which Lighthouse refuses to score. Reports go to `lighthouse-results/` (gitignored, a CI artifact) and the medians, computed as `lhci assert` computes them (`lighthouse-summary.mts`, tested in `test/lighthouse-summary.test.ts`), are printed, and added to the job summary in CI. Lab numbers only.

  In CI a missed budget decides neither merges nor deploys until #76 lands. On a pull request into `main`, a push to `main` or a manual dispatch on `main` the step runs with `continue-on-error`, so a missed budget neither blocks the merge nor holds back the front end's production deploy, and the step after it writes a warning annotation and a line in the job summary naming each URL and metric that missed and linking #76, read from the failed assertions `lhci assert` saves (`.lighthouseci/assertion-results.json`); on a pull request it says the miss does not block the merge, on `main` that it does not hold the deploy back. Only a missed budget is a warning: when Lighthouse fails with no failed assertion on record (a syntax error in `lighthouserc.cjs` or `lighthouse.mts`, Chromium failing to launch, a build-stamp mismatch, or a failed report upload), that step writes an error and fails the job on every event, the deploy on `main` included. On a manual dispatch on any other branch, or a pull request into any other branch, a missed budget still fails the `web` job, and so would one on any trigger added later. The reports are uploaded either way. The budgets are the same on every event and are never loosened; the exemption exists because the fixed 4x slowdown below makes TBT move with the runner's CPU, about 80 to 300 ms on unchanged code: on 2026-11-07 it failed `main` twice (run 42362572282) on code that had passed on its pull request, and PR #79 at 201 and 209 ms against the 200 ms budget with no runtime change, until a rerun. WCAG A and AA accessibility stays gated by the axe scan: it runs in the end-to-end suite and still blocks every merge and deploy on any WCAG 2.0–2.2 A or AA violation, in light and dark. Lighthouse's accessibility score also counts best-practice rules outside those tags, and a miss there is a warning like any other budget. A Lighthouse warning on a pull request or on `main` is a finding to look at, not noise ([`docs/runbooks/deploy.md`](../../../docs/runbooks/deploy.md#the-front-end-deploy)).

  Five runs rather than three, so the median moves only when three runs do. They take about 7.5 minutes locally, and about 9 on CI's runners at the pace of the last three-run gate (327 s).

  The CPU slowdown is Lighthouse's fixed 4x, which multiplies the host's own task times, so TBT measures the runner as well as the code. The reference phone is slower than every host this gate runs on, by a factor that differs per host, and 4x is a constant, so the gate is gentler than a calibrated one wherever that factor is above 4. On an Apple-silicon laptop it is far gentler: at 4x its TBT is about 10 ms where a calibrated run gives about 100 to 210. On GitHub's runners, calibrating from a frozen built page measured about 3.4x to 5x, so 4x is about right on the slowest runner CPU seen and gentler on the rest. Lighthouse's documented calibration, the host's `benchmarkIndex` through its CPU slowdown calculator, was tried and dropped: on four runner CPU types the index understated this site's page work by about 2x and failed pages the laptop passed. The calibrated gate, its evidence and the open question it raises about the three image-led pages are issue #76 and the branch `lhci/snapshot-calibration` (`docs/runbooks/lighthouse-calibration-resume.md` there). Until it lands, read a local TBT as a check that nothing regressed badly, not as the phone's number.
- **Lighthouse on the Vercel preview** (`preview-lighthouse.mts`, run by `.github/workflows/preview-lighthouse.yml`): the gate measures `next start` and the mock CMS, so it measures the code and never sees what a reader gets from Vercel: the CDN, HTTP/2 and TLS, compression, the hosted image optimiser (its AVIF sizes differ from `next start`'s) and the hosted CMS's real images and pages. This run measures each pull request's preview with the gate's own settings (`lighthouserc.preview.cjs` spreads `lighthouserc.cjs`: mobile, the fixed 4x CPU slowdown, five runs per URL, Playwright's Chromium) and posts one comment on the pull request, edited in place on every later preview (found by a hidden marker, never a second comment), with per-URL medians of LCP, TBT and CLS, the LCP element and the LCP image's bytes, the preview URL and the commit. Informational: it is a separate workflow, never a required check. Each URL is warmed and measured on its own, so a URL that fails (a page that stopped answering, a refused header, a Lighthouse error) gets a row saying why while the others are still measured, and the job stays green; it fails only when nothing reached the pull request. Lab numbers from the hosted content, so they move when the content does.

  **Trigger.** GitHub's `deployment_status` event, which Vercel sends for the GitHub Deployments it creates; the workflow takes a successful, non-production status from `vercel[bot]`, looks up the open pull request whose head is the deployed commit (the event carries no number; none means nothing to do, and so does a status without a preview URL), and runs with a concurrency group per pull request, so a newer preview cancels an older run. GitHub runs a `deployment_status` workflow from the deployed commit, so a pull request that edits the workflow runs its own version. The Vercel project's Git setting that creates GitHub Deployments was off when this was written (`createDeployments` disabled), so the workflow is idle until it is turned on; nothing else needs to change.

  **The secret.** Previews sit behind Vercel's deployment protection, which answers a request without the right header with a redirect to its sign-in page (a 302, not a 401). The repository secret `VERCEL_PROTECTION_BYPASS` holds the project's protection bypass secret and is sent as `x-vercel-protection-bypass` on the warm-up requests and, through Lighthouse's `extraHeaders`, on every request Lighthouse's Chromium makes. Lighthouse records its settings in each report, so the raw runs in `.lighthouseci/` carry the header: the script writes redacted copies to `lighthouse-preview-results/` (gitignored, the run's artifact), searches every copy and the comment body for the value before writing or posting anything, deletes the copies and exits 1 on a hit, and never prints it; the workflow masks it too. The raw directory is never uploaded; `lhci` and Chrome run with a minimal environment, without the GitHub token. Chrome sends the header on every request the page makes, and every page on a preview loads Vercel's preview toolbar from `vercel.live` (injected on previews only; production visitors never load it), which would carry the secret to that origin, so the preview config blocks `https://vercel.live/*` in Chrome (`blockedUrlPatterns`): the request is never made, and the measurement matches what a production visitor loads. The warm-up requests are single fetches of the HTML and load nothing it references. As the safety net, after measuring, the script checks each run's requests for any origin but the preview's: such runs are named in the comment, their reports are not kept, and the job fails. Lighthouse still lists a request Chrome blocked, with the record's defaults (status −1, no protocol, no bytes), finished, and over within a millisecond, and it does not carry Chrome's error text, so the check skips only a request that matches the run's own blocked patterns and shows all of that (0.013 ms observed). That is a heuristic, not proof, and the block is the control: a request that was sent and then reset or timed out carries the same defaults, so the duration is the tell, and it counts, as does one that matches but was answered, and every other foreign request. The pattern match is anchored; anything it does not match is counted. Measured on 2026-11-07 before the block, every page made exactly that one `vercel.live` request and the check caught it. Rotation is in [`docs/runbooks/deploy.md`](../../../docs/runbooks/deploy.md).

  **The URL list.** `preview-urls.mts`, not `sampled-urls.mts`: a preview reads the hosted CMS, whose content differs from the seed, and three of the seed's paths do not exist there (on 2026-11-07, `/welcome/`, `/resources/page/2/` and `/resources/article/taxonomies-versus-meta/` answered 404 on production). It samples the same routes and states with paths the hosted content has, checked against production that day, minus the library's page 2 (the hosted library has exactly 12 resources, one page) and the 404s; the file says which and why. It is content, so it drifts: a path that stops answering shows in the comment as a warm-up failure, and the list is corrected by hand. Each URL is requested once with the header before Lighthouse runs, because ISR renders on the first request and the comment should show the page a reader gets.

  **Cost.** The first time a preview serves an image at the width Lighthouse's phone picks it is one transformation against the Vercel project's monthly image allowance (Hobby: 5,000); the runs after the first hit that preview's cache (`x-vercel-cache: HIT` on 2026-11-07). The sampled pages load 19 images between them, so one run costs at most 19 transformations, about 0.4% of the month, and a pull request with ten previews about 190. Keep the list short; a page added for its content rather than a new route or state buys little.

  **Locally**, against any preview: `vercel deploy` from `apps/web` prints the preview URL (never `--prod`), then, with `VERCEL_PROTECTION_BYPASS` set to the value of `VERC_DEP_PROT` in `.env.local`, `pnpm web:lighthouse:preview --origin https://…vercel.app --comment-file comment.md` warms, measures and writes the comment to the file instead of posting it. A wrong or missing header fails each URL at its warm-up request with the reason; an unset variable fails at once. Exit codes: 0 every URL measured, 2 some could not be and the comment says why, 1 nothing was written or the secret reached another origin.

  **To make it blocking later**, once it has proved stable across pull requests: add an `assert` block to `lighthouserc.preview.cjs` (the gate's assertions can be spread in the same way its collect settings are), run `lhci assert` after `collect` in `preview-lighthouse.mts` and return its exit code, drop `continue-on-error` from the measure step, and add the job to the required checks. Its numbers would still move with the hosted content, so a budget there should be looser than the gate's or read against a recorded baseline rather than a fixed number.

## What the mock serves

Public routes, shaped like a real WordPress running the plugin (the captured fixtures in `test/fixtures/wp/` are the reference), with WordPress's `WP_Error` bodies for 400s and 404s. Every response from the resources, taxonomy and `resource-hub/v1` routes, errors included, carries the [no-cache header the contract states](../../../packages/ui/README.md#how-the-two-sides-talk), as the plugin's `NoCacheHeader` filter sends it. `Allow: GET` is on every response from a matched route whose anonymous permission check passes, as `rest_send_allow_header()` adds it: the collections, a readable item and the plugin's routes, but not a missing or unreadable item.

Query parameters are read as PHP and core read them: `name[]=` arrays as well as comma lists, and the last value of a repeated `name=`. Bad ones get core's 400 `rest_invalid_param`, in core's two stages. First the arguments with a `validate_callback`, which are only `page` and `per_page`: when either fails, the 400 names those alone. Otherwise every other argument is validated as it is sanitized (`rest_parse_request_arg()`, and `sanitize_post_statuses()` for `status`), and the 400 names every failure, in the order the query string gives the parameters. Each failure is keyed by the parameter's name, an array item's included (`include=1,x` fails as `include`, with `include[1] is not of type integer.`), and carries core's code in `data.details` (`rest_invalid_type`, `rest_out_of_bounds`, `rest_not_in_enum`, `rest_forbidden_status`, and for the term filters, whose schema is `oneOf` a list and an object, `rest_no_matching_schema` and `rest_one_of_multiple_matches`). `test/mock-cms.test.ts` holds core 7.1.4's own responses as the expected bodies. `_embed` follows `rest_parse_embed_param()`: absent embeds nothing; empty, `0`, `1` or `true` embeds everything; any other value is a list of link relations (`_embed=wp:term`), so `_embed=false` embeds nothing.

- `GET /wp-json/wp/v2/resources` with `_embed`, `per_page` (1 to 100, default 10), `page`, `slug` (cleaned with `sanitize_title_for_query()`, as `WP_Query` cleans `post_name__in`, before matching), `include`, `order`, `orderby` (core's whole enum: `author`, `date`, `id`, `include`, `modified`, `parent`, `relevance`, `slug`, `include_slugs`, `title`), `status`, and the `resource_topic`, `resource_type` and `resource_flag` term-ID filters. `X-WP-Total`, `X-WP-TotalPages` and `Link` headers; a page past the end is core's 400 `rest_post_invalid_page_number`; `orderby=include` with no `include` is core's 400 `rest_orderby_include_missing_include`, and `orderby=relevance` is core's 400 `rest_no_search_term_defined`, as the mock serves no `search`; any `status` but `publish`, known or not, is a 400 `rest_invalid_param` whose `details.status` is core's `rest_forbidden_status` with status 401, as `sanitize_post_statuses()` refuses a reader who cannot edit posts before it checks the enum.

The slug is cleaned as `sanitize_title()` cleans it (`mock-cms/sanitize.mts`, which lists what it leaves out), as are the terms' `slug` filter and the slugs the control endpoints derive or accept.

Under `/__mock/`, a path the front end never requests. JSON in and out; errors are a 4xx `{ "error": "…" }`. `mock-cms/client.mts` wraps them for specs: `const cms = mockCms(); await cms.reset();`.

Every change to a resource moves its `modified` strictly forward, by a second past the old value when the clock has not moved on since the last change, so a spec can check that a change bumped it.

Control requests are never counted, so the counters show what the app did. Every spec should `reset()` in `beforeEach`, because the mock is one process shared by every test and specs that change the data must not assume another file's state.

**A reset does not clear the app's cache.** `/__mock/reset` puts the mock's data back, but the app under test keeps whatever its fetch Data Cache already holds for as long as the app process runs. A page one test rendered can still be served from the cache in a later test after the mock has changed or been reset. Specs must not rely on a reset to clear it. Either give each test data of its own, such as distinct slugs from `createResource` or `renameSlug`, so no cached entry applies, or call the app's revalidate route for the tags or paths the test changed, as the CMS would. IDs are data of their own by construction: the mock never hands out an ID twice in one process, across resets included (`nextId` in `state.mts`), because the related route and the by-ID reads are fetched by ID and a reused one would be served an earlier test's cached answer.

**Each run starts with an empty Data Cache and an empty route cache.** `next build` wipes `.next/server/route-cache`, where the ISR routes (the listings, the resource page and the pages catch-all) store what they answer, 308s and 404s included, so no stored entry outlives the build; the Data Cache is the one to clear by hand. Next.js writes fetch entries to disk under `.next/cache/fetch-cache`, where they outlive the process, but it keeps the marks `revalidateTag` sets only in the memory of the process that received the call. A restarted `next start` would therefore serve an entry an earlier run had already revalidated, such as a listing a spec changed and then cleared through the revalidate route. That is an artefact of restarting the app between runs, not a fault the site has on Vercel, where the Data Cache and its tags live together. So the web server command in `playwright.config.ts` deletes that directory between `next build` and `next start` (`scripts/clear-fetch-cache.mts`, in Node so it runs on any platform), and no spec has to refill the listings for the next run. The same script runs before every `next build` through the `build` script, so the prerender probes read the mock live rather than the previous build's answers (ADR 0043). A reused app (`RH_E2E_REUSE=1`) is not restarted and keeps its cache in memory and on disk; after a run stopped halfway, restart it.

**Within a run, specs that read a listing clear it after `reset()`.** The start-of-run clear does not cover what happens during the run: the shell's header links to `/resources/`, and the browser prefetches that link on every page it opens, so a listing can be rendered and stored at any moment of any spec, with whatever the mock held then. Since the build has prerendered the routes (ADR 0043) those prefetches fetch real segment data, for the type listings and the rows a page shows as well, so a render can be in flight on the server while a spec's `beforeEach` clears the cache and finish after it, fresh. A test that needs the next read to render again (to meet a fault, to see a change) clears after its own setup and polls, as `listings.spec.ts`'s failed-lead test does. `app-cache.mts` exports `clearAppCache(request)`, which sends the batch of term events that clears every listing and term tag (`resources`, `terms`, every `type:` and `topic:` tag) and the first page of every listing as a path; `listings.spec.ts` and `data-layer.spec.ts` call it after `reset()` in `beforeEach`, and `data-layer.spec.ts` also calls it around the test that changes the library, so no later spec is served that listing.

**Every revalidation waits out the app server's clock skew.** Next.js 16.4.5 stamps `revalidateTag(tag, { expire: 0 })` with `Date.now()` (`next/dist/server/lib/incremental-cache/file-system-cache.js`) but decides whether the tag has expired against `performance.timeOrigin + performance.now()` (`tags-manifest.external.js`, `areTagsExpired`). The two agree only while nobody moves the wall clock. When macOS's `timed` slews it ahead after an NTP correction, `Date.now()` runs ahead of the monotonic clock for the rest of the process's life, a just-revalidated entry reads as stale but not yet expired, and the next request is served the cached copy while Next.js refetches in the background (`incremental-cache/index.js`): `x-nextjs-cache: STALE`, the old title, a 200 where a renamed slug should be a 308. One full run failed twenty specs that way while `timed` had slewed the clock by 43 ms, and a rerun of the same build passed; the slew is the likely cause, not a proven one. So every spec posts to the revalidate route through `postRevalidate` in `revalidation.mts` (`clearAppCache` too), which after a 200 asks the app for its skew at `/fixtures/clock/` (a fixture route answering `{ skewMs }`, `Date.now()` minus the monotonic clock) and waits `max(0, skew) + 5 ms` before returning, so no read that follows can meet the stale entry. A skew over 250 ms either way fails the run with a message naming it, since that is a clock problem, not a slew to wait out. Set `RH_E2E_SKEW_LOG` to a file path to have each measurement appended to it as a line of JSON; on a healthy laptop the skew stays within a millisecond either way. To check whether a run that failed with stale data met a clock change, look for `timed` applying one during the run:

```sh
log show --last 2h --predicate 'process == "timed"' | grep cmd,apply
```

Open, for the owner: whether the revalidate route itself (`app/api/revalidate/route.ts`) should wait out the skew before answering 200, so the CMS, not only this harness, never reads a stale page right after a revalidation. The harness does not change the route.
