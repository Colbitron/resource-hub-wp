# Resource Hub: Next.js front end

The front end of the project, at `apps/web/`. The root `CLAUDE.md` holds what applies to the whole project, including the hard constraints, the workflow, the deploy order and the contract with the CMS, in one copy; read it first. This file holds what applies only to this app.

## Hard constraints

- **The CMS URL never reaches the browser.** `WP_API_URL` is server-only (never `NEXT_PUBLIC_`), every CMS request happens on the Next.js server, and every CMS URL in rendered output is rewritten (ADR 0040). This reduces exposure; it is not a security boundary.

## What it is

A Next.js App Router app, TypeScript, deployed on Vercel, that renders a resources library from the WordPress REST API and rebuilds pages on demand when the CMS says so.

**Core (the demo does not ship without all of it):**
1. Routes, all server-rendered, all with a trailing slash (`trailingSlash: true`), mirroring the CMS's permalinks: `/resources/` (everything), `/resources/[type]/` (one type), `/resources/topic/[topic]/` (one topic), `/resources/[type]/topic/[topic]/` (one type within one topic), each paginated as `…/page/[n]/`, and `/resources/[type]/[slug]/` (the single resource, including the related items from the plugin's related route). Filters and pagination are path segments, never search params, because reading `searchParams` makes an App Router page dynamic; one topic and one type at a time (ADR 0034). `topic` and `page` are reserved and never type slugs. On a single resource the slug is the identity and the type segment is checked: a wrong type, or an old slug found through the plugin's resolve route (called only when the current-slug lookup misses), gets a computed single-hop 308 to the canonical URL with `Cache-Control: no-store`; never send a permanent redirect without a cache header (ADR 0035). The mechanism, measured and recorded in ADR 0035's 2026-11-05 amendment: the single-resource page renders on every request (no `generateStaticParams`, `await connection()` first, no `loading.tsx`), calls `resourceForRequest` from `lib/redirects.ts` before rendering anything and outside any Suspense boundary, and that function returns the resource or calls `permanentRedirect()` with the canonical path computed in one step, which Next.js then sends as a 308 with `private, no-cache, no-store, max-age=0, must-revalidate` and never stores. From an ISR route the same redirect is prerendered and stored with `s-maxage`, and a dynamic bail-out only on the redirect branch is a runtime 500, so the resource route is dynamic by design, with the Data Cache behind it; the listings stay ISR. An upper-case letter in a segment, or a trailing `/page/1/`, redirects to the canonical URL from `proxy.ts` (`lib/canonical-path.ts`), matched on every `/resources/**` path and reading no data, so the listings, which are ISR and would store a `permanentRedirect()`, never redirect themselves and the resource page's decision only meets canonical segments (ADR 0035's listings amendment); the hex case of a percent escape is invisible to the page and renders as canonical (ADR 0049). The listings are the eight routes under `app/resources/`, each a thin shell over `components/ListingPage.tsx` with `export const revalidate = 3600` as a literal and a `generateStaticParams` returning `[]`, so the build never needs the CMS and a listing renders on its first request; the library is the optional catch-all `[[...rest]]` for that reason, and `topic/` and `page/` win over `[type]` (ADR 0050). A listing answers an unknown term or a page past the end with `notFound()` and an empty filter combination with a 200. The rendered body has the CMS domain stripped from every link (ADR 0036), its images rewritten to `/media/…` (ADR 0040) and the related-resources block marker swapped for a server component (ADR 0037), all in one parse pass on the server.
2. Data layer in `lib/wp/`, server-only: typed fetchers over `fetch` with `next: { tags: [...] }` so revalidation is tag-based (`resources`, `terms`, `resource:{slug}`, `topic:{slug}`, `type:{slug}`, each fetch's tags taken from the functions in `lib/tags.ts` per ADR 0046), and Zod parsing derived from the shared JSON Schemas (see the contract in the root `CLAUDE.md`) plus the core REST payloads, so a CMS change fails loudly, not silently.
3. `app/api/revalidate/route.ts`, served at `/api/revalidate/`: the on-demand revalidation endpoint per the contract in the root `CLAUDE.md`. It is served at `/api/revalidate/`, with the slash, because `trailingSlash: true` answers `/api/revalidate` with a 308 that the plugin's POST will not follow, so the plugin must post to the slashed path; the plugin and the contract text in the root `CLAUDE.md` move to it in their own contract pull request, which has not landed yet (ADR 0043). ADR 0048 records how it works: the bearer is checked before the body is read, as SHA-256 digests compared with `timingSafeEqual`; the body must be `application/json`, is read under a 64 KB cap and parsed with the reader schema; every body problem is a `400` whose message names the first issue's path and never a value; `revalidateTag(tag, { expire: 0 })` and `revalidatePath` clear the union of each event's current and previous state from `lib/tags.ts`; it fetches nothing from the CMS; and it answers with the exact response shapes the plugin expects. It is the front end's critical path, read line by line before merge.
4. Static generation with ISR as the safety net (a long `revalidate` interval) and on-demand revalidation as the primary path, for the listings; the single-resource page renders per request so that its redirects are never stored (ADR 0035, amended 2026-11-05), and its data comes from the same tagged Data Cache. Record the reasoning as an ADR.
5. Accessibility and performance as gates, not claims: semantic landmarks, keyboard-reachable filters, no layout shift from late content, and `next/image` with sized images through Vercel's image optimizer, sourced from the same-origin `/media/…` rewrite (ADRs 0039, 0040). The owner's plan includes 5,000 optimized images a month; the fallback is proxying the originals and WordPress's sizes through Cloudflare with no transformations. Lighthouse mobile performance and accessibility both 95 or better on `/resources` and a single resource.
6. Tests and gates: TypeScript strict, ESLint, Playwright end to end (filtering works; the revalidate route rejects a bad bearer and a bad body and accepts a good one), all in GitHub Actions on every push; Vercel preview deploys per PR.

**Stretch, in order, only once core is green:**
1. A GraphQL data path beside REST (when the plugin side adds WPGraphQL), with a short written comparison.
2. Draft preview via the signed token from the plugin.
3. Lighthouse CI budgets and an axe check inside the Playwright run so the numbers are produced by the pipeline, not read off a screenshot.

## Standards and workflow

- Next.js 16, App Router, TypeScript strict, pnpm. Server Components by default; client components only for the filter controls. Styling is plain CSS on the shared tokens, no framework and no web fonts (ADR 0045): component styles come from `@colbitron/resource-hub-ui` and are imported by the component that renders the markup; `components/Shell.tsx` imports the tokens and the app's own `shell.css`, never `layout.tsx`. Test-only pages are `app/**/page.fixture.tsx`, routes only under `RH_FIXTURES=1`, which Playwright's web server sets.
- `AGENTS.md` here is written by `next dev`: this Next.js version differs from older ones, so read the relevant guide in `node_modules/next/dist/docs/` before writing code.
- ADR 0043 records the caching model: the `fetch` Data Cache with `next: { tags }`, a route `revalidate` as the ISR safety net, and `revalidateTag` plus `revalidatePath` from the revalidate route, without Cache Components. ADR 0046 records which tags and paths each event revalidates and which tags each fetch carries. ADR 0047 records the one server-side pass over `content.rendered` in `lib/content/render.tsx`: the allow-list sanitiser (kses is no guard against `unfiltered_html`), the image trust rule, embeds as links and the `renderBlock` seam for the block marker. ADR 0048 records the revalidate route: digest comparison before the body, the 64 KB body cap, the `{ expire: 0 }` profile, tags plus paths, no CMS fetches and the error bodies. ADR 0049 (proposed) records the data layer's fetch policy in `lib/wp/fetch.ts`: the one-hour ISR interval, the ten-second timeout, the error mapping and the redirect policy for non-canonical slugs. ADR 0050 records the listing routes: ISR on first request with no build-time CMS call, and what each kind of request gets. Decisions still to record as ADRs for this app: the `/media/` rewrite versus a Route Handler (pending in ADR 0040's 2026-11-05 amendment), and REST versus GraphQL. These are the project's talking points.
- The shared package comes from the workspace as `"@colbitron/resource-hub-ui": "workspace:*"` in this app's `package.json` (ADR 0041).
- End-to-end specs are `e2e/*.spec.ts`; `pnpm web:test:e2e` starts the mock CMS in `e2e/mock-cms/` (a Node server shaped like the plugin's WordPress, with control endpoints under `/__mock/` for changing its data from a spec), then builds the app with the fixture routes and runs the specs against `next start`, with `WP_API_URL` pointing at the mock and `REVALIDATE_SECRET` set to the fixed test value in `e2e/mock-cms/config.mts`. The suite runs one worker, because every spec file resets the mock in `beforeEach`. Ports 3310 (app) and 4010 (mock), overridable with `RH_WEB_PORT` and `RH_MOCK_CMS_PORT`. Front-end e2e never uses wp-env or the hosted CMS; `e2e/README.md` has the routes, the controls and the seed. Playwright's Chromium must be installed (`pnpm exec playwright install chromium` in `apps/web`).
- Local work: run `pnpm web:dev` from the repository root (or `pnpm dev` here), with `WP_API_URL` in `.env.local` pointing at the wp-env CMS, `http://localhost:8888/wp-json` by default.

## Follow-ups

Open work noted in reviews, each for its own pull request:

- **A scroll wrapper for tables in the HTML pass** (`lib/content/render.tsx`): wrap each body `<table>` in a focusable, labelled region that scrolls horizontally, so a table too wide for a phone scrolls instead of squeezing its cells.
- **Demote a body's `<h1>` in the HTML pass**: a body heading at level 1 becomes an `<h2>`, so the page keeps one `<h1>`; today `resource.css` only styles it at the second level.
- **`metadataBase` from a server-only `SITE_URL`**, so the canonical and `og:url` are absolute on every listing and resource page (ADR 0050's follow-up).
- **A `not-found.tsx`** for the resource route and the listings, in the site's shell, in place of Next.js's default 404 page.
- **Failure injection in the mock CMS** (a control that makes a route answer 500 or time out), so an e2e test can cover the resource route's 500 and its `error.tsx` boundary.
