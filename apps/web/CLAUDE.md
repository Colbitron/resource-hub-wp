# Resource Hub: Next.js front end

The front-end half of a two-repo headless WordPress demo. The other half is `../resource-hub-wp` (the WordPress plugin and wp-env). Read both CLAUDE.md files before changing the contract in either.

## Standards to build to

React, TypeScript, Next.js; REST (GraphQL as a stretch); Playwright; GitHub Actions; WCAG and Core Web Vitals. The reference shape is a headless WordPress site on Next.js and Vercel with ISR and on-demand revalidation from the CMS; this should look like a small, clean instance of that shape. Ambition here means depth, not feature count: fast, accessible, tested, and every choice explainable in one sentence.

## Hard constraints

- **Fresh, generic code only.** Nothing here may be copied or adapted from any prior employer's codebase or packages. Generic Next.js patterns only; when in doubt, write it the textbook way and record the choice.
- **Never describe this as production code.** It is a demonstration of a pattern, written fresh.
- **No secrets in git.** `REVALIDATE_SECRET` and `WP_API_URL` live in `.env.local` (gitignored) and in Vercel project settings.
- **The CMS URL never reaches the browser.** `WP_API_URL` is server-only (never `NEXT_PUBLIC_`), every CMS request happens on the Next.js server, and every CMS URL in rendered output is rewritten (ADR 0007). This reduces exposure; it is not a security boundary.

## What it is

A Next.js App Router app, TypeScript, deployed on Vercel, that renders a resources library from the WordPress REST API and rebuilds pages on demand when the CMS says so.

**Core (the demo does not ship without all of it):**
1. Routes, all server-rendered, all with a trailing slash (`trailingSlash: true`), mirroring the CMS's permalinks: `/resources/` (everything), `/resources/[type]/` (one type), `/resources/topic/[topic]/` (one topic), `/resources/[type]/topic/[topic]/` (one type within one topic), each paginated as `…/page/[n]/`, and `/resources/[type]/[slug]/` (the single resource, including the related items from the plugin's related route). Filters and pagination are path segments, never search params, because reading `searchParams` makes an App Router page dynamic; one topic and one type at a time (ADR 0001). `topic` and `page` are reserved and never type slugs. On a single resource the slug is the identity and the type segment is checked: a wrong type, or an old slug found through the plugin's resolve route (called only when the current-slug lookup misses), gets a computed single-hop 308 to the canonical URL with `Cache-Control: no-store`; never send a permanent redirect without a cache header (ADR 0002). The rendered body has the CMS domain stripped from every link (ADR 0003), its images rewritten to `/media/…` (ADR 0007) and the related-resources block marker swapped for a server component (ADR 0004), all in one parse pass on the server.
2. Data layer in `lib/wp/`, server-only: typed fetchers over `fetch` with `next: { tags: [...] }` so revalidation is tag-based (`resources`, `resource:{slug}`, `topic:{slug}`, `type:{slug}`), and Zod parsing derived from the shared JSON Schemas (see the contract below) plus the core REST payloads, so a CMS change fails loudly, not silently.
3. `app/api/revalidate/route.ts`: the on-demand revalidation endpoint per the contract below. Constant-time bearer comparison, body validation against the schema, `revalidateTag` and `revalidatePath` for the union of each event's current and previous state, and the exact response shapes the plugin expects.
4. Static generation with ISR as the safety net (a long `revalidate` interval) and on-demand revalidation as the primary path. Record the reasoning as an ADR.
5. Accessibility and performance as gates, not claims: semantic landmarks, keyboard-reachable filters, `next/image` with sized images through Vercel's image optimizer, sourced from the same-origin `/media/…` rewrite (ADR 0007) (the plan includes 5,000 optimized images a month; the fallback is proxying the originals and WordPress's sizes through Cloudflare with no transformations; ADR 0006), no layout shift from late content. Lighthouse mobile performance and accessibility both 95 or better on `/resources` and a single resource.
6. Tests and gates: TypeScript strict, ESLint, Playwright end to end (filtering works; the revalidate route rejects a bad bearer and a bad body and accepts a good one), all in GitHub Actions on every push; Vercel preview deploys per PR.
7. `README.md` with the architecture diagram shared with the WordPress repo and a decisions section; ADRs under `docs/adr/`, in the same format as the WordPress repo's.

**Stretch, in order, only once core is green:**
1. A GraphQL data path beside REST (when the plugin side adds WPGraphQL), with a short written comparison.
2. Draft preview via the signed token from the plugin.
3. Lighthouse CI budgets and an axe check inside the Playwright run so the numbers are produced by the pipeline, not read off a screenshot.

## The contract with the CMS

Change this only by changing both repos in the same sitting. The JSON Schemas in the WordPress repo's `packages/ui/schemas/` (`@colbitron/resource-hub-ui`, ADR 0010 there) are the source of truth and its `packages/ui/README.md` holds the semantics a schema cannot express; this section summarises them and mirrors the WordPress repo's CLAUDE.md. Change a schema and its fixtures first, then both contract sections.

- **Content read:** this app reads `GET {WP_API_URL}/wp/v2/resources?_embed&per_page=…&page=…&resource_topic=…&resource_type=…&resource_flag=…`, `GET {WP_API_URL}/wp/v2/resources/{id}` (and `?slug=`), and the taxonomy endpoints `{WP_API_URL}/wp/v2/resource_topic`, `{WP_API_URL}/wp/v2/resource_type`, and `{WP_API_URL}/wp/v2/resource_flag`. Meta is `summary` and `source_url`, under `meta`. `related_picks` is editor-only on the CMS side; this app never reads it, because the related route does the merging (ADR 0030 there). Featured is the `resource_flag` term `featured`, not meta (ADR 0009 on the WordPress side): a featured resource has that term's ID in `resource_flag`.
- **Related:** `GET {WP_API_URL}/resource-hub/v1/related/{id}?count=3` (1 to 10) returns `{ "items": [ { "id": 12, "source": "pick" | "topic" } ] }`, at most `count` items, picks first, already merged (picks first, unpublished picks skipped, no duplicates, capped at `count`; a resource with no topics gets its picks alone). Call it once and do no merging here. This app then reads the objects with `GET {WP_API_URL}/wp/v2/resources?include={ids}&orderby=include&_embed`.
- **Resolve:** `GET {WP_API_URL}/resource-hub/v1/resolve?slug=…` returns `{ "id": 12, "type": "webinar", "slug": "current-slug" }` for a published resource found by its current or an old slug, or a 404. Call it only when the current-slug lookup misses.
- **Errors from both routes:** core's `WP_Error` shape, `{ "code", "message", "data": { "status" } }`, for 400 and 404.
- **Revalidation request** (CMS to this app): `POST /api/revalidate`, header `Authorization: Bearer {REVALIDATE_SECRET}`, header `Content-Type: application/json`, body a batch of 1 to 25 events. One WordPress PHP request is one batch; events for the same id are deduplicated (earliest `previous`, latest state); more than 25 are split into several requests.
  ```json
  { "version": 1, "events": [
    { "type": "resource", "event": "publish" | "update" | "unpublish" | "trash" | "delete", "id": 123, "slug": "example", "rest_url": "https://cms.example/wp-json/wp/v2/resources/123", "types": ["type-slug"], "topics": ["topic-slug"], "previous": { "slug": "old-example", "types": ["type-slug"], "topics": ["topic-slug"] } | null },
    { "type": "term", "taxonomy": "resource_topic" | "resource_type", "event": "create" | "update" | "delete", "id": 45, "slug": "topic-slug", "name": "Topic name", "previous": { "slug": "old-slug", "name": "Old name" } | null }
  ] }
  ```
  `types` has exactly one element. The top-level fields are the public state the event concerns: after the save for `publish` and `update`, the last public state for `unpublish`, `trash` and `delete`. `previous` is set on `update` only, with every field filled, and is `null` otherwise. Refresh on `publish` and `update`; remove on the other three (the refetch returns nothing and the page becomes `notFound()`); revalidate the union of the current and previous state. Restoring from the trash sends nothing. `resource_flag` sends no term events. A body with a `version` this app does not understand is a 400.
- **Revalidation response:** `200 { "revalidated": ["/resources/", "/resources/webinar/example/"] }` listing the paths revalidated; `400 { "error": "…" }` for a malformed body; `401 { "error": "unauthorized" }` for a bad or missing bearer; `500 { "error": "…" }` on failure. The plugin shows these to the editor, so the messages must be plain and accurate.
- **Public URLs**, the same on both sites, always with a trailing slash: `/resources/`, `/resources/[type]/`, `/resources/topic/[topic]/`, `/resources/[type]/topic/[topic]/`, `/resources/[type]/[slug]/`, and `…/page/[n]/` on every listing. `topic` and `page` are reserved and never type slugs. The slug is the identity; a wrong type segment, or an old slug found through resolve, redirects with a computed single-hop 308 and `Cache-Control: no-store`; never send a permanent redirect without a cache header. Those redirects are this app's; the CMS redirects no one, and its theme pages answer anonymous visitors with a 404, with `robots.txt` and `noindex` on top (ADR 0031 there). The CMS's URLs are absolute (`get_permalink()`, `content.rendered`, `_embed` media); this app strips the CMS domain from every link in the HTML it renders and rewrites every image, including `<img src>` and `srcset` in `content.rendered`, to `/media/…`, which `next.config.ts` rewrites to the CMS's uploads directory (ADR 0007). Cache tags are `resources`, `resource:{slug}`, `topic:{slug}` and `type:{slug}`.
- **Block marker:** the related-resources block renders `<div data-rh-block="related-resources" data-count="3" data-topic="topic-slug" data-topic-id="45" data-exclude="123">` with its `<h2>` heading and a fallback `<ul>` of links. This app parses `content.rendered` (`html-react-parser`, `replace`) on the server, never in the browser, and swaps the wrapper for its `<RelatedResources>` server component, fetched with the `topic:{slug}` tag. `data-topic` is the term's current slug, resolved by the CMS at render time, and names the cache tag; `data-topic-id` is the term ID, for the `resource_topic` filter on `/wp/v2/resources`; `data-exclude` is the ID of the post the block sits in, left out of the list.
- **Shared styles:** `@colbitron/resource-hub-ui` holds `tokens.css`, `related.css` and `card.css`; the class names (`.rh-related`, `.rh-card…`) and tokens are part of the contract. This app pins an exact version from GitHub Packages, installed on Vercel through an `NPM_RC` environment variable (the `registry=https://registry.npmjs.org` line, a `@colbitron` scope line, and a classic PAT with `read:packages` and an expiry), and imports the CSS from the component that uses it, never from `layout.tsx`. It stays private so it is not mistaken for a general-use package; only if the pnpm-with-`NPM_RC` spike fails does it become public on npmjs (ADR 0005). No shared JavaScript.
- **Configuration on this side:** `WP_API_URL` (the CMS's `/wp-json` base, server-only, never `NEXT_PUBLIC_`) and `REVALIDATE_SECRET`, plus `NPM_RC` in Vercel project settings for the shared package.

## Standards and workflow

- Next.js 16, App Router, TypeScript strict, pnpm. Server Components by default; client components only for the filter controls. No CSS framework decision has been made; keep styling small and dependency-light, and record the choice as an ADR.
- Agent-first build. The code is written by agents and reviewed by a human: the revalidate route and the data layer's parsing get read line by line before merge; the rest goes through the gate. The gate is typecheck, lint, Playwright, and a reviewer agent on a different model than the implementer. Nothing merges until all of it passes.
- Work on branches and open pull requests so the review has a diff to read. Small PRs, one concern each. Commit messages say what and why.
- Record each real decision as an ADR as it is made (tags versus paths for revalidation, ISR interval, REST versus GraphQL, styling). These are the project's talking points.
- Local toolchain as of 2026-11-03: Node 24 and pnpm present. The CMS runs in `../resource-hub-wp` under wp-env (Docker) at `http://localhost:8888` by default; point `WP_API_URL` there for local work.
