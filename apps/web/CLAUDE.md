# Resource Hub: Next.js front end

The front end of the project, at `apps/web/`. The root `CLAUDE.md` holds what applies to the whole project, including the hard constraints, the workflow, the deploy order and the contract with the CMS, in one copy; read it first. This file holds what applies only to this app.

## Hard constraints

- **The CMS URL never reaches the browser.** `WP_API_URL` is server-only (never `NEXT_PUBLIC_`), every CMS request happens on the Next.js server, and every CMS URL in rendered output is rewritten (ADR 0040). This reduces exposure; it is not a security boundary.

## What it is

A Next.js App Router app, TypeScript, deployed on Vercel, that renders a resources library from the WordPress REST API and rebuilds pages on demand when the CMS says so.

**Core (the demo does not ship without all of it):**
1. Routes, all server-rendered, all with a trailing slash (`trailingSlash: true`), mirroring the CMS's permalinks: `/resources/` (everything), `/resources/[type]/` (one type), `/resources/topic/[topic]/` (one topic), `/resources/[type]/topic/[topic]/` (one type within one topic), each paginated as `…/page/[n]/`, and `/resources/[type]/[slug]/` (the single resource, including the related items from the plugin's related route). Filters and pagination are path segments, never search params, because reading `searchParams` makes an App Router page dynamic; one topic and one type at a time (ADR 0034). `topic` and `page` are reserved and never type slugs. On a single resource the slug is the identity and the type segment is checked: a wrong type, or an old slug found through the plugin's resolve route (called only when the current-slug lookup misses), gets a computed single-hop 308 to the canonical URL (ADR 0035). The mechanism, decided 2026-11-06 and measured in ADR 0035's amendment of that date: the single-resource page is ISR like the listings (`export const revalidate = 3600` as a literal, a `generateStaticParams` returning `[]`, no `connection()`, no `loading.tsx`), calls `resourceForRequest` from `lib/redirects.ts` before rendering anything and outside any Suspense boundary, and that function returns the resource or calls `permanentRedirect()` with the canonical path computed in one step, or `notFound()`. Whatever it answers, a 200, a 308 or a 404, is stored under the tags of the fetches that decided it and served as a route-cache hit until a resource event clears it (ADR 0046's union of current and previous state covers a stored redirect at the old URL and a stored 404 at the new one); a 500 is never stored. Next.js serves a stored response with `s-maxage` alone, which a browser ignores and Chromium then keeps a 308 for ever, so the `headers()` rule in `next.config.ts` (`lib/route-headers.ts`) puts `public, max-age=0, must-revalidate` on every response of the route, the header Vercel's CDN sends browsers anyway; never send a permanent redirect a browser may keep (ADR 0025, amended). An upper-case letter in any script, an escape of a character Next.js decodes in params, upper-case hex or NFD form in a multi-byte escape, a repeated slash, or a trailing `/page/1/` on a listing, redirects to the canonical URL from `proxy.ts` (`lib/canonical-path.ts`) with `no-store`, reading no data: the listings never redirect themselves, and no request differing from a stored slug only in case or form reaches an ISR route, because Next.js keys a stored entry by the decoded path and a case-insensitive file system shares it between `/About/` and `/about/`, `/Дом/` and `/дом/` alike (ADR 0035's 2026-11-06 amendment). The proxy's matcher is every `/resources/**` path plus any other path holding an upper-case letter, a `%` or `//`, outside `/api/`, `/media/` and `/_next/`, so a canonical page path never runs it (`test/proxy-matcher.test.ts` compiles it as Next.js does). The page itself treats either hex case of an escape as canonical, since Next.js upper-cases the hex before a page sees it (ADR 0049). The listings are the eight routes under `app/resources/`, each a thin shell over `components/ListingPage.tsx` with `export const revalidate = 3600` as a literal and a `generateStaticParams` returning `[]`, so the build never needs the CMS and a listing renders on its first request; the library is the optional catch-all `[[...rest]]` for that reason, and `topic/` and `page/` win over `[type]` (ADR 0050). A listing answers an unknown term or a page past the end with `notFound()` and an empty filter combination with a 200. The rendered body has the CMS domain stripped from every link (ADR 0036), its images rewritten to `/media/…` (ADR 0040) and the related-resources block marker swapped for a server component (ADR 0037), all in one parse pass on the server.
   **Pages (ADR 0052).** `app/[[...path]]/page.tsx`, an optional catch-all at the root, serves `/` and every path no other route claims: the CMS's static front page at `/`, every other published WordPress page at its parent chain (`/about/`, `/about/team/`), and `components/WelcomePage.tsx` (the site's name, a sentence and a link to the library, a 200, never a redirect) at `/` when no front page is set, which is the hosted CMS's state today. Like the resource page it is ISR since 2026-11-06 (`revalidate = 3600` as a literal, a `generateStaticParams` returning `[]`, no `connection()`, no `loading.tsx`, an `error.tsx` beside it; `test/page-route.test.ts` pins that): the build never renders `/` from the CMS, each path is stored on its first request under the `pages` tag, a page event clears the tag and the paths it names (the front page swapping in at `/`, a stored 308 at `/welcome/` or at a moved page's old path, a stored 404 where a page is then published), every response carries the same `headers()` rule's `Cache-Control` as the resource page, and the proxy's case redirect runs first (ADR 0052's 2026-11-06 amendment). The decision is `pageForRequest` in `lib/page-request.ts`, called before anything renders, in the page and in `generateMetadata`: a segment that is not a slug or holds a dot (`favicon.ico`, `robots.txt`; WordPress never stores a dot in a slug), or a first segment the front end's own routes use (`RESERVED_ROOT_SEGMENTS` in `lib/routes.ts`: `resources`, `api`, `media`, `_next`), is a 404 without a request, and so is a path over the plugin's 2010-byte cap (`MAX_PAGE_PATH_LENGTH`); static and dynamic routes win over the catch-all, so `/resources/…` and `/api/revalidate/` never arrive here, and the `/media/` rewrite runs before dynamic routes, so the list only matters for what falls through (`/api/other/`, a page the CMS saved as `api` before the plugin's suffix rule). Otherwise the path, in canonical form (each segment through `canonicalSlug`), is looked up once through the plugin's page route (`lookupPage` in `lib/wp/pages.ts`), which answers the page and its canonical path now. A miss is a 404, or the welcome page at `/`; so is the plugin's 400 for an over-long path and core's 404 `rest_no_route` from a CMS without the route (a preview against the hosted CMS before the plugin deploys, a CMS rollback), neither cached, so a front end a deploy ahead never answers a 500 for them. An answer whose path differs from the request, or a request with an upper-case letter outside a percent escape (the hex case of an escape is invisible to the page, as for resources), redirects to the page's path in one computed hop, after looking that path up too and getting the same page at it, so two cache entries that disagree (one from before a move, one after) are a 404 rather than a loop: so the front page's own slug (`/home/`) redirects to `/`, and a page moved under another parent redirects from its old path when its slug is unique (the plugin guesses it); a wrong parent whose slug two pages share, a renamed page's own old path (core keeps no old slugs for pages) and the posts page are 404s, with the reasons in ADR 0052 and the plugin's `CLAUDE.md`. A matching answer is read by ID (`getPageById`, core's 404 and 401 are "not found", and a page with `content.protected` is refused, since a password-protected page is never served) and rendered by `components/PageArticle.tsx`: the title as the `<h1>` and the page's `content.rendered` through the same one pass as a resource's body (`renderContent`, with the page's ID as `postId`), in the shared `components/prose.css`; metadata is the title through the site template, the excerpt as the description, and the canonical path. The fixed point holds as for resources: a redirect's target is built from the CMS's canonical segments, which the plugin answers with themselves, and `test/page-request.test.ts` checks it over generated paths.
2. Data layer in `lib/wp/`, server-only: typed fetchers over `fetch` with `next: { tags: [...] }` so revalidation is tag-based (`resources`, `terms`, `resource:{slug}`, `topic:{slug}`, `type:{slug}` and `pages`, the last on every page lookup and page read and cleared by page events only, each fetch's tags taken from the functions in `lib/tags.ts` per ADRs 0046 and 0052), and Zod parsing derived from the shared JSON Schemas (see the contract in the root `CLAUDE.md`) plus the core REST payloads, so a CMS change fails loudly, not silently.
3. `app/api/revalidate/route.ts`, served at `/api/revalidate/`: the on-demand revalidation endpoint per the contract in the root `CLAUDE.md`. The plugin posts to `/api/revalidate/`, with the trailing slash, because `trailingSlash: true` answers `/api/revalidate` with a 308 that the plugin's POST does not follow (ADR 0043). ADR 0048 records how it works: the bearer is checked before the body is read, as SHA-256 digests compared with `timingSafeEqual`; the body must be `application/json`, is read under a 64 KB cap and parsed with the reader schema; every body problem is a `400` whose message names the first issue's path and never a value; `revalidateTag(tag, { expire: 0 })` and `revalidatePath` clear the union of each event's current and previous state from `lib/tags.ts`; it fetches nothing from the CMS; and it answers with the exact response shapes the plugin expects. It is the front end's critical path, read line by line before merge.
4. Static generation with ISR as the safety net (a long `revalidate` interval) and on-demand revalidation as the primary path, for every route: the listings, the single-resource page and the pages catch-all (ADR 0035 and ADR 0052, amended 2026-11-06, reversing the per-request rendering of 2026-11-05). A stored redirect or 404 is cleared by the same event that makes it wrong, and a `headers()` rule keeps browsers asking again; the data comes from the same tagged Data Cache. The reasoning is in those amendments.
5. Accessibility and performance as gates, not claims: semantic landmarks, keyboard-reachable filters, no layout shift from late content, and `next/image` with sized images through Vercel's image optimizer, sourced from the same-origin `/media/…` rewrite (ADRs 0039, 0040). The owner's plan includes 5,000 optimized images a month; the fallback is proxying the originals and WordPress's sizes through Cloudflare with no transformations. Lighthouse mobile performance and accessibility both 95 or better on `/resources` and a single resource.
6. Tests and gates: TypeScript strict, ESLint, Playwright end to end (filtering works; the revalidate route rejects a bad bearer and a bad body and accepts a good one), all in GitHub Actions on every push; Vercel preview deploys per PR.

**Stretch, in order, only once core is green:**
1. A GraphQL data path beside REST (when the plugin side adds WPGraphQL), with a short written comparison.
2. Draft preview via the signed token from the plugin.
3. Lighthouse CI budgets and an axe check inside the Playwright run so the numbers are produced by the pipeline, not read off a screenshot.

## Standards and workflow

- Next.js 16, App Router, TypeScript strict, pnpm. Server Components by default; client components only for the filter controls. Styling is plain CSS on the shared tokens, no framework and no web fonts (ADR 0045): component styles come from `@colbitron/resource-hub-ui` and are imported by the component that renders the markup; `components/Shell.tsx` imports the tokens and the app's own `shell.css`, never `layout.tsx`. Test-only pages are `app/**/page.fixture.tsx`, routes only under `RH_FIXTURES=1`, which Playwright's web server sets.
- `AGENTS.md` here is written by `next dev`: this Next.js version differs from older ones, so read the relevant guide in `node_modules/next/dist/docs/` before writing code.
- ADR 0043 records the caching model: the `fetch` Data Cache with `next: { tags }`, a route `revalidate` as the ISR safety net, and `revalidateTag` plus `revalidatePath` from the revalidate route, without Cache Components. ADR 0046 records which tags and paths each event revalidates and which tags each fetch carries. ADR 0047 records the one server-side pass over `content.rendered` in `lib/content/render.tsx`: the allow-list sanitiser (kses is no guard against `unfiltered_html`), the image trust rule, embeds as links and the `renderBlock` seam for the block marker. ADR 0048 records the revalidate route: digest comparison before the body, the 64 KB body cap, the `{ expire: 0 }` profile, tags plus paths, no CMS fetches and the error bodies. ADR 0049 (proposed) records the data layer's fetch policy in `lib/wp/fetch.ts`: the one-hour ISR interval, the ten-second timeout, the error mapping and the redirect policy for non-canonical slugs. ADR 0050 records the listing routes: ISR on first request with no build-time CMS call, and what each kind of request gets. Decisions still to record as ADRs for this app: the `/media/` rewrite versus a Route Handler (pending in ADR 0040's 2026-11-05 amendment), and REST versus GraphQL. These are the project's talking points.
- The shared package comes from the workspace as `"@colbitron/resource-hub-ui": "workspace:*"` in this app's `package.json` (ADR 0041).
- End-to-end specs are `e2e/*.spec.ts`; `pnpm web:test:e2e` starts the mock CMS in `e2e/mock-cms/` (a Node server shaped like the plugin's WordPress, with control endpoints under `/__mock/` for changing its data from a spec), then builds the app with the fixture routes and runs the specs against `next start`, with `WP_API_URL` pointing at the mock and `REVALIDATE_SECRET` set to the fixed test value in `e2e/mock-cms/config.mts`. The suite runs one worker, because every spec file resets the mock in `beforeEach`. Ports 3310 (app) and 4010 (mock), overridable with `RH_WEB_PORT` and `RH_MOCK_CMS_PORT`. Front-end e2e never uses wp-env or the hosted CMS; `e2e/README.md` has the routes, the controls and the seed. Playwright's Chromium must be installed (`pnpm exec playwright install chromium` in `apps/web`).
- Local work: run `pnpm web:dev` from the repository root (or `pnpm dev` here), with `WP_API_URL` in `.env.local` pointing at the wp-env CMS, `http://localhost:8888/wp-json` by default.

## Follow-ups

Open work noted in reviews, each for its own pull request:

- **A 404 page in the HTML for `notFound()`**: on Next.js 16.4.5 a listing's, the resource page's or the page route's `notFound()` is sent as the framework's empty `__next_error__` document, and `app/not-found.tsx` appears only after hydration; ISR stores that same document (measured 2026-11-06), so the stored 404s change nothing here. Until ADR 0052 an unmatched URL got the page in its HTML from the prerendered `/_not-found` route; the root catch-all now claims every such URL and decides its 404 by one cached CMS lookup, so no 404 has the page in its HTML (ADR 0050's 2026-11-05 amendment, pinned in `e2e/errors.spec.ts`). What the review measured: a `beforeFiles` rewrite, or a `proxy.ts` `NextResponse.rewrite()` to a path no route matches, does render the not-found page in the HTML with status 404, and the Next.js docs recommend that for 404s decidable from the path alone (reserved words, segments that cannot be slugs). Every `notFound()` that depends on data (unknown terms, unknown slugs, pages past the end) still sends the empty error document, because `getErrorRSCPayload` hard-codes it, and `global-not-found` does not change that. The rewrite is not implemented; the data-dependent case needs Next.js upstream.
