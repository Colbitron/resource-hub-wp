# Resource Hub: Next.js front end

The front end of the project, at `apps/web/`. The root `CLAUDE.md` holds what applies to the whole project; read it first. This file holds the rules for every edit in this app. Rules for one area load from `.claude/rules/` when you touch its files: `caching-and-redirects.md` for routes, the data layer and redirects, `revalidation.md` for the revalidate route and the tags, `contract.md` for the readers and shared paths. How the pieces work is in `docs/architecture/caching.md` and `docs/architecture/revalidation.md`, the contract in `packages/ui/README.md`, running and configuring the app in `README.md`, and each module's reasoning in its docblock.

## Hard constraints

- **The CMS URL never reaches the browser.** `WP_API_URL` is server-only (never `NEXT_PUBLIC_`), every CMS request happens on the Next.js server, every CMS URL in rendered output is rewritten, and no error message names the CMS origin (ADR 0040). This reduces exposure; it is not a security boundary.
- **Never `dangerouslySetInnerHTML`.** CMS HTML goes through `renderContent`, the one server-side pass in `lib/content/render.tsx`, which renders React nodes from an allow-list, strips the CMS domain from links, rewrites images to `/media/…` and hands the block marker to `renderBlock`. kses is no guard, because editors have `unfiltered_html`. The two `dangerouslySetInnerHTML` uses are in `app/layout.tsx`: the theme's head script and the `<noscript>` style rule beside it, both constants exported from `lib/theme.ts`, built from no input, never CMS HTML.

## What it is

A Next.js App Router app, TypeScript, deployed on Vercel, that renders a resources library and the CMS's pages from the WordPress REST API and rebuilds pages on demand when the CMS says so.

**Core (the demo does not ship without all of it):**
1. **Routes**, all with a trailing slash (`trailingSlash: true`), mirroring the CMS's permalinks: the listings under `app/resources/`, the single resource `/resources/[type]/[slug]/`, and the CMS's pages, `/` and `/[page]/…/`, from the root catch-all `app/[[...path]]/`. The route list is in `README.md`. Every route is ISR; the build prerenders a bounded set from the CMS when it answers and nothing when it does not (`lib/prerender.ts`, ADR 0043), so `next build` runs with the mock CMS up in the e2e harness and against a placeholder `WP_API_URL` in CI's production build alike.
2. **Data layer** in `lib/wp/`, server-only.
3. **`app/api/revalidate/route.ts`**, the on-demand revalidation endpoint.
4. **Accessibility and performance gates:** semantic landmarks, keyboard-reachable filters, no layout shift from late content, and `next/image` with sized images from the same-origin `/media/…` rewrite. Measured by the pipeline on the URLs in `e2e/sampled-urls.mts`: Lighthouse CI on mobile, medians of five runs, performance at least 0.95, accessibility 1, LCP at most 2500 ms, CLS at most 0.05 and TBT at most 200 ms (`lighthouserc.cjs`), axe with zero WCAG 2.0–2.2 A and AA violations in light and dark (`e2e/a11y.spec.ts`), and, on each page led by an image, its HTML at most the 14,600 bytes of Lighthouse's first simulated round trip (a page the owner has exempted, for content that is wanted, at most 43,800) and its LCP image preload within those 14,600 bytes on the wire, after the font preload and before the first `<style>`, `<script>` and stylesheet link (the CMS page excepted, whose LCP image is lazy until #86) (`e2e/document-size.spec.ts`, whose docblock has why and the exemption rule). Lab numbers only. A budget or a rule that fails is a finding to fix in the design, never a threshold to loosen. The one exemption, from the 14,600-byte whole-document check, is an owner decision with its cost stated in that docblock, for content that is wanted, never a way to pass a page that fails for any other reason. Every one of these blocks a merge and the production deploy except a Lighthouse budget miss: until issue #76 calibrates its CPU slowdown, a missed Lighthouse budget on a pull request into `main` or on `main` is a warning in the run, not a failure, while any other Lighthouse failure still blocks (`e2e/README.md`, "Lighthouse CI"). WCAG A and AA accessibility stays gated by the axe scan, which blocks both. The budgets are unchanged, and a Lighthouse warning is still a finding to fix, not to wave through.
5. **Tests and gates:** TypeScript strict, ESLint, Vitest unit tests, Playwright end to end against the mock CMS, the axe scan and Lighthouse CI from item 4, and pixel baselines of the design specimen (`app/fixtures/specimen/`) rendered in Playwright's Linux Docker image, all in GitHub Actions on every push; Vercel preview deploys per PR.

## Standards and workflow

- Next.js 16, App Router, TypeScript strict, pnpm. Server Components by default; client components only where the browser holds the state: the filter controls, the listing focus and the theme control, `ThemeToggle`, whose stored choice and head script are `lib/theme-store.ts` and `lib/theme.ts` (`packages/ui/DESIGN.md`, "Theme and colour scheme"); the specimen's fixed copies of that control, `StillThemeFieldset`, are a test-only fourth. Styling follows `packages/ui/DESIGN.md`, the one written home of the visual system: plain CSS on the shared tokens from `@colbitron/resource-hub-ui` (`"workspace:*"` in this app's `package.json`), imported by the component that renders the markup (`components/Shell.tsx` imports the tokens and the app's own `shell.css`, never `layout.tsx`), and Figtree as the only typeface, loaded by `app/fonts.ts` with `next/font/local` from the shared package's file and applied by the root layout, which is the one thing `layout.tsx` does for styling. The brand layer is DESIGN.md's "Brand" section: the mark and the header's lockup in `components/Brand.tsx`, the same mark as the site's icon in `app/icon.svg` (`test/brand-mark.test.tsx` keeps the two the same), and the committed apple touch icon, 32 px icon, `favicon.ico` and default share image (`app/apple-icon.png`, `app/icon.png`, `app/favicon.ico`, `app/opengraph-image.png`), which `pnpm brand:images` draws in the screenshot gate's pinned Playwright image and the screenshot run checks against a fresh render (`--check`). Test-only pages are `app/**/page.fixture.tsx`, routes only under `RH_FIXTURES=1`, which Playwright's web server sets.
- `AGENTS.md` here is written by `next dev`: this Next.js version differs from older ones, so read the relevant guide in `node_modules/next/dist/docs/` before writing code.
- The module docblocks in `lib/tags.ts`, `lib/wp/fetch.ts`, `lib/redirects.ts`, `lib/page-request.ts`, `lib/prerender.ts`, `lib/canonical-path.ts`, `lib/path-decision.ts`, `components/DataNotFound.tsx`, `lib/content/render.tsx` and `app/api/revalidate/route.ts` hold the rules of each piece; read the docblock before changing a module. Open decisions are issues #51 (an unreadable event), #52 (the `/media/` rewrite), #53 (the content pass) and #54 (flag terms).
- End-to-end specs are `e2e/*.spec.ts`, run with `pnpm web:test:e2e` against the mock CMS in `e2e/mock-cms/`, never wp-env or the hosted CMS. `e2e/README.md` has the setup, the ports, the routes, the controls and the seed.
- The design gates run with `pnpm web:test:e2e` (axe and the specimen's checks), `pnpm web:test:screenshots` (Docker) and `pnpm web:test:lighthouse`; how each works, its tolerances and what to do when CI and a laptop disagree are in `e2e/README.md`, "The design gates". A design change regenerates the baselines with `pnpm web:test:screenshots:update`, and the images are looked at and committed with the change; a new token in `packages/ui/tokens.css` must appear in the specimen (`test/specimen-tokens.test.ts`).
