# Resource Hub: Next.js front end

The front end of the project, at `apps/web/`. The root `CLAUDE.md` holds what applies to the whole project, including the hard constraints, the workflow, the deploy order and the contract with the CMS, in one copy; read it first. This file holds what applies only to this app.

## Hard constraints

- **The CMS URL never reaches the browser.** `WP_API_URL` is server-only (never `NEXT_PUBLIC_`), every CMS request happens on the Next.js server, and every CMS URL in rendered output is rewritten (ADR 0040). This reduces exposure; it is not a security boundary.

## What it is

A Next.js App Router app, TypeScript, deployed on Vercel, that renders a resources library from the WordPress REST API and rebuilds pages on demand when the CMS says so.

**Core (the demo does not ship without all of it):**
1. Routes, all server-rendered, all with a trailing slash (`trailingSlash: true`), mirroring the CMS's permalinks: `/resources/` (everything), `/resources/[type]/` (one type), `/resources/topic/[topic]/` (one topic), `/resources/[type]/topic/[topic]/` (one type within one topic), each paginated as `…/page/[n]/`, and `/resources/[type]/[slug]/` (the single resource, including the related items from the plugin's related route). Filters and pagination are path segments, never search params, because reading `searchParams` makes an App Router page dynamic; one topic and one type at a time (ADR 0034). `topic` and `page` are reserved and never type slugs. On a single resource the slug is the identity and the type segment is checked: a wrong type, or an old slug found through the plugin's resolve route (called only when the current-slug lookup misses), gets a computed single-hop 308 to the canonical URL (ADR 0035). The mechanism, decided 2026-11-06 and measured in ADR 0035's amendment of that date: the single-resource page is ISR like the listings (`export const revalidate = 3600` as a literal, a `generateStaticParams` returning `[]`, no `connection()`, no `loading.tsx`), calls `resourceForRequest` from `lib/redirects.ts` before rendering anything and outside any Suspense boundary, and that function returns the resource, or calls `permanentRedirect()` with the canonical path computed in one step, or returns the not-found decision, which the page answers with `components/DataNotFound.tsx` (the "404s decided by data" paragraph below). Whatever it answers, a 200, a 308 or a 404, is stored under the tags of the fetches that decided it and served as a route-cache hit until a resource event clears it (ADR 0046's union of current and previous state covers a stored redirect at the old URL and a stored 404 at the new one); a 500 is never stored. Next.js serves a stored response with `s-maxage` alone, which a browser ignores and Chromium then keeps a 308 for ever, so the `headers()` rule in `next.config.ts` (`lib/route-headers.ts`) puts `public, max-age=0, must-revalidate` on every response of the route, the header Vercel's CDN sends browsers anyway; never send a permanent redirect a browser may keep (ADR 0025, amended). An upper-case letter in any script, an escape of a character Next.js decodes in params, upper-case hex or NFD form in a multi-byte escape, a repeated slash, or a trailing `/page/1/` on a listing, redirects to the canonical URL from `proxy.ts` (`lib/canonical-path.ts`) with `no-store`, reading no data: the listings never redirect themselves, and no request differing from a stored slug only in case or form reaches an ISR route, because Next.js keys a stored entry by the decoded path and a case-insensitive file system shares it between `/About/` and `/about/`, `/Дом/` and `/дом/` alike (ADR 0035's 2026-11-06 amendment). The proxy's matcher is every `/resources/**` path, every other `/api/**` path but the revalidate route, any other path holding an upper-case letter, a `%`, a `//`, a dot or a segment over 200 characters, outside `/media/`, `/_next/` and the favicon, and any path over the page cap, so an ASCII canonical page path never runs it (a percent-encoded one does, through the `%` clause, and gets nothing back; `test/proxy-matcher.test.ts` compiles it as Next.js does and checks it reaches every path `lib/path-decision.ts` acts on). The page itself treats either hex case of an escape as canonical, since Next.js upper-cases the hex before a page sees it (ADR 0049). The listings are the eight routes under `app/resources/`, each a thin shell over `components/ListingPage.tsx` with `export const revalidate = 3600` as a literal and a `generateStaticParams` returning `[]`, so the build never needs the CMS and a listing renders on its first request; the library is the optional catch-all `[[...rest]]` for that reason, and `topic/` and `page/` win over `[type]` (ADR 0050). A listing answers an unknown term or a page past the end with `DataNotFound` and an empty filter combination with a 200. The rendered body has the CMS domain stripped from every link (ADR 0036), its images rewritten to `/media/…` (ADR 0040) and the related-resources block marker swapped for a server component (ADR 0037), all in one parse pass on the server.
   **Pages (ADR 0052).** `app/[[...path]]/page.tsx`, an optional catch-all at the root, serves `/` and every path no other route claims: the CMS's static front page at `/`, every other published WordPress page at its parent chain (`/about/`, `/about/team/`), and `components/WelcomePage.tsx` (the site's name, a sentence and a link to the library, a 200, never a redirect) at `/` when no front page is set, which is the hosted CMS's state today. Like the resource page it is ISR since 2026-11-06 (`revalidate = 3600` as a literal, a `generateStaticParams` returning `[]`, no `connection()`, no `loading.tsx`, an `error.tsx` beside it; `test/page-route.test.ts` pins that): the build never renders `/` from the CMS, each path is stored on its first request under the `pages` tag, a page event clears the tag and the paths it names (the front page swapping in at `/`, a stored 308 at `/welcome/` or at a moved page's old path, a stored 404 where a page is then published), every response carries the same `headers()` rule's `Cache-Control` as the resource page, and the proxy's case redirect runs first (ADR 0052's 2026-11-06 amendment). The decision is `pageForRequest` in `lib/page-request.ts`, called before anything renders, in the page and in `generateMetadata`: a segment that is not a slug or holds a dot (`favicon.ico`, `robots.txt`; WordPress never stores a dot in a slug), or a first segment the front end's own routes use (`RESERVED_ROOT_SEGMENTS` in `lib/routes.ts`: `resources`, `api`, `media`, `_next`), is a 404 without a request, and so is a path over the plugin's 2010-byte cap (`MAX_PAGE_PATH_LENGTH`); the one definition is `pagePathProblem` in `lib/routes.ts`, and since 2026-11-06 `proxy.ts` answers those same paths first, with the not-found page's HTML (the "404s decided from the path" paragraph below), so the route's own check is a second line. Static and dynamic routes win over the catch-all, so `/resources/…` and `/api/revalidate/` never arrive here, and the `/media/` rewrite runs before dynamic routes, so the list only matters for what falls through (`/api/other/`, a page the CMS saved as `api` before the plugin's suffix rule). Otherwise the path, in canonical form (each segment through `canonicalSlug`), is looked up once through the plugin's page route (`lookupPage` in `lib/wp/pages.ts`), which answers the page and its canonical path now. A miss is a 404, or the welcome page at `/`; so is the plugin's 400 for an over-long path and core's 404 `rest_no_route` from a CMS without the route (a preview against the hosted CMS before the plugin deploys, a CMS rollback), neither cached, so a front end a deploy ahead never answers a 500 for them. An answer whose path differs from the request, or a request with an upper-case letter outside a percent escape (the hex case of an escape is invisible to the page, as for resources), redirects to the page's path in one computed hop, after looking that path up too and getting the same page at it, so two cache entries that disagree (one from before a move, one after) are a 404 rather than a loop: so the front page's own slug (`/home/`) redirects to `/`, and a page moved under another parent redirects from its old path when its slug is unique (the plugin guesses it); a wrong parent whose slug two pages share, a renamed page's own old path (core keeps no old slugs for pages) and the posts page are 404s, with the reasons in ADR 0052 and the plugin's `CLAUDE.md`. A matching answer is read by ID (`getPageById`, core's 404 and 401 are "not found", and a page with `content.protected` is refused, since a password-protected page is never served) and rendered by `components/PageArticle.tsx`: the title as the `<h1>` and the page's `content.rendered` through the same one pass as a resource's body (`renderContent`, with the page's ID as `postId`), in the shared `components/prose.css`; metadata is the title through the site template, the excerpt as the description, and the canonical path. The fixed point holds as for resources: a redirect's target is built from the CMS's canonical segments, which the plugin answers with themselves, and `test/page-request.test.ts` checks it over generated paths.
   **404s decided from the path (issue #46, 2026-11-06).** On Next.js 16.4.5 a `notFound()` thrown by a page is sent as the framework's empty `__next_error__` document, with `app/not-found.tsx` only in the inlined RSC payload, so without JavaScript, and to a crawler, the body is empty; the only response that has the page in its HTML is the prerendered `/_not-found` route, which the router renders for a URL no route matches, and since the root catch-all matches every URL nothing reaches it on its own. So `proxy.ts` answers every 404 that is decided from the path alone, before any route runs, with `NextResponse.rewrite()` to `/404` with `status: 404` (`NOT_FOUND_ROUTE` in `lib/path-decision.ts`), and the rewrite puts the routes' own `public, max-age=0, must-revalidate` on the response. The two servers the app runs on answer that rewrite differently, both measured 2026-11-06 and written up in `proxy.ts`: under `next start`, `/404` is the pathname Next.js treats as its 404 page, so it serves the prerendered `app/not-found.tsx` with status 404 and `noindex` set by the server, one route-cache entry shared by every junk URL, and `s-maxage=31536000` alone unless the rewrite sets a header; on Vercel, `/404` is the static `404.html` its Next.js builder writes from the same prerender for its own 404 routing, served from one CDN copy for every junk URL with no page render and no entry per URL (the proxy itself still runs as a function on every junk request), and with the status the proxy's response carries, which is why the status is set explicitly (without it a static file is a 200, a soft 404). On both servers a client-side navigation to a junk URL gets a 404 for its RSC request, which the router answers with a full document load (any non-ok RSC response does that), and that load gets the not-found HTML with status 404. The App Router's `/_not-found` was the first target: the same page under `next start`, but on Vercel a prerendered function route, rendered and stored once per junk URL, with a 200 unless the status is set, so it was dropped. Which paths, each by the function its route uses so the two cannot disagree: outside the library, what the page catch-all answers without a request (`pagePathProblem`: a dot or a non-slug in a segment, a reserved first segment, the cap), except the front end's own routes under those segments (`OWN_ROUTE_PATHS`: the revalidate route and the favicon) and everything under `/_next/` and `/media/`, which the framework and the uploads rewrite own (a junk `/_next/x/` still gets the catch-all's empty 404, as the matcher keeps out of `/_next/`); under the library, a shape no listing or resource route has (`parseResourcesSegments`, pinned to the route directories by `test/routes.test.ts`), a listing whose segments the listing refuses (`validListing`, the one validation `components/ListingPage.tsx` uses) and a resource whose type or slug segment is not a slug. The 404 is decided on the canonical form and wins over the redirect, so `/Robots.TXT` is one 404 and not a 308 and then a 404. Pinned under `next start` in `e2e/errors.spec.ts`, with JavaScript off and on, and a client-side navigation; the e2e suite never runs on Vercel, so the Vercel half is checked by hand on a preview (`curl` the paths in the spec's `PATH_DECIDED` list: status 404, `x-matched-path: /404`, the heading in the body) whenever `proxy.ts`, the matcher or Next.js changes. Every 404 that needs the CMS (an unknown slug, an unknown term, a page past the end, a path no page has) is the route's, and has had the page in its HTML too since the same day, through `DataNotFound` (next paragraph); the rewrite stays for the paths decided here because it renders nothing and stores nothing per junk URL.
   **404s decided by data (issue #46, 2026-11-06).** A route never throws `notFound()` where no Suspense boundary encloses it: React's server renderer runs no error boundaries, so such a throw aborts the shell and Next.js 16.4.5 sends its empty `__next_error__` document (`getErrorRSCPayload`; vercel/next.js#62228), which ISR then stores. Instead the decision (`resourceForRequest`, `pageForRequest`, the listing's checks) returns a not-found decision, the page returns `<DataNotFound />`, and that component throws `notFound()` inside its own Suspense boundary whose fallback is `components/NotFoundContent.tsx`, the same content `app/not-found.tsx` renders. The server renderer writes the fallback into the HTML, Next.js's HTML error handler sets status 404 and adds `noindex`, and because an ISR page is rendered completely before it is answered or stored, the status is set before anything is sent: 404, the page in the HTML, `noindex`, stored and served as a route-cache hit, cleared by events like any entry. On hydration React renders the boundary again and `app/not-found.tsx` takes its place, with no console error; a client-side navigation gets the same page. Redirects are unchanged: the decision runs first and throws `permanentRedirect()` outside every boundary. `generateMetadata` returns `NOT_FOUND_METADATA` on a not-found decision and never throws `notFound()`: for a crawler Next.js counts as unable to run JavaScript (Bingbot, not Googlebot) metadata renders in the `<head>`, outside every boundary, and a throw there stored the empty document for every reader (measured). Measured 2026-11-06 under `next start` and on a remote-built Vercel preview (first request and cached, browser, Googlebot and Bingbot user agents): every such 404 is a 404 with `<h1>Page not found</h1>` in the HTML and no `__next_error__`, and the 308s and 200s are unchanged. `test/data-not-found.test.tsx` pins the shape and that nothing else in `app/`, `components/` or `lib/` calls `notFound()`; `e2e/errors.spec.ts` pins the wire, JavaScript off and on, a crawler first, and a client-side navigation. The route must stay ISR for this: a dynamic render streams the shell, and its status, before the boundary fails.
2. Data layer in `lib/wp/`, server-only: typed fetchers over `fetch` with `next: { tags: [...] }` so revalidation is tag-based (`resources`, `terms`, `resource:{slug}`, `topic:{slug}`, `type:{slug}` and `pages`, the last on every page lookup and page read and cleared by page events only, each fetch's tags taken from the functions in `lib/tags.ts` per ADRs 0046 and 0052), and Zod parsing derived from the shared JSON Schemas (see the contract in the root `CLAUDE.md`) plus the core REST payloads, so a CMS change fails loudly, not silently.
3. `app/api/revalidate/route.ts`, served at `/api/revalidate/`: the on-demand revalidation endpoint per the contract in the root `CLAUDE.md`. The plugin posts to `/api/revalidate/`, with the trailing slash, because `trailingSlash: true` answers `/api/revalidate` with a 308 that the plugin's POST does not follow (ADR 0043). ADR 0048 records how it works: the bearer is checked before the body is read, as SHA-256 digests compared with `timingSafeEqual`; the body must be `application/json`, is read under a 64 KB cap and parsed with the reader schema; every body problem is a `400` whose message names the first issue's path and never a value; `revalidateTag(tag, { expire: 0 })` and `revalidatePath` clear the union of each event's current and previous state from `lib/tags.ts`; it fetches nothing from the CMS; and it answers with the exact response shapes the plugin expects. It is the front end's critical path, read line by line before merge.
4. Static generation with ISR as the safety net (a long `revalidate` interval) and on-demand revalidation as the primary path, for every route: the listings, the single-resource page and the pages catch-all (ADR 0035 and ADR 0052, amended 2026-11-06, reversing the per-request rendering of 2026-11-05). A stored redirect or 404 is cleared by the same event that makes it wrong, and a `headers()` rule keeps browsers asking again; the data comes from the same tagged Data Cache. The reasoning is in those amendments.
5. Accessibility and performance as gates, not claims: semantic landmarks, keyboard-reachable filters, no layout shift from late content, and `next/image` with sized images through Vercel's image optimizer, sourced from the same-origin `/media/…` rewrite (ADRs 0039, 0040). The owner's plan includes 5,000 optimized images a month; the fallback is proxying the originals and WordPress's sizes through Cloudflare with no transformations. Lighthouse mobile performance and accessibility both 95 or better on `/resources` and a single resource.
6. Tests and gates: TypeScript strict, ESLint, Playwright end to end (filtering works; the revalidate route rejects a bad bearer and a bad body and accepts a good one), all in GitHub Actions on every push; Vercel preview deploys per PR.

## Standards and workflow

- Next.js 16, App Router, TypeScript strict, pnpm. Server Components by default; client components only for the filter controls. Styling is plain CSS on the shared tokens, no framework and no web fonts (ADR 0045): component styles come from `@colbitron/resource-hub-ui` and are imported by the component that renders the markup; `components/Shell.tsx` imports the tokens and the app's own `shell.css`, never `layout.tsx`. Test-only pages are `app/**/page.fixture.tsx`, routes only under `RH_FIXTURES=1`, which Playwright's web server sets.
- `AGENTS.md` here is written by `next dev`: this Next.js version differs from older ones, so read the relevant guide in `node_modules/next/dist/docs/` before writing code.
- ADR 0043 records the caching model: the `fetch` Data Cache with `next: { tags }`, a route `revalidate` as the ISR safety net, and `revalidateTag` plus `revalidatePath` from the revalidate route, without Cache Components. ADR 0046 records which tags and paths each event revalidates and which tags each fetch carries. ADR 0047 records the one server-side pass over `content.rendered` in `lib/content/render.tsx`: the allow-list sanitiser (kses is no guard against `unfiltered_html`), the image trust rule, embeds as links and the `renderBlock` seam for the block marker. ADR 0048 records the revalidate route: digest comparison before the body, the 64 KB body cap, the `{ expire: 0 }` profile, tags plus paths, no CMS fetches and the error bodies. ADR 0049 (proposed) records the data layer's fetch policy in `lib/wp/fetch.ts`: the one-hour ISR interval, the ten-second timeout, the error mapping and the redirect policy for non-canonical slugs. ADR 0050 records the listing routes: ISR on first request with no build-time CMS call, and what each kind of request gets. Decisions still to record as ADRs for this app: the `/media/` rewrite versus a Route Handler (pending in ADR 0040's 2026-11-05 amendment), and REST versus GraphQL. These are the project's talking points.
- The shared package comes from the workspace as `"@colbitron/resource-hub-ui": "workspace:*"` in this app's `package.json` (ADR 0041).
- End-to-end specs are `e2e/*.spec.ts`; `pnpm web:test:e2e` starts the mock CMS in `e2e/mock-cms/` (a Node server shaped like the plugin's WordPress, with control endpoints under `/__mock/` for changing its data from a spec), then builds the app with the fixture routes and runs the specs against `next start`, with `WP_API_URL` pointing at the mock and `REVALIDATE_SECRET` set to the fixed test value in `e2e/mock-cms/config.mts`. The suite runs one worker, because every spec file resets the mock in `beforeEach`. Ports 3310 (app) and 4010 (mock), overridable with `RH_WEB_PORT` and `RH_MOCK_CMS_PORT`. Front-end e2e never uses wp-env or the hosted CMS; `e2e/README.md` has the routes, the controls and the seed. Playwright's Chromium must be installed (`pnpm exec playwright install chromium` in `apps/web`).
- Local work: run `pnpm web:dev` from the repository root (or `pnpm dev` here), with `WP_API_URL` in `.env.local` pointing at the wp-env CMS, `http://localhost:8888/wp-json` by default.

The data-decided half works around vercel/next.js#62228 (`getErrorRSCPayload` hard-codes the empty shell when `notFound()` aborts it; #98583 and #100606 propose fixes, none released as of stable 16.4.5 and canary 16.5.0-canary.42).
