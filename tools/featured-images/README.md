# Featured images for the seeded resources

Two scripts for issue #6: one renders an abstract featured image per resource in the seeder's catalogue, the other sets them as featured images on a WordPress site. The PNGs land in `artifacts/featured-images/` (gitignored) and are never committed; re-running the generator reproduces them exactly.

## Generate

```sh
pnpm images:generate            # writes artifacts/featured-images/<slug>.png and contact-sheet.png
```

`generate.mts` reads the slugs and types from `wp-content/plugins/resource-hub-wp/src/Seed/Seeder.php` and fails if a type has no accent in its table (or the table names a type the seeder no longer has), so the two cannot drift apart silently. It renders an HTML template with the headless Chromium that `apps/web`'s Playwright already installs (`pnpm exec playwright install chromium` in `apps/web` if it is missing), resolved from there so this tool adds no dependency. `contact-sheet.png` shows every image at its full frame, in the 16:9 card crop and in the centre-square crop, for approval.

## Import

```sh
pnpm images:import local                                    # the wp-env of this checkout
pnpm images:import local --force                            # replace images that are already set
pnpm images:import local --no-revalidate                    # set images without the revalidation save
pnpm images:import local --revalidate-only                  # only the revalidation save, for every resource

pnpm images:import host --ssh user@host --wp-path /path/to/wordpress
RH_SSH_TARGET=user@host RH_WP_PATH=/path/to/wordpress pnpm images:import host
```

For each slug in the seeder's catalogue the script finds the published `resource` with that slug, skips it when it already has a featured image (unless `--force`, which imports a new attachment and leaves the old one in the library), and otherwise runs `wp media import --post_id=<id> --featured_image --alt="" --title="<resource title>"` and checks that WordPress could decode the file (a damaged file with a PNG signature is accepted, keeps its header's dimensions and gets no generated sizes). A failed decode is rolled back: the new attachment is deleted and the previous featured image put back, or cleared when there was none, with each step's outcome in the report line; it counts as failed. A slug with no published resource gets a warning and is counted as "skipped (no post)": the catalogue holds 16 entries and a site seeded with the default 12 is normal. A run interrupted between the import and the meta write leaves an attachment on the post with no `_thumbnail_id`; the next run finds it by parent, title and file name (`<slug>.png`, or the `<slug>-N.png` WordPress gives a second copy), checks it decodes, and reuses it rather than importing a duplicate (one that does not decode is deleted and the import happens afresh; an editor's same-titled upload with another file name is never touched; a file copied into uploads before its attachment row was written is the one leftover WordPress never lists). The run exits non-zero only for a real failure: a WP-CLI, SSH or import error, a catalogue slug with no PNG in the directory (both targets check that before staging anything), or a run that set nothing and found nothing already set, which means a wrong `--wp-path` or an unseeded site.

Both targets stage only the catalogue's PNGs plus a `slugs.txt` and the script, and remove the staging directory afterwards even when the run fails: `local` copies into the directory wp-env bind-mounts as `/var/www/html` (no change to `.wp-env.json`) and runs the worker through `wp-env run cli`; `host` makes a `mktemp -d` under the host's `/tmp` (`$TMPDIR` if set there) over `ssh`, streams the files into it as a `tar` through the same `ssh` shell (not `scp`: it speaks SFTP, which Cloudways chroots to `/home/master`, where the shell's `/tmp` does not exist), runs the worker over `ssh` with the host's `wp`, and deletes the directory. `RH_WP_BIN` is the path of the host's `wp` binary when it is not on `PATH`, one path with no arguments. The worker changes into the WordPress root before its first `wp` call and checks once with `wp core is-installed` that WP-CLI can load the site: WP-CLI evaluates `wp-config.php` rather than including it, so a relative `require` in it (Cloudways's `require_once 'wp-salt.php'`) resolves against the working directory and is a fatal error from anywhere else, and the check turns a broken setup into one message instead of a stack trace per slug. The SSH target and WordPress path are arguments or environment variables, never in the repository.

**Revalidation.** Setting a featured image is a meta write, and the plugin sends resource events only from `wp_after_insert_post`, so on its own the import would leave the front end's cached pages without the images. After each image is set the worker therefore saves the resource again through `wp_update_post( array( 'ID' => $id ) )` in a `wp eval` that first re-reads the post and saves only while it is still a published `resource` (an editor may have drafted or trashed it since the lookup, and a save naming a status would publish it again; such a resource is reported and left alone). The save changes nothing in the post: `wp_update_post()` keeps the stored status, and the seeded bodies and excerpts hash the same before and after a save with no user, so kses does not touch them (`RH_WP_USER`, a login or ID, runs the save as that user for content that would need `unfiltered_html`). The hook derives an `update` event (publish to publish), sends it at WP-CLI shutdown and prints its result: an accepted batch appears on the resource's `saved` line ("Revalidation accepted (200)."), anything else as the plugin's own warning line above a `warning … saved, but the plugin reported a problem` line, and the summary counts the two apart. Either way the result is recorded in the resource's `_rh_last_revalidation` and shown on the Resource Hub status page and in the Resources list's Revalidation column; a plugin warning is not an import failure and does not change the exit status. The save bumps the resource's modified date, as any editor save does, and the first one creates a revision. `--no-revalidate` skips the save; `--revalidate-only` does only the save, for every catalogue slug with a resource, images untouched, which is how to re-send after a run that skipped everything as already set. On wp-env, which has no front end configured, every send is recorded as `not_configured`, which is expected.

## Decisions

- **2400×1260**: twice the 1200×630 Open Graph frame (1.91:1) and under WordPress's 2560 px big-image threshold, so there is no `-scaled` copy; each PNG is around 50 KB, far under the 1 MB target and the 5 MB ceiling.
- **Crops**: the composition's weight stays in the centre square, so the 16:9 `object-fit: cover` card crop (about 3.5% off each side) and a square messaging preview (the centre 1260×1260) both keep the panel and its motif whole.
- **No text**: the images are abstract, in the language of the owner's LinkedIn post cards (paper, soft palette orbs, the five-dot row, the warm panel, the lemon squiggle), with the resource type's accent dominating: article mint, ebook grape, webinar coral, podcast lemon, case study cobalt, the same mapping as the front end's `lib/type-accents.ts`.
- **Empty alt text**: the image is decorative next to the resource's printed title, so the import sets `--alt=""` and the REST payload's `alt_text` is `""`.
- **Seeded randomness**: layout and motif variation come from a PRNG seeded with the slug, so every run on the same machine with the same Playwright (Chromium) version gives byte-identical files, and resources of one type look related without being identical. A different Chromium may rasterise the same layout a pixel differently; the composition is still the same.
