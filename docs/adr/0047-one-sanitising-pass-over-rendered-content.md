# One server-side pass sanitises `content.rendered` and rewrites its URLs

A resource's body arrives as `content.rendered`: HTML that editors wrote, with the CMS's absolute URLs in it. [ADR 0040](0040-the-cms-url-never-reaches-the-browser.md) says one parse pass owns every rewrite in it; [ADR 0036](0036-cms-links-are-made-relative.md) and [ADR 0037](0037-block-marker-swapped-for-a-server-component.md) say what two of them are. This records the pass as built, in `apps/web/lib/content/render.tsx`, and the decisions it took that those ADRs did not.

## The single pass

`html-react-parser` parses the string once and calls `replace` for every top-level node before it renders anything of its own; below the top level the pass maps each element's children itself. The pass returns a new element for every element node, built from an allow-list, or nothing; text becomes a string for React, from the parser at the top level and from the pass below it. React escapes text and attribute values, and nothing uses `dangerouslySetInnerHTML`, so no fragment of the input reaches the page as markup. Links, images, the sanitising, the block marker and embeds are all decided in that one `replace`, in `renderContent(html, cmsUrls(), { renderBlock })`.

## An allow-list sanitiser, because kses is not a guard

WordPress filters post content with kses, but editors and administrators have `unfiltered_html`, so any of them can save a `<script>`, an `onerror` or a `javascript:` link, and `content.rendered` carries it to the front end as is. The front end treats the body as untrusted and keeps only what it recognises:

- Elements: `h1` to `h6`, `p`, `br`, `hr`, `wbr`, `ul`, `ol`, `li`, `dl`, `dt`, `dd`, `a`, `img`, `figure`, `figcaption`, `blockquote`, `q`, `cite`, `code`, `pre`, `kbd`, `samp`, `var`, `table`, `caption`, `thead`, `tbody`, `tfoot`, `tr`, `th`, `td`, `em`, `strong`, `b`, `i`, `u`, `s`, `del`, `ins`, `sub`, `sup`, `small`, `mark`, `abbr`, `time`, `details`, `summary`, `div`, `span`.
- Attributes on any of them: `class` (tokens of letters, digits, `-` and `_`), `id`, `title`, `lang`, `dir`. No `class` token may start with `rh-`, in any case: that is the prefix of the app's own classes, and a body could use them to restyle the page around it (`rh-card__link`, whose `::after` is `inset: 0`, would stretch a link over everything positioned below it; `rh-skip` is the skip link's). The one exception is `rh-related` on the block marker's wrapper, the class the plugin gives it and the shared stylesheet styles ([ADR 0038](0038-shared-styles-through-npm-rc.md)). Per element: `href`, `target` (`_blank` only) and `rel` (known tokens) on `a`; `src`, `srcset`, `sizes`, `alt`, `width`, `height` on `img`; `colspan`, `rowspan` and `scope` on cells; `start` and `reversed` on `ol`; `cite` on `blockquote` and `q`; `datetime` on `time`; `open` on `details`. Every value is checked against a pattern or a set. `style` and every `on*` attribute are never read.
- URL attributes (`href`, `src`, `srcset`, `cite`) may be `http`, `https`, `mailto`, `tel` or relative, judged on the URL as the WHATWG parser reads it, so case, surrounding spaces, tabs and newlines in the scheme make no difference, and entities are already decoded by the HTML parser. Anything else (`javascript:`, `data:`, `vbscript:`) is dropped.
- `script`, `style`, `noscript`, `template`, `object`, `embed`, `svg`, `math`, forms and their controls, `base`, `meta`, `link`, `head`, `title`, `canvas`, `dialog` and the obsolete raw-text elements are dropped with everything inside them. Any other element the list does not name is unwrapped: its children are kept and go through the same checks.
- Duplicate attributes keep the first, as a browser does, so `HREF="javascript:…" href="/ok"` loses its link rather than keeping the safe-looking one. htmlparser2 does this itself (it lower-cases each name and stores only the first), and a test pins it. Comments, the doctype and processing instructions render nothing.
- Every `id` is rendered with the prefix `c-`, and a same-page link to `#name` becomes `#c-name` to match. Browsers expose an element with an `id` as a global of that name, so `<div id="TURBOPACK">` or `id="webpackChunk_N_E"` in a body would replace the object Next.js's bootstrap script reads (DOM clobbering); nothing the page runs looks up a name starting with `c-`. No `aria-*`, `for` or `headers` attribute is allowed, so nothing else refers to an `id`.

The sanitiser is written inside `replace` rather than taken from a library. The allow-list is a few dozen names and a dozen patterns, short enough for the line-by-line read this file gets; a library (`sanitize-html`, DOMPurify on jsdom) would sanitise the string first and parse it again, a second pass with its own configuration to keep in step with this one, and its output would still need every rewrite here applied on top. Writing it here also keeps the invariant that makes the approach sound visible in one place: the parser renders nothing itself, the output is never serialised and re-parsed, so the mutation tricks that defeat string sanitisers do not apply. The test suite runs the pass over sixty-odd injection vectors, pins the exact output of each one whose output is short, checks that content after each vector still renders, and runs the captured fixture.

## Depth has a limit, and a body never makes the page fail

A body nested more than 256 elements deep renders as plain text: every tag, comment and declaration removed, the content of `<script>`, `<style>` and the other raw-text elements left out, common entities decoded. WordPress's own blocks nest a dozen levels at most, so the limit is far beyond real content, and far below the depths that break the libraries: `html-react-parser` recurses once per level and throws a `RangeError` at about 2,000 nested `<div>`s, and htmlparser2's stack handling is quadratic in depth (a megabyte of nested `<div>`s, 200,000 levels, takes about five seconds to parse).

Three layers enforce it. Before the parse that renders, a pre-pass runs htmlparser2 itself over the body, with the same options. It is a direct dependency of the app, pinned to 12.0.0, the version `html-dom-parser` declares. That is the same version as the parse that renders, not the same copy: `html-react-parser` loads `html-dom-parser`'s CommonJS build, in Vitest and in the Next server bundle alike, and that build parses with a copy of htmlparser2 bundled inside it (`lib/node_modules/htmlparser2`). `test/content-parser-version.test.ts` holds the two together: it fails unless `html-dom-parser` declares the pinned version and the bundled copy's sources, embedded in its source maps since it ships no `package.json`, are that release's byte for byte. The pre-pass counts the elements the parser holds open, from its own `onopentagname` and `onclosetag` events and its own judgement of which elements are void, and throws at the first element past 256, which stops the parse; that body renders as the plain text. Because it is the parser, comments, attribute values, `<script>`, `<textarea>`, CDATA, implied end tags and foreign content are read exactly as in the parse that renders, and the tree that parse builds can be no deeper. Because it stops at 257 open elements, the parser's work per tag, which grows with the depth (it searches its stack for every end tag and shifts it for every start tag), stays bounded, so the pre-pass is linear in the length of the body. During the pass the depth is no longer counted: the pre-pass decided it on the same parser version. Nor does the pass do work per level for each node: it maps each element's children itself rather than through `domToReact`, which resets the prototype of every node in the subtree it is given on every call, and it knows whether it is inside a link from a count it keeps as it descends rather than by walking up the parents. Both had cost the depth times the size of the body, about a second at 255 levels under the cap; the slowest body measured under the cap now is about 174,000 sibling `<a>` elements, at 0.3 to 0.4 s, which is the cost of that many elements at any depth. Around both, any error from the parse or the pass renders the plain text instead and is logged on the server. The plain-text rendering is built by a linear scan, never by the parser, so it is safe on the input that defeated it. Only a misconfigured CMS URL still throws, before the `try`, so configuration errors stay loud.

The size cap stays as a second line of defence: a body longer than 512 Ki UTF-16 code units (`MAX_CONTENT_LENGTH`, measured as `html.length`, which costs nothing and is what the parser's work scales with) renders as the plain text without reaching the parser. A body renders once per revalidation before ISR caches it, and only editors can write one; real bodies are a few tens of kilobytes.

This replaces the first design, taken while the project owner was away on 2026-11-05, which was a hand-written scan that counted open elements by name and refused to parse past 1,024, with the cap to bound what got past it. The cap alone did not bound the time. The scan could not see end tags the way the parser does, so end tags hidden in comments, `<script>`, `<textarea>`, attribute values or CDATA lowered its count while the parser nested tens of thousands deep, and tens of thousands of unmatched `</p>` after that each cost the parser a search of its stack. Measured under the cap, blocks of 1,000 `<i>` with their 1,000 end tags hidden in `<!--…-->`, repeated to 37,000 deep and followed by about 60,000 `</p>`, took 1.6 to 2.9 s for one render, and the same with the end tags in `<script>`, `<textarea>`, an attribute value or CDATA 1.6 to 3.7 s (the review measured 3.4 to 4.0 s); the earlier estimates of 0.6 s per megabyte and 0.3 s per render were wrong. The scan itself took 1.0 s on `"<a".repeat(262144)`, because it read each tag name to its end from every `<`. With the pre-pass each of those inputs takes 4 to 9 ms, because each passes depth 256 early and the pre-pass stops it there, so the parse that renders never runs. A body that stays at a legal depth near the cap is parsed and rendered in full and costs much more, up to about 350 ms: a reviewer measured 351 ms for 254 `<div>`s then a `<p>`, repeated to the size cap. The owner reversed the earlier "no tokenizer" call overnight on 2026-11-05: using the parser's own tokenizer is not a second tokenizer to keep in step, which was the reason for rejecting one.

## The image trust rule

An image is a CMS image only when its URL, read relative to the uploads directory, has the uploads directory's origin exactly (scheme, host and port), lies under its path, and carries no user name or password. Only those become `/media/…`, which `next.config.ts` proxies to the CMS, and only those reach `next/image`, which renders a CMS image that has both a `width` and a `height` (so the space is reserved, [ADR 0039](0039-vercel-image-optimizer.md)) with a `sizes` sized to the content column. A CMS image without both is a plain lazy `<img>` whose `srcset` is rebuilt from the candidates that are CMS images too.

## External images are kept, CMS-host images that are not uploads are dropped

An image on a host that is not the CMS's stays a plain lazy `<img>` by its `src` alone, with `referrerpolicy="no-referrer"`: it says nothing about the CMS, editors do embed the odd third-party image, and dropping it would make the demo look broken for no gain. `no-referrer` removes only the `Referer` header: the reader's IP address, user agent and any cookies for that host still reach a host the editor chose, so an external image is a tracking pixel the editor can place. The stricter option is an allow-list of image hosts whose default is empty (an image on an unlisted host is dropped) together with a Content-Security-Policy `img-src` that says the same to the browser; that choice is the project owner's and is pending. An image that names a CMS host but is not a CMS image (`http:` where the CMS is `https:`, another port, a path outside the uploads directory, credentials in the URL) is dropped: it cannot be served through `/media/`, and rendering it would put the CMS's address in the page.

## CMS links that lead nowhere on the front end are unwrapped

A link on the CMS stays a link only when its rewrite is a route the front end serves: `/` without a query, `/resources` and everything under it, or an upload's `/media/…`. Any other CMS link (`/wp-json/…`, `/wp-admin/`, `/wp-login.php`, `/xmlrpc.php`, `/feed/`, `/wp-content/…` outside uploads, `/?post_type=…&p=…`, or one whose rewrite still names the CMS because of a port the configuration does not list) is unwrapped: the `<a>` goes and its text stays. Made relative, these would be 404s on the front end, and left absolute they would show the CMS's address; neither is a useful link. This is the default chosen while the project owner was away on 2026-11-05 and is pending their review. Relative links the editor wrote are left as written, since they never named the CMS.

## Where the CMS host can still appear

No attribute the pass renders names the CMS, except the `href` or `cite` of a `mailto:` or `tel:` URL (below). "Names the CMS" means containing a configured host, or host and install path, in any case, as a whole host, and an internationalised host in its punycode form (`xn--mnchen-3ya.example`, what `URL` gives) or its Unicode form (`münchen.example`, what an editor types; its non-ASCII letters match in lower case only): not preceded by a letter, digit or `-` (unless they end a percent escape, as in `%2Fcms.example`), and not followed by one or by `.` and one, so `cms.example.org`, `cms.example-2` and `evilcms.example` are other hosts and `www.cms.example`, `editor@cms.example`, `cms.example:8443` and `cms.example.` name it. Hosts in URLs compare with every trailing dot removed, so `cms.example..` is the CMS.

- An `href` (or `cite`, or an embed's `src`) that still names the CMS after the rewrite loses its query when the query is what names it (`/resources/?u=https://cms.example/wp-admin/` becomes `/resources/`), and is unwrapped like a CMS link with no route when its path or hash does. The query, not the whole link, goes first because the query is usually a tracking or share parameter around a link that still works without it.
- A `mailto:` or `tel:` URL is exempt from that rule and kept as written, even when it names the CMS: `mailto:editor@cms.example`, and on a CMS at an apex domain `mailto:info@example.com`, stay links. An address on the CMS's domain is content the editor chose to write, not the CMS's URL, and without the exemption every contact link on an apex-domain CMS would lose its link. The scheme allow-list is unchanged, and the link's other attributes still follow the rules here. This is the default chosen while the project owner was away on 2026-11-05 and is pending their review.
- A `title`, `id` (checked before its `c-` prefix), `datetime` or `class` token that names the CMS is dropped, the words of an `alt` that name it are removed, an image whose own URL names it is dropped, and so is a `srcset` candidate that does. Every other attribute value goes through one last check before its element is created and is dropped if it names the CMS, so the rule holds for values no case above foresaw (`sizes`, say).
- Only an autolink's content is replaced. A link whose text, trimmed, is its own `href` (WordPress turns a pasted URL into `<a href="u">u</a>`) or is a CMS URL written out (an absolute http(s) URL on a CMS host) shows the rewritten target instead; when there is none to show, its own content stays. Any other link keeps its content as it is, markup included, even when its text names the CMS: `<a href="https://cms.example/wp-admin/"><b>bold</b> cms.example</a>` is unwrapped to its bold word and its text, not flattened to bare text, since editor-typed text is left as written. An iframe's `title` becomes the link's text unless it is the `src` itself or names the CMS, when the rewritten `src` is shown instead.
- The plain-text fallback cannot tell a link's text from prose, so it takes the CMS out of all of it: each CMS origin (a name right after `//`, with its scheme and port) is removed, so an autolink reads as its rewritten path, and then each word that still names the CMS is removed.

Editor-typed text is otherwise left as written, in a paragraph, in `<code>` or as the content of an unwrapped link: rewriting it would corrupt code samples and prose that discuss the CMS, and an editor who types the address has chosen to publish it.

## Embeds become links

WordPress renders an embed block as an `<iframe>`, or leaves the raw URL as text when no oEmbed provider answered. The pass turns an `<iframe>`, `<video>` or `<audio>` anywhere into a link to its `src` (a `<video>` or `<audio>` without one, to its first `<source>` whose `src` makes a link), titled by its `title` when it has one, and a raw embed URL into a link to itself. Inside a link, where a browser would not nest another, each becomes its text, and an `<a>` inside an `<a>` is unwrapped. A link degrades gracefully, loads nothing from a third party and needs no allow-list of providers.

A `<pre>` whose only child is text loses the newline right after its start tag, as the browser already dropped it from the CMS's HTML and React would otherwise write it back as a blank first line.

## The marker seam

`<div data-rh-block="related-resources">` is found in the same pass. `data-count` (1 to 10), `data-topic` (a slug by `isSlug` in `lib/routes.ts`, and already in the form `canonicalSlug` gives, which is the form WordPress writes, so `topic:{slug}` is the tag the data layer sets), `data-topic-id` and `data-exclude` (positive integers) are validated and handed, with the text of the block's `<h2>` (without the content of dropped elements such as `<script>`), to an injectable `renderBlock(props, fallback)`. The caller passes the resource's ID as `postId`, and it is the one excluded, whatever `data-exclude` says; a marker that disagrees still renders. At most five markers in a body reach `renderBlock`, the first five in document order (a marker nested in another comes after it), since each costs the server a related-route call and a fetch; the rest render their fallback. A marker inside a link renders its fallback too, because the block renders links and a browser would not nest them, and a `renderBlock` that throws renders that block's fallback and is logged, while the rest of the body renders as usual. (An error inside the component `renderBlock` returns happens later, when React renders it, and is for an error boundary.) The fallback is the wrapper as the pass renders it, its class kept and its `data-*` attributes dropped, with the CMS's own heading and list of links rewritten like any other content. The default `renderBlock` returns the fallback; slice 4 plugs in `<RelatedResources>`. An invalid marker renders the fallback without calling `renderBlock`.

## Considered options

- **A sanitising library before the parse.** Rejected above: a second pass to configure, and the rewrites still needed.
- **A hand-written scan of the tags before the parse, with the size cap to bound what it misses.** The first design, replaced above: the scan cannot read end tags as the parser does, and the cap did not bound the time (1.6 to 3.7 s for one render under it).
- **A copy of htmlparser2's tokenizer for the pre-pass.** Rejected: a second tokenizer to keep in step with the parser. Running the parser itself, at the version the parse that renders uses, needs nothing kept in step but that version, and a test holds it.
- **Only the size cap, set lower.** Rejected: the time grows with depth times the number of tags, so a cap low enough to bound it would refuse real bodies.
- **Trusting kses.** Rejected: `unfiltered_html` makes it no guard for the roles that write resources.
- **Treating `http:` CMS images as CMS images, as `rewriteHref` does for links.** The rewrite would serve them over https anyway. Rejected: the review that set the acceptance criteria asked for origin equality, and the cost is one missing image on content that still has a pre-https URL, which the editor can fix.
- **Dropping external images.** Not chosen for now: editors use them and `no-referrer` keeps the page's URL from the other host, though not the reader's IP address or user agent (see above). An allow-list with an empty default plus a CSP `img-src` is the stricter option, pending the project owner's choice.
- **Making every CMS link relative, whatever its path.** Rejected for paths the front end does not serve: a relative `/wp-admin/` is a 404, and an absolute one shows the CMS.
- **Rewriting the CMS host in text and `<code>`.** Rejected: it would corrupt code samples, and the text is the editor's.
- **Keeping `style`.** Rejected: WordPress's blocks put layout in classes, and inline styles are a channel for CSS injection with no content that needs it.
- **Rendering embeds as iframes from an allow-list of providers.** Rejected for now: third-party frames load scripts the page does not control, and a link is enough for a demo.

## Consequences

- A new kind of element in resource bodies is a change to the allow-list here, with a test; the default for anything unknown is to unwrap it, so content survives and attributes do not.
- No attribute the pass renders names the CMS, except a `mailto:` or `tel:` URL, and neither does the plain-text fallback; editor-typed text in the markup rendering is left as written. The fixture test asserts the first half on a body whose text does not name the CMS.
- `cmsUrls()` in `lib/env.ts` gives the pass the site base, the media origin and the uploads directory from the environment.
- `parseSrcset` is exported from `lib/urls.ts` so each candidate can be judged on its own. It and every pattern in the pass run in linear time: trailing runs are trimmed with a loop (`withoutTrailing`), because `/,+$/` on a long comma run followed by anything else is quadratic (200 KB took 13.5 s), and the `srcset` descriptor pattern has no two quantifiers that can share digits. The tests hold 500 KB of each, just under the size cap so it reaches the pass, to under a second.

## Amendment, 2026-11-05: tables scroll in a labelled region, and an editor's `h1` moves every body heading down one level

Two additions to the pass, from the resource-page review. Neither changes the allow-lists: content still cannot carry an `rh-` class, a `role`, a `tabindex` or any `aria-*` attribute, and the markup below is the pass's own.

**Tables.** Every `<table>` the pass renders is wrapped in `<div class="rh-table-scroll" role="region" tabindex="0" aria-label="…">` (`tableRegion`), and `components/resource.css` gives the region `overflow-x: auto` and the tokens' focus ring. A table wider than the column, which on a phone is any table with a few columns of long words, then scrolls inside the column instead of widening the page or breaking its words. A box that scrolls must be reachable from the keyboard to be scrolled without a pointer (WCAG 2.1.1, axe's `scrollable-region-focusable`), so the region is a tab stop, and a tab stop needs a name, so it is a named `region`. The name is the text of the table's `<caption>` (its first `caption` child, as a browser takes it), through `textOf`, so the content of dropped elements is left out, and with every word that names the CMS removed, since it renders as an attribute; with no caption, or nothing left of one, it is "Table". A table inside a `figure.wp-block-table` is wrapped itself, not the figure, so the figure's caption stays outside the scrolling box. A table inside a link renders bare, because a focusable region there would be an interactive element inside another.

- The region is a tab stop even when its table fits. Removing it then would need client JavaScript to measure the table, and an extra stop on a page with few tables costs less than a client component in the body.
- WordPress's table block writes its caption as a `<figcaption>` after the table, not a `<caption>`, so a table block's region is named "Table" today. Naming it from the figure's caption instead is a small change to `tableLabel`, not made here because the review asked for the `<caption>`.

**Headings.** The page's own `<h1>` is the resource's title, so a body that renders an `<h1>` of its own has every heading shown one level down, capped at `h6` (`headingName`): `h1`, `h3`, `h2` become `h2`, `h4`, `h3`. Shifting every level, not only `h1`, keeps the body's headings in the order the editor gave them relative to each other. The rule applies only when the body has an `<h1>`; a body without one keeps its levels as written.

- **Rejected: always shift.** WordPress's editor starts a body's headings at `h2`, under the post title it renders as the `h1`, so most bodies already fit under the page's `<h1>`; shifting them all would make every ordinary body jump from the page's `h1` to `h3`, the heading-order fault the shift exists to avoid.
- **Rejected: demote `h1` alone.** `h1`, `h2` would become `h2`, `h2`, losing the editor's nesting, and `h1`, `h3` would keep its skip.

Whether the body has an `<h1>` is decided before the parse that renders, by the depth pre-pass, which already runs htmlparser2 over the whole body and is now `outline`: an `<h1>` counts when it opens outside every element whose content the pass leaves out (`DROPPED_WITH_CONTENT`, and `iframe`, `video` and `audio`, which become links), so an `<h1>` in a `<template>`, a `<noscript>` or a comment does not shift the rest. It is decided once per body, so a heading's level never depends on what comes after it in the stream. Two edge cases remain: an `<h1>` inside a block marker counts even when `renderBlock` replaces the marker, and the cap merges `h5` and `h6` when both are used under an `<h1>`. The marker's own `<h2>`, read for `renderBlock`'s `heading`, is read as written; its fallback rendering shifts with the rest. Slice 4's `<RelatedResources>` renders a heading of its own, and should render it one level down too when the body's headings move; `RelatedBlockProps` does not carry the level yet. `resource.css` no longer styles a body `h1`, since none renders.
