# CI runs on Depot CI, the deploys included

Every push to `main` runs the whole gate, the plugin inside wp-env and the front end against its mock CMS, and then deploys the CMS and then the front end (ADRs 0005, 0051); every pull request runs the part of the gate its changes reach. Until 2026-11-07 that ran on GitHub Actions. The repository is private on GitHub's free plan, and the gate used about 2,009 runner minutes in four days; the plan's spending limit was reached, and GitHub refused jobs from 2026-11-07 23:23 UTC, which stopped merges and deploys alike. Separately, the owner wants CI that keeps running through a GitHub Actions outage; issue #74 has the history.

**CI runs on Depot CI, from `.depot/workflows/`.** The workflows keep GitHub Actions' syntax. `ci.yml` began as the Depot migrator's copy of GitHub's and was then edited for Depot: the front end's one `web` job is split into parallel jobs, Lighthouse runs as five shards by URL with one more job merging their medians, and the jobs that run Node share a setup action. A run waits about three minutes, for the slowest job rather than the sum. GitHub's `ci.yml` and `screenshot-baselines.yml` are deleted, so nothing runs or deploys twice.

**A pull request runs only the jobs its changes reach, and never Lighthouse.** Depot bills each job's sandbox time, so a first job, `scope`, classifies the paths the pull request's merge commit changes (`.depot/scripts/ci-scope.mjs` has the rules): `wp-content/` reaches the plugin's gate, `apps/` the front-end jobs, documentation nothing, and every other path, the shared package, the root files, `.depot/` and any path added later, both; a docs-only pull request runs `scope` alone. When the paths cannot be read for certain, the scope is unknown and every job runs. Pushes to `main` and dispatches, on `main` or a tag, are never scoped and run everything. Lighthouse's five shards and its medians job run only there: they were most of a run's cost, and until issue #76 a budget miss blocks nothing, on `main` a warning as before. Before pushing a front-end change (`apps/` other than Markdown, or `packages/ui/`) the author runs `pnpm web:test:lighthouse:quick`, one run per URL, and reads the medians: a smell test on the author's machine, not a gate. `main`'s five-run medians are the record.

**The deploys run there, in the same order.** `deploy` needs the plugin's gate, so a front-end failure never blocks a CMS deploy or a rollback; `deploy-web` needs `deploy` and every front-end job, so the front end never goes live ahead of the CMS it reads or on a commit whose checks failed. On `main` every job runs, so `deploy-web` still waits on every Lighthouse shard. Their secrets live in Depot.

## Considered options

- **Paying GitHub's overage.** About $33–78 a month at this pace, and every run still stops when GitHub Actions does. Rejected.
- **A self-hosted runner on the owner's Mac.** No minutes to buy, but CI then depends on the laptop being awake and online, and pull-request code runs on the machine that holds the owner's credentials. Rejected.
- **Depot's or Blacksmith's GitHub-runner products**, which keep GitHub Actions as the orchestrator and swap only the machine. Rejected: both install on a GitHub organisation, and this repository belongs to a personal account. Blacksmith's quickstart says it is limited to organisations and not available for personal repositories (<https://docs.blacksmith.sh/introduction/quickstart>); Depot's runner quickstart connects a GitHub organisation and its runner groups (<https://depot.dev/docs/github-actions/quickstart>).
- **Lighthouse on pull requests too**, scoped by path like the other jobs: about 11 sandbox-minutes on every front-end pull request for misses that block nothing until #76. Rejected; its cost is below.
- **Staying on GitHub Actions.** Rejected: jobs stay refused until the limit resets, and an outage still stops every merge and deploy.

Depot CI was chosen because it accepts personal accounts and ran the whole suite natively in its trial, Docker and wp-env for the plugin and the amd64 Playwright image for the screenshots included.

## Consequences

- **Cost.** About $20 a month for the Developer plan, which includes 2,000 sandbox-minutes a month at 2 vCPU, shared with Depot's other sandbox products; past that, $0.006 a minute for 2 vCPU, billed per second (<https://depot.dev/pricing>, read 2026-11-07; confirm there before relying on it). A full run, on every push to `main` and every dispatch, uses about 17.5 sandbox-minutes, 11 of them Lighthouse (trial run zkp83r7b3s). A pull request uses about 3 for the plugin alone, 3.5 for the front end alone (trial run clmqq17s1c), 6.8 for both or a shared path and 0.1 for documentation; weighted by the 56 pull requests merged 2026-11-05 to 2026-11-07, Pacific time (26 both, 9 plugin, 17 front end, 4 neither), about 4.7. At the pace of the four days before the move, about 1,500 runs a month (`gh run list`), 28% of them pushes to `main`, that is about 12,500 sandbox-minutes: about $63 over the included minutes and $83 in all, a little past the rejected overage, against about $165 with every job on every run and $130 with Lighthouse scoped by path like the rest. Most of what remains is `main`'s full runs, and each parallel job bills its own setup, so sharding buys a shorter wait with more billed minutes. The move is for the limit and the outage, not the price; at four runs a day it costs the plan alone.
- **The secrets live in Depot** (`depot ci secrets`), not in GitHub's repository secrets. Listing, rotating them and the cutover switch are in [`docs/runbooks/deploy.md`](../runbooks/deploy.md).
- **The checks change names** and are reported on pull requests by the `depot-code-access` GitHub app, not by GitHub Actions.
- **The ADR guard keeps its GitHub copy for now.** The check runs on `pull_request_target`, and its safety rests on running `main`'s copy of the workflow, never the pull request's. Depot runs a copy too, and both copies are guarded paths. GitHub's `.github/workflows/adr-approval.yml` is the check of record only while GitHub Actions runs jobs: the owner has set a small Actions budget, and if the limit is reached again, Depot's copy may be the only one running, with its trust unconfirmed. It is tested after the merge, with the owner's go-ahead because it touches a guarded path, by a throwaway pull request, never merged and never labelled, that changes only `.depot/workflows/adr-approval.yml`, putting `echo "PR COPY"; exit 0` at the top of its run script: a red Depot check means Depot ran `main`'s copy; a green one, or "PR COPY" in its log, means it ran the pull request's and cannot be trusted. Whether Depot CI delivers the `labeled` and `unlabeled` types is unconfirmed too; its compatibility page lists `on.pull_request_target` and `on.<event_name>.types` as supported, not each type (<https://depot.dev/docs/ci/compatibility>).
- **`preview-lighthouse.yml` stays on GitHub for now; moving it is a follow-up.** Depot CI's compatibility page lists `on.deployment_status` ("Deployment status triggers") as supported (<https://depot.dev/docs/ci/compatibility>), so the trigger is no obstacle; the workflow is informational and was left out of this move to keep it small. It still uses GitHub Actions minutes, and if the GitHub limit is reached again it does not run; nothing waits on it, so that costs a comment, never a merge or a deploy.
- **A Lighthouse error first shows up on `main`.** A crash, missing runs or a failed report upload is no longer caught before the merge: it fails `main`'s run and holds `deploy-web` back until a fix lands, while the CMS deploy goes ahead. A budget regression likewise first appears there, as a warning. The smell test runs the same harness and should catch most breakages before the push, but it is not a gate, and a laptop's numbers differ from CI's 2-vCPU sandboxes. `depot ci run` on a branch is not scoped and runs Lighthouse, for CI's numbers before a merge.
- **Lighthouse is sharded by URL.** Each URL's five runs stay in one shard on its own 2-vCPU sandbox, so a shard asserts what a single run of the whole list would for its URLs, and the medians are merged into one table.
- **Rollback** is restoring `.github/workflows/ci.yml` from git and unsetting the Depot variable `DEPOT_DEPLOY_ENABLED`, which keeps Depot's deploy jobs off while they still test it. It needs Actions minutes: if GitHub's limit is reached again, GitHub refuses the restored workflow's jobs until it resets or the budget is raised. The steps are in the runbook.
