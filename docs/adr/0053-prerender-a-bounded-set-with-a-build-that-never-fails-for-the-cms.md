# The build prerenders a bounded set from the CMS when it answers, and nothing when it does not

[ADR 0043](0043-fetch-cache-with-tags-without-cache-components.md) made every route ISR with `generateStaticParams` returning `[]`, so `next build` rendered nothing from WordPress and a front-end deploy could never fail because the CMS was down. That rule had a cost on the client that was only measured on 2026-11-07. Next.js 16.4.5 writes a prefetch-hint manifest (`.next/server/prefetch-hints.json`) only for routes with at least one prerendered path, and when an ISR route is rendered at runtime with no entry in that manifest it marks every segment of the response `PrefetchDisabled` (`getMissingPrefetchHintPolicy` in `next/dist/server/app-render/create-transport-tree-from-loader-tree.js`; the client honours the bit in `segment-cache/scheduler.js`). With nothing prerendered, no route was in the manifest, so on the library page `<Link>` fetched no data for any row: four route-tree requests of about 0.7 KB for the static topic links and nothing else, and a click from the library to a resource cost a full RSC round trip, measured at a median of 454 ms on a throttled mobile profile (150 ms latency, 1.6 Mbps) against 61 to 67 ms once the row was prefetched. The same `[]` also kept the library's first page, each type's first page and the site's root, the pages a reader opens first, off the CDN until someone had asked for them.

**The decision: prerender a bounded set, and never let the CMS fail the build.** Four routes prerender at build: the library's first page `/resources/`, each type's first page `/resources/{type}/`, the root `/`, and the resource pages for the union of the 50 most recently published resources and the 10 most recent of each type, each slug once (`RECENT_RESOURCES` and `RECENT_PER_TYPE` in `apps/web/lib/prerender.ts`). Each `generateStaticParams` calls a probe in that module which makes the page's own reads through the data layer, under a 10 s budget per route (`PRERENDER_TIMEOUT_MS`, on top of the data layer's 10 s per request), and returns the params whose reads succeeded, or `[]` with one build warning on any error, timeout, unreadable answer or missing `WP_API_URL`. Because every data-layer read is a `fetch` with `cache: "force-cache"`, the render that follows the probe finds its reads in the Data Cache and makes no request of its own, so the window in which a CMS failure could reach a page render is the render itself, and it reads nothing new. Everything else is unchanged: `dynamicParams` stays on, every route keeps `revalidate = 3600` and its tags, a prerendered page and one rendered on demand are stored, served and cleared the same way, and topic listings, later pages and other CMS pages are never prerendered, since they grow with what editors add. A build the CMS does not answer, such as CI's production build against the `cms.example` placeholder, prerenders none of these pages and is otherwise the same build; measured at 2.4 s with four warnings naming the routes, against a median of 2.3 s with the mock answering and 2.3 s before the change.

**The catch-all stays, and the router's route prediction goes.** The library is `app/resources/[[...rest]]/page.tsx` because a plain `app/resources/page.tsx` has no dynamic segment and is prerendered whether or not the CMS answers, which would make the build fail when it does not; so the catch-all cannot be replaced without giving up the rule above. Its cost is on the client. With the routes in the manifest, the router's optimistic routing (`experimental.optimisticRouting`, on by default; `segment-cache/optimistic-routes.js`) learns the library's own tree from its `/_tree` response and from then on predicts every row and type link under `/resources/` as a path of the catch-all, the only dynamic child it knows there, and prefetches the row's page segment under the catch-all's key, which the server answers 404: a console error per link, nothing prefetched, and a full fetch on the click. Whether a given load does this is a race between that tree response and the links' prefetch tasks, which create their route entries when scheduled (`readOrCreateRouteCacheEntry` in `segment-cache/scheduler.js`): measured both ways on Next.js 16.4.5, twelve rows fetched correctly on one cold load and seven 404s on the next. The prediction is therefore turned off in `next.config.ts`. Without it every link asks the server for its own route tree, about 0.7 KB, and prefetches the right segments on every load; `apps/web/e2e/prefetch.spec.ts` fails on any request under the catch-all's key and on any failed prefetch.

## Considered options

- **Prerender nothing, the status quo.** Rejected: it is what disabled prefetching, and it keeps the entry pages off the CDN until their first visitor.
- **Prerender everything: every listing, every page of every listing, every resource.** Rejected for the reason 0043 gave: the build would grow without bound with what editors add, and take as long as the CMS is slow.
- **`prefetch={true}` on the row links, leaving the build alone.** Rejected: it fetches the full page data for every visible row, about 43 KB each on this design against about 5.8 KB for a tree and a page segment, and for a row no reader has opened yet it costs the CMS an ISR render per prefetch, on every library view.
- **A static `app/resources/page.tsx` in place of the catch-all**, so the router has no catch-all to predict. Rejected: it is prerendered unconditionally, so a build with the CMS down fails.
- **`dynamicParams = false` on the catch-all**, which the router treats as a closed parameter and never predicts. Rejected: `/resources/` would then be served only when the build listed it, so a build the CMS did not answer would leave the library a 404 until the next deploy.
- **Leaving the prediction on and accepting the race.** Rejected: a 404 in the console and no prefetch on some loads is worse than today's behaviour on those loads, and not reproducible enough to test.
- **A bounded set with a probe that falls back to `[]`, and route prediction off.** Chosen. The flag is experimental and undocumented; if an upgrade drops it, `e2e/prefetch.spec.ts` is what notices, and the prerender keeps working.

## Consequences

- The rule that survives from 0043 is that a build never *fails* for a CMS reason, not that it never *reads* the CMS. A build with the CMS up and a build with it down differ in which pages are stored at deploy; both serve every page.
- The row prefetch and the click latency above depend on the resource route being in the manifest, which needs at least one prerendered resource; a CMS that was down at build time leaves that deploy with the old behaviour until the next deploy.
- The set is the build's. `generateStaticParams` is not run again at revalidation, so a resource published after the deploy renders on its first request as before, and the manifest entry the route already has keeps its prefetching on.
- The build cache carries the Data Cache: `next build` keeps `.next/cache/fetch-cache`, which Vercel restores between builds, so a second build within the hourly interval can prerender from the previous build's CMS answers rather than ask again, and a page revalidated in production meanwhile is prerendered stale until the next event or the interval clears it. The e2e harness clears that directory before `next start`, not before the build, so a local rebuild shows the same.
- A route that imports the probe module imports what it reads with, and Next.js inlines every stylesheet in a route's module graph into that route's HTML: reaching the listing's reads through `components/ListingPage.tsx` put 3 KB gzipped of listing CSS into the resource page and over the 14,600-byte first-round-trip budget, so the reads live in `lib/listing-data.ts`, with no CSS, and the component imports them from there.
- The e2e harness's build runs with the mock up (Playwright starts the mock first), so the suite tests the prerendered pages; `e2e/lighthouse.mts` was reordered to start the mock before its build for the same reason. The prerendered set, its storage and its prefetching are pinned in `apps/web/e2e/prefetch.spec.ts`; the selection, the probes and the fallback in `apps/web/test/prerender.test.ts`.
- The numbers, the mechanism and the measurement method are in [`docs/architecture/caching.md`](../architecture/caching.md), "Prefetching".
