# Resource URLs are `/resources/[type]/[slug]/`, mirrored on both sites, and a resource has exactly one type

A resource's path carries its type, `/resources/[type]/[slug]/` rather than `/resources/[slug]/`, for search: a subfolder per type gives the library a visible hierarchy (Ahrefs: subfolders "provide a sense of hierarchy"), with each type's hub at `/resources/[type]/` as the parent of its resources. A path segment can only hold one value, so a resource has exactly one type: validated on save, and shown in the editor as radio buttons rather than the checkbox list [ADR 0007](0007-one-post-type-with-a-type-taxonomy.md) described.

Listings filter by one topic and one type at a time, and filters and pagination are path segments, not query strings. In the Next.js App Router, reading `searchParams` makes a page dynamic, so a function runs on every hit; path segments can be prerendered. Five types plus "any" by five topics plus "any" is 36 listings, times their pages. How the front end builds those routes is [ADR 0034](0034-filters-and-pagination-are-path-segments.md).

The full route set is `/resources/`, `/resources/[type]/`, `/resources/topic/[topic]/`, `/resources/[type]/topic/[topic]/` and `/resources/[type]/[slug]/`, and every listing paginates as `…/page/[n]/`. `topic` and `page` are therefore reserved and can never be a type slug. WordPress refuses either as a `resource_type` slug, on create and on edit, with an admin error message that says the slug is reserved, so a bad type never reaches a payload the schema would reject. That covers a slug generated from a name too: a type named "Topic" is refused rather than saved as `topic`.

The same paths exist on both sites. The post type's rewrite slug is `resources/%resource_type%`, using the rewrite tag core registers for the taxonomy, with a `post_type_link` filter to fill it, so `get_permalink()` returns the mirrored path on the CMS domain and stays absolute. The front end strips the CMS domain from every link in the HTML it renders, which turns those permalinks, and the absolute CMS links editors type, into front-end links with no rewriting on this side. Both sites use a trailing slash. The CMS does not redirect readers to the front end: its theme pages answer anonymous visitors with a 404 ([ADR 0031](0031-cms-theme-pages-are-for-logged-in-users.md)), and the mirrored paths are there so an editor's permalink and preview have the same shape as the public URL. How the front end keeps the CMS's address out of the browser, images included, is [ADR 0039](0039-vercel-image-optimizer.md) (images) and [ADR 0040](0040-the-cms-url-never-reaches-the-browser.md).

## Considered options

- **`/resources/[slug]/`.** Rejected: the single resource's URL shows no hierarchy.
- **Filters and page numbers as query strings.** Rejected: reading `searchParams` makes every listing dynamic, as above.
- **A post type per type.** Rejected in [ADR 0007](0007-one-post-type-with-a-type-taxonomy.md); type paths keep one post type.

## Consequences

- The slug is the identity and the type segment is checked: on the front end, a URL with the wrong type redirects to the canonical one ([ADR 0025](0025-redirects-are-computed-308s-with-no-store.md)).
- The one-type rule is enforced on REST saves, the block editor's only save path. Quick and Bulk Edit save outside REST: they cannot change the type, which is hidden from both and whose terms are dropped from a Bulk Edit request, and they cannot move a resource without exactly one type to published or scheduled. Quick Edit refuses the save with a message; Bulk Edit keeps that resource's status, saves the rest and names it in a notice. A resource already published or scheduled keeps its status through them, so an edit there never makes it worse. A type that resources still have cannot be deleted from the Types screen, including its bulk delete, or over REST, because a published resource without one has no path. The classic `post.php` form submission, WP-CLI and PHP calls, the seeder among them, are not guarded; XML-RPC is turned off ([ADR 0044](0044-xml-rpc-is-off-in-the-plugin.md), 2026-11-05), and even with it on, deletion through XML-RPC is guarded, because `wp.deleteTerm` checks `delete_term`, which `UsedTypes` covers. The revalidation hook never sends an event whose top-level `types` isn't exactly one element, so the front end never receives an invalid state from any of the unguarded paths.
- Topics are managed by editors, so the number of prerendered listings grows with them.
- Changing the permalink structure needs a rewrite flush on the host, and activation does not run on a deploy where the plugin is already active, so the deploy job gains a `wp rewrite flush` after activating the plugin, in the same slice as the permalink change.
- The revalidation payload carries the old type and slug on `update` ([ADR 0016](0016-previous-state-on-update.md)), so the front end can clear the path a resource left.
- The schemas also reject `topic` and `page` wherever a type slug appears ([ADR 0010](0010-contract-as-json-schema-in-a-shared-package.md)); WordPress's refusal is the first line, the schema the check that the two sides agree.

## Amendment, 2026-11-05: no slug stores an escape the router decodes

Because the slug is the identity and sits in the path, its stored form must be the form a URL delivers. `sanitize_title()` keeps any well-formed percent escape an editor types, so `case%2dstudy` would be stored as typed. Next.js 16 decodes, in route params, every escape of the characters `encodeURIComponent()` leaves unescaped: `A-Z a-z 0-9 - _ . ! ~ * ' ( )`, RFC 3986's unreserved characters plus `! * ' ( )`. The page for `case%2dstudy` would receive `case-study` and could not be reached at its own URL, or would redirect to itself.

So the CMS never stores one. On save, a `resource` post slug and a `resource_topic`, `resource_type` or `resource_flag` term slug has each escape of a character in that set decoded, in either hex case. Every other escape is left encoded, for example `%e6%97%a5`, `%e2%80%99`, `%20`, `%2f`, `%25`, `%26`, `%2b`, `%2c`, `%3a`, `%3b`, `%3d` and `%40`. Core's own sanitising then runs on the result, and the two repeat until no such escape is left, because sanitising can make a new one: core protects each escape as `---XX---` and turns every `---XX---` back into `%XX`, so dashes decoded from `%2d`, two literal hex digits and a kept escape can join, and `%2d%2d%2d41%20` sanitises after one pass to `%4120`. Each pass shortens the slug, so the repetition ends. Core's uniqueness check runs on the final slug, so a decoded slug that is taken gets core's `-2` suffix. Core keeps `-` and `_`, turns `.` into `-`, lower-cases letters and strips `~ ! ' ( ) *`: `case%2dstudy` is stored as `case-study`, `%41BC` as `abc`, `x%7Ey` as `xy` and `case%27study` as `casestudy`. A slug that decodes to nothing is treated as empty, so core generates it from the title or the term name.

The hooks run before core checks uniqueness: `pre_wp_unique_post_slug` for posts in any status core checks, `wp_insert_post_data` for `draft`, `pending` and `auto-draft`, which core does not check, and `pre_term_slug` for terms on create and edit. Every save path that writes a slug, whether REST, the block editor, the classic form, Quick Edit, Bulk Edit, the term screens, WP-CLI or PHP, goes through `wp_insert_post()` or `wp_insert_term()` and `wp_update_term()`, so none of those is missed. One path changes a post without saving it: the cron publish of a scheduled resource (`check_and_publish_future_post()`, then `wp_publish_post()`) writes only the status, and no slug hook runs. A slug generated from a term name needs nothing, because core strips every percent escape from a term name on save. A slug stored with such an escape before this rule is decoded the next time its post or term is saved, and a save repairs only the object saved.

What is left is repaired by hand with `wp resource-hub decode-slugs`. It lists every `resource` post and every term in the three taxonomies whose stored slug has such an escape, with the decoded slug and anything already holding it, and changes nothing. With `--apply` it saves each through core, with `wp_update_post()` or `wp_update_term()`, so the slug is decoded, the old one is kept in `_wp_old_slug`, uniqueness is checked and the front end is revalidated, as on any save. It does not guess at collisions it cannot resolve: a term whose decoded slug another term has is skipped and reported. A post keeps its old slug in `_wp_old_slug` as usual. A term edit is refused with core's "already in use" error (`duplicate_term_slug`) if the decoded slug belongs to another term, even an edit that leaves the slug alone, so the editor must type a new slug; core gives that error no HTTP status, so over REST the plugin makes it a 400 rather than a 500.

The revalidation payload never carries such an escape either. Its events read stored slugs, and a slug stored before the rule can still have one: `previous` on the save that decodes it, the removal of a resource not saved since, a topic or type not saved since that a resource lists. The front end treats a slug with such an escape as invalid everywhere and answers the whole batch with a 400, so one such slug would lose every event in it. So the dispatcher passes every slug field of every event, `previous` included, through the same sanitise-then-decode a save does before it checks and batches the events. A slug that decodes to nothing names no servable path: `previous.slug` then repeats the current slug, a top-level slug becomes the object's ID, and an empty type or topic is dropped.

Considered options:

- **Decode before core sanitises.** Rejected: decoding the raw input can create an escape. In `%%32d`, `%32` decodes to `2`, leaving `%2d`. Decoding a sanitised slug cannot create one by itself, because there every `%` already starts an escape; the sanitising after it can, which is why the two repeat.
- **A global `sanitize_title` filter.** Rejected: it would change every post type and taxonomy on the site.
- **Repair legacy slugs automatically, in an upgrade routine on a version bump.** Rejected: it would save content on a deploy nobody is watching, and a term collision needs an editor to choose a new slug. A command run by hand shows its dry run first and reports what it cannot do.
- **Reject such slugs with an error.** Rejected: the editor meant the decoded character, and decoding gives them the slug they meant.
