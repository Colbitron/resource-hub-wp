# The data layer's fetches: a one-hour ISR interval, a ten-second timeout, and slugs normalised but not redirected

Every CMS read goes through one wrapper in `apps/web/lib/wp/fetch.ts`, which opts into the Data Cache with `cache: 'force-cache'`, the request's tags ([ADRs 0043](0043-fetch-cache-with-tags-without-cache-components.md), [0046](0046-which-tags-and-paths-each-event-revalidates.md)) and `next: { revalidate: CMS_REVALIDATE_SECONDS }`. This records the values and rules that wrapper and its fetchers fix.

## The ISR interval is 3600 seconds

On-demand revalidation is the primary path, and the interval is the safety net. The plugin sends each batch once and does not retry ([ADR 0013](0013-three-second-timeout-and-no-retries.md)), so after a send that failed (the front end down, a timeout, a wrong secret) the interval is the only thing that brings the pages back in step. An hour bounds that staleness to something an editor will tolerate while asking each cached URL of the CMS at most once an hour, in the background, on a 2 GB server that has no cache in front of its REST responses ([ADR 0023](0023-next-data-cache-is-the-only-http-cache.md)).

This is a default chosen while the project owner was away on 2026-11-05 and is pending their review; hence `proposed`. It is one constant, `CMS_REVALIDATE_SECONDS`. Pages that set a route `revalidate` must write the same number as a literal, because Next.js reads segment config statically and cannot import it.

## A CMS request times out after ten seconds

`CMS_TIMEOUT_MS` is 10,000, covering the headers and the body. A healthy WordPress answers these reads in well under two seconds even with a cold object cache, so ten gives a slow but working CMS five times that, while a hung one fails the render with a `CmsError` long before a Vercel function's duration limit instead of holding the function open. A resource page makes at most three requests in sequence on a cold cache, so its worst case stays near thirty seconds.

Two consequences of using an `AbortSignal` for it. Next.js does not memoize a fetch that carries a signal, so the wrapper memoizes per render with React's `cache` instead. Next.js's lock on each Data Cache key already makes concurrent cold reads of a 200 one request, but an answer it does not cache (a by-ID miss, a resolve miss) would reach the CMS once per call without the memoization; the e2e suite checks that case. And Next.js drops the signal when it refreshes a stale entry in the background, so that refresh is not bounded; the visitor is served the stale entry meanwhile.

## Errors map to three plain outcomes

A 404 the fetcher names (core's `rest_post_invalid_id`, the plugin's `resource_hub_not_found`) and core's 401 `rest_forbidden` for an unpublished post become `null`, and the page calls `notFound()`. Core's 400 `rest_post_invalid_page_number` becomes `NO_SUCH_PAGE`. Everything else throws a `CmsError` whose message names the endpoint's path under `WP_API_URL` and never the CMS origin: any other status (a 404 `rest_no_route` included, which means the plugin or the route is missing, not the resource), a redirect, a timeout, a network error (named by its code, because Node's message prints the address), a body that is not JSON, or a body the reader schema refuses. As a backstop the message is scrubbed of each configured CMS host, both with its port and as a bare hostname.

Mapping core's 401 `rest_forbidden` on a by-ID read to a miss is right for core, which answers that way for a draft or a trashed post. The trade-off: a REST-lockdown plugin on the CMS that answers anonymous readers with the same 401 would turn every by-ID read into a 404 page, while the list and slug reads, which treat any 401 as an error, throw and fail loudly.

A slug read that comes back with resources but none with the slug asked for throws a `CmsError` (reason `schema`) rather than being a miss. Core's `slug` filter returns only exact matches, so other resources mean the filter was dropped on the way (a plugin, a proxy) and the answer is to a different question; a miss would make every resource page a 404 and hide that, as the by-ID read already refuses a body for another ID. An empty list is still a miss.

## Redirects from the CMS are refused, not followed

Every CMS fetch sets `redirect: "error"`. Followed silently, a redirect (http to https, a `www` host, a CMS that moved) would put the final 200 in the Data Cache under the original URL and leave a `WP_API_URL` that needs fixing looking healthy, at the cost of a hop on every uncached read. Refused, it fails the render with a `CmsError` of reason `redirect` and the message "the CMS answered with a redirect; check WP_API_URL". A 3xx that reaches the reader anyway (one without a `Location`) gets the same reason. The REST API answers these reads directly, so a redirect is always a configuration error to fix, never a route to take.

## Mixed-case and other non-canonical URLs redirect; the data layer only normalises

`canonicalSlug` lower-cases a slug and percent-encodes it as WordPress stores it, so `/resources/Webinar/` fetches the same data as `/resources/webinar/`, and every fetcher sends and tags the canonical form. The data layer does nothing more: it never decides a URL is wrong. The policy for the page pull requests is that a path whose type, topic or slug segment is not in canonical form gets a single-hop 308 to the canonical URL with `Cache-Control: no-store`, the same response as a wrong type segment ([ADRs 0025](0025-redirects-are-computed-308s-with-no-store.md), [0035](0035-type-paths-with-a-computed-no-store-308.md)), so each page has one URL. That redirect is built in the redirect-mechanism pull request; until then a non-canonical URL renders the canonical page's content.

*Amended 2026-11-05, with the redirect mechanism ([ADR 0035](0035-type-paths-with-a-computed-no-store-308.md)'s amendment):* the percent-encoding half of this rule cannot be enforced by a page. Next.js normalises `params` before the page runs: the hex of an escape arrives upper-cased whatever was sent (`%e6%97%a5` and `%E6%97%A5` both arrive as `%E6%97%A5`), and escapes of `encodeURIComponent`'s unescaped characters (`A-Z a-z 0-9 - _ . ! ~ * ' ( )`) arrive decoded (`%52esource` as `Resource`, `%27` as `'`). So the redirect rule is: an upper-case ASCII letter outside an escape redirects to the lower-case canonical URL; the hex case of an escape is treated as canonical, or the redirect would point at itself. The data layer's own canonical form is unchanged.

*Amended again 2026-11-05, after review:* a slug may no longer hold a percent escape, in either hex case, of a character Next.js decodes in `params`: `encodeURIComponent`'s unescaped set, `A`-`Z`, `a`-`z`, `0`-`9`, `-`, `_`, `.`, `!`, `~`, `*`, `'`, `(`, `)`. The set was measured on Next.js 16.4.5 under `next start` by requesting `a%XXb` for every byte 0x20 to 0x7e; every other escape arrives encoded with its hex upper-cased. (A first version of this rule named RFC 3986's unreserved characters only, and a type stored as `arti%27cle` still redirected to its own URL for ever; a second review found it.) Next.js decodes such an escape in `params`, so a stored `case%2dstudy` reached the page as `case-study`: its own URL named another slug, and a redirect to it could point at itself (a type `😀%41` redirected to its own URL for ever, found by the fixed-point test in `test/redirects.test.ts`, which now models the measured set). `slugProblem` now refuses it, so the reader schemas, the builders and the redirect decision all do. WordPress's `sanitize_title` keeps an escape an editor types, so such a slug can be stored; a response or event that carries one fails the reader schema with a `CmsError` or a 400 that names it, rather than producing a URL that cannot work.

## The filter bar reads at most 1,000 terms a taxonomy

`listTerms` pages through a taxonomy a hundred at a time and stops after ten pages. Past 1,000 terms something is wrong with the CMS, but throwing would fail every listing page, whose filter bar needs the list. So it returns the first 1,000 by name and logs a `console.warn` that names the taxonomy and not the CMS origin; the bar is missing terms until the CMS is fixed.

## A collection is parsed one item at a time

*Amended 2026-11-05:* a list answer (`/wp/v2/resources` and the three taxonomy collections) is no longer parsed as a whole. Parsed whole, one resource or term the reader schema refused made the entire answer a `CmsError`, so one bad item took down every listing it appeared in: the library, its type and topic listings, the related sections that include it, and, for a bad term, every listing whose filter bar lists that taxonomy. The case that forced this is a slug WordPress stored with an escape an editor typed, such as `case%2dstudy`, which the previous amendment makes the front end refuse; the plugin will normalise such slugs on save in its own pull request, but the front end must not depend on that, nor on every other field of every item being right.

The rule, in `cmsGetList` in `apps/web/lib/wp/fetch.ts`:

- The body must be an array, or the read throws a `CmsError` (reason `schema`), as before.
- Each element is parsed with the item schema. One that fails is skipped, and a `console.warn` names the endpoint path, the element's position, its ID when it has one that is a WordPress ID, and the paths of the fields that failed (`slug`, `title`, `_embedded.wp:term.0.0.slug`). It never names the CMS origin, and it never gives the issue messages, because a refinement's message can quote part of the value (`slugProblem` names the escape it found).
- The elements that pass keep the CMS's order.
- `X-WP-Total` and `X-WP-TotalPages` are read as the CMS sent them, so the page numbers still match the CMS's pages.
- *Amended again 2026-11-05, after review; a default chosen while the project owner was away, pending their review:* a list of **four or more** elements in which **more than half** fail throws a `CmsError` (reason `schema`). That is a systematic break, a changed field or a plugin rewriting the response, and hiding it would empty every listing without a sign. Its message names the counts and the first failing element by position, ID and field paths, as the warnings do (`4 of 7 items fail the reader schema; the first: item 0 (ID 500) at title`), never an issue message, so it cannot quote a value either. Any smaller list, and any list in which half or fewer fail, only skips. The rule this replaces, "throw when every element fails", made two ordinary cases fragile: the last page of a listing whose only resource is bad, and a final `listTerms` page holding one bad term, which failed the filter bar and so every listing page. An empty list stays an empty list.
- **Small lists.** Below four elements, "more than half" is one bad item in a list of one or two in a list of two or three, which is too little to call systematic. Such a list whose items all fail comes back empty: a listing page past the first then has no cards, inside the CMS's page count (the headers are kept, so the pagination still links to it, and it is not `NO_SUCH_PAGE`); a filter bar's last page adds no terms. Four is the smallest list in which "more than half" means at least three bad items.
- **One summary line.** Whenever a list skips anything, one more `console.warn` follows its per-item lines, `CMS list /wp/v2/resources: skipped 5 of 12`, a stable line for log-based alerting to match. It is not logged when the list throws, since the `CmsError` is the signal then. `listResources` also returns the page's `skipped` count on `ResourceListing`, so a page could say so; no page uses it yet.
- **Once per render.** A page and its `generateMetadata` read the same list, and each read parsed it again and logged the same warnings twice. The parsed outcome, the list or the error it threw, is now memoized in React's `cache`, the per-render scope the request memoization (`load`) already uses, by the response object and the item schema, so each list is parsed and warned about once per render.

It applies to `listResources`, `getResourcesByIds` and `listTerms`. The reads of one object, by ID and through the resolve route, are parsed whole and fail as before; their messages keep the issue messages, which can quote part of a value (`slugProblem` names the escape it found), and the `CmsError` doc comment says exactly what a message may hold. The two reads by slug, `getResourceBySlug` and `getTermBySlug`, get an answer that is a list, so they are parsed per item too, and the slug check runs on what passed. Core returns at most one item for a slug. An answer in which every item failed throws whatever its size, naming the first one's field paths, rather than coming back as a miss: a miss would make the resource's page, or the term's listing, a 404 and replace the last good render that ISR otherwise keeps serving. A bad stranger beside a good match is skipped; with no good match among several, `getResourceBySlug` throws, and its message says how many items were skipped. One rule for every list answer, with this one check added for the slug reads, was preferred to a stricter rule for them, which would have bought nothing for the requested item.

`checkTaxonomy` is not part of the per-item rule: a term of another taxonomy in a taxonomy's collection still throws, because core serves one taxonomy per endpoint and such a term means the endpoint is answering for the wrong one.

What the human sees:

- **A resource with a bad field disappears from every listing it was in.** The page it would have been on shows one card fewer; the counts and page numbers include it, so a listing can say 15 resources and show 14. The server log carries one warning per render that parsed it.
- **Its own page**, for the escaped slug, is a 404: Next.js decodes the escape before the page runs, so `/resources/article/case%2dstudy/` reaches the page as the slug `case-study`, which names nothing, and the resolve route finds nothing for it either. Had `case-study` been an old slug of a resource, resolve would find that one and the redirect rules would send a 308 to it, as for any old slug ([ADR 0035](0035-type-paths-with-a-computed-no-store-308.md)). For a resource whose slug is fine but another field is bad (a missing title, a bad embedded term), its own page reads it by slug, the one item in the answer fails, and the page fails with a `CmsError`, as it did before.
- **A bad term** disappears from the filter bar. Every resource that carries it fails the item schema through its embedded term and disappears from listings; a listing page of four or more on which more than half of them do throws.
- **A related section** loses a bad resource like an unpublished one. A related read is three IDs by default (the related route's `count`, 1 to 10), so `getResourcesByIds` for a small set whose resources all fail returns no items under the threshold, and the host page does not have to contain a throw for that case; it renders an empty section, or none. A larger set (four or more IDs) in which more than half fail still throws, which is the systematic case: the page should then render without the related section rather than fail. That containment, catching the `CmsError` from the related reads around the section only, is the related-section pull request's job.
- **A bad flag term fails every resource that carries it.** `resource_flag` terms are embedded in `_embedded['wp:term']` like the other two taxonomies', and `wpEmbeddedTermListSchema` in `apps/web/lib/wp/schemas/rest.ts` parses every entry of the three known taxonomies strictly, flags included (only entries of other taxonomies are dropped unread). So a `featured` term with a bad slug or an empty name makes every featured resource fail the item schema: each disappears from every listing and its own page fails, and the featured listing, whose every resource carries the term, throws once it has four or more. Flag terms send no events ([ADR 0046](0046-which-tags-and-paths-each-event-revalidates.md)), so fixing the term in the CMS clears nothing by itself. The library, the featured listing, the related reads and the by-ID reads come back on the next event of any kind, since every event clears `resources`; a type or topic listing and a resource read by slug wait for an event that names them, a topic or type term event (which clears `terms`), or the one-hour interval. The schema is unchanged by this amendment; whether flag entries should be parsed leniently, since the front end reads only their IDs and the `featured` slug, is left to the owner.
- A fix in the CMS does not show until the cached answer is cleared, as for any cached bad 200 (see the consequences below): the bad item stays hidden until the next event or the interval.

## Considered options

- **A shorter interval (five minutes).** Repairs a failed send sooner, at twelve times the background load on a CMS with no cache in front of it. Rejected for now; the value is one constant.
- **A day, or no interval (`false`).** A failed send would leave a page wrong for a day or until the next edit to it. Rejected while sends are never retried.
- **No timeout, relying on the function's duration limit.** A hung CMS would hold every rendering function for minutes. Rejected.
- **Treating any 404 as a miss.** A missing route would make every page a 404 rather than an error, hiding a broken deploy. Rejected: misses are named by status and code.
- **Fetching with the slug as given and redirecting in the data layer.** The data layer has no response to redirect with, and two forms of one slug would be two cache entries. Rejected.
- **Following CMS redirects (`fetch`'s default).** Works through a misconfigured `WP_API_URL` while caching each answer under a URL that never served it. Rejected for `redirect: "error"`.
- **Throwing past 1,000 terms.** Visible, but takes every listing page down with it. Rejected for the cap and a warning.
- **Parsing a collection as a whole** (as before the 2026-11-05 amendment). Loud, but one bad item fails every listing it appears in. Rejected for skipping per item and failing only past a threshold.
- **Skipping every bad item, even when none is left.** A listing would go empty without an error when a field changes for every resource. Rejected: a list of four or more in which more than half fail throws.
- **Throwing only when every item fails** (the first version of this amendment). One bad resource alone on the last page of a listing, or one bad term alone on the last page of a taxonomy, failed the render, and the second failed every listing through its filter bar. Rejected for the four-item, more-than-half threshold.
- **Throwing on any proportion over half, whatever the size.** The same fragility for lists of one to three. Rejected: below four the list only skips.
- **Repairing a bad item** (decoding an escaped slug, defaulting a missing title). The data layer would invent CMS data and could produce a URL that names another resource. Rejected: the plugin normalises slugs on save; the front end skips.

## Consequences

- The Data Cache stores only 200s. A miss by slug is a 200 with an empty list and is cached under its tags; a miss by ID and a resolve miss are a 404 or 401 and are asked again on every render.
- A 200 whose body fails the schema (for a list, one of four or more items in which more than half fail, or a slug read whose every item fails) is cached like any other 200, so the render keeps throwing until the interval passes or an event clears its tags. ISR keeps serving the last good page meanwhile.
- Fixing the CMS does not heal such a cached bad 200 before it expires: the Data Cache does not know the CMS changed. A test revalidation from the plugin's status page clears most of them, because every event invalidates `resources` ([ADR 0046](0046-which-tags-and-paths-each-event-revalidates.md)), which the library listing, the by-ID, related, resolve and flag reads and the filter bar's term lists all carry. What it misses are the reads tagged only by their own slug or term (another resource by slug, another type's or topic's listing and term lookup); those wait for an event that names them, or for the interval.
- Some costs are left for the page pull requests to absorb. An unknown slug costs a cached empty-list read (and a resolve request, which is not cached because its miss is a 404) per distinct URL a visitor or crawler tries; an out-of-range page number costs one uncached 400 from the CMS per request. The pages decide how to bound these (static params, the route's own caching of a `notFound()`), not the data layer.
- A change to the interval or the timeout is a change to one constant and to this record.
