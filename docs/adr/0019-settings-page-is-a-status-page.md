# The settings page is a status page with a test button

The front-end URL and revalidation secret come from the `RESOURCE_HUB_FRONTEND_URL` and `RESOURCE_HUB_REVALIDATE_SECRET` constants, falling back to options ([ADR 0005](0005-hosted-wordpress-on-cloudways.md)). CLAUDE.md planned "a small settings page" for the fallback. When a revalidation fails, the first question is which configuration is in force and whether the front end answers at all, and a page of input fields answers neither. The page is therefore a status page first: it shows which source is active for each value (constant or option), never displays the secret, and has a "Send test revalidation" button.

The button sends a real `update` event for a published resource, not a synthetic ping, so a pass proves the whole path the front end takes for a save: the bearer check, the schema, and the revalidation of real paths and tags. It defaults to the most recently modified published resource, and a searchable picker lets the admin choose a specific published resource instead. With no published resource there is nothing real to send, so the button is disabled.

Because it is a real event, its result is recorded like any other: in the chosen resource's `_rh_last_revalidation` meta ([ADR 0018](0018-revalidation-results-shown-in-the-editor.md)) and, when PostHog is configured, as a PostHog event ([ADR 0032](0032-revalidation-results-logged-to-posthog.md)). It is also stored in a non-autoloaded option, which the status page shows, so the page can answer "did the last test pass?" without loading that option on every request.

Amended 2026-11-05, with the choices the build made. The page also writes the two fallback options, through the Settings API: the front-end URL must be the site's origin only, `https://`, with `http://localhost` and `http://127.0.0.1` allowed for development, with any port but no path (the send appends `/api/revalidate`, so a path would double it), query string, fragment or credentials, and is stored without a trailing slash, else the stored value is kept and a settings error says why; the secret field is never prefilled, so an empty submission keeps the stored secret, and a field whose constant is defined is disabled because the constant wins. A disabled field is not submitted, so `options.php` saves null for it, and both sanitizers keep the stored value for null. Each field saves on its own, so a refused URL with a new secret still saves the secret; the page says so. The URL is set by an administrator, so link-local addresses and IP hosts are accepted by design; the check is about carrying the secret safely, not about which hosts may be reached. Both options are stored with autoload off: a new one through the `wp_default_autoload_value` filter (WordPress 6.6+), and one that already existed autoloaded, including a legacy `autoload = 'yes'` row, is switched off with `wp_set_option_autoload_values()` on its next save, from the `pre_update_option_{$option}` filter, which runs before core's check for an unchanged value, so a save that changes nothing (an empty secret field keeps the stored secret) switches it off too. A configured URL that is not HTTPS, other than the local machine, is flagged on the status table. The picker is server-rendered with the twenty most recently modified published resources, and a small script searches the public `wp/v2/resources` collection with `status=publish` as the admin types; the page itself needs `manage_options`. The last test's record goes in the non-autoloaded option `resource_hub_last_test`: the result the send returned, without the body, plus the time of the test and the resource's ID. It is built from that result, never by reading the resource's meta again after the send, which could show another send's record, such as a `pending` left on a site whose cron never runs. The default resource is resolved once, when the page is rendered, and its ID travels in a hidden field, so the label and the resource sent always match; Enter in the picker's search runs the search rather than submitting the form, and the button is disabled once the form is sent. With nothing published the button is `aria-disabled` rather than `disabled`, so it stays reachable by keyboard and announces the visible reason beside it. The handler is an `admin-post.php` action with a nonce and the capability check, and it redirects back with `rh_test` naming what happened (`sent`, `none` or `not_published`), which the page turns into a notice; any other value shows nothing.

Amended 2026-11-05, the secret's rule. `REVALIDATE_SECRET` is at least 32 printable ASCII characters with no whitespace; both sides refuse anything else. The front end refuses its own `REVALIDATE_SECRET` by that rule, so a secret pasted with a trailing newline or a space would otherwise leave an editor with a permanent 401 and no hint why. On the CMS the rule is `Config::is_valid_secret()`: 32 to 256 characters, each 0x21 to 0x7E, so no whitespace, no control characters and nothing outside ASCII; 256 is room for any generated token and a bound on the header. The secret field's sanitizer checks a new secret as submitted, without trimming or cleaning it, and refuses one that breaks the rule with a plain settings error that never repeats the value; the stored secret is kept, and an empty field still keeps it. A secret already in force that breaks the rule, from the `RESOURCE_HUB_REVALIDATE_SECRET` constant or from an option saved before the rule, counts as not configured: nothing is sent, the result is recorded as `not_configured`, and the status table warns beside the secret's source. Until this amendment `Config::secret()` trimmed both the constant and the option, as it still trims the front-end URL; trimming the secret is dropped, because the front end does not trim, and a trimmed secret would hide a stray newline that breaks the value an operator copies to the front end. The secret is now used exactly as defined, and a constant with surrounding whitespace is refused with the warning rather than quietly repaired.

## Considered options

- **A synthetic test event, or a `HEAD` or ping request.** Rejected: it would pass while a real payload still failed the front end's schema or its revalidation, which is exactly the failure the button is for.
- **Storing the result in an autoloaded option.** Rejected: WordPress loads autoloaded options on every request, and only this page reads the result.

## Consequences

- A defined constant wins over the option, as CLAUDE.md specifies, and the page shows which one is in force.
- The secret is write-only from the admin's point of view; the page can say it is set, never what it is.
- The test button is the quickest check after a deploy or a secret rotation, without editing content: it re-sends a resource's current state, which on the front end is an ordinary refresh of that resource.
- A test leaves its result on the chosen resource, where an editor opening that resource sees it like the result of a save.
- The page needs a capability check and a nonce on the test action, like every admin action here.
