# Revalidation results are stored in meta and shown where the editor already is

The send runs in cron after the save has returned ([ADR 0012](0012-revalidation-is-sent-from-wp-cron.md)), so the editor cannot learn the result from the save response. The result is stored in post meta `_rh_last_revalidation`: a status that moves from `pending` to `sent` or `failed`, the HTTP code, the event, the time, and the response body cut to about 1 KB. It is exposed as a read-only field registered with `register_rest_field()` in the `edit` context only, so it never appears in the public responses the front end reads.

A batch ([ADR 0014](0014-one-php-request-is-one-batch.md)) gets one response, and that result is written to every resource in the batch, each copy noting that it was sent with N other changes. A bulk edit of twenty resources therefore leaves twenty results, and whichever resource an editor opens shows the outcome of the request that carried it, rather than only the first or last resource holding it.

In the block editor, after a save that is not an autosave completes, a small script polls `?context=edit&_fields=…` about once a second for up to about ten seconds, then dispatches the outcome to `core/notices`. When the editor loads a resource whose last result was a failure, it shows that failure. The notice text maps each outcome to plain words: 200, 400, 401, 500, timeout, any other code, and not configured.

Amended 2026-11-05, to match what the hook stores: each record holds `status` (`pending`, `sent` or `failed`), `outcome`, `code`, `event`, `time`, `batch_id` (shared by every object in the batch and by the PostHog event), `others` (how many other changes travelled with it), `body` (valid UTF-8, cut to about 1 KB), `error` (a transport error or a plain message, else `null`) and `duration_ms`. The outcomes are `pending` while scheduled, then `ok`, `bad_body` (a 200 whose body is not a JSON object with a `revalidated` array, which means the URL reaches something other than the revalidate route), `bad_request`, `unauthorized`, `server_error`, `unexpected_code`, `timeout`, `transport_error`, `not_configured`, `no_single_type` (held back because the resource does not have exactly one type) and `encode_error` (the payload could not be encoded as JSON, so nothing was sent). Only `ok` is `sent`. Should core refuse to store a record, it is stored again with an empty body and an `error` saying so, so a result never stays `pending` for that reason.

Amended 2026-11-05, with the choices the editor-facing build made: polling runs only after a save where the status before or after it is `publish`, so a draft save shows nothing. A success is a snackbar and anything else a dismissible notice; on load, a last result that is not `sent` (a failure or a pending) is shown. A 400 or a 500 quotes the front end's `error` string from the stored JSON body, never the raw body.

Amended again 2026-11-05, after review. "This save's result" is a polled record whose `time` is at or after the saved post's `modified_gmt`, both from the server's clock, and whose `batch_id` is not that of the record the save response carried (the record from before the save, because the hook writes at `shutdown`, after the response is built); the first record that passes fixes the batch, and later polls must match it. An earlier save's late result therefore does not count: it either landed before this save, or the save response carried that earlier save's own record, pending or final. The script is a `registerPlugin()` component whose effects abort their in-flight requests with an `AbortController` when the next save starts or the editor closes. A save that then starts no poll of its own, because it failed (a 400 for the one-type rule, say) or sent nothing, resumes the earlier save's poll if it had not finished, so a refused save never hides the earlier save's result. The resumed poll gets a fresh ten-second window, not the time the earlier poll had left. Whether a `pending` is stale is judged with the server's clock, the `Date` header of the REST response, never the browser's. The sentences have one source, `ResultText::sentences()` in PHP, handed to the editor's script with `wp_localize_script()`; only the "sent with N other changes" clause is written twice, as the same two msgids in PHP's and JavaScript's `_n()`, because a plural rule cannot be handed over. A `pending` older than five minutes is shown everywhere as "No answer recorded: the send may not have run", display only (the record is never rewritten): a scheduled batch is spawned at once and WP-Cron's lock lasts 60 seconds, so five minutes of `pending` means the cron request never ran. The term notice is printed through `{$taxonomy}_term_edit_form_top` as an inline notice, so nothing is read from the request. The list column shows a label and the relative time, never the body.

Amended again 2026-11-05, closing the gap the previous amendment left: three saves inside one send's few seconds, where the first save's late result overwrote the second save's pending before the third save's response was built, so the third save's poll took the second batch's result for its own. The store now compares before it writes, for batches that stored their own `pending` only: a final result from the cron callback is not written over a `pending` from another batch. A cron batch stores its own `pending` when it is scheduled, so a `pending` from another batch found when its result arrives was written after it, by a later save, and that batch's own result will replace it; an older send's result can no longer replace a newer save's pending, before or after the next save's response is built. A send that falls back to running at once because core refused to schedule it is guarded the same way: it stores its own `pending` before it tries to schedule, so a `pending` from another batch that lands during its send of up to three seconds is newer and is kept. Every other final result is written whatever is stored: a held-back event, a send under WP-CLI or on an unconfigured site, and the status page's test. Those have no `pending` of their own, so the `pending` they find may be older than they are, or left by a send that never ran because cron is broken, and skipping it would hide a real result, such as a save that removed the type, behind an earlier save's send. The cron callback and the fallback tell the store which case it is with an explicit flag. The accepted cost: if the newer send never completes, the guarded result is lost, and the record stays `pending` until the five-minute stale-pending display covers it. The store's read and its write are not atomic, so a `pending` written between them is still overwritten. The guard protects only a `pending`, so an older cron result can still overwrite a later final that is not a `pending`, for example a held-back save's result. The two-save case found in the same review, where the second save's poll ends on `pending`, is not a misattribution, and this does not cover it: the poll ends there only when the second batch's own send has not finished inside the ten-second window, for example because the first send's cron request still held WP-Cron's lock when the second batch was scheduled, so it waited for a later request to spawn cron. The guard does not make that send finish sooner. What it changes is what the poll reads meanwhile: the second save's own `pending`, never the first save's result, so the notice says the result is pending, which is true, and the final result is on the record afterwards, shown on the next load if it is a failure and in the list column.

## Bulk actions, trash and Quick Edit

Those paths never open the block editor, so a "Revalidation" column on the Resources list screen (`manage_resource_posts_columns` and `manage_resource_posts_custom_column`, reading the same meta) shows their results. It is hidden by default through `default_hidden_columns` for the `edit-resource` screen, because most people will not care and the table stays clean; anyone who does turns it on in Screen Options.

## Consequences

- Accepted trade-off: a failed trash or Quick Edit stays invisible until someone turns the column on.
- A batch's per-resource copies cost one meta write per resource in the batch, at most 25 per request.
- A force delete has no post left to hold meta, and a deleted term has no term meta, so those results are recorded only by the PostHog event ([ADR 0032](0032-revalidation-results-logged-to-posthog.md)), when PostHog is configured. Otherwise they are only printed, when the send ran under WP-CLI ([ADR 0012](0012-revalidation-is-sent-from-wp-cron.md)), and not recorded at all from the admin. There is no `error_log()` call: it is an error under the VIP ruleset ([ADR 0006](0006-vip-minimum-ruleset-in-the-gate.md)).
- Term events record their result in term meta and show it on the term edit screen ([ADR 0017](0017-term-events.md)).
- The editor retries a failure by saving again ([ADR 0013](0013-three-second-timeout-and-no-retries.md)).
