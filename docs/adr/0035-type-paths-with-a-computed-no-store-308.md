# A resource lives at `/resources/[type]/[slug]/`, and any other URL for it gets a computed 308 with `no-store`

A single resource's URL includes its one type, mirroring the CMS's permalink ([ADR 0024](0024-type-paths-mirrored-on-both-sites.md)): a subfolder per type gives the library a visible hierarchy for search. The slug is the identity and the type segment is checked. When the type in the URL is not the resource's current type, the page sends a 308 to the canonical URL, computed from the current data, in a single hop to a URL that always answers 200, with `Cache-Control: no-store`. When the slug matches no current resource, the page calls the CMS's `GET /resource-hub/v1/resolve?slug=…` and, if it finds the resource under an old slug, sends the same kind of 308; otherwise it returns a 404. The old path is revalidated as well, so the edge cache stops serving it.

A type can change and change back. With a stored redirect and header-less permanent redirects, browsers keep the first redirect and loop. A Playwright test on 2026-11-04 across Chromium 156, Firefox 157 and WebKit 27.2 showed it: Chromium caches a header-less 308 indefinitely and fails webinar → podcast → webinar with `ERR_TOO_MANY_REDIRECTS`, while with `no-store`, `no-cache` or a `max-age` all three engines asked the server again. Chromium's `GetFreshnessLifetimes` gives 301 and 308 `TimeDelta::Max()` unless a header overrules it; Firefox gives 0 heuristic freshness without `Last-Modified`; WebKit gives a 301 365 days and a 308 zero, and drops redirects marked `no-store`, `no-cache` or `must-revalidate`. Google asks for permanent redirects only "when you're sure that the redirect won't be reverted".

The requirement is fixed: a single-hop 308 with `Cache-Control: no-store`. The mechanism that sends it is chosen and verified in slice 3. Next.js's `permanentRedirect()` documents no way to set response headers, and while a response is streaming it falls back to a meta refresh, so slice 3 checks what Vercel actually sends for it and otherwise uses `proxy.ts` or a route handler that sets the status and headers itself.

## Considered options

- **`/resources/[slug]/`.** Rejected: no hierarchy in the URL.
- **A stored redirect table with plain 301s.** Rejected: the loop above.

## Consequences

- Rule: never send a permanent redirect without a cache header.
- A Playwright round-trip test changes a type, changes it back, and follows both URLs.
- The current-slug lookup comes first; resolve is called only on a miss, so renamed resources cost one extra request and current ones none.
- A type re-slug in the CMS needs no redirect table: every resource page under the old type segment redirects through the same check.

## Amendment, 2026-11-05: the mechanism, measured, is a page that renders on every request

The requirement above is unchanged. This records what Next.js 16.4.5 actually sends for each way of redirecting, measured under `next start` with throwaway routes against the e2e mock CMS (ports 3370 and 4070), `curl` and raw headers, and the mechanism chosen from it. The decision itself is `apps/web/lib/redirects.ts`; the test-only page `/fixtures/redirect/[type]/[slug]/` and `apps/web/e2e/redirects.spec.ts` prove it.

### What was measured

**`permanentRedirect()` from a dynamic render** (a dynamic segment without `generateStaticParams`, or any page after `connection()`): `HTTP/1.1 308 Permanent Redirect`, `location: /spike/target/`, `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`, `Content-Type: text/html; charset=utf-8`, no `x-nextjs-cache`. The same on every request; nothing is stored.

**`permanentRedirect()` from an ISR route** (`export const revalidate = 3600` with `generateStaticParams`): the redirect is treated as a page. A param that redirects at build time is prerendered as a 308 (`●` in the build output; its `.meta` file holds `"status": 308`, the `location` and the fetch's tags, `resource:{slug}` and `terms`). It is served as `HTTP/1.1 308`, `x-nextjs-cache: HIT`, `x-nextjs-prerender: 1`, `Cache-Control: s-maxage=3600, stale-while-revalidate=31532400`. A param first seen at runtime is rendered once (`MISS`) and then served the same way (`HIT`). So ISR does store the redirect. The revalidation event for a type change does clear it, through the tags on the entry: after webinar to podcast plus the event, the old URL re-rendered (`MISS`) as a 308 to the new one, and after the change back it re-rendered as a 200; inside Next's own cache the round trip holds. The header is the problem: `s-maxage` only, no `max-age`, no `no-store`. Chromium gives a 308 with neither `max-age` nor `Expires` an infinite freshness lifetime (the evidence in [ADR 0025](0025-redirects-are-computed-308s-with-no-store.md)), so a browser would keep it, and a CDN keeps it for the hour unless the event reaches it. What Vercel's CDN forwards to browsers for an ISR response was not measured here.

**Making only the redirecting render dynamic in an ISR route** (`await connection()`, a `cache: "no-store"` fetch, or a `next: { revalidate: 0 }` fetch before `permanentRedirect()`): at build, the redirecting param is left out of the prerender with no error, and from then on that param is rendered dynamically for ever, served `private, no-cache, no-store` even once the data makes it a 200. At runtime it fails: a path that was prerendered (the old URL, re-rendered after a type change) and a path never seen at build (`generateStaticParams` returning `[]`) both answer `HTTP/1.1 500 Internal Server Error` with the digest `DYNAMIC_SERVER_USAGE`; six 500s across the three variants, and `generateStaticParams` returning `[]` with `connection()` on every render is a 500 on every request. The build-time bail-out is a documented path; the runtime one is not.

**Guarding the page against an added `generateStaticParams`** (re-measured after review, same setup, 2026-11-05). Seven throwaway copies of the fixture page, each asked for a canonical URL, a wrong-type URL and a URL never seen at build, twice each:

| Route segment config | `generateStaticParams` | Build | Runtime |
|---|---|---|---|
| `connection()` (no segment config) | none | `ƒ` | 200, 308, 404, all `private, no-cache, no-store, max-age=0, must-revalidate` |
| `connection()` | lists the canonical and the wrong-type param | `ƒ`: both params bail out at build | as above |
| `connection()` | returns `[]` | `●` | **500 on every request** (`DYNAMIC_SERVER_USAGE`, six of six) |
| `dynamic = "force-dynamic"`, with or without `connection()` | lists both params | `ƒ` | 200, 308, 404, all with the `no-store` header above |
| `dynamic = "force-dynamic"` and `connection()` | returns `[]` | `●` | as above: no 500 |
| `revalidate = 0` and `connection()` | lists both params, or returns `[]` | `ƒ`, or `●` | as above: no 500 |

The Data Cache survives both `force-dynamic` and `revalidate = 0`, because the data layer asks for `cache: "force-cache"` on every fetch: 20 renders of a new resource's canonical URL and 10 of its wrong-type URL made one CMS request between them, in each of three routes (`connection()` alone, `force-dynamic`, `revalidate = 0`). An unknown slug is not cached: five requests for one made one CMS slug read, cached as an empty list, and five resolve requests, one per request, because resolve's miss is a 404 and the Data Cache stores only 200s ([ADR 0049](0049-data-layer-fetch-policy.md)).

**When streaming has begun**: a `permanentRedirect()` inside a `<Suspense>` boundary, or in a page under a `loading.tsx`, is `HTTP/1.1 200 OK` whose body carries `<meta id="__next-page-redirect" http-equiv="refresh" content="0;url=/spike/target/"/>` and the RSC payload `NEXT_REDIRECT;replace;/spike/target/;308;`. No 308 reaches the wire. The decision must therefore run before anything is rendered, and the resource route must not have a `loading.tsx`.

**`proxy.ts`** (Next 16's middleware): runs on the Node.js runtime (`process.env.NEXT_RUNTIME` was `nodejs`; the docs say the `runtime` option is not available in a proxy file). `NextResponse.redirect(url, 308)` with the header set gives `HTTP/1.1 308`, `cache-control: no-store`, `location: /spike/target/`, `Refresh: 0;url=/spike/target/`. It can import and run the data layer: `getResourceBySlug` returned the resource. But its `fetch` is not Next's patched one: two proxy calls for one slug made two CMS requests, where twenty dynamic page renders from the Data Cache made none. It runs before the route cache on every matched request: a prerendered page kept `x-nextjs-cache: HIT` and still carried a fresh `x-proxy-time` header each time. Cost locally, 300 sequential requests: a static page 0.48 ms mean without the proxy and 0.61 ms through it; a proxy redirect with no data 0.44 ms; the proxy with the data layer 0.93 ms against a loopback mock, which on the hosted CMS would be one CMS round trip per page view (ADR 0023: no cache in front of the REST API).

**A Route Handler** sets status and headers freely (`HTTP/1.1 308`, `cache-control: no-store`, `location`; 0.91 ms), but a `route.ts` and a `page.tsx` cannot share a segment: the build fails with `Conflicting route and page at /spike/handler/[type]/[slug]`. The resource path would have to be a handler that renders the page itself, with no layout, metadata or streaming.

**`headers()` in `next.config.ts`**: a `Cache-Control: no-store` rule on a path applies to every response of that path. The ISR 200 kept `x-nextjs-cache: HIT` and got `Cache-Control: no-store`; the page's 308 got `no-store` in place of Next's dynamic header. It does not reach the built-in trailing-slash 308: that response carried neither the rule's `x-config-header` nor any `Cache-Control`, and the proxy did not run for it either.

**The built-in trailing-slash 308**, in full: `HTTP/1.1 308 Permanent Redirect`, `location: /fixtures/cards/`, `Refresh: 0;url=/fixtures/cards/`, `Date`, `Connection: keep-alive`, `Keep-Alive: timeout=5`, `Transfer-Encoding: chunked`. No `Cache-Control`, no `Vary`. The same for `POST /api/revalidate`.

**How the page sees a segment**: Next.js normalises `params` before the page runs. `%E6%97%A5` and `%e6%97%a5` both arrive as `%E6%97%A5`; `%41bc` arrives as `Abc` and `foo%2Dbar` as `foo-bar`; `a%2Fb`, `a%20b` and `100%25` arrive as sent; `%2e%2e` is collapsed by the router; a malformed escape (`100%`) is a 500 from Next.js before any page runs. The page cannot tell the two hex cases apart, so a redirect from one to the other would be a redirect to itself.

### What Vercel's documentation says (not measured here)

Everything above was measured under `next start`, with no CDN in front. Vercel's documentation, read on 2026-11-05, says its CDN changes the header a browser sees. From [Cache-Control headers](https://vercel.com/docs/headers/cache-control-headers), under `s-maxage`: "When `Cache-Control` is the only cache header on the response, Vercel's proxy consumes `s-maxage`. After processing it, the CDN does not include it in the final HTTP response to the client." Under "Set Cache-Control for a page": "Vercel consumes `s-maxage`, so the browser receives `cache-control: public, max-age=0, must-revalidate` instead of your value." ([CDN cache](https://vercel.com/docs/caching/cdn-cache) says the same, and lists 308 among the cacheable statuses.) The same page's priority table shows the browser getting `public, max-age=0`, without `must-revalidate`; the two are not reconciled. Neither page says how this applies to an ISR response or to a redirect in particular.

If it holds for an ISR 308, the browser gets `max-age=0` and revalidates the redirect on every request, and the only stored copy is the CDN's, which the revalidation event for the type change purges through the route's tags. That would make the ISR alternative compatible with [ADR 0025](0025-redirects-are-computed-308s-with-no-store.md)'s loop evidence, where a `max-age` was enough for all three engines to ask the server again. It would not meet this record's literal rule (`no-store`), and between the change in the CMS and the event reaching the front end the CDN would keep serving the old redirect. None of this has been measured on Vercel: the Vercel project is not set up yet ([issue #12](https://github.com/Colbitron/resource-hub-wp/issues/12)).

### The mechanism, chosen by default and pending the owner's review

`/resources/[type]/[slug]/` renders on every request: a dynamic segment with no `generateStaticParams`, `export const dynamic = "force-dynamic"`, and `await connection()` first. `force-dynamic` is what keeps it dynamic if `generateStaticParams` is ever added (the table above); `connection()` says so at the point of use. The page calls `resourceForRequest(type, slug)` from `apps/web/lib/redirects.ts` before rendering anything and outside any Suspense boundary. The function looks the slug up in canonical form through the data layer, asks the resolve route only on a miss ([ADR 0029](0029-old-slugs-resolve-through-core.md)), and returns the resource, or calls `permanentRedirect()` with the canonical path computed in one step from the CMS's current answer, or `notFound()`. Next.js then sends `HTTP/1.1 308` with `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` and stores nothing, so there is no redirect for ISR, a CDN or a browser to keep, and a type changed and changed back is answered afresh each time. The data layer's Data Cache keeps the lookups off the CMS: 30 renders, one CMS request. `decideResourceRequest` is the same decision without Next.js, for the unit tests.

Non-canonical segments: an upper-case ASCII letter outside a percent escape in either segment redirects to the lower-case canonical URL (`/resources/Webinar/Slug/`, and `%52esource`, which Next.js decodes to `Resource`); the hex case of an escape is invisible to the page and is treated as canonical, so `%E6%97%A5` renders. A slug may not hold an escape of a character Next.js decodes in params, which is `encodeURIComponent`'s unescaped set, `A-Z a-z 0-9 - _ . ! ~ * ' ( )`: measured on Next.js 16.4.5 under `next start` by requesting `a%XXb` for every byte 0x20 to 0x7e, an escape of one of those characters arrives decoded and every other escape arrives with its hex upper-cased ([ADR 0049](0049-data-layer-fetch-policy.md), amended). A type stored as `arti%27cle` would otherwise reach the page as `arti'cle` and redirect to its own URL for ever. So a redirect's target is a fixed point: `test/redirects.test.ts` checks over thousands of generated slugs and requests that following one never redirects again. A reserved or invalid type segment and an invalid slug are 404s before any lookup. When resolve names the URL that was just asked for, the slug lookup's cached miss is stale next to it; that is a 404 until the next event, not a redirect to itself.

"Single hop" holds from a URL with its trailing slash. A request without one whose segment is also non-canonical (`/resources/Webinar/slug`) takes Next.js's built-in slash 308 first and then the computed one: two hops.

This is the contract-literal choice: it is the only mechanism measured that sends every redirect with `no-store`, in one hop, computed from the CMS's current answer. It is the default while the project owner reviews the trade-off below, not a settled decision.

### What it costs on Vercel

Locally the price is small: 1.6 ms a dynamic render against 0.8 ms for an ISR hit. On Vercel it is a different kind of cost, none of it measured yet:

- **A function invocation on every view.** Every page view and every crawler hit on a single resource runs a function and pays for its CPU time, where ISR would serve the stored page from the CDN.
- **Time to first byte from the function's region**, not the nearest edge, plus a cold start when no instance is warm.
- **Misses reach the CMS on a visitor's request.** After a revalidation clears a tag, the next render fetches from a CMS that has no cache in front of its REST API ([ADR 0023](0023-next-data-cache-is-the-only-http-cache.md)), where ISR would refetch in its own background regeneration.
- **No CDN-cacheable HTML** for the single-resource page.
- **The 200 carries `no-store` too**, Next.js's dynamic header. Browsers may then keep the page out of the back/forward cache; unconfirmed, as browsers differ and are relaxing this rule.
- **Each unknown slug costs one uncached resolve request per page view**, because resolve's 404 is never stored. Bots probing URLs and readers' typos therefore reach the CMS one for one. Mitigations: a Vercel Firewall rate-limit rule on `/resources/*/*/`, or a resolve route that answers a miss with a 200 and an empty body, which the Data Cache would store. The second is a contract change, so it is an option for a later pull request, not part of this one.

### Against the project's targets

`apps/web/CLAUDE.md` asks for Lighthouse mobile performance and accessibility of 95 or better on a single resource, and the root `CLAUDE.md` for good Core Web Vitals and a site shaped like "Next.js and Vercel with ISR and on-demand revalidation". The time to first byte of a dynamic single-resource page on Vercel is unmeasured, so whether this choice keeps that page at 95 is not known yet.

### Recommendation

Keep the dynamic page as the default, because it is the choice that meets the contract to the letter, and treat it as pending the owner's review. Once the Vercel project exists (issue #12), run a one-route spike on a preview deployment: an ISR route that redirects and the dynamic route, both checked with `curl -I` for the status and the `Cache-Control` the browser receives, a type change and change back followed in a browser, and a Lighthouse mobile run on each. The spike also tests a third variant, the ISR route with a `CDN-Cache-Control` or `Vercel-CDN-Cache-Control` header: when either is set, Vercel's documentation says the CDN takes its caching from that header and forwards `Cache-Control` to the client unchanged, so an ISR 308 could be held by the CDN, and purged by the event's tags, while the browser still receives `no-store`. Unmeasured: whether a page's `Cache-Control` and these headers can be set together on a prerendered 308 (a page cannot set response headers itself, and Next.js may override a `headers()` rule's `Cache-Control` on a page), and whether the browser then sees `no-store` on the redirect. Then decide, and amend this record with the numbers.

### Considered and rejected

- **ISR page with a plain `permanentRedirect()`.** Under `next start` the 308 is prerendered and stored with `s-maxage=3600` and no `no-store`, which a browser that receives that header keeps for ever. On Vercel the browser may instead get `max-age=0` (above), which would make it safe against the loop but not `no-store`; unmeasured. The alternative the spike will test, with and without a `CDN-Cache-Control` / `Vercel-CDN-Cache-Control` header that would let `no-store` reach the browser unchanged (Recommendation).
- **ISR page that bails out to a dynamic render only when it redirects.** A 500 at runtime (`DYNAMIC_SERVER_USAGE`) on every prerendered path and every path not seen at build.
- **`connection()` alone as the guard.** Adequate today, but a `generateStaticParams` returning `[]` makes every request a 500. Kept, with `force-dynamic` beside it.
- **`export const revalidate = 0` in place of `force-dynamic`.** Measured to behave the same: dynamic, `no-store` on every redirect, the Data Cache kept. Not chosen because a `revalidate` export reads as an ISR interval, and [ADR 0049](0049-data-layer-fetch-policy.md) asks that a route `revalidate` be the data layer's 3600; `force-dynamic` says what is meant.
- **`proxy.ts` with the data layer.** `no-store` and single-hop, but a CMS request per page view, before the cache, on a CMS with no REST cache.
- **A Route Handler at the resource path.** Cannot share the segment with the page.
- **A `headers()` rule putting `no-store` on `/resources/:type/:slug/`, with an ISR page.** Keeps the Full Route Cache for the 200 (0.74 ms a hit) and tells every cache downstream not to keep the 308, but the 200 is then not cached by any CDN or browser either, the 308 is still stored by ISR until an event or the hour clears it, and the rule cannot be made conditional on the status. It would need its own round-trip test for the stored 308.
- **Cache Components (PPR) with the decision in the dynamic part.** Already rejected by [ADR 0043](0043-fetch-cache-with-tags-without-cache-components.md); and a redirect after the static shell is flushed is a meta refresh.

### Consequences

- The resource page has `export const dynamic = "force-dynamic"`, no `generateStaticParams` and no `loading.tsx`, and calls `resourceForRequest` first. With `force-dynamic`, adding `generateStaticParams` changes nothing on the wire (measured above); without it, a `generateStaticParams` returning `[]` would make every request a 500. A route `revalidate` with prerendered params would store the redirects; `e2e/redirects.spec.ts` asserts `no-store` and no `x-nextjs-cache` on every redirect, so it would fail.
- The e2e suite covers the real route: `e2e/resource-page.spec.ts` asserts on `/resources/[type]/[slug]/` that a wrong type and an old slug each get one 308 with `no-store` and no `x-nextjs-cache` to a URL that answers 200, that mixed case gets the proxy's 308, that an unknown slug is a 404, and that Chromium follows webinar → podcast → webinar with every redirect from the server. `e2e/redirects.spec.ts` keeps the same contract on the fixture route `/fixtures/redirect/[type]/[slug]/` with every edge case of the decision.
- `generateMetadata` calls `resourceForRequest` too, but only to share the decision and its memoised fetches: it cannot send the status by itself. Measured on 16.4.5 under `next start` with a throwaway page whose `generateMetadata` alone redirected: a browser's request got `HTTP/1.1 200` with `<meta id="__next-page-redirect" http-equiv="refresh">` and `NEXT_REDIRECT;…;308` in the payload, because metadata streams after the initial UI; the same request from an HTML-limited bot (`facebookexternalhit`) got the 308, because for those metadata blocks the render. `notFound()` from `generateMetadata` alone was likewise a 200 for a browser and a 404 for the bot. So the page's own call, before anything renders, is what sends the 308 or the 404; the per-render memoization in `lib/wp/fetch.ts` means the two calls cost one CMS request (`e2e/resource-page.spec.ts` checks the counters: one slug lookup per render, resolve once per 404).
- The route has an `error.tsx`. Measured on 16.4.5 under `next start`: a `CmsError` thrown by the page under a segment error boundary is still `HTTP/1.1 500` with `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`; and a `permanentRedirect()` or `notFound()` thrown by the page never reaches the boundary, so the 308 and the 404 are unchanged. The 500's body is not the site's shell: it is Next.js's empty `<html id="__next_error__">` document with the flight payload, and the root layout, the sentence and the "Try again" button appear only once the client has hydrated, so a reader without JavaScript, and a crawler, get an empty page with the 500 status. What the boundary changes is only what a hydrated reader sees: the site's shell with a sentence and a "Try again" button, in place of Next.js's bare "Application error" page. It takes no `error` prop, so no message or digest, and so no CMS detail, can reach the page; `test/resource-route.test.ts` pins that, the `force-dynamic` export, the absence of `generateStaticParams` and `loading.tsx`, and the `connection()` and `resourceForRequest` calls in both the page and `generateMetadata`.
- The built-in trailing-slash 308 stays as Next.js sends it, with no `Cache-Control`: neither `headers()` nor the proxy reaches it. That is harmless: `/path` to `/path/` is a function of the URL alone and never changes, so a browser keeping it can never be wrong, and the slashed URL then goes through the computed check. The rule "never send a permanent redirect without a cache header" is kept for every redirect whose target can change.
- The listing pages will be ISR. Their only redirect is the canonical-form one for a mixed-case segment ([ADR 0049](0049-data-layer-fetch-policy.md)), whose target, like the slash redirect's, is a function of the URL alone; the listing pull requests decide whether to send it from the ISR page, stored but never wrong, or from a proxy matched on `/resources/:path*` with no data (0.44 ms a redirect, 0.13 ms added to every other matched request).
- `lib/wp/cards.ts` exports `resourceType`, the one rule for which resources have a URL, shared by the card mapping and the redirect decision.

## Amendment, 2026-11-05: the listings' canonical-form redirects come from `proxy.ts`, for every `/resources/**` path

The listing pages (`/resources/`, `/resources/[type]/`, `/resources/topic/[topic]/`, `/resources/[type]/topic/[topic]/` and `…/page/[n]/`) are ISR ([ADR 0050](0050-listings-are-isr-that-render-on-first-request.md)). This record's measurement above settles where their redirects can come from: a `permanentRedirect()` from an ISR page is prerendered and stored with `s-maxage=3600` and no `max-age`, and a dynamic bail-out on the redirect branch alone is a runtime 500. So the listings send no redirect of their own. `apps/web/proxy.ts`, matched on `/resources/:path*`, sends every redirect that can be decided from the path alone, and the pages answer everything that needs data with `notFound()`.

### What the proxy decides

Two rules, in `apps/web/lib/canonical-path.ts`, both functions of the URL and nothing else, so the answer can never be wrong and never changes with the CMS's data:

- An upper-case ASCII letter outside a percent escape, in any segment after `resources`, is lower-cased: `/resources/Webinar/` is `/resources/webinar/`. An escape of a character Next.js decodes in params (`%57ebinar`, `a%27b`) is decoded first, as Next.js would decode it before a page sees it: the set is `DECODED_IN_PARAMS` in `lib/routes.ts`, `encodeURIComponent`'s unescaped set, imported by the proxy so that it and `slugProblem` share one definition. None of those characters is one a URL serialiser escapes in a path, so the target is received exactly as computed and the proxy never redirects a path to itself. Every other escape is left exactly as sent, hex case included, because Next.js normalises the hex before a page sees it ([ADR 0049](0049-data-layer-fetch-policy.md)'s amendment), so a redirect between `%e6` and `%E6` would be a redirect to itself. A segment with a `%` that does not begin a well-formed escape (`%4%41`, `%zz`, a trailing `%`) is left exactly as sent, because decoding the escape after a stray `%` makes a new escape: `/resources/x/%4%41/` would go to `%4a` and then to `j`, a chain rather than one hop. No route renders such a segment, so it gets the route's 404 or Next.js's 400 with no redirect first.
- A trailing `/page/1/` is dropped: page 1 of a listing is the listing's own path. It is dropped once, and not when another `page/1` would be left at the end (`/resources/page/1/page/1/` is no listing and stays the route's 404), so the computed form is always a fixed point: canonicalising it again changes nothing.

The response is a 308 with `Cache-Control: no-store` and a path-only `Location` that keeps the query string, so it is a single hop to a URL that renders. Nothing else is decided there: an unknown type or topic, a page past the end, a page segment with no canonical form (`0`, `01`, `x`) and the resource page's wrong-type or old-slug cases all need data, and the proxy never reads the data layer, whose `fetch` is not the Data Cache's (measured above: a CMS request per matched request).

### `/Resources/…` is a 404, by design

The matcher `/resources/:path*` is case-sensitive, so a request for `/Resources/` or `/RESOURCES/webinar/` never reaches the proxy and gets the app's 404. That is deliberate rather than a gap to close with a wider matcher: no page has ever been served under a capitalised prefix, so there is no link or index entry to carry over, and the proxy stays scoped to the one prefix the site uses. An earlier version of `lib/canonical-path.ts` also lower-cased the `resources` segment; behind this matcher that code could never run, so it was removed. The case rule therefore covers the segments after `resources` only.

### Why every `/resources/**` path, not the listings alone

The matcher covers the resource page too, so the resource page's own decision in `lib/redirects.ts` meets only canonical segments: its mixed-case branch stays as a second line, reachable only by a request that did not pass through the proxy, and a stored slug never holds an escape the proxy would decode differently from Next.js (`slugProblem`). One rule for the case of every segment under `/resources/`, in one place, rather than the listings redirecting in the proxy and the resource page redirecting in its render, and no path on which the two could disagree or double up: the proxy's target is canonical by construction, so the page's check passes and no second hop follows. Next.js's own trailing-slash 308 still runs before the proxy and carries no cache header; a slashless non-canonical path takes two hops, as recorded above.

### Measured cost

Under `next start` against the e2e mock (ports 3400 and 4100), 300 sequential loopback `GET`s each after 20 warm-ups, mean and p95, the same build with `proxy.ts` present and then removed:

| Response | Without the proxy | Through the proxy |
|---|---|---|
| `/resources/`, ISR 200 `HIT` | 0.42 ms, p95 0.53 ms | 0.61 ms, p95 0.77 ms |
| `/resources/webinar/`, ISR 200 `HIT` | 0.33 ms, p95 0.42 ms | 0.47 ms, p95 0.68 ms |
| `/resources/Webinar/`, proxy 308 | | 0.19 ms, p95 0.23 ms |
| `/resources/page/1/`, proxy 308 | | 0.18 ms, p95 0.26 ms |
| `/`, static 200, not matched | 0.19 ms, p95 0.23 ms | 0.20 ms, p95 0.23 ms |

About 0.15 ms on every listing hit, and a redirect for a fifth of a millisecond, with no data read. An unmatched route pays nothing.

### Consequences

- `proxy.ts` must stay free of the data layer and of anything that varies with the CMS; `test/canonical-path.test.ts` holds the rules and checks that every path the builders in `lib/routes.ts` produce is already canonical, so a redirect's target is a fixed point.
- `e2e/listings.spec.ts` asserts, for mixed case, `/page/1/` and both together, one 308 with `no-store` and no `x-nextjs-cache` to a URL that answers 200, and follows one in Chromium.
- A 404 from a listing is stored by ISR like a 200, under the tags of the fetches that decided it, so a term `create` or a publish clears it; a syntactically bad page segment is a stored 404 per distinct URL, which is what any unknown URL costs.

## Amendment, 2026-11-06: the resource page is ISR, its redirects are stored, and a `headers()` rule keeps browsers asking

The owner's decision, 2026-11-06, reverses the mechanism chosen above: `/resources/[type]/[slug]/` is an ISR route like the listings ([ADR 0050](0050-listings-are-isr-that-render-on-first-request.md)), with `export const revalidate = 3600` as a literal and a `generateStaticParams` returning `[]`, and no `connection()` or `force-dynamic`. The reason is the cost table above: every view of a resource page ran a function, paid its cold start and its region's time to first byte, and left no HTML for the CDN; and the thing the dynamic page bought, a redirect that is never stored, is bought another way. Every resource event already revalidates the union of the resource's current and previous state, tags and paths alike ([ADR 0046](0046-which-tags-and-paths-each-event-revalidates.md)), so a stored redirect at the old URL and a stored 404 at the new one are cleared by the same event that makes them wrong. The literal rule in [ADR 0025](0025-redirects-are-computed-308s-with-no-store.md), `no-store` on every permanent redirect, is replaced by its purpose: a browser never keeps a redirect whose target can change. The decision itself is unchanged: `resourceForRequest` in `lib/redirects.ts` still computes the canonical path in one step from the CMS's current answer and calls `permanentRedirect()` or `notFound()` before anything renders.

### What was measured, under `next start` against the e2e mock (ports 3370 and 4070), Next.js 16.4.5

The wire headers of the resource route, before and after. "Before" is the dynamic page as merged; "ISR" is the change alone; "ISR + rule" is what this amendment ships.

| Response | Before (dynamic) | ISR, no rule | ISR + `headers()` rule |
|---|---|---|---|
| 200, canonical URL | `private, no-cache, no-store, max-age=0, must-revalidate`; no `x-nextjs-cache` | `s-maxage=3600, stale-while-revalidate=31532400`; `MISS` then `HIT` | `public, max-age=0, must-revalidate`; `MISS` then `HIT` |
| 308, wrong type or old slug | the same `no-store` header, every time | `s-maxage=3600, stale-while-revalidate=31532400`; `MISS` then `HIT` | `public, max-age=0, must-revalidate`; `MISS` then `HIT` |
| 404, unknown slug | the same `no-store` header, every time | `s-maxage=3600, stale-while-revalidate=31532400`; `MISS` then `HIT` | `public, max-age=0, must-revalidate`; `MISS` then `HIT` |
| 500, `CmsError` | `private, no-cache, no-store, max-age=0, must-revalidate` | unchanged; never stored, the next request renders again | unchanged |
| 308 from `proxy.ts` (mixed case) | `no-store` | unchanged | unchanged |
| 200 of a listing | `s-maxage=3600, stale-while-revalidate=31532400` | unchanged | unchanged |

Three observations beside the table. A freshly rendered ISR 308 (`MISS`) carries `location` twice with the same value, and the stored copy (`HIT`) once; every client reads the first, and the e2e helpers do too. Next.js's `sendRenderResult` sets `Cache-Control` only when none is set, so a `headers()` rule is kept on an ISR response and the response is still answered from the route cache (`x-nextjs-cache: HIT`); the 500 path sets its own header unconditionally and keeps `no-store`. The build prerenders nothing: `generateStaticParams` returns `[]`, the build log marks the route `●`, and the prerender manifest holds no resource path.

**What a stored entry is, and what clears it.** The entry is whatever the decision produced, under the tags of the fetches that decided it: `resource:{slug}` and `terms` from the slug lookup, plus `resources` from resolve on a miss. Measured, each with the event the plugin would send: a type change turns the stored 200 at the old URL into a 308 and the stored 308 at the new URL into a 200, and the change back reverses both; a rename turns a stored 404 at the new slug (a crawler's early visit) into the page and the stored 200 at the old slug into a 308, and the rename back clears that stored 308; an unpublish turns the stored 200 into a 404; the 500 is never stored, so a CMS that recovers is seen on the next request. An unknown slug now costs the CMS one slug lookup and one resolve request per distinct URL per interval, where the dynamic page cost one resolve request per page view, because the stored 404 answers the repeats; `e2e/resource-page.spec.ts` counts both.

**Why a `headers()` rule, and which.** Next.js sends a stored response with `s-maxage` alone, which a browser ignores, so a stored 308 reaches a browser with no freshness information at all, and Chromium keeps such a 308 for ever ([ADR 0025](0025-redirects-are-computed-308s-with-no-store.md)'s evidence), which no revalidation can undo. Vercel's documentation says its CDN consumes `s-maxage` and sends browsers `public, max-age=0, must-revalidate`; `next start`, which the e2e suite and anyone self-hosting runs, does not. The rule in `lib/route-headers.ts`, applied through `next.config.ts`'s `headers()`, puts that same string on every response of the route, so a browser sees one header whatever serves it. Its source, `/resources/:type((?!(?:topic|page)/)[^/]+)/:slug`, leaves the topic listing and the library's page `n` to Next.js's own header; a unit test compiles it with the matcher Next.js uses. The value carries no `s-maxage`, so the 500 and any other status announce nothing a shared cache could keep, and no `no-store`, which would forbid the route cache's purpose. A page cannot set its own response headers, and the rule cannot vary by status, so the 200 and the 404 get it too; they carried no validator before, so a browser refetched them anyway.

**The cache key, and why the proxy now covers every path.** Next.js stores a runtime ISR entry under `.next/server/route-cache/APP_PAGE/{route hash}/$/{decoded path}`: per route, so a 404 from the pages catch-all at `/Resources/` cannot stand in for the library at `/resources/`, but by the decoded path, so `/%41bout/` and `/About/` share a key, and on a case-insensitive file system (macOS, where the suite runs) so do `/About/` and `/about/`. Measured on the pages catch-all with no proxy in front: a request for `/Company/` before any for `/company/` stored the page's 308 to `/company/` under that key, and `/company/` then redirected to itself. The resource page was already safe, because `proxy.ts` lower-cased every `/resources/**` path first; the catch-all was not. So `proxy.ts` now matches every path but `/api/`, `/media/` and `/_next/` (`canonicalPath` in `lib/canonical-path.ts`): rule 1, lower-casing and decoding, applies to every segment of every page path and to the `resources` segment itself, rule 2 (`/page/1/`) stays the library's. `/Resources/…` is therefore a case redirect to `/resources/…`, no longer the 404 by design recorded in the listings amendment above: that 404 existed to keep the proxy scoped to one prefix, and the proxy is no longer scoped. The pages' own mixed-case branches remain as a second line that only a request bypassing the proxy could reach. What Vercel's cache keys on is unmeasured; the proxy makes the question moot, because it runs before the cache.

**After review, the same day.** Three refinements to the proxy, each measured under `next start` and unit-tested. First, the case rule covers every script: a valid UTF-8 escape sequence is decoded, taken with the text around it to NFC and lower case, and encoded again in lower-case hex, which is what a WordPress slug holds (`sanitize_title` runs `remove_accents`, which normalises NFD to NFC when PHP's `intl` extension is loaded, then `sanitize_title_with_dashes` applies `mb_strtolower` and lower-cases the hex), so `/%D0%94%D0%BE%D0%BC/` (`Дом`) is one hop to `/%d0%b4%d0%be%d0%bc/` and `/%E6%97%A5/` to `/%e6%97%a5/`, and `/cafe%CC%81/` (NFD) to `/caf%c3%a9/`; measured: the proxy sees the path as sent, hex case included, so the lower-hex target passes through and nothing loops. APFS folds case in every script and compares normalisation forms as equal, so without this `/Дом/` and `/дом/` shared a route-cache key on a development machine. Invalid sequences and ASCII escapes Next.js does not decode are left as sent; an ASCII character a normalisation produces that a URL parser would encode (U+1FEF composes to a backtick) is encoded, or the target would not be a fixed point. A property test takes every code point of the Basic Multilingual Plane, in either hex case, raw and after an `e`, through the rule and checks the result is a fixed point that survives a URL parser. What the rule does not cover: a CMS without `intl` can store an NFD slug, whose own URL this rule would redirect to a 404, so the claim is "no request differing from a stored slug only in case, in any script, or in hex case, or in NFD form where the CMS stores NFC, reaches an ISR route". Second, the matcher is narrowed to what can need a redirect: every `/resources/**` path (the `/page/1/` rule) and any other path with an upper-case ASCII letter, a percent escape or a repeated slash, outside `/api/`, `/media/` and `/_next/`, so a canonical page path, the ISR hit, never runs the proxy. Next.js tests a matcher at runtime with a flagless `RegExp`, so `[A-Z]` is case-sensitive there; `test/proxy-matcher.test.ts` compiles the sources with Next.js's own `tryToParsePath` and `getMiddlewareRouteMatcher` and checks the root and canonical page paths against them. Next.js's own 308 collapses a repeated slash before the proxy runs (`/about//team/` to `/about/team/`, measured), so that entry is a belt to its brace; `canonicalPath` collapses it too. Third, the e2e `location()` helpers now assert that every `Location` value of a response is the same before reading the first, so the duplicate on a `MISS` 308 is pinned as harmless rather than ignored. The redirect, storage and 404 tests of `redirects.spec.ts`, `resource-page.spec.ts`, `pages.spec.ts`, `errors.spec.ts` and `listings.spec.ts` were also run once under Playwright's WebKit (2370) against the same servers, with the Chromium-only DevTools tests left out: 76 passed, and the 4 that failed are the keyboard-focus tests (Tab reaching the skip link, the filters and a table's region), where WebKit does not tab to links by default; nothing about a redirect or a stored response differed. The suite's project stays Chromium.

### What is expected on Vercel, unmeasured

The CDN should store the resource page, its 308 and its 404 as it stores a listing, purge them when the revalidate route calls `revalidateTag` and `revalidatePath`, and send browsers `public, max-age=0, must-revalidate` whether from the rule or from its own handling of `s-maxage`. The orchestrator's review verifies on a preview deployment: the header a browser receives on a stored 308, that a type change and change back is followed by a browser without a kept redirect, and that `/About/Team/` gets the proxy's `no-store` 308 and not a stored entry. If Vercel's build ignores a `headers()` `Cache-Control` on an ISR route, the browser still gets `max-age=0` from the CDN's own rewrite; if it honours the rule, the header is the same string.
