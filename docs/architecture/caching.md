# Caching, URLs and redirects

For a contributor changing caching, data fetching, URLs or redirects on the front end, or the REST cache headers and the related and search routes' object caches on the CMS. The decision is [ADR 0043](../adr/0043-fetch-cache-with-tags-without-cache-components.md) (the caching model, and what the build prerenders) with [ADR 0024](../adr/0024-type-paths-mirrored-on-both-sites.md) and [ADR 0025](../adr/0025-permanent-redirects-are-computed-and-never-kept-by-browsers.md) (URLs and redirects). How a revalidation request reaches the route is in [revalidation.md](revalidation.md).

## The model

- **One HTTP cache.** Every CMS read is a `fetch` with `cache: "force-cache"` and `next: { tags, revalidate }` through the wrapper in `apps/web/lib/wp/fetch.ts`, so it lives in the Next.js Data Cache, which persists across deployments and instances. Varnish and Cloudflare sit between the front end and WordPress, so the plugin's `NoCacheHeader` sends the [no-cache header the contract states](../../packages/ui/README.md#how-the-two-sides-talk) on every anonymous read: a copy cached upstream would survive a revalidation, and a 404 is as cacheable as a 200. Verified 2026-11-05 that the header does not stop the Data Cache from storing the response (`e2e/revalidate.spec.ts`). No Cache Components, no `'use cache'`, no `unstable_cache`.
- **On-demand first, ISR as the safety net.** The revalidate route clears tags and paths when the CMS says so. Every fetch also revalidates after `CMS_REVALIDATE_SECONDS` (one hour), the only thing that brings a page back in step after a send that failed, since the plugin never retries. Pages that set a route `revalidate` write the same number as a literal, because Next.js reads segment config statically.
- **A CMS request times out** after `CMS_TIMEOUT_MS`. Errors become `null` (a named 404 or 401, so a 404 page), `NO_SUCH_PAGE`, or a `CmsError` that never names the CMS origin. Redirects from the CMS are refused, not followed. A collection is parsed one item at a time, with the threshold in `LIST_FAILURE_MIN_ITEMS`; the docblocks in `fetch.ts` hold the rules.
- **The build prerenders a bounded set, and never fails for a CMS reason** (ADR 0043, amended 2026-11-07). Every route but the search page is ISR with a `generateStaticParams`; the search page prerenders nothing ([The search page](#the-search-page)). Four of them prerender from the CMS when it answers at build: the library's first page, each type's first page, the root, and the resource pages for the 50 newest resources and the 10 newest of each type, each once (`RECENT_RESOURCES` and `RECENT_PER_TYPE` in `apps/web/lib/prerender.ts`). Each calls a probe there that makes the page's own reads under a budget (`PRERENDER_TIMEOUT_MS`, 10 s, for the library, the type listings and the root; `RESOURCE_PRERENDER_TIMEOUT_MS`, 30 s, for the resource pages, whose probe makes up to a hundred reads eight at a time) and returns the params whose reads succeeded: all of them, the ones decided when the budget ran out, or, when a list or more than half of the resource candidates fail (`MAX_FAILED_SHARE`), `[]`; a failed candidate on its own is skipped and counted in the route's one build warning. So a build with the CMS absent, down or slow prerenders less or nothing, waits at most about 60 s for it in all, and is otherwise the same build, and a prerendered page is rendered from reads the probe already put in the Data Cache. Every other `generateStaticParams` returns `[]`: topic listings, later pages and other CMS pages grow with what editors add and render on their first request. The deploy order (CMS first, then the front end) is what keeps the first renders correct. The library's own path, `/resources/`, is the optional catch-all `app/resources/[[...rest]]/page.tsx` so that its prerender can be conditional: a route with no dynamic segment is prerendered at build whether or not the CMS answers. Static and dynamic siblings win over a catch-all, so the page serves `/resources/` alone.
- **The Data Cache stores only 200s.** A miss by slug is a 200 with an empty list and is cached under its tags; a miss by ID and a resolve miss are a 404 or 401 and are asked again on every render. The page route answers a miss with a 200 and `page: null` for the same reason.

## Tags, and what each event clears

The tags are `resources`, `terms`, `resource:{slug}`, `topic:{slug}`, `type:{slug}` and `pages`. The rules are code in `apps/web/lib/tags.ts`, whose docblock is the full statement; `test/tags.test.ts` writes each fetch's tags out by hand and checks the functions against them.

- **A resource event** clears `resources`, `resource:{slug}`, `type:{t}` and each `topic:{p}`, and the paths `/resources/`, the resource's page, its type listing, each topic listing and each type-plus-topic listing, for both its current state and its `previous` state. Refresh and remove clear the same things; the refetch decides what is shown.
- **A term event** clears `resources`, `terms` and `topic:{slug}` or `type:{slug}` for the current and the previous slug, and the paths `/resources/` and the term's own listing for each slug.
- **The related-resources block's list** (`relatedBlockTags`, the fetch in `lib/wp/related.ts` for `components/RelatedResources.tsx`) carries `topic:{slug}` and `terms`, the topic listing's tags: every resource event names the resource's topics in both its states, so any change to a resource in or out of the topic clears it, and the topic's own event clears both its slugs; `resources` is not on it, so a resource event elsewhere leaves every block alone. Its URL also carries the topic's canonical slug as `rh_topic`, which core ignores, so the cache key names the slug the tag is made from and a marker whose slug disagrees with its topic ID never shares an entry tagged for another topic.
- **A page event** clears `pages` and the paths named at the top level and in `previous`. It clears nothing of the library's, and no resource or term event clears `pages`.
- **Search** (`searchTags`, the three fetches in `lib/wp/search.ts`: the plugin's search route and the `include=` reads of the resources and the pages it names) carries `resources`, `terms` and `pages`: the library's tags, since any resource event or term rename can change what matches and what a match says, and `pages`, since its results hold pages too. The tags are the same for every query, so they are fixed before the request whatever the query or the answer. The resource read's URL can also be one the related section reads; both callers' tags hold `resources` and `terms`, so the shared entry is cleared whichever stored it.
- **The union rule.** Every event invalidates the union of its current and previous state; the route never diffs the two. So a stored redirect at an old URL and a stored 404 at a new one are cleared by the same event that made them wrong.
- **`terms`** is produced by term events only and carried by every fetch that embeds or lists terms, so a term rename reaches every page that shows the name (every listing, every resource page, the filter bar), which the event cannot name. Term events keep `resources` too, because the resolve route answers with the type slug.
- **Pagination is covered by tags only.** `…/page/{n}/` is never revalidated as a path: an event cannot say how many pages a listing has, and every page of a listing fetches with the same tags as its first page.

**Fetch tagging rule.** Tags are fixed before the request, from the URL and its parameters, never from the response, so a miss is cached under the tags a later publish clears. Next.js keys a cached fetch by its URL, method and headers, not its tags, so two pages that fetch one URL share one entry under whichever page's tags came first; a tag that depends on the calling page (the type segment a resource page was reached under) is never put on a shared URL. The fetches whose result can change with any resource carry `resources`: the featured list, the filter bar's term lists, whose counts WordPress updates on every publish and trash without a term event, and the resource page's related section's two reads, the plugin's related route (`lib/wp/related.ts`) and the `include=` read of the resources it names (`getResourcesByIds` in `lib/wp/resources.ts`), both under `relatedTags`; the section catches a `CmsError` from either around itself, so a CMS without the route (one deploy behind) renders the page without it. A related read that fails at render time is stored with the page: ISR keeps that render as a 200 without the section (or with the block's fallback in place of its list) until an event clears the page's tags or the hour's revalidation passes.

**The canonical slug form.** A slug goes into a path or tag in one form, `canonicalSlug` in `lib/routes.ts`: existing escapes kept, every character a path segment does not allow percent-encoded as UTF-8, and the whole result lower-cased, which is WordPress's own form. The reserved type slugs are checked in any case. `slugProblem` also rejects a lone surrogate, a dot segment, a canonical form over 200 characters (Next.js drops a tag longer than 256 characters with only a warning), and any escape of a character Next.js decodes in params. The front end's readers are therefore stricter than the shared schema; the comment on `slugSchema` in `lib/wp/schemas/common.ts` lists the differences.

## What each route stores

All three kinds of route that store a response are ISR (the fourth, [the search page](#the-search-page), stores none): `export const revalidate = 3600` as a literal, a `generateStaticParams` (the probes in `lib/prerender.ts` on the four routes that prerender, `[]` on the rest), no `connection()`, nothing from `next/headers`, no `searchParams`, no `force-dynamic`, and no `loading.tsx`. The unit tests `test/listing-routes.test.ts`, `test/resource-route.test.ts`, `test/page-route.test.ts` and `test/prerender.test.ts` pin that, and `test/route-segments.test.ts` walks `app/` so a page no list names is held to it as well. A route renders a path at build when the probe named it and on its first request otherwise, stores what it answered under the tags of the fetches that decided it, serves it from the route cache (`x-nextjs-cache: HIT`) until an event or the interval clears it, and never stores a 500. A prerendered path and one rendered on demand are stored and served the same way, which `e2e/prefetch.spec.ts` checks; that an event clears a prerendered page as it clears one rendered on demand follows from the tags being the same fetches' tags, and `e2e/pages.spec.ts`'s root tests exercise it on the prerendered `/`. One window differs: an event fired while a build runs clears the live deployment, not the build in progress, so the new deployment's prerendered pages carry pre-event data until the next event or the interval.

- **The listings** (`app/resources/**`, eight routes over `components/ListingPage.tsx`): a 200, or a stored 404 for an unknown term or a page past the end, cleared by the term `create` or the publish that adds a page. An empty filter combination where both terms exist is a 200. A listing never redirects. The library's first page also reads the `featured` flag's listing for its lead, two more fetches (the flag term by slug and the flagged resources) tagged `resources` and `terms`, so any resource event clears the lead with the page.
- **The resource page** (`app/resources/[type]/[slug]/`): `resourceForRequest` in `lib/redirects.ts` runs before anything renders and returns the resource or the not-found decision, or calls `permanentRedirect()` to the canonical path computed in one step; the page answers the not-found decision with `DataNotFound` ([Not-found pages](#not-found-pages)). The 200, the 308 (a wrong type, an old slug found through resolve) and the 404 are all stored. Measured 2026-11-06: a type change turns the stored 200 at the old URL into a 308 and the stored 308 at the new URL into a 200, and the change back reverses both; a rename turns a stored 404 at the new slug into the page and the stored 200 at the old slug into a 308; an unpublish turns the stored 200 into a 404. An unknown slug costs the CMS one slug lookup and one resolve request per distinct URL per interval.
- **The pages catch-all** (`app/[[...path]]/`): `pageForRequest` in `lib/page-request.ts` decides the same way, under the `pages` tag. The welcome page is stored at `/` when no front page is set; the front page's own slug is a stored 308 to `/`; a wrong parent with a unique slug is a stored 308 to the page's path. A redirect goes out only after the target's own lookup has answered the same page at that path, so two cache entries that disagree give a 404 rather than a loop.

**The decision runs before streaming begins.** In a route rendered per request, once a Suspense boundary or a `loading.tsx` has flushed, Next.js can only send a 200 with a meta refresh for a redirect, and a 200 for `notFound()`. An ISR route is rendered completely before it is answered, which is what lets the not-found boundary below set a 404; the decision still runs first and outside every boundary, so a redirect is thrown before the shell and nothing depends on a boundary but the 404. `generateMetadata` calls the same decision to share the memoised fetches, but cannot send the status itself, and on a not-found decision it returns `NOT_FOUND_METADATA` rather than throwing ([Not-found pages](#not-found-pages) has why): a page and its `generateMetadata` make one CMS request between them (`lib/wp/fetch.ts` memoises per render with React's `cache`).

## The search page

`/search/?q=…&page=n` (`app/search/page.tsx`, issue #115) is the one dynamic route (ADR 0043, amended 2026-11-07): it reads `searchParams`, so Next.js renders it on every request, because a query is the visitor's own words and none can be prerendered. Everything else about the model holds, and `test/route-segments.test.ts` pins it and fails on a second dynamic route:

- **Reads.** `searchSite` in `lib/wp/search.ts` makes up to three fetches, the plugin's search route and the `include=` reads of the resources and the pages it names, each the data layer's `force-cache` fetch under `searchTags()` (`resources`, `terms`, `pages`; [Tags](#tags-and-what-each-event-clears)). A repeated query and page is expected to be answered from the Data Cache with no CMS request until an event clears one of those tags or the hour passes, and each distinct query and page to be its own entry: measured under `next start`, not yet on Vercel (below). A query the plugin would refuse (under 2 or over 100 code points once normalised) and a `page` outside 1 to 10 are answered without a request (`lib/search-request.ts`), and so is a query holding a control character, which the front end refuses though the CMS would not. `generateMetadata` makes the same reads as the page, through the data layer's per-render memoisation, so the two make one set of requests between them.
- **No stored page.** The page exports no `revalidate`, `dynamic` or `generateStaticParams`, has no `loading.tsx` and no Suspense boundary, and reads no other request-time API. Next.js answers it with `private, no-cache, no-store, max-age=0, must-revalidate`; no `headers()` rule matches it, because `search` is one of `RESERVED_ROOT_SEGMENTS`.
- **Statuses.** Every state is a 200: no query, a query too short, too long or holding a control character, results, no results, a page past the last or one the route would refuse (the "no results on this page" state with a link to page 1), and a CMS without the route (`rest_no_route`, "Search isn't available right now"). It never redirects and never answers a 404: `DataNotFound`'s 404 holds only on an ISR route ([Not-found pages](#not-found-pages)). A CMS error is not caught and is a 500 with `no-store`, through `app/search/error.tsx`, because the page awaits its read before anything is sent. `/search/{anything}/` and a mixed-case `/Search/` are the proxy's 404 from the path alone (`lib/path-decision.ts`); `/search?q=…` is Next.js's trailing-slash 308, query kept.
- **Pagination** links are plain `<a>`s, not `<Link>`s, so a page of results is never prefetched: a prefetch here would be a function run and a CMS search for a page the reader may not open, counted by the rate limit below.
- **The edge.** The Hobby plan's one Vercel Firewall rate-limit rule, "Rate limit search", covers `^/search(/.*)?$` on production, 60 requests per 60 s per IP, published in log mode, so it counts and does not yet block ([The search results on the CMS](#the-search-results-on-the-cms)).

**2026-11-07, measured.** Under `next start` against the mock CMS (`e2e/search.spec.ts` pins it): three requests for one new query made one request to the search route and three renders, no `x-nextjs-cache` header and `no-store` on each; after a term event cleared the tags the next request read the CMS again; a CMS 500 was a 500 with `no-store`. On a remote-built Vercel preview (`vercel deploy` from `apps/web`, not `--prebuilt`) of the same branch, whose hosted CMS did not have the search route yet: every state above a 200 with `noindex` and the header above, a repeated query `x-vercel-cache: MISS` both times, so the edge stores nothing and every request is a function run, `/search/x/` a 404, and with a query, "Search isn't available right now" in the HTML and no CMS address. **Not yet measured on Vercel:** whether the search fetches of a dynamic render land in the Data Cache there, so that a repeated query makes no second CMS request. That needs the hosted CMS to answer the route, and is to be measured once [#121](https://github.com/Colbitron/resource-hub-wp/pull/121) is deployed.

## The related list on the CMS

`GET /resource-hub/v1/related/{id}` keeps each merged list in the object cache under `related:{id}:{count}` in the `resource_hub` group, stored with `wp_cache_set_salted()` for a day; `RelatedCache` in the plugin is the full statement. The salt is one stamp, the plugin's own `last_changed` in that group. Core's `terms` stamp is left out on purpose: core bumps it from `clean_post_cache()` on every post save on the site, autosaves included, so an entry would last only until the next save of anything, the same churn that rules out core's query cache. The plugin bumps its stamp when a resource that was or becomes published is saved (a publish, an update, an unpublish, a trash, a save as another post type), when a published resource is force-deleted (at `before_delete_post`, and again at `after_delete_post`, the one hook that fires after core's `clean_post_cache()`: `deleted_post` fires once the row is gone but before that cleaning, so a list computed in between could still read the deleted post from WP_Query's `post-queries` cache and be stored under the new salt), when a published resource's topics are set or removed outside a save (`set_object_terms`, `deleted_term_relationships`), and when a topic is created, edited or deleted; a draft's saves and topic changes bump nothing, because no list shows a draft. The salt is read once, before the lookup, and the list is stored under that same salt, so a bump that lands while a list is computed leaves an entry the next read misses rather than a stale one. Known costs: any bump empties every resource's lists, not only the ones the change is on, which is cheap because each list is two small queries recomputed on its next request; without a persistent object cache (wp-env, or a host without Redis or Memcached) an entry lives for one request, so both queries run on every read; and the anonymous response carries the no-cache header like every route here, so between the CMS and the front end it is the front end's Data Cache, not an upstream cache, that saves the CMS repeat reads of the route by the resource page's related section.

## The search results on the CMS

`GET /resource-hub/v1/search?q=…&page=n` keeps each page of results in the object cache under `search:{md5(q)}:{page}` in the `resource_hub` group, stored with `wp_cache_set_salted()` for a day, where `q` is the query as normalised (whitespace runs collapsed, ends trimmed); `SearchCache` in the plugin is the full statement. The salt is two stamps: the related lists' (above), which every change to a published resource turns over, and a search-only stamp, the `last_changed` of the `resource_hub_search` group, which turns over when a page that was or becomes public is saved or force-deleted, when Settings > Reading changes (the posts page is left out of results) and on every `resource_type` term event. A second stamp keeps page saves and type renames from emptying the related lists, which can see neither. The route answers the same for every reader, since it searches only published resources and pages with no password, so the key names no user. Known costs: a bump empties every query's pages; without a persistent object cache every request runs the search; a page past the last one with results runs one more query, a one-row count, because core leaves `found_posts` at 0 when the page it fetched is empty; a `summary` or type changed outside a post save (WP-CLI, a script) is not seen until the entry expires, as with `related_picks`; and each distinct query and page is its own entry here and in the front end's Data Cache, which a crawler can multiply. The front end's `/search/` is bounded at the edge: the Hobby plan's one Vercel Firewall rate-limit rule went to search ([issue #115](https://github.com/Colbitron/resource-hub-wp/issues/115), the owner's call, over [issue #48](https://github.com/Colbitron/resource-hub-wp/issues/48)), published in log mode as "Rate limit search", path regex `^/search(/.*)?$`, production only, 60 requests per 60 s per IP. It covers the front end's `/search/` and nothing else. The CMS's own `/wp-json/resource-hub/v1/search` is public and outside it, so a crawl straight at the CMS costs one uncached search per new (q, page), two queries for a page past the last, and one object-cache entry each. The anonymous response, a 400 included, carries the no-cache header like every route under `/resource-hub/v1/`.

## Redirects

**Rule: never send a permanent redirect a browser may keep.** Chromium gives a 301 or 308 with no cache header an infinite freshness lifetime, so with a stored redirect table and header-less 301s, webinar to podcast to webinar loops with `ERR_TOO_MANY_REDIRECTS`. Every redirect here is computed from the current state, sent in a single hop to a URL that answers 200, and carries a cache header.

- **From `proxy.ts`, decided from the path alone**, with `Cache-Control: no-store`: an upper-case letter in any segment, in any script (decoded, NFC, lower-cased, re-encoded in lower-case hex), a decoded escape of a character Next.js decodes in params, a repeated slash, and a trailing `/page/1/` on a listing. The rules are in `lib/canonical-path.ts`, and `lib/path-decision.ts` decides between this redirect, a [not-found rewrite](#not-found-pages) and nothing. The matcher is every `/resources/**` path, every other `/api/**` path but the revalidate route, any other path with an upper-case letter, a `%`, a `//`, a dot or a segment over 200 characters outside `/media/`, `/_next/` and the metadata files (the favicon, the icons and the share image), and any path over the page cap, so an ASCII canonical page path never runs it; a percent-encoded one does, through the `%` clause, and gets nothing back, since telling its escapes from ones the redirect fixes needs decoding. `test/proxy-matcher.test.ts` compiles the matcher as Next.js does and checks it reaches every path the decision acts on. The proxy never reads the data layer: its `fetch` is not the Data Cache's, and a CMS request there would reach the CMS on every matched request.
- **From the ISR pages, computed from data**, stored and cleared by events: a wrong type segment, an old slug, a wrong parent, the front page's own slug. Next.js sends a stored response with `s-maxage` alone, which a browser ignores, so a stored 308 would reach a browser with no freshness information. The `headers()` rule in `next.config.ts` / `lib/route-headers.ts` puts `public, max-age=0, must-revalidate` on every response of the resource page and the pages catch-all, the header Vercel's CDN sends browsers anyway; the listings keep Next.js's header, because their only redirects come from the proxy. The rule cannot vary by status, so the 200 and the 404 get it too.
- **Next.js's own trailing-slash 308** carries no cache header and is reached by neither the proxy nor the `headers()` rule. It needs none: `/path` to `/path/` is a function of the URL alone and never changes. A slashless non-canonical path takes two hops.
- **`/Resources/…`** is a case redirect to `/resources/…` since 2026-11-06; before that it was a 404 by design.

**The cache key.** Next.js stores a runtime ISR entry under `.next/server/route-cache/APP_PAGE/{route hash}/$/{decoded path}`: per route, but by the decoded path, so `/%41bout/` and `/About/` share a key, and on a case-insensitive file system (macOS, where the e2e suite runs) so do `/About/` and `/about/`. Measured on the pages catch-all with no proxy: a request for `/Company/` before any for `/company/` stored the 308 to `/company/` under that key, and `/company/` then redirected to itself. That is why the proxy runs on every path that can need a redirect, before any route. What Vercel keys on is unmeasured; with the proxy running first, it does not matter.

## Not-found pages

Every 404 has the site's not-found page (`app/not-found.tsx`) in its HTML, with status 404 and `noindex`, for a reader without JavaScript and for a crawler. There are two kinds, answered in two places.

- **Decided from the path alone, by `proxy.ts`.** A path no route could answer with anything but a 404 is rewritten to `/404` (`NOT_FOUND_ROUTE` in `lib/path-decision.ts`) with `status: 404` and the routes' `public, max-age=0, must-revalidate`, before any route runs and with no CMS request. Which paths is decided by the routes' own checks, so the two cannot disagree: outside the library, what the page catch-all refuses without a request (`pagePathProblem`: a dot or a non-slug in a segment, a reserved first segment, a path over the cap), except the front end's own routes there (`OWN_ROUTE_PATHS`) and everything under `/_next/` and `/media/`; under the library, a shape no route has (`parseResourcesSegments`), a listing the listing would refuse (`validListing`) and a resource whose type or slug segment is not a slug. The 404 is decided on the canonical form and wins over the redirect, so `/Robots.TXT` is one 404, not a 308 and then a 404. Under `next start`, `/404` is the pathname the server treats as its 404 page, answered with the prerendered not-found page and one route-cache entry shared by every junk URL. On Vercel, `/404` is the static `404.html` the Next.js builder writes from the same prerender, served from one CDN copy with no render and no entry per URL. **The status must be on the rewrite**: Vercel serves a rewritten response with the status the proxy's response carries, and a static file has none of its own, so without it the body is right and the status is 200, a soft 404. The junk path still costs a proxy invocation.
- **Decided by data, by the route.** An unknown slug, an unknown term, a page past the end or a path no page has: the decision (`resourceForRequest`, `pageForRequest`, the listing's checks) returns a not-found decision, and the page returns `<DataNotFound />` (`components/DataNotFound.tsx`), which throws `notFound()` inside its own Suspense boundary whose fallback is `components/NotFoundContent.tsx`, the content `app/not-found.tsx` renders. The server renderer writes the fallback into the HTML, Next.js's HTML error handler sets the 404 and adds `noindex`, and on hydration `app/not-found.tsx` takes the boundary's place. No route calls `notFound()` itself; `test/data-not-found.test.tsx` checks that nothing else in `app/`, `components/` or `lib/` does.

**Why the boundary.** Next.js renders `app/not-found.tsx` through a client error boundary, and React's server renderer (Fizz) runs no error boundaries: the only thing that catches a throw on the server is the nearest Suspense boundary. A `notFound()` with no Suspense boundary around it aborts the shell, and Next.js 16.4.5 then sends its error-recovery document, `<html id="__next_error__">` with an empty body and the not-found page only in the inlined RSC payload (`getErrorRSCPayload` in `next/dist/server/app-render/app-render.js` hard-codes that shell; [vercel/next.js#62228](https://github.com/vercel/next.js/issues/62228)). ISR stored that empty document for every reader.

**The boundary depends on ISR.** A boundary that fails after the shell has streamed leaves the status already sent, so in a route rendered per request the not-found page would arrive with a 200, a soft 404. An ISR route is rendered completely before it is answered or stored, so the status is set first and the stored entry keeps the 404 and the HTML. The routes therefore stay ISR (no `connection()`, no request-time API, here or in a layout or a component they import) for this as well as for their redirects. The unit tests read only the route files, so a request-time API in a layout or an imported component is caught only by the e2e suite.

**`generateMetadata` must not throw `notFound()`.** For a crawler Next.js counts as unable to run JavaScript (Bingbot, not Googlebot), metadata renders in the `<head>`, outside every boundary, so a throw there aborts the shell as before, and ISR stores that empty document for every reader of the URL. On a not-found decision it returns `NOT_FOUND_METADATA`, the not-found page's title; Next.js adds `noindex` itself.

**A client-side navigation** to either kind gets a 404 for its RSC request, which the router answers with a full document load (`fetchServerResponse` does that for any non-ok RSC response), and that load gets the 404 HTML.

`e2e/errors.spec.ts` pins both kinds under `next start`: JavaScript off and on, the first request and the stored one, a crawler asking first, and a client-side navigation. The suite never runs on Vercel, so the Vercel half is checked by hand on a preview ([deploy runbook](../runbooks/deploy.md#verifying-on-a-vercel-preview)).

## Lab notes

Everything below was measured under `next start` against the e2e mock CMS on Next.js 16.4.5, with `curl` and raw headers unless stated. Nothing has been measured on Vercel's CDN.

**2026-11-04, browser redirect caching.** A Playwright test across Chromium 156, Firefox 157 and WebKit 27.2: Chromium caches a header-less 308 indefinitely and fails the webinar to podcast to webinar round trip; with `no-store`, `no-cache` or a `max-age`, all three engines asked the server again. Engine source agrees: Chromium's `GetFreshnessLifetimes` gives 301 and 308 `TimeDelta::Max()` unless a header overrules it; Firefox gives 0 heuristic freshness without `Last-Modified`; WebKit gives a 301 365 days and a 308 zero, and drops redirects marked `no-store`, `no-cache` or `must-revalidate`.

**2026-11-05, how a redirect can be sent.** `permanentRedirect()` from a dynamic render is a 308 with `private, no-cache, no-store, max-age=0, must-revalidate`, stored nowhere. From an ISR route it is treated as a page: prerendered or rendered once, then served `HIT` with `s-maxage=3600, stale-while-revalidate=…` and no `max-age`, and cleared by the revalidation event through the entry's tags. Making only the redirecting render dynamic in an ISR route (`connection()`, a `no-store` fetch) is a 500 at runtime (`DYNAMIC_SERVER_USAGE`) for every path not prerendered, and `generateStaticParams` returning `[]` with `connection()` is a 500 on every request. A `permanentRedirect()` inside a Suspense boundary or under a `loading.tsx` is a 200 with a meta refresh. `proxy.ts` can set status and headers freely, but its `fetch` is not the Data Cache's: two proxy calls for one slug made two CMS requests. A Route Handler cannot share a segment with a page. A `headers()` rule in `next.config.ts` applies to every response of a path, keeps the route cache (`HIT`), and does not reach the built-in trailing-slash 308. Next.js normalises `params` before a page runs: `%e6%97%a5` arrives as `%E6%97%A5`, `%41bc` as `Abc`, `foo%2Dbar` as `foo-bar`; a malformed escape is a 500 before any page runs.

Per-request cost, 300 sequential loopback `GET`s each, mean and p95:

| Response | Mean | p95 |
|---|---|---|
| ISR 200, `HIT` | 0.83 ms | 1.00 ms |
| ISR 308, stored | 0.72 ms | 0.91 ms |
| Dynamic 200 rendered from the Data Cache | 1.62 ms | 2.39 ms |
| Dynamic 308 rendered from the Data Cache | 1.80 ms | 2.41 ms |
| Route Handler 308 | 0.91 ms | 1.15 ms |
| Proxy 308, no data | 0.44 ms | 0.55 ms |
| Proxy with the data layer, one CMS request each | 0.93 ms | 1.14 ms |
| Static page, no proxy / through the proxy | 0.48 ms / 0.61 ms | 0.61 ms / 0.73 ms |

The resource page was first built as a dynamic render (`force-dynamic`, `connection()`), the only mechanism measured that sends every redirect with `no-store`. It was reversed on 2026-11-06 because of what it costs on Vercel: a function invocation, a cold start and a region's time to first byte on every view, no CDN-cacheable HTML, and one uncached resolve request per page view for every unknown slug.

**2026-11-05, the proxy's cost** on the listings, the same build with `proxy.ts` present and removed: about 0.15 ms on every listing hit (0.42 to 0.61 ms mean for `/resources/`), a redirect in about 0.19 ms with no data read, and nothing on an unmatched route.

**2026-11-06, the resource page as ISR.** The wire headers of the route before and after:

| Response | Dynamic (before) | ISR, no rule | ISR with the `headers()` rule |
|---|---|---|---|
| 200, 308 and 404 | `private, no-cache, no-store, max-age=0, must-revalidate`, never stored | `s-maxage=3600, stale-while-revalidate=…`; `MISS` then `HIT` | `public, max-age=0, must-revalidate`; `MISS` then `HIT` |
| 500, `CmsError` | `no-store` | unchanged, never stored | unchanged |
| 308 from `proxy.ts` | `no-store` | unchanged | unchanged |

A freshly rendered ISR 308 (`MISS`) carries `location` twice with the same value and the stored copy once; the e2e helpers assert every `Location` agrees before reading the first. The build prerendered nothing then (it prerenders the bounded set since 2026-11-07; see "Prefetching" below). The pages catch-all got the same treatment the same day, measured in `e2e/pages.spec.ts`. The redirect, storage and 404 specs were also run once under WebKit: nothing about a redirect or a stored response differed.

**2026-11-06, the 404's HTML** (issue #46), under `next start` and on a remote-built Vercel preview, the first request and the stored one, with browser, Googlebot and Bingbot user agents. A data-decided 404 through `DataNotFound`: status 404, `<h1>Page not found</h1>` and `noindex` in the HTML, no `__next_error__`, a route-cache hit on the second request (`x-vercel-cache: HIT` on Vercel), the routes' `Cache-Control` unchanged, and no console error after hydration in Chromium; the 308s and 200s unchanged. Keeping `notFound()` out of `generateMetadata` alone, with the page still throwing outside a boundary, changed nothing: tried 2026-11-06 on the resource route under `next build` and `next start` against the mock CMS, an unknown slug was still a 404 with the empty `__next_error__` document, for browser and Googlebot user agents, on the first request and the stored one. The proxy's rewrite: under `next start`, an `x-nextjs-cache: HIT` on a junk URL never asked for before, where the catch-all's own 404 stored one entry per URL, and a response header of `s-maxage=31536000` alone unless the rewrite sets one; on Vercel, `x-matched-path: /404` and `x-vercel-cache: HIT` on the first request for a new URL. The App Router's `/_not-found` was the first target and was dropped: the same page under `next start`, but on Vercel a prerendered function route, rendered and stored once per junk URL (`x-vercel-cache: MISS`, a body that embeds the URL), with the proxy's 200 unless the status is set. Separately, a `loading.tsx` beside the ISR resource page left a wrong-type request a 308 with its `Location`, `MISS` then `HIT`, for a browser and for Bingbot, with the loading fallback and a meta refresh as its body; the 200 with a meta refresh above was the route when it was dynamic. Not measured on Vercel, and the route keeps the decision first with no `loading.tsx` regardless.

**Expected on Vercel, unmeasured.** The CDN should store the resource page, its 308 and its 404 as it stores a listing, purge them on `revalidateTag` and `revalidatePath`, and send browsers `public, max-age=0, must-revalidate` whether from the rule or from its own handling of `s-maxage`. The checks to run on a preview deployment are in the [deploy runbook](../runbooks/deploy.md#verifying-on-a-vercel-preview).

## Prefetching

What the client router fetches for a `<Link>` before it is clicked, and why the build prerenders a bounded set for it (ADR 0043, amended 2026-11-07). Measured 2026-11-07 on Next.js 16.4.5 under `next start` against the mock CMS, with Chromium driven over CDP: requests read off the wire with their `Next-Router-Segment-Prefetch` header and encoded size; a 412 × 915 mobile viewport unless stated; click latency from the click on the first row of `/resources/` until that resource's `h1` was rendered, under `Network.emulateNetworkConditions` at 150 ms latency and 1.6 Mbps down, seven and five samples, medians.

**The mechanism.** Next.js writes `.next/server/prefetch-hints.json` at build for every route with at least one prerendered path. When an ISR route is rendered at runtime with no entry there, `getMissingPrefetchHintPolicy` (`next/dist/server/app-render/create-transport-tree-from-loader-tree.js`) marks every segment of the response `PrefetchDisabled` (hint bit 1024), and the client skips those segments (`client/components/segment-cache/scheduler.js`). With every `generateStaticParams` returning `[]`, no route was in the manifest, so the library's row links were never prefetched. One prerendered path per route is what puts the route in the manifest; after that a path that was never prerendered gets ordinary hints too.

| Build | Prerendered pages | RSC requests on a cold `/resources/` load | Rows prefetched (of 12) | Bytes per row | Click, library to resource, throttled |
|---|---|---|---|---|---|
| Nothing prerendered (before) | 11, none from the CMS | 4 route trees for the topic links, about 0.7 KB each | 0 | 0 | median 454 ms (448 to 462, 7 samples) |
| The bounded set (after), route prediction on | 32: the root, the library, 5 type listings, 14 resources | 18 before a scroll, 42 after: a route tree and a page segment per row and per type link, on the loads that won the race below; 404s on the loads that lost it | 2 before a scroll, 12 after; the same at 1280 px; or 0 | about 5.9 KB: a 0.7 KB route tree and a 5.1 KB page segment (7.4 KB for the long-form resource) | median 64 and 67 ms (55 to 74, two runs of 7 and 5) |
| The bounded set, route prediction off (shipped) | 32 | 22 before a scroll, 43 after; no 404 in three cold loads | 2 before a scroll, 12 after | about 5.9 KB | median 61 ms (56 to 65, 7 samples) |

**The catch-all's prediction is a race, and route prediction is off.** From `/resources/`, served by `app/resources/[[...rest]]`, the router's optimistic routing (`experimental.optimisticRouting`, on by default) learns the library's tree from its own `/_tree` response (`{"n":"rest","t":"oc","k":"","s":["page","topic"]}`: the catch-all, with `page` and `topic` as its static siblings) and from then on predicts any link under `/resources/` whose first segment is not `page` or `topic` as a path of that catch-all (`matchKnownRoute` in `segment-cache/optimistic-routes.js`), so a row's or a type listing's page segment is requested under `/resources/$oc$rest/__PAGE__`, which the server answers 404. Whether a load does this depends on whether that tree response has arrived before the links' prefetch tasks create their route entries (`readOrCreateRouteCacheEntry`, `segment-cache/scheduler.js`): on the first cold load measured, every row fetched its own `/_tree` and `/resources/$d$type/$d$slug/__PAGE__` segment and nothing was fetched as the catch-all's; on a later load of the same build, seven requests (five type links and the two visible rows) went out under `$oc$rest` and came back 404, as console errors, with nothing prefetched for them, which `e2e/brand.spec.ts` caught. The flag only controls whether the server sends each dynamic segment's static siblings and the client predicts from them, so it is set to `false` in `next.config.ts`: every link asks the server for its own tree (about 0.7 KB) and prefetches the right segments on every load, measured over three cold loads with no 404 and a click median of 61 ms (56 to 65, 7 samples). `e2e/prefetch.spec.ts` fails on any request under the catch-all's key and on any prefetch that is not a 200.

**A route's CSS is its module graph's.** The first version of the probe module imported `loadListing` from `components/ListingPage.tsx`, and every route importing the probes then carried the listing's stylesheets (`listing.css`, `card.css`, `lead.css`) inlined in its HTML whether or not it rendered them: the resource page went from 13,354 to 16,384 bytes gzipped, over the 14,600-byte first round trip that `e2e/document-size.spec.ts` holds every image-led page to unless the owner has exempted it, for content that is wanted (the spec's docblock has the rule). The reads live in `lib/listing-data.ts`, with no CSS import, and the component imports them from there.

**The build.** Three warm builds each, the fetch cache cleared before every build, the mock answering: 2.79, 2.26 and 2.21 s before (11 static pages, 0 CMS requests); 2.84, 2.30 and 2.30 s after (32 static pages, 39 CMS requests: the probes' lists and term lookups, one slug lookup per resource, and the page lookup for `/`; the renders made none of their own). Against a CMS with five full types the same probes make up to about 140 requests, from every build that can reach it, Vercel previews included. Against `https://cms.example/wp-json`, which never resolves: 2.39 s, 11 static pages, four warnings `prerender {route}: nothing prerendered at build, so each path renders on its first request; CMS request to … failed: network error ENOTFOUND`. A hung CMS costs at most the data layer's 10 s per request and each probe's budget; a CMS that answers each request slowly costs at most the budgets, 10 s for each of three routes and 30 s for the resource route, about 60 s in all, and the resource route keeps the candidates decided by then.

**The fetch cache is emptied before every build.** `next build` keeps `.next/cache/fetch-cache` between builds and Vercel restores it from its build cache, and a second build with it present made no CMS request: the probes and the renders read the previous build's answers. Worse, a stale entry (older than the hour) is served to `generateStaticParams`, which runs in a work unit that does not wait for fresh data, while the render that follows refetches it in the foreground. Measured 2026-11-07: a build with the mock up, every entry in that directory aged two hours with `touch`, the mock stopped and the same `WP_API_URL`: the probes answered from the stale copies and named every path, every render then failed with `CmsError … ECONNREFUSED`, and `next build` exited 1 ("Export encountered an error on /resources/[type]/[slug]/page … exiting the build"). With `WP_API_URL` pointed at another port the cache is never hit, since the URL is part of the key, so that repro does not show it. The `build` script therefore runs `scripts/clear-fetch-cache.mts` before `next build` (CI, Vercel through `buildCommand` in `vercel.json`, and the harness all build through it): the same repro then prerenders nothing, with the four warnings, and exits 0. The harness runs the script again between the build and `next start`, for the tag marks (`e2e/README.md`).

**A param is decoded.** Next.js `encodeURIComponent`s each `generateStaticParams` value and keys the page by the decoded path. Passed as WordPress stores it, a resource slugged `%e6%97%a5%e6%9c%ac-guide` was written to `.next/server/app/resources/article/%e6%97%a5%e6%9c%ac-guide.html` and its own URL was a `MISS` while the decoded path `/resources/article/日本-guide/` was a `HIT`; decoded (`paramValue` in `lib/prerender.ts`) it is written as `日本-guide.html` and both forms are a `HIT` on their first request (measured 2026-11-07 against the mock, the slug published through its control endpoint before the build).

## Known costs

- **Any resource event re-renders every stored listing.** Each listing renders the filter bar, whose two taxonomy lists carry `resources` as well as `terms` so each term's count stays right. A `publish` of one webinar marks every stored listing stale, not only the ones it is on. The re-render is cheap, since the listing fetches of untouched listings keep their own tags and stay cached. If it ever shows in function time, the fix is to split the term-count lists from `resources`.
- **Every distinct junk path stores its own 404.** A 404 from a listing, the resource page or the pages catch-all is stored for up to the interval like a 200, and each costs one CMS lookup first. Only a path the proxy can rule out from its shape (a dot, a reserved segment, a non-slug) escapes that, through the [rewrite](#not-found-pages). A crawler or an attacker can mint unlimited distinct paths, each a stored entry and a CMS request. The bound belongs at the edge, a Vercel Firewall rate-limit rule, not in the app: a 404 decided without a request is stored all the same. Tracked in [issue #48](https://github.com/Colbitron/resource-hub-wp/issues/48); the Hobby plan's one rate-limit rule went to search instead ([below](#the-search-results-on-the-cms)), so this one waits for another plan or another bound.
- **The search page renders on every request.** It is the one dynamic route, so each request is a function run and nothing is stored at the edge (measured on a Vercel preview). Its reads are expected to come from the Data Cache, so that a repeated query costs a render and no CMS request and each distinct query and page one CMS search and one Data Cache entry; that is measured under `next start` and not yet on Vercel. A crawler minting queries is bounded only by the "Rate limit search" rule, which is in log mode until it is switched to deny ([The search page](#the-search-page)).
- **Search at the CMS origin is unbounded.** The "Rate limit search" rule covers the front end's `/search/` only. `/wp-json/resource-hub/v1/search` is public, so a crawl straight at the CMS costs one uncached search per new (q, page), plus a one-row count query for a page past the last with results, and one object-cache entry each ([The search results on the CMS](#the-search-results-on-the-cms)).
- **The first request to a cleared page waits for the CMS.** `{ expire: 0 }` makes the next request a miss that waits for fresh data, chosen so a removal never serves one more stale render.
- **A data-decided 404's HTML rests on Next.js internals.** `DataNotFound` depends on Next.js 16.4.5's HTML error handler setting the 404 from a `notFound()` caught by a Suspense boundary; an upgrade that changes that breaks it, and the status and `<h1>` assertions in `e2e/errors.spec.ts` are what catch it. When a release renders the not-found boundary into the recovery document itself (vercel/next.js#62228; #98583 and #100606 propose fixes, none in stable 16.4.5 or canary 16.5.0-canary.42), a plain `notFound()` from the page would do and `DataNotFound` can be retired; the e2e suite passes either way, so check the release notes on each upgrade.
- **A REST-lockdown plugin would turn by-ID reads into 404 pages.** A by-ID read treats a 401 as a miss, so if a plugin on the CMS answered anonymous REST reads with 401, every page that reads by ID would become a 404, while list and slug reads would throw and fail loudly.
- **A `related_picks` change made outside a save lasts up to a day.** `update_post_meta()` from WP-CLI or a script fires no `wp_after_insert_post`, so it sends no revalidation event and does not bump the related cache's salt; the old list is served until the entry expires or another bump turns the salt over.
- **Between the CMS deploy and the front-end deploy**, a page change reaches the front end through the hourly interval only when the front end cannot yet read a new event type; additive changes have no gap.
