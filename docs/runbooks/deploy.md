# Deploying, rolling back and rotating secrets

For the maintainer deploying the CMS or the front end, rolling either back, or rotating a secret. The decisions are [ADR 0005](../adr/0005-hosted-wordpress-on-cloudways.md) (the host), [ADR 0051](../adr/0051-front-end-production-deploys-through-a-vercel-deploy-hook.md) (the front-end deploy) and [ADR 0053](../adr/0053-ci-runs-on-depot-ci.md) (CI on Depot CI); the workflow is `.depot/workflows/ci.yml`, run by Depot CI, whose comments explain each step. A run's state, logs, job summaries and artifacts are read with `depot ci status <run-id>`, `depot ci logs <attempt-id>`, `depot ci summary` and `depot ci artifacts list <run-id>`, or in Depot's dashboard.

## How a deploy happens

Nothing is deployed by hand. A push to `main` runs the gate on Depot CI, then the `deploy` job syncs the plugin, Relevanssi and the CMS theme to the Cloudways host and activates them, then the `deploy-web` job starts the front end's Vercel production build. The CMS goes first and the front end second, so the front end never goes live ahead of the CMS it reads; additive contract changes make that order safe. The CMS deploy needs only the CMS gate, so a front-end failure never blocks a CMS deploy or a rollback. Pull requests and other branches never deploy; pull requests get Vercel preview deploys.

## Which jobs a pull request runs

A push to `main` and every plain dispatch run every job; only a pull request is scoped, and only a rollback dispatch skips the front-end jobs, by a clause of its own ("Rolling back", below). Its first job, **Scope: the jobs this change needs**, diffs the merge commit Depot checks out against the base (`.depot/scripts/ci-scope.mjs`, whose tests run in the same job) and decides from the changed paths, renames counted at both ends:

| The pull request changes | Runs | About |
|---|---|---|
| only `wp-content/` (and inert paths) | the plugin's gate | 3.1 sandbox-minutes |
| only `apps/` (and inert paths), but for the two files below | the front-end jobs | 3.6 |
| `packages/`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.wp-env.json`, `.depot/`, `.gitignore`, `apps/web/e2e/browser-container.mts` or `apps/web/e2e/playwright-image.mts` (the pinned screenshot container, which the plugin's Playwright imports for the CMS theme's baselines; `PLUGIN_IMPORTS` in `ci-scope.mjs`), any other path, or both `wp-content/` and `apps/` | the plugin's gate and the front-end jobs | 6.9 |
| only inert paths: `docs/`, `.claude/`, `.github/`, `tools/`, a Markdown file at the root | nothing but the scope job and `CI result` | 0.1 |

**No pull request runs Lighthouse**, whatever it changes: the five `web-lighthouse` shards and `web-lighthouse-medians` show as skipped on every pull request and run on every push to `main` and every dispatch, which take about 17.9 sandbox-minutes with them ("CI cost", below). So a broken Lighthouse harness, unlike every other failure, first shows up on `main`, where it holds `deploy-web` back until a fix lands; the CMS deploy still goes ahead. In their place, before pushing a pull request that changes `apps/` (other than Markdown) or `packages/ui/`, the author runs `pnpm web:test:lighthouse:quick` and reads the medians, as part of the local gate before the push: a smell test on the author's machine, not a gate, with the full five-run `pnpm web:test:lighthouse` for a big change (`apps/web/e2e/README.md`, "Lighthouse CI"). `main`'s five-run medians are the measurement of record.

A skipped job shows as skipped in `depot ci status`, not as passed or failed; the pull request's checks list it as skipped too. PR #144, which changed only README files, lists eleven `CI /` checks as skipped (the three front-end jobs, the five Lighthouse shards, their medians and both deploys) beside a green `CI / CI result`. When the scope job cannot read the paths for certain, its summary says why and every job runs; if it fails, every job behind it but `CI result` is skipped, and `CI result` and the run are red. Neither deploy can run behind a skipped job, and on `main` no job is skipped (the reasoning is in `ci.yml`, above the triggers). To run a job a pull request skipped, Lighthouse included, the whole workflow can be run by hand on the branch, `depot ci run --workflow .depot/workflows/ci.yml`, which is event `api`, never scoped; there a Lighthouse budget miss fails its shard, as on any event but a push or dispatch on `main`.

**The check the ruleset on `main` requires is `CI / CI result`**, the `ci-result` job, and no other. Depot reports each job to GitHub as a check run named `CI / <job name>`, published by the Depot Code Access app (`depot-code-access`), and GitHub documents a check run that concluded `skipped` as passing, so requiring a scoped job's check would let through every pull request that skipped it, the gate's included. `ci-result` needs the scope job, the gate and the three front-end jobs that run on a pull request, always runs, and leaves the verdict to `.depot/scripts/ci-result.mjs`, deny by default: the scope job must have succeeded, and each other job must have succeeded, except that on a pull request a job may be skipped when the scope job's output for its side, `plugin` for the gate and `web` for the front-end jobs, is `false`. A failed or cancelled scope job, a skip the outputs do not explain, or any skip off a pull request makes it red. It does not read Lighthouse, which never runs on a pull request, or the deploys. A new job goes in its `needs` (and the script's `JOBS`) or in the exempt list in `ci-scope.test.mjs`, whose test fails the scope job, and so `CI result`, until it does. The script's pull-request paths are tested in `ci-result.test.mjs`, which the scope job runs, since a `depot ci run` is never a pull request.

**The ruleset pins the check's source to the `depot-code-access` app**, so a check of the same name from anything else cannot satisfy it. Depot offers extra check-publishing apps, Depot Checks, Depot Checks 2 and Depot Checks 3, for organizations that reach GitHub's API rate limits; they publish the same check names, so with a pin in place a check one of them published would block the merge. Do not connect them while the pin stands (<https://depot.dev/docs/ci/observability/github-checks>, read 2026-11-07). The check means only what the workflow behind it says: Depot runs a pull request's own copy of `ci.yml` and `.depot/scripts/`, so a pull request can change `ci-result` itself, and the required check is worth something only with the owner's review of every change under `.depot/`. A cancelled run's `CI / CI result` concludes `cancelled` or `failure`, never green, so a cancelled run blocks the merge until it is re-run.

A new top-level path runs everything until a rule in `ci-scope.mjs` says otherwise; add the rule, and its case to `ci-scope.test.mjs`, in the pull request that adds the path. A plugin spec that imports another file under `apps/` fails `ci-scope.test.mjs`, which follows the plugin's imports into `apps/`, until the file is in `PLUGIN_IMPORTS`.

### Preview Lighthouse

`.depot/workflows/preview-lighthouse.yml` measures a pull request's Vercel preview and posts one comment on it, blocking nothing (`apps/web/e2e/README.md`, "The design gates"). It runs on Depot CI on GitHub's `deployment_status` event, which Vercel sends for the GitHub Deployments it creates. Its first job, **Find the pull request and whether it reaches the front end**, takes a successful, non-production status from `vercel[bot]`, finds the open pull request whose head is the deployed commit, lists that pull request's files through GitHub's pull request files API and classifies them with `ci-scope.mjs --pr-files`, the same rules as the table above. The second job, **Measure the preview**, runs only when the `web` side is reached, or when the list is incomplete or unreadable, so in doubt it measures: a pull request that changes only `wp-content/` or inert paths posts nothing, spends about 4 seconds, and keeps any earlier comment as it was.

The comment is the Depot Code Access app's (`depot-code-access[bot]`): Depot's `github.token` is that app's installation token, and the app holds `pull_requests: write` and `issues: write` (`gh api apps/depot-code-access`, read 2026-11-07; Depot's compatibility page, <https://depot.dev/docs/ci/compatibility>, "Permissions", says the installation must grant what a job's `permissions` ask for). That page does not say the token is narrowed to what a job asks for, and the app also holds `contents: write`, `workflows: write`, `actions: write` and `secrets: read`, so until the check below has run, assume either job's token may carry all of them. Each job asks only for what it uses; the token is passed by name only to the steps that call GitHub's API, the checkouts leave none in `.git/config`, and lhci and Chrome never get it. A pull request that already has the comment `github-actions[bot]` left while the workflow ran on GitHub Actions gets a second one, which later previews edit.

**The trial, 2026-11-07: run f4q02z8k5s.** `depot ci run` reports event `api` and carries no `deployment_status` payload, so the trial ran the workflow with three temporary edits, removed before the commit: the first job's `if:` was `github.event_name == 'api'`, and the deployed commit and preview URL were PR #98's head (`a162a677`) and the `environment_url` of its Vercel deployment's success status, read with `gh api repos/Colbitron/resource-hub-wp/deployments/<id>/statuses`. Everything else ran as written: the lookup found #98, the files API listed its 38 files and `web=true`, all eight URLs were measured five times, every one of the 40 uploaded reports had the header redacted, every run's one foreign request was `vercel.live`, blocked, and the comment was posted on #98 by `depot-code-access[bot]`. The first job took 4 s and the measurement 8 min 15 s. The same classification run locally on merged PRs #92 (plugin only) and #95 (docs only) gave `web=false`.

**What the first real event must show**, on the first pull request after the merge whose preview deploys: a Preview Lighthouse run in `depot ci run list` with trigger `deployment_status` (if none appears, Depot is not receiving the event, and nothing else is wrong); the first job's log line `Deployed commit <sha>; this workflow runs from <sha>`, which says which commit's copy of the workflow Depot runs (GitHub runs the deployed commit's; Depot's docs do not say); and, for a front-end pull request, the comment edited or posted by `depot-code-access[bot]`, or, for a plugin-only or docs-only one, the measure job skipped and nothing posted. Until then the trigger, its payload fields (`deployment.sha`, `deployment.environment`, `deployment_status.environment_url`, `deployment_status.creator.login`) and the per-pull-request concurrency group are unexercised on Depot. Three more checks, once:

- **The log masks the secret.** In the measure job's log (`depot ci logs <attempt-id>`), the step environment shows `VERCEL_PROTECTION_BYPASS` as `***`, if Depot prints step environments as GitHub does, and a count-only search for the value finds nothing: with the value in the shell's environment as `VERC_DEP_PROT` (from wherever it is kept, never typed on the command line), `depot ci logs <attempt-id> | grep -cF -e "$VERC_DEP_PROT"` prints `0`. If the host does not mask, the outputs are still guarded: the reports are redacted and searched for the secret before they are written, and the comment before it is posted; only the log would need the workflow's own `::add-mask::`, which it already sends. The canary probe saw Depot mask secret values as `***` ("How Depot matches a variant", below); this check confirms it for this job's log.
- **The token is narrowed to the job's `permissions:`.** First look for a token-permissions listing in the job's setup log, as GitHub prints under "Set up job"; if Depot prints one, that settles it. Otherwise run one temporary step at the top of the `pr` job, with `env: GH_TOKEN: ${{ github.token }}`, through `depot ci run` as the trial did (an `api` run's token is the same app's; a real event's run would answer more exactly), and remove it after: `gh api -i "repos/$GITHUB_REPOSITORY/actions/secrets?per_page=1" | grep -iE '^HTTP/|^x-accepted-github-permissions:' || true`. It reads (secret names only, and `grep` keeps even those out of the log) an endpoint that needs `secrets: read`, which the app holds and the job does not ask for. `-i` prints the response's headers, never the request's, so the token is not printed. A `200` means the token is not narrowed and carries the app's whole installation; a `403` with `X-Accepted-GitHub-Permissions: secrets=read` means it is narrowed (GitHub's "Troubleshooting the REST API" documents the header). An installation token has no scopes to read, so `X-OAuth-Scopes` says nothing here. If it is not narrowed, record it here and in the workflow's header, and weigh it with "What a pull request can reach", below.
- **Two pull requests' previews at once do not cancel each other.** The measure job's concurrency group is the pull request's number, with the deployed commit as a fallback should Depot evaluate `needs` there as empty; two front-end pull requests deploying together should both get their comment.

### CI cost

The figures behind ADR 0053's "Cost". Depot's Developer plan is about $20 a month and includes 2,000 sandbox-minutes a month at 2 vCPU, shared with Depot's other sandbox products; past that it is $0.006 a minute for 2 vCPU, billed per second (<https://depot.dev/pricing>, read 2026-11-07; confirm there before relying on it).

**A run's sandbox-minutes**, the sum of its jobs' times (`depot ci workflow show <workflow-id>` lists each):

| Run | Sandbox-minutes | Trial run |
|---|---|---|
| Every job: a push to `main`, a dispatch, a `depot ci run` | 17.9: the measured 17.8 of run zkp83r7b3s, plus CI result's 0.07 (4 s). Its parts, each rounded and so not summing to the total: the five Lighthouse shards and the medians 11.1 (664 s), the gate 3.2, end-to-end 2.1, screenshots 0.8, checks 0.7, scope 0.05 | zkp83r7b3s; CI result 6nc6zbxd7m |
| A pull request reaching both sides, or a shared path | 6.9: the same run without Lighthouse | zkp83r7b3s |
| The front end alone | 3.6 | clmqq17s1c |
| The plugin alone | 3.1 | fxprsxt9wx |
| Documentation alone | 0.1: the scope job 0.05, CI result 0.07 | |

**The pull-request mix.** The 56 pull requests merged 2026-11-05 to 2026-11-07, Pacific time, classified by these rules: 26 both, 9 plugin, 17 front end, 4 neither. Weighted, (26 × 6.9 + 9 × 3.1 + 17 × 3.6 + 4 × 0.1) / 56 = 268.9 / 56, about 4.8 sandbox-minutes a pull request.

**A month at the pace of the four days before the move**: about 1,500 runs (`gh run list`), 28% of them pushes to `main`, so about 420 full runs and 1,080 pull-request runs.

| Rules | Sandbox-minutes a month | Cost a month |
|---|---|---|
| These: pull requests scoped by path, Lighthouse off them | 420 × 17.9 + 1,080 × 4.8 ≈ 12,700 | (12,700 − 2,000) × $0.006 ≈ $64, $84 with the plan |
| Lighthouse scoped by path like the other jobs, on the 43 of 56 pull requests that reach the front end: (268.9 + 43 × 11.1) / 56 ≈ 13.3 a pull request | 420 × 17.9 + 1,080 × 13.3 ≈ 21,900 | ≈ $119, $139 with the plan |
| Every job on every run | 1,500 × 17.9 = 26,850 | ≈ $149, $169 with the plan |

Most of what remains is `main`'s full runs, and each parallel job bills its own setup, so sharding buys a shorter wait with more billed minutes.

**Preview Lighthouse** runs once per preview, about once per pull-request run: its first job, about 4 s (0.07 sandbox-minutes), on every one, and the measurement, 8 min 15 s (8.25) in run f4q02z8k5s, on the 43 of 56 that reach the front end. Cancelled runs, when a newer preview of the same pull request supersedes one, are counted as whole.

| Preview Lighthouse | Sandbox-minutes a month | Cost a month, on top of CI's |
|---|---|---|
| Front-end pull requests only, as built: 0.07 + 43/56 × 8.25 ≈ 6.4 a pull-request run | 1,080 × 6.4 ≈ 6,900 | ≈ $41, so ≈ $126 in all with the plan |
| Every pull request: 0.07 + 8.25 ≈ 8.3 | 1,080 × 8.3 ≈ 9,000 | ≈ $54 |

At four runs a day in the same mix, a month stays within the plan's included minutes, Preview Lighthouse included: about 34 full runs × 17.9 + 86 pull-request runs × (4.8 + 6.4) ≈ 1,570.

## Secrets

Six secrets feed the two deploy jobs, and a seventh the Preview Lighthouse workflow. None is in git. All seven are Depot CI secrets (`depot ci secrets list --repo Colbitron/resource-hub-wp` shows the names, never the values).

- **The six deploy secrets are scoped to `main`** (set 2026-11-08). Each has one variant, `colbitron-resource-hub-wp`, with the attributes `repository=colbitron/resource-hub-wp` and `branch=main`, and no repository-wide variant.
- **`VERCEL_PROTECTION_BYPASS` is scoped to the repository alone**, because Preview Lighthouse reads it on pull requests ("What a pull request can reach", below).

To check a secret's variants, names and attributes only:

```sh
depot ci secrets list <NAME> --repo Colbitron/resource-hub-wp --output json | jq -r '.secrets[].variants[] | "\(.name) \([.attributes[]? | "\(.key)=\(.value)"])"'
```

None of the seven is a GitHub repository secret: CI and the deploys run on Depot (ADR 0053), so their GitHub copies were deleted, `VERCEL_PROTECTION_BYPASS`'s included, since nothing on GitHub Actions reads it now. A rollback of CI to GitHub Actions sets them there again first ("Rolling CI back to GitHub Actions", below).

| Secret | Holds |
|---|---|
| `DEPLOY_SSH_KEY` | Private half of a key used only for deploys |
| `DEPLOY_HOST` | SSH hostname or IP of the server |
| `DEPLOY_USER` | SSH user |
| `DEPLOY_PATH` | Absolute path of the plugin directory itself, ending in `wp-content/plugins/resource-hub-wp`; the job refuses anything else, because `rsync --delete` into the wrong directory would remove other plugins. Relevanssi's target, `wp-content/plugins/relevanssi` beside it, and the theme's, `wp-content/themes/resource-hub` under the same WordPress root, are derived from the same checked value |
| `DEPLOY_KNOWN_HOSTS` | The server's pinned host key line or lines, so the sandbox never trusts on first use |
| `VERCEL_DEPLOY_HOOK_URL` | The Vercel project's deploy hook for `main`; the URL is the credential |
| `VERCEL_PROTECTION_BYPASS` | The Vercel project's deployment protection bypass secret (Vercel env var `VERC_DEP_PROT`), sent as `x-vercel-protection-bypass` by `.depot/workflows/preview-lighthouse.yml` to reach a pull request's preview; nothing else reads it |

The CMS's own configuration (`RESOURCE_HUB_FRONTEND_URL`, `RESOURCE_HUB_REVALIDATE_SECRET`, and the optional `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST`) is `define()`d in the host's `wp-config.php`. The front end's (`WP_API_URL`, `REVALIDATE_SECRET`, `SITE_URL`, optionally `WP_MEDIA_ORIGIN`) lives in the Vercel project's environment variables; `apps/web/README.md` describes each.

**How Depot matches a variant.** From a canary probe on 2026-11-07, throwaway pull requests #104 and #105:

- `--branch` is matched against a pull request's head branch, never its base. A `branch=main` variant was hidden from both pull requests.
- A pull request from a branch named `rollback-probe-2` received a `rollback-*` variant. Never add a branch pattern for rollback: any branch that matches it gets the deploy secrets.
- A repository-and-branch variant beats a repository-only one.
- A run that matches no variant gets an empty string.
- Depot masks the values in logs as `***`.

**Pull requests from forks do not run on Depot CI.** <https://depot.dev/docs/ci/compatibility> (read 2026-11-08) lists "Pull request workflows triggered from forks" as unsupported: "Support for this is planned." The same page, on review and review-comment events, says "Runs for pull requests from forks get a read-only GITHUB_TOKEN and no secrets." Check that page again when fork support lands.

**What a pull request can reach.** Depot CI runs the workflow as the pull request has it, so a pull request that edits the workflow can read any secret its run is given. The deploy secrets are not given to a same-repository pull request: their only variant is scoped to `main`, and a same-repository pull request's head is never `main`. A fork's pull request from the fork's own `main` would have head branch `main`, and Depot matches the head branch; what keeps the deploy secrets from it is that Depot does not run fork pull requests today. If Depot ever gives fork runs secrets, `branch=main` alone stops protecting them, and the scoping needs rethinking. What remains:

- **The bypass secret.** `VERCEL_PROTECTION_BYPASS` stays repository-wide on purpose: `.depot/workflows/preview-lighthouse.yml` reads it on pull-request previews. Now that the repository is public, a same-repository pull request could read it. It only unlocks Vercel's protected previews of code that is public anyway, so that is accepted.
- **The cache.** Depot Cache is not isolated by branch (Depot documents that for its GitHub Actions runners; it is assumed for Depot CI), so a same-repository pull request whose workflow saved a cache entry could write a key that `main`'s runs then restore, and the deploy builds from what it installs. The only collaborator is the owner, so this is accepted.
- **The ruleset.** The ruleset `main` (id `26828944`) has been active on the default branch since 2026-11-08, when the repository went public, with no bypass actors. It blocks deleting `main` and force-pushing to it, requires a pull request with 0 approvals, and requires `CI / CI result` alone, from the `depot-code-access` app (integration 219785). Why that check, why that app and what a pull request can still change behind it are in "Which jobs a pull request runs", above. PR #145 merged under it with that check green from `depot-code-access`, so the ruleset counts the check runs Depot publishes; a merge blocked by a red or missing check has not been seen yet. Check it with `gh api repos/Colbitron/resource-hub-wp/rulesets/26828944` and `gh api repos/Colbitron/resource-hub-wp/rules/branches/main`. The repository also has secret scanning with push protection, Dependabot alerts, approval of workflow runs on pull requests from all external contributors, and read-only default workflow permissions.

## The cutover switch, `DEPOT_DEPLOY_ENABLED`

Both deploy jobs also require the Depot CI variable `DEPOT_DEPLOY_ENABLED` to be `true`. It kept Depot's trial runs from deploying while GitHub's copy of the workflow still did, and while it is unset nothing on Depot CI reaches the host or Vercel, whatever the event or ref: the two jobs report as skipped.

**At the cutover**, in this order:

1. Merge the pull request that deletes `.github/workflows/ci.yml` with the variable still unset. The merge's push to `main` is then the first push run on Depot CI: it exercises the gate and saves the caches from `main`, and its two deploy jobs report as skipped.
2. Once that run is green, set the variable: `depot ci vars add DEPOT_DEPLOY_ENABLED --repo Colbitron/resource-hub-wp --value true`, and check it with `depot ci vars list --repo Colbitron/resource-hub-wp`.
3. Start the first Depot CI deploy by hand and watch it to the end: `depot ci dispatch --repo Colbitron/resource-hub-wp --workflow ci.yml --ref main`, then `depot ci status <run-id>` until both deploy jobs finish.

Before the merge, Depot CI ran one `pull_request` run, from PR #98's own copy of the workflow before it was scoped: run 8bt9mr07zz (`depot ci workflow show 2z7chvtrxv`: trigger `pull_request`, ref `refs/pull/98/merge`), so the merge ref the scope job diffs is confirmed. Every other trial was a `depot ci run` of local files, event `api`. The scoped `pull_request` path (the check names on the pull request, the Lighthouse jobs skipped, and the scope job's use of `github.event.pull_request.head.sha`) is first exercised by the first pull request run of the scoped workflow; check that run's jobs and checks, and that the scope job's summary lists the changed paths rather than "Every job runs: no pull request head SHA", which would mean Depot left the head SHA out and nothing is being scoped.

**Afterwards**, a follow-up pull request drops the variable's line from both jobs' `if:` and then the variable (`depot ci vars remove DEPOT_DEPLOY_ENABLED --repo Colbitron/resource-hub-wp --force`). Until it lands, removing the variable is the quickest way to stop Depot CI deploying.

## Rolling CI back to GitHub Actions

If Depot CI has to be left (ADR 0053, "Rollback"):

1. Relax the ruleset on `main` first (the repository's Settings, Rules, or `gh api repos/Colbitron/resource-hub-wp/rulesets`): it requires `CI / CI result` from `depot-code-access`, which a run on GitHub Actions never publishes, so until it changes no pull request can merge, the rollback's own included. Remove the requirement, or require a check the restored workflow publishes from `github-actions`, and restore it if CI comes back to Depot.
2. Unset the switch, `depot ci vars remove DEPOT_DEPLOY_ENABLED --repo Colbitron/resource-hub-wp --force` (`--repo` selects the repository's variant; `--force` skips the confirmation prompt), so Depot CI deploys nothing while both run. This works only while the jobs still test it; after the follow-up, delete `.depot/workflows/ci.yml` in the same pull request as step 3 instead.
3. In a pull request, restore `.github/workflows/ci.yml` from git, and `screenshot-baselines.yml` and `preview-lighthouse.yml` if they are wanted. The files were deleted in different commits, so restore each from the parent of the commit that deleted it, one file at a time: `git log --diff-filter=D --format=%h -- .github/workflows/<file>` names that commit, and `git checkout <that commit>~1 -- .github/workflows/<file>` brings the file back. `ci.yml` and `screenshot-baselines.yml` were deleted together (`61c4d2aa`, "Retire GitHub Actions' CI"), `preview-lighthouse.yml` later, when it moved to Depot CI ("Run Preview Lighthouse on Depot CI"). Restoring `preview-lighthouse.yml` also means deleting `.depot/workflows/preview-lighthouse.yml` in the same pull request, so only one comments, and setting `COMMENT_AUTHOR` in `apps/web/e2e/lighthouse-preview-summary.mts` back to `github-actions[bot]`. Step 2 is what keeps the two from both deploying.
4. Before the merge, set the six deploy secrets again as GitHub repository secrets, the five `DEPLOY_*` and `VERCEL_DEPLOY_HOOK_URL`: their GitHub copies were deleted, so without them the restored deploy jobs run with empty values. With `preview-lighthouse.yml` restored, set `VERCEL_PROTECTION_BYPASS` there too; its GitHub copy was deleted as well. `gh secret set <name>` prompts for each value; `gh secret list` shows which exist. GitHub repository secrets have no branch scope, so on GitHub Actions a pull request that edits the workflow can read them again. Also make sure the account has Actions minutes left: if the limit is reached, GitHub refuses the restored workflow's jobs until it resets or the budget is raised.
5. Merge; the push to `main` runs and deploys on GitHub Actions.

## The CMS deploy

The `deploy` job runs only after the gate passes, only for a push to `main` or a manual `workflow_dispatch` on `main`; no other ref deploys. A dispatch with the `rollback_sha` input deploys that earlier commit of `main` instead of `main`'s head, after the gate has run on it ("Rolling back", below). One deploy runs at a time and a running deploy is never cancelled; a waiting run is replaced by a newer one, which is safe between pushes because the newer commit includes the older. It is not safe around a rollback: a rollback dispatched while a push's run waits replaces that run, and nothing re-runs it, so the merged commit is neither gated nor deployed until the next push; after a rollback, check whether a push was waiting and dispatch `main` again if one was ("Rolling back", below). Whether Depot replaces waiting runs as GitHub documents is unconfirmed.

From a fresh checkout it builds the block and the theme's `build/`, runs `composer install --no-dev` in the plugin directory (in a container; see [Composer in a container](#composer-in-a-container)), and rsyncs that directory over SSH into the plugin directory on the host with `--delete-delay --delay-updates`, so changed files swap in together at the end and stale ones are removed after. The rsync is an allowlist: the host receives `resource-hub.php`, `src/`, `build/` and `vendor/` and nothing else. **A new runtime file or directory has to be added to the allowlist in the workflow.** `packages/` never reaches the host.

Before that, it deploys Relevanssi, the free search plugin the CMS runs beside ours ([`site-plugins/README.md`](../../site-plugins/README.md)). It runs `composer install --no-dev` in `site-plugins/`, in the same container with the whole workspace mounted, which puts the locked version in `wp-content/plugins/relevanssi/`, and fails unless that directory's `relevanssi.php` declares the version `site-plugins/composer.lock` pins and every file in it matches WordPress.org's published SHA-256 for that version (`downloads.wordpress.org/plugin-checksums/relevanssi/<version>.json`, the list `wp plugin verify-checksums` reads, compared by `.depot/scripts/plugin-checksums.mjs`): every listed file present and unchanged, `lib/` included, and nothing unlisted. The lock pins the version and the archive's URL but no hash of the archive, since WordPress.org builds its zips on demand and a zip's hash can change between downloads of one release; the per-file list is what it publishes and keeps fixed. So an empty, partial or altered install never reaches the next step, and neither does one the checksum list cannot be downloaded for. It then rsyncs that directory, whole, into `wp-content/plugins/relevanssi/` under the WordPress root that `DEPLOY_PATH` names, with the plugin sync's flags. The target is fixed, so the `--delete` there can only remove files inside Relevanssi's own directory. It goes first so that a failure leaves the plugin on the host as it was. `site-plugins/` itself, with its `vendor/`, stays behind.

After the plugin it syncs the CMS block theme, `wp-content/themes/resource-hub/`, into `wp-content/themes/resource-hub/` under the same WordPress root, with the plugin sync's flags. The target is fixed, so the `--delete` there can only remove files inside the theme's own directory, never another theme. It is an allowlist too: the host receives `style.css`, `theme.json`, `functions.php`, `inc/`, `templates/`, `parts/`, `assets/` (the pagination stylesheet `functions.php` reads), `js/` (the theme control's script `inc/theme-control.php` reads) and `build/` and nothing else, so `README.md`, `package.json`, `scripts/` (the build), `figtree.sha256` (a test's record) and `node_modules/` stay behind. `build/` is gitignored and written by the job's `pnpm build`, so right after the build, before anything reaches the host, the job fails unless `build/assets.php`, `build/tokens.css` and every file `theme.json` loads (Figtree's) are there and not empty: without the manifest `functions.php` registers no stylesheet, quietly. **A new runtime file or directory in the theme has to be added to its allowlist too.** `.depot/scripts/theme-allowlist.test.mjs`, which the scope job runs on every pull request and the deploy job again on the commit it deploys, before any SSH (two pull requests can each pass alone and still merge into a `main` that would ship a theme missing a file), fails until every tracked file in the theme is either shipped or named as staying behind, and until everything the theme loads is shipped: the paths in `functions.php` and `inc/` built from `__DIR__`, `dirname( __DIR__ )` or `get_theme_file_uri()` and `_path()` with one single-quoted literal (any other reference there to the file's or the theme's directory, such as `__FILE__`, `get_stylesheet_directory()` or a double-quoted or concatenated path, fails it with its file and line, unless the test's `UNRESOLVED` names it with the reason what it reaches is already covered), `theme.json`'s `file:./` sources and template parts, the parts the templates include, and the build's copies. The theme goes after the plugin because its templates render the plugin's blocks, and those only ever gain: a failed theme sync leaves a newer plugin beside the theme as it was, which still renders.

It then activates the plugin with WP-CLI if it is not active, then Relevanssi the same way (its first activation creates its tables; its settings are the plugin's code, so none is stored), then the theme ([Activating the theme](#activating-the-theme), below), runs `wp rewrite flush` (activation clears the rules only when the plugin was inactive, so a deploy that changes the permalink structure would otherwise keep the old rules; it runs after the theme's activation, the deploy's last change), runs `wp resource-hub search-index`, reads the site's `home` URL over SSH and requests `{home}/wp-json/` to check that the REST API answers. `search-index` rebuilds Relevanssi's index only when it is out of date: when Relevanssi has no complete index, as after its first activation; when its tables are not at the database version its code expects; or when Relevanssi's version, its database version, the version its tables are at or the plugin's index settings (with the plugin's own index-logic version) differ from the stamp the last complete build stored in the `resource_hub_search_index_stamp` option. On every other deploy it changes nothing, because a rebuild empties the index first and live search would find nothing or part of the library while it ran. A rebuild is one pass over the published resources and pages, a few dozen. The stamp is deleted before a rebuild starts and written only when it completes on up-to-date tables, so a rebuild that fails, times out or is killed leaves the index reading as stale, and the next deploy tries again.

**The index step does not fail the deploy.** By then the plugin and Relevanssi are live, and failing would only hold back the front-end deploy, which does not read the index, without repairing it. A failure, or a run past the step's 4-minute limit, shows as a "Search index not built" warning annotation on the run, and the job goes on. When you see it, read the step's log, then run the rebuild by hand (below). Between rebuilds Relevanssi keeps the index current on each save, and the plugin re-indexes the resources of a renamed or deleted topic or type from WP-Cron. WP-CLI runs from the WordPress root, because the host's `wp-config.php` requires `wp-salt.php` by a relative path.

Relevanssi itself upgrades its tables only on an admin page load (`relevanssi_admin_init`), never from WP-CLI, so before rebuilding, `search-index` calls the same version-gated upgrade, `relevanssi_create_database_tables()`, which does nothing when the tables are current. The deploy's database user has the privileges it needs (ALL on its database, MariaDB 10.11.19; verified read-only on the host, 2026-11-08).

**WP-CLI on the host by hand.** Each manual command in this runbook runs from the WordPress root, which is `DEPLOY_PATH` without its `/wp-content/plugins/resource-hub-wp` suffix, through the pinned PHP, over the deploy user's SSH access:

```sh
ssh -i <deploy key> <DEPLOY_USER>@<DEPLOY_HOST> 'cd <WordPress root> && php8.4 /usr/local/bin/wp <command>'
```

`<deploy key>` is a private key authorised for that user (the deploy's own, `DEPLOY_SSH_KEY`, or the maintainer's), and `<DEPLOY_USER>` and `<DEPLOY_HOST>` are those secrets' values. The commands below give the `<command>` part.

**The manual rebuild:** `resource-hub search-index`, that is `ssh -i <deploy key> <DEPLOY_USER>@<DEPLOY_HOST> 'cd <WordPress root> && php8.4 /usr/local/bin/wp resource-hub search-index'`, rebuilds if the index is out of date, and says so when it is current; add `--force` to rebuild a current index, at the cost of the empty window while it runs. Use it after a "Search index not built" warning, or for any other doubt about the index.

If `/resources/` URLs 404 on the host after a change that the deploy did not flush, `rewrite flush` (`ssh -i <deploy key> <DEPLOY_USER>@<DEPLOY_HOST> 'cd <WordPress root> && php8.4 /usr/local/bin/wp rewrite flush'`) is the manual equivalent (plain `wp` runs the host's 8.2; see [The host's CLI PHP](#the-hosts-cli-php)). Locally, `pnpm wp rewrite flush`.

### Activating the theme

The deploy makes `resource-hub` the active theme on every deploy, as it does the plugin: its 404 is the one theme page anonymous visitors get (ADR 0031), and it lists no pages (issue #89's first rule), and logged-in previews look like the front end. The step reads the active theme first (`option get stylesheet --skip-themes`), switches only when it is another one, and then makes two checks. The first, `theme is-active resource-hub`, loads WordPress with the theme and the plugins, so it runs `functions.php` and `init`, but it renders no template and no block. The second is a render: an anonymous request for `{home}/resources/`, with a query string unique to the run so no cache layer answers it, which the lockdown answers with the theme's `templates/404.html`; it must be a 404 with `rh-not-found` in a class attribute, a class only that template writes on the CMS (Twenty Twenty-Five's 404 has none). How each failure leaves the host:

- **The theme sync fails:** nothing is switched. The theme the host runs keeps running, beside the plugin and Relevanssi as just synced.
- **`theme activate` fails:** WP-CLI refuses a theme it cannot find or that has no `style.css` or index template, exits 1 and leaves the stylesheet option unchanged, so the previous theme stays active.
- **A check fails after a switch:** WordPress does not load with the theme (a `functions.php` that fatals on the host), or its 404 does not render (any status but 404, or no `rh-not-found`). The step switches back to the theme it found, with `--skip-themes` so the new theme is not loaded for the switch, and fails the job. If that switch fails too, the error names the command to run by hand ([Rolling back](#rolling-back)).
- **A check fails with the theme already active:** the synced files are live and there is no other theme to go back to. The job fails; roll back as below.

**Known limit: a check that cannot run counts as failed.** If the SSH connection drops (exit 255), the home URL cannot be read or curl gets no answer during a check, the step cannot tell that from a broken theme, so after a switch it switches back and fails the job. On the theme's first deploy that leaves Twenty Twenty-Five active until the job is retried (`depot ci retry <run-id> --job <job-id>`) or the next deploy runs. If the connection is still down for the switch-back, that fails too, and the error names the command to run by hand.

Each failure fails the job, so the steps after it do not run: the rewrite flush, the index, the smoke check and `deploy-web`. The step was run against wp-env on 2026-11-08 (WP-CLI 2.12.0), its script as written with `ssh` pointed at the container and the home URL check widened to wp-env's `http://localhost`: a switch from Twenty Twenty-Five, an already active theme, a `functions.php` that throws after a switch (switched back to Twenty Twenty-Five, exit 1) and while already active (exit 1), and a 404 template without `rh-not-found`, after a switch (switched back, exit 1) and while already active (exit 1). The host's WP-CLI is 2.12.0 too ([Host notes](#host-notes)) but not pinned; the step uses only `option get`, `theme activate`, `theme is-active` and `--skip-themes`.

**The theme's first deploy switches the hosted CMS from Twenty Twenty-Five** to `resource-hub`. From then on the lockdown's 404 is this theme's. Anything saved for Twenty Twenty-Five in the Site Editor, templates or style changes, stays in the database with that theme and does not carry over; the new theme's templates are its files. The deploy user can write the themes directory ([Host notes](#host-notes)). After the deploy, request any theme page anonymously, say `{home}/resources/`, for a 404 with no navigation or page titles, then log in and look at a page and a resource.

### Composer in a container

Both installs run in the official `composer:2` image, pinned by digest in the job's `COMPOSER_IMAGE` (Composer 2.11.1 on PHP 8.5.12, read on 2026-11-08), as the runner's uid and gid so what they write is not root-owned for the rsyncs, and with the flags they had on the runner. There is no PHP on the runner and no `shivammathur/setup-php`. On Depot, which sets no `ImageOS` or `ImageVersion`, setup-php takes the runner for self-hosted and installs PHP from a php-builder release on github.com, a download with no fallback whose HTTP status is ignored and whose output setup-php discards; while github.com returned 504s on 2026-11-08 that failed 3 of 4 deploy attempts (runs `ps_tnct8c2vqz`, `ps_s2wtzg81c9`) with only "Could not setup PHP 8.4" in the log. The image's PHP need only meet the plugin's floor: `vendor/composer/platform_check.php` takes it from `composer.json`, not from the PHP running Composer (the plugin's `vendor/` came out byte-identical on 8.4.27 and 8.5.12 on 2026-11-08), and `site-plugins/`' `config.platform.php` (8.4) fixes its resolution. To move the image, read the new digest with `docker buildx imagetools inspect composer:2`, check `php -v` against the floor, and update the digest and the versions in the job's comment.

**Known residual risk: the deploy depends on Docker Hub.** The image is pulled anonymously on each deploy, so a Docker Hub outage or its rate limit on anonymous pulls (HTTP 429) fails the install step, visibly, with Docker's error in the log, before any SSH call or rsync; nothing has reached the host. Redeploy once Docker Hub answers: `depot ci retry <run-id> --job <job-id>` for the failed deploy job, or `depot ci dispatch --repo Colbitron/resource-hub-wp --workflow ci.yml --ref main`.

**Composer's download cache.** Both installs share one Composer cache directory, restored before them and saved after them under the rule for every cache in the workflow (saved only from `main`, only on a miss; the comment above `jobs` in `ci.yml`). Its key is a literal version (`composer-dist-v1-…`), the hash of both `composer.lock` files and the image's digest, with no restore keys, so it changes, and the next deploy downloads afresh, exactly when a lock or the image does. The plugin's lock is in the key although its install downloads nothing today, so that a production dependency added there changes the key: a hit never saves, so without that the new dist would be downloaded on every deploy. The image sets `COMPOSER_HOME=/tmp`, so its own cache, `/tmp/cache`, would go with the container; the job mounts `$RUNNER_TEMP/composer-cache` into both containers and points `COMPOSER_CACHE_DIR` at it, creating it first as the runner user, since Docker would create a missing mount source as root and the installs, as the runner's uid, could not write it. The save runs after the check of Relevanssi's files, so a run whose Relevanssi install failed, which would leave the cache all but empty, or whose files failed the check, saves nothing. **If a bad entry is ever restored, bump `v1` to `v2` in the key** in `ci.yml` and deploy again: `depot ci retry` would restore the same entry.

With the cache restored, the two installs need neither GitHub nor wpackagist nor WordPress.org's plugin downloads. The rest of the deploy still needs the network: the image is pulled from Docker Hub, and the step after the installs fetches Relevanssi's checksums from `downloads.wordpress.org/plugin-checksums/`. On 2026-11-08 both installs, run a second time with `docker run --network none` on a filled cache, produced output byte-identical to the online run; at `-vv` (a local run) Composer printed "Loading … from cache" for each dist. On Depot, trial run `wqf81sfz32` filled and saved the cache and `6dvrpw81wd` restored it and ran both installs with `--network none`, and Relevanssi passed its checksum check. At the deploy's default verbosity the only network attempt either log shows on a hit is to `repo.packagist.org/lists/all/summary.json`, the filter list behind Composer's `policy` setting, which fails with a warning that the package information "was loaded from the local cache and may be out of date", and the install goes on. With no cached copy of that list, Composer's documented default (`policy.ignore-unreachable`) is to skip it; that case was not tested here.

**Accepted risk: nothing verifies `composer/installers`.** Neither lock carries a `dist.shasum` (empty for `composer/installers`, absent for Relevanssi), and Composer 2.11.1 checks a dist only against that value, so it verifies none, cached or downloaded (`FileDownloader.php`, lines 178–182). Relevanssi is covered by the checksum step after the installs. `composer/installers` is not, and it is a Composer plugin: its code runs inside the second install's container, with the whole workspace mounted. An entry under `main`'s exact key can be written only by a run that sets `SAVE_CACHES`, which an unmodified workflow does only on `main`; a same-repository pull request that edits the workflow could do it too, and only the owner can open one, while Depot CI does not run pull requests from forks. That is the exposure already accepted for Depot Cache ("The cache", under "What a pull request can reach" in [Secrets](#secrets)), and it is accepted here on the same terms. No verification step is added, because GitHub's generated zipballs are not guaranteed byte-stable, so a pinned hash of the archive would break on a regeneration rather than on tampering.

**Known residual risk: a cache miss still downloads from GitHub.** On the first deploy after a lock or image change, or after Depot evicts the entry, nothing is cached. `site-plugins/composer.lock` locks `composer/installers` with a dist URL on `api.github.com`, which redirects to `codeload.github.com`, and if that download fails Composer falls back to a git clone from github.com. So a GitHub outage that reaches those hosts during a miss still fails the Relevanssi install, and with it the deploy, before anything is copied; on 2026-11-08 `api.github.com` timed out and returned 504s (even for `/zen`) while `codeload.github.com` and github.com answered, which failed main's deploy at that step (run `ps_5p5433sgjn`) with the host untouched. Redeploy once GitHub answers, as for Docker Hub above; that deploy fills the cache. The plugin's own install locks no production package and downloads nothing. **The gate keeps a GitHub dependency of its own:** wp-env builds its CLI images on each fresh runner from a Dockerfile it generates, which runs `composer global require --dev phpunit/phpunit` (`lib/runtime/docker/docker-config.js` in `@wordpress/env`), and those dists download from GitHub, so a GitHub outage can fail the gate, and the deploy waits on the gate. That is wp-env's, and this repository leaves it alone.

### The host's CLI PHP

The deploy runs every WP-CLI call on the host as `php8.4 /usr/local/bin/wp`, the job's `WP_CLI` variable, because the host's default CLI PHP is 8.2 (`/usr/bin/php -> /etc/alternatives/php -> php8.2`, server-wide and root-owned), Cloudways' console has no setting for it, and `WP_CLI_PHP` names the PHP for WP-CLI's subprocesses, not the interpreter its phar runs on. Before the rsync it reads the PHP version those calls run on (`$WP_CLI cli info --format=json`) and fails unless it meets the plugin's floor, `require.php` in its `composer.json` (`.depot/scripts/host-php-floor.mjs`); a pass logs the host's CLI PHP. It guards one failure: the deployed `vendor/composer/platform_check.php` enforces the floor, so on a lower CLI PHP every WP-CLI call after the rsync fatals, leaving the host half-deployed and the front-end deploy skipped while the web PHP serves readers as usual (run `ps_lzqkzvjvch`, 2026-11-07: floor 8.4, plain `wp` on 8.2.35). It reads the root's `require.php` alone, which is the whole floor only while the plugin installs no production package and requires no `ext-*`: `platform_check.php` takes the highest lower bound across the root and every non-dev package, plus their extensions. The script's tests fail when the plugin's `composer.lock` gains a non-dev package or the root a requirement other than `php`; the guard must then read the generated `platform_check.php` instead. When it fails nothing has been copied. Align the two, then redeploy: raise the pinned binary in `WP_CLI` to one the host has at or above the floor; or, if the floor rose further than the host can follow, lower `require.php` and run `pnpm composer update --lock`, which works only if the code, `Requires PHP` in `resource-hub.php`, `testVersion` in `phpcs.xml.dist`, `.wp-env.json` and the locked dev toolchain all still hold on the lower version, and the toolchain needs 8.4 for `composer install` (ADR 0005's amendment). Output it cannot read, a floor not of the form `>=X.Y` or `>=X.Y.Z`, and a failed SSH call fail the step too, each with its own error.

## The front-end deploy

The `deploy-web` job needs `deploy` and every front-end job (`web-checks`, `web-e2e`, `web-screenshots`, the five `web-lighthouse` shards and `web-lighthouse-medians`), runs only on `main` (a push or a plain dispatch on `main`, never a rollback dispatch, which skips it and every front-end job; "Rolling back", below), reads `main`'s head through the API and fires the hook only if it is still the commit the run tested; otherwise it leaves a notice and the newer run deploys. A failed run that a newer push supersedes deploys nothing, and if the newer run fails, production stays at the last commit whose run fired the hook until the next green run on `main`. The hook answers with a queued job, and the step logs its id and state and ends: it does not wait on the build. **A green CI run means the build was queued, not that it succeeded**; a failed Vercel build leaves the previous production deployment serving, and its result is on Vercel.

**What it waits for.** On the commit, the front-end jobs must have passed the lint, typecheck, unit tests, production build and fixture-route check, the end-to-end suite (the axe scan and the document-size check included), the screenshots and the brand-image check, and every Lighthouse shard and the medians job, which run on `main` and never on a pull request. A Lighthouse budget miss does not hold the deploy back until issue #76 calibrates the gate: GitHub's runners, where CI ran until 2026-11-07, varied about 2–3x in CPU speed, so TBT on unchanged code moved between about 80 and 300 ms; on 2026-11-07 main's run 42362572282 missed it twice on code that had passed on its pull request, which skipped the deploy until it was started by hand, and PR #79 missed it at 201 and 209 ms against the 200 ms budget with no runtime change, which blocked its merge until a rerun. On a manual dispatch from any branch but `main`, a miss still fails its shard's job. Only a missed budget is a warning: any other Lighthouse failure, where no failed assertion is on record (a broken harness, Chromium failing to launch, a build-stamp mismatch), fails its shard's job on every event and so blocks the deploy. WCAG A and AA accessibility stays gated by the axe scan in the end-to-end suite, which blocks the merge and the deploy on any WCAG A or AA violation.

**A Lighthouse warning on a `main` run is a finding to look at, not noise.** The run's annotations and the shard's job summary name each URL and metric that missed and its median, the `web-lighthouse-medians` job's summary has every URL's medians in one table, and the reports are in the `web-lighthouse-reports-<shard>` artifacts. A single miss just over budget on TBT is most likely a slow runner; if the same URL and metric miss again on the next run, or a median is well past its budget, or the miss is on accessibility or CLS, which do not depend on the runner's speed, treat it as a regression and fix it in a new pull request, checking the fix with the local smell test and, for CI's numbers, a `depot ci run` of the branch.

**The build reads the CMS.** Since 2026-11-07 (ADR 0043, amended) `next build` prerenders the library, each type's first page, the root and the newest resources from `WP_API_URL`: about 40 requests on the seed, up to about 140 with five full types, from every preview and production build. A CMS that does not answer costs the build one warning per route (`prerender {route}: nothing prerendered at build …`) and no prerendered page, never a failure; the deployed app then renders each page on its first request as before. The build's first step empties `.next/cache/fetch-cache` (`scripts/clear-fetch-cache.mts`, run by the `build` script), because Vercel restores that directory from its build cache and a stale copy of a CMS answer served to the build with the CMS down fails the build; so Vercel must run the `build` script, which `buildCommand` in `apps/web/vercel.json` sets to `pnpm build`. Do not replace it with `next build`. A revalidation event fired while a build runs clears the live deployment only, so the new deployment's prerendered pages carry pre-event data until the next event or the hourly interval.

On the Vercel project:

- Root Directory is `apps/web`.
- `apps/web/vercel.json` sets `git.deploymentEnabled.main` to `false`, so a push to `main` creates no Git-triggered production deployment, while every other branch and every pull request still gets a preview; and `buildCommand` to `pnpm build`, the script that empties the fetch cache before `next build` (above).
- "Automatically expose System Environment Variables" is on. `next.config.ts` recognises a Vercel build by the `VERCEL` variable and fails the build when `WP_API_URL` (or `WP_MEDIA_ORIGIN`) or `SITE_URL` is missing; with the setting off, a Vercel build without a base would deploy with every `/media/` image a 404.
- `WP_API_URL`, `REVALIDATE_SECRET` and `SITE_URL` are set for Production and for Preview, because Preview builds fail without them. On Preview, `SITE_URL` is the production origin, so a preview's canonical points at the public page.

**First-deploy check, closed 2026-11-06.** Two things were unconfirmed when the hook was built: whether a deploy hook still deploys a branch whose `deploymentEnabled` is `false`, and whether Vercel reads `git.deploymentEnabled` from `apps/web/vercel.json` when the Root Directory is `apps/web`. The merge of pull request #40 (`1c3e17f`) produced exactly one production deployment, created by the hook after CI. So the setting is read from `apps/web/vercel.json` with that Root Directory, and it does not block deploy hooks. The fallback that was held in reserve, an Ignored Build Step in the dashboard, is not needed.

## Rolling back

**The CMS** is rolled back by dispatching CI on `main` with the commit to redeploy as the `rollback_sha` input (issue [#130](https://github.com/Colbitron/resource-hub-wp/issues/130)). The run stays on `main`, so it reads the deploy secrets, whose only variant is scoped to `main` ("Secrets", above). It is an input and not a ref because Depot refuses a dispatch on a tag ("Workflow … not found or does not have workflow_dispatch trigger", canary probe of 2026-11-07) and a tag or branch run would read the secrets as empty; never add a `rollback-*` variant to get round that. Only a commit that has been on `main`, from the deploy job's floor onward (below), can be deployed this way.

1. **Pick the commit.** `git log --first-parent --oneline origin/main` lists `main`'s merges, newest first; take the merge of the last good pull request and expand it: `git rev-parse <short sha>`. The input must be the full 40-character SHA in lower case. A short SHA, a branch, a tag, upper case or anything else is refused, never resolved.
2. **Dispatch.** `--ref main` is the only ref that deploys, and `--workflow` takes the file's basename:

   ```sh
   depot ci dispatch --repo Colbitron/resource-hub-wp --workflow ci.yml --ref main --input rollback_sha=<full sha>
   ```

   To deploy `main`'s head again, as after a Docker Hub or GitHub outage, dispatch with no `--input`; that is the plain dispatch, which also deploys the front end.
3. **Watch it to the end**, `depot ci status <run-id>`. The run is in `main`'s concurrency group, so it waits for a run on `main` that is under way. GitHub keeps one waiting run per group and replaces it with a newer one, and that cuts both ways here: a push to `main` arriving while the rollback waits replaces the rollback, and a rollback dispatched while a push's run waits replaces that run. Nothing re-runs a replaced run. So if the rollback ended cancelled with nothing deployed, dispatch it again once `main` is quiet; and once it has deployed, look in `depot ci run list` for a push run on `main` that was waiting and ended cancelled, and if there was one, dispatch `main` with no input (step 2) so that merged commit is gated and deployed, or leave it until the next push if the rollback is meant to hold. Whether Depot replaces waiting runs as GitHub documents is unconfirmed. A failed job is retried with `depot ci retry <run-id> --job <job-id>`.
4. **Afterwards**, land the fix, or a revert (below), before anything else merges: the next push to `main` deploys `main`'s head again and undoes the rollback.

**What a rollback dispatch runs.** The scope job, then the plugin's gate on the rollback target (about 3 sandbox-minutes), then `deploy` of that target, and `CI result`. The front-end jobs, the five Lighthouse shards and their medians, and `deploy-web` are skipped: they would test `main`'s head, which the rollback does not ship, and the deploy hook always builds `main`'s head. `CI result` reads those skips as the rollback's and is green when the gate and scope passed (`.depot/scripts/ci-result.mjs`). The gate runs on the target rather than being skipped because "on `main`" alone does not mean "gated": a merge whose `main` run went red was never deployed and is still an ancestor of `main`, and so is every commit inside a merged pull request. One run of the gate keeps the rule that nothing reaches the host unchecked, and it also means a red gate on `main`'s head, which may be why you are rolling back, cannot block the rollback. Testing `main`'s head instead would say nothing about the commit being deployed.

**What is checked before anything reaches the host.** In both the gate and the deploy, the checkout is `main`'s full history (`fetch-depth: 0`; the packs were about 57 MB on 2026-11-08, by `git count-objects -vH`), and `.depot/scripts/rollback-target.mjs` reads the input, the event, the ref and the run's own SHA through `env`, never into a script, and refuses, failing the job, when: the event is not `workflow_dispatch` or the ref is not `refs/heads/main`; the input is not a full lower-case SHA; the checkout is shallow or is not at the dispatched commit; the SHA is not a commit in `main`'s history or not an ancestor of `main`'s head (`git merge-base --is-ancestor`); or it predates the floor. Only then does the next step detach the checkout onto the SHA the check wrote to its output, and every later step builds, tests and deploys that commit. The deploy's own checks run on it as on any deploy, each before "Configure SSH": the theme's build, the theme allowlist test, the two Composer installs, Relevanssi's checksums and the host's CLI PHP. The step list is in `ci.yml`, "Rolling back", above its triggers; the script's tests (`rollback-target.test.mjs`) run in the scope job on every pull request.

**The floor.** `ROLLBACK_FLOOR` in `ci.yml`'s `env` is the earliest commit the deploy job can deploy: `cb22fd9a`, the merge of #137 (2026-11-08), which gave the job its current shape. The workflow that runs is `main`'s, but it reads the checkout for the files it deploys and the scripts it runs. Just below the floor the one thing missing is `.depot/scripts/theme-allowlist.test.mjs`, whose step fails on the missing file; older commits also lack the theme's `theme.json` and `site-plugins/composer.lock`. Each of those steps runs before any SSH, so a too-old target fails before anything reaches the host; the check refuses it first, by name, and points here. The deploy runs the target's own allowlist test against the target's own `ci.yml`, not the running one, so a later change to the allowlist is caught only by moving the floor. A commit older than the floor is rolled back to with a revert pull request. Move the floor forward whenever the deploy job changes in a way an older checkout cannot satisfy: a file or script it starts reading, a pnpm script it starts running, an allowlist entry it drops. Adding an allowlist entry or a check that passes on older trees does not move it.

**The rollback dispatch is proven.** The first real one, run `dxzmqskb8s` on 2026-11-08 (`depot ci status dxzmqskb8s`), rolled back to `main`'s own head, which is idempotent: `depot ci dispatch --repo Colbitron/resource-hub-wp --workflow ci.yml --ref main --input rollback_sha=1528d36fdf63c06abdfe4509990e216c049b9e3f`. It went green. The gate and the deploy job each logged `Rolling back: 1528d36f… is on main, at or after the deploy job's floor…` and `HEAD is now at 1528d36`, the deploy job also logged `Deploying 1528d36f…`, the host's CLI PHP check reported 8.4.27, and the CMS deployed. `Deploy the front end to Vercel` and every front-end job were skipped, and `CI result` logged `event "workflow_dispatch", rollback yes`. So Depot delivers a dispatch's `inputs` to the conditions and `env` as GitHub does, and the full-depth checkout works on a dispatch. Before it, the validation was proven by its unit tests, and the step wiring by `depot ci run` of a throwaway workflow on 2026-11-08, committed for the runs and dropped, event `api`, no secrets and no SSH. Run `fxtbh9zhxp` checked `main` out at full depth, ran the same check step against an ancestor after the floor (`90563e67`: accepted, detached onto, and the shared setup action resolved from the detached tree), ran the shallow-checkout refusal in a second job, and confirmed that `inputs.rollback_sha == ''` is true and `!= ''` false on a run with no input, so a push to `main` keeps every job; its refusals step failed on the trial's own `git commit-tree` wanting an identity. Run `cwlfxtfvl9` repeated the acceptance and ran the refusals: a commit not on `main`, a short SHA, upper case, shell metacharacters (which ran nothing), a branch name, a pre-floor commit, a SHA git does not know, a SHA on a push and a SHA on a tag ref, each refused with nothing written to the step's output, and the empty input passing as a plain run. If a rollback's deploy job ever logs `Not a rollback`, Depot did not deliver the input, and the run deployed `main`'s head as a plain dispatch does. Still unconfirmed: whether Depot replaces a waiting run in a concurrency group (step 3, above).

**The fallback: a revert pull request.** For a commit older than the floor, or if the dispatch cannot be made to work, revert on a branch (`git revert -m 1 <merge-sha>` for a merged pull request, `git revert <sha>` for a single commit), open a pull request, merge it once `CI / CI result` is green, and watch the push's run: the full gate, Lighthouse included, then the CMS deploy, then the front end's. To land the change again later, revert the revert in a new pull request, with the fix on top. A revert also deploys both sides at once, where a rollback dispatch deploys the CMS alone.

**The front end** is rolled back on Vercel, by promoting an earlier production deployment (Instant Rollback), or by a revert, since a merge to `main` deploys both sides. A rollback dispatch never touches it: the hook cannot deploy an earlier commit, because it always builds `main`'s head (ADR 0051). After an Instant Rollback, Vercel stops assigning the production domain to new deployments, so the deploys `deploy-web` starts afterwards still build but are not served until someone undoes the rollback or promotes a deployment on Vercel; a green CI run on `main` does not end it.

**The theme.** A rollback dispatch or a revert redeploys the theme as it was at that commit and keeps it active. To put the host on another theme at once, with no deploy, run ("WP-CLI on the host by hand", under [The CMS deploy](#the-cms-deploy))

```sh
ssh -i <deploy key> <DEPLOY_USER>@<DEPLOY_HOST> 'cd <WordPress root> && php8.4 /usr/local/bin/wp theme activate twentytwentyfive --skip-themes'
```

or name any theme that `theme list --skip-themes` shows; `--skip-themes` keeps a theme that fatals from being loaded for the switch. The next deploy activates `resource-hub` again, so that holds only until the next merge to `main`: land the revert or the fix first. A revert that takes the theme out of the deploy leaves it on the host and active, since the deploy job no longer knows it; switch away with the same command.

A rollback or revert that changes `site-plugins/composer.lock` redeploys Relevanssi at the version it then pins, checked against WordPress.org's checksums for that version, and rebuilds its index if that version or the index settings differ. A revert that takes Relevanssi out of the deploy leaves it on the host and active, since the deploy job no longer knows it. The plugin then does not use it, and Relevanssi runs on its own defaults; to switch it off, run `php8.4 /usr/local/bin/wp plugin deactivate relevanssi` from the WordPress root.

An Instant Rollback of the front end and a rollback of the CMS are separate actions. Because contract changes are additive, a CMS rolled back one step still serves a front end that is one step ahead.

## Rotating secrets

A Depot CI secret is updated in the Depot dashboard (Secrets, then the secret, then edit its `colbitron-resource-hub-wp` variant), or with the CLI, piping the value so it never lands in the shell's history or a file:

```sh
printf '%s' "$VALUE" | depot ci secrets set <NAME> colbitron-resource-hub-wp --from-stdin --repo Colbitron/resource-hub-wp --branch main
```

**Always name the variant and pass both scope flags.** Omitting a scope flag can widen the variant (with neither flag and no variant name, `set` creates a `default` variant). `VERCEL_PROTECTION_BYPASS` is the one exception: its variant is scoped to the repository alone, so set it with `--repo` and no `--branch`:

```sh
printf '%s' "$VALUE" | depot ci secrets set VERCEL_PROTECTION_BYPASS colbitron-resource-hub-wp --from-stdin --repo Colbitron/resource-hub-wp
```

Afterwards, check the attributes with the listing in "Secrets", above.

- **The deploy hook.** Create a new hook for `main` in the Vercel project's Git settings, update `VERCEL_DEPLOY_HOOK_URL` in Depot CI, then delete the old hook.
- **The protection bypass secret.** Regenerate it in the Vercel project's Deployment Protection settings, then update `VERCEL_PROTECTION_BYPASS` in Depot CI, where the Preview Lighthouse workflow reads it, and the local `VERC_DEP_PROT`. Until Depot's copy is updated the Preview Lighthouse comment reports a refused header; nothing deploys through it.
- **The revalidation secret.** It is one value on both sides: `RESOURCE_HUB_REVALIDATE_SECRET` in the host's `wp-config.php` and `REVALIDATE_SECRET` in the Vercel project. It must meet [the secret's rule](../../packages/ui/README.md#configuration); the CMS treats one that breaks it as not configured. Change the front end first, redeploy, then the CMS, then press "Send test revalidation" on Settings > Resource Hub, which sends a real event and records the result.
- **The deploy SSH key.** Generate a new key used only for deploys, add its public half on the host, update `DEPLOY_SSH_KEY` in Depot CI, then remove the old public key from the host.
