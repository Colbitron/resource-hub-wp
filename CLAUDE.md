# Resource Hub

A headless WordPress demo in one repository (ADR 0033): a WordPress plugin, a Next.js front end, and the contract package they share. This file holds what applies to the whole project, including the contract, in one copy. Each part with specifics of its own has a `CLAUDE.md` beside it: `wp-content/plugins/resource-hub-wp/CLAUDE.md` for the plugin and `apps/web/CLAUDE.md` for the front end. Read this file and the one for the part you are changing.

## Standards to build to

Headless WordPress with Next.js over REST (GraphQL as a stretch); React and TypeScript; custom Gutenberg blocks and modular plugins to WordPress Coding Standards and PSR-12; Composer; GitHub Actions; PHPUnit and Playwright; WordPress VIP habits (no direct DB assumptions, object cache, no filesystem writes); WCAG and Core Web Vitals. The reference shape is a headless WordPress site on Next.js and Vercel with ISR and on-demand revalidation from the CMS; this should look like a small, clean instance of that shape. Ambition here means depth, not feature count: a small system where every decision has a one-sentence reason, and a front end that is fast, accessible and tested.

## Hard constraints

- **Fresh, generic code only.** Nothing here may be copied or adapted from any prior employer's codebase or packages. Generic WordPress and Next.js patterns only; when in doubt, write it the textbook way and record the choice.
- **Never describe this as production code.** It is a demonstration of a pattern, written fresh.
- **No secrets in git.** On the CMS side, the revalidation secret and front-end URL live in `.env` (gitignored) and in wp-env's `config` or `define()` overrides; on the front end, `REVALIDATE_SECRET` and `WP_API_URL` live in `apps/web/.env.local` (gitignored) and in Vercel project settings. Never in a committed file.

## What it is

A filterable resources library: WordPress models it and pushes changes, Next.js renders it and rebuilds pages on demand.

- **The plugin**, `resource-hub`, at `wp-content/plugins/resource-hub-wp/`: the `resource` post type and its taxonomies and meta, the related and resolve REST routes, the `resource-hub/related-resources` block, the revalidation hook, and the settings status page. Registered in the plugin, not a theme. It runs in a `wp-env` environment configured at the repository root, and is deployed to the hosted CMS.
- **The front end**, a Next.js App Router app in TypeScript at `apps/web/`, deployed on Vercel: it renders the library from the WordPress REST API, always on its own server, and revalidates on demand when the CMS says so.
- **The contract package**, `@colbitron/resource-hub-ui` at `packages/ui/`: the JSON Schemas both sides check themselves against (ADR 0010) and the stylesheet both render with, consumed through the pnpm workspace and never published (ADR 0041).
- **The CMS theme, planned for slice 5**, at `wp-content/themes/resource-hub/`: a full block theme kept in sync with the front end through the `packages/ui` tokens and CSS. It is for editors and logged-in previews only; anonymous visitors get a 404 (ADR 0031). The directory does not exist yet.
- **Documentation:** `README.md` at the root with the architecture diagram, the layout and the decisions list; one ADR per real decision under `docs/adr/`, in one sequence for the whole project.

## The contract between the CMS and the front end

Contract changes land in one pull request that touches both sides and the schemas, and they stay additive: add a field, route or event before anything relies on it, and remove the old one only after nothing does, so the front end never breaks against a CMS one deploy behind. The JSON Schemas in `packages/ui/schemas/` (ADR 0010) are the source of truth and `packages/ui/README.md` holds the semantics a schema cannot express; this section summarises them. Change a schema and its fixtures first, then this section, then the code on both sides.

- **Server side only:** the front end makes every CMS request on the Next.js server, with the CMS's `/wp-json` base in `WP_API_URL`, a server-only environment variable (never `NEXT_PUBLIC_`), so the CMS's address never reaches the browser (ADR 0040). WordPress emits absolute CMS URLs everywhere (`get_permalink()`, `content.rendered`, `_embed` media); the front end rewrites them: links lose the CMS domain (ADR 0036), and images, including `<img src>` and `srcset` in `content.rendered`, become `/media/…`, which `next.config.ts` rewrites to the CMS's uploads directory, one to one. This reduces exposure; it is not a security boundary.
- **Content read:** the front end reads `GET {WP_API_URL}/wp/v2/resources?_embed&per_page=…&page=…&resource_topic=…&resource_type=…&resource_flag=…`, `GET {WP_API_URL}/wp/v2/resources/{id}` (and `?slug=`), and the taxonomy endpoints `{WP_API_URL}/wp/v2/resource_topic`, `{WP_API_URL}/wp/v2/resource_type`, and `{WP_API_URL}/wp/v2/resource_flag`. Meta is `summary` and `source_url`, under `meta` because of `show_in_rest`. `related_picks` is in the REST `edit` context only, for the editor's picker; the front end never reads it, because the related route does the merging (ADR 0030). Featured is the `resource_flag` term `featured`, not meta (ADR 0009): a featured resource has that term's ID in `resource_flag`.
- **Related:** `GET {WP_API_URL}/resource-hub/v1/related/{id}?count=3` (1 to 10) returns `{ "items": [ { "id": 12, "source": "pick" | "topic" } ] }`, at most `count` items, already merged: picks first, unpublished picks skipped, no duplicates, capped at `count`; a resource with no topics gets its picks alone. The front end calls it once, does no merging of its own, and then reads the objects with `GET {WP_API_URL}/wp/v2/resources?include={ids}&orderby=include&_embed`.
- **Resolve:** `GET {WP_API_URL}/resource-hub/v1/resolve?slug=…` returns `{ "id": 12, "type": "webinar", "slug": "current-slug" }` for a published resource found by its current or an old slug, or a 404. The front end calls it only when the current-slug lookup misses.
- **Errors from both routes:** core's `WP_Error` shape, `{ "code", "message", "data": { "status" } }`, for 400 and 404.
- **Revalidation request** (WordPress to front end): `POST {FRONTEND_URL}/api/revalidate/` (with the trailing slash, like every front-end path), header `Authorization: Bearer {REVALIDATE_SECRET}`, header `Content-Type: application/json`, body a batch of 1 to 25 events. One PHP request is one batch; events are deduplicated per resource ID for resource events and per (taxonomy, term ID) for term events (earliest `previous`, latest state, except that a removal after an `update` in the same request carries the state from before the request at the top level); more than 25 are split into several requests.
  ```json
  { "version": 1, "events": [
    { "type": "resource", "event": "publish" | "update" | "unpublish" | "trash" | "delete", "id": 123, "slug": "example", "rest_url": "https://cms.example/wp-json/wp/v2/resources/123", "types": ["type-slug"], "topics": ["topic-slug"], "previous": { "slug": "old-example", "types": ["type-slug"], "topics": ["topic-slug"] } | null },
    { "type": "term", "taxonomy": "resource_topic" | "resource_type", "event": "create" | "update" | "delete", "id": 45, "slug": "topic-slug", "name": "Topic name", "previous": { "slug": "old-slug", "name": "Old name" } | null }
  ] }
  ```
  `types` has exactly one element. The top-level fields are the public state the event concerns: after the save for `publish` and `update`, the last public state (`$post_before`) for `unpublish`, `trash` and `delete` (or, after an `update` in the same request, the state before the request). `previous` is set on `update` only, with every field filled, and is `null` otherwise. The front end refreshes on `publish` and `update`, removes on the other three (the refetch returns nothing and the page becomes `notFound()`), and revalidates the union of the current and previous state. Restoring from the trash sends nothing. `resource_flag` sends no term events. A body with a `version` the front end does not understand is a 400.
- **Revalidation response:** `200 { "revalidated": ["/resources/", "/resources/webinar/example/"] }` listing the paths revalidated; `400 { "error": "…" }` for a malformed body; `401 { "error": "unauthorized" }` for a bad or missing bearer; `500 { "error": "…" }` when the front end fails. The plugin records status and body and shows them to the editor, so the messages must be plain and accurate.
- **Public URLs**, the same on both sites, always with a trailing slash: `/resources/`, `/resources/[type]/`, `/resources/topic/[topic]/`, `/resources/[type]/topic/[topic]/`, `/resources/[type]/[slug]/`, and `…/page/[n]/` on every listing. `topic` and `page` are reserved and never type slugs. The slug is the identity; a wrong type segment, or an old slug found through resolve, redirects with a computed single-hop 308 and `Cache-Control: no-store`; never send a permanent redirect without a cache header (ADRs 0025, 0035). Those redirects are the front end's; the CMS redirects no one, and its theme pages are a 404 for anonymous visitors, with `robots.txt` and `noindex, nofollow` on top (ADR 0031). `get_permalink()` stays absolute; the front end strips the CMS domain from every link in the HTML it renders. Cache tags on the front end are `resources`, `resource:{slug}`, `topic:{slug}` and `type:{slug}`.
- **Block marker:** the related-resources block renders `<div data-rh-block="related-resources" data-count="3" data-topic="topic-slug" data-topic-id="45" data-exclude="123">` with its `<h2>` heading and a fallback `<ul>` of links. The front end parses `content.rendered` (`html-react-parser`, `replace`) on its server, never in the browser, and swaps the wrapper for its `<RelatedResources>` server component, fetched with the `topic:{slug}` tag, in the same pass that strips link domains and rewrites images to `/media/` (ADR 0037). `data-topic` is the term's current slug, resolved at render time from the stored term ID, and names the `topic:{slug}` cache tag; `data-topic-id` is that ID, for the `resource_topic` REST filter; `data-exclude` is the ID of the post the block sits in, left out of the list.
- **Shared styles:** `@colbitron/resource-hub-ui` (`packages/ui/`) holds `tokens.css`, `related.css` and `card.css`; the class names (`.rh-related`, `.rh-card…`) and tokens are part of the contract. Every consumer takes the package through the pnpm workspace (`"@colbitron/resource-hub-ui": "workspace:*"`); it is never published (ADR 0041). WordPress loads the CSS through `block.json` only where the block is used; the front end imports it from the component that uses it, never from `layout.tsx`; the planned theme uses the same tokens. No shared JavaScript.
- **Configuration, CMS:** `RESOURCE_HUB_FRONTEND_URL` and `RESOURCE_HUB_REVALIDATE_SECRET` as PHP constants (wp-config or wp-env `config`), falling back to options. Optional `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST` constants turn on results logging (ADR 0032); unset, it is skipped. None of them is ever committed. `REVALIDATE_SECRET` is 32 to 256 printable ASCII characters with no whitespace; both sides refuse anything else. The settings page is a status page: it shows which source is active, never displays the secret, and has a "Send test revalidation" button that sends a real `update` event for the most recently modified published resource or one chosen in a searchable picker, is disabled when nothing is published, and records its result like any real event, in that resource's `_rh_last_revalidation` and in PostHog when configured, plus a non-autoloaded option the status page reads (ADR 0019).
- **Configuration, front end:** `WP_API_URL` (the CMS's `/wp-json` base, server-only, never `NEXT_PUBLIC_`) and `REVALIDATE_SECRET`.

## Standards and workflow

- Each part's language and framework standards are in its own `CLAUDE.md`.
- Agent-first build. The code is written by agents and reviewed by a human: the critical paths get read line by line before merge (on the CMS, the revalidation hook, auth and permission callbacks, and the sanitizers; on the front end, the revalidate route and the data layer's parsing); the rest goes through the gate. The gate is PHPCS, PHPUnit and Playwright for the plugin; typecheck, lint and Playwright for the front end; the schema test for `packages/ui`; and a reviewer agent on a different model than the implementer. Nothing merges until all of it passes.
- Work on branches and open pull requests so the review has a diff to read. Small PRs, one concern each. Commit messages say what and why.
- Record each real decision as an ADR as it is made, one decision per record, with rejected options where some were considered. Every ADR goes in `docs/adr/` with the next free number, whichever part it concerns; a decision that replaces another marks the old one `status: superseded by NNNN` and keeps it.
- **Local environment, decided 2026-11-03: `@wordpress/env` on Docker is the canonical environment.** `.wp-env.json` at the repository root is committed, mounts `wp-content/plugins/resource-hub-wp`, and maps `packages/ui` into the containers so PHPUnit can read the schemas (ADR 0042); the same `wp-env` commands run the PHPUnit suite locally and in GitHub Actions. LocalWP is not used; a second environment would mean a second test setup to keep in step. Host toolchain as of 2026-11-03: Node 24 and pnpm present; Docker installed (start it first); no PHP, Composer, or WP-CLI on the host. Composer ships in the wp-env cli containers, so all PHP tooling runs there with no host install: `pnpm composer`, `pnpm lint`, `pnpm test:php` from the repository root (see the root `package.json`). One pnpm workspace (`pnpm-workspace.yaml`: `wp-content/plugins/*`, `apps/*`, `packages/*`) with one lockfile; the root's `pnpm build`, `pnpm lint:js` and `pnpm test:e2e` delegate to the plugin package with `pnpm --filter`, `pnpm web:dev`, `web:lint`, `web:typecheck` and `web:build` do the same for `apps/web`, and `pnpm test:schemas` runs the `packages/ui` test. wp-env serves the CMS at `http://localhost:8888` and the tests site at `:8889`. The container is the source of truth for test results.
- **Hosted CMS, decided 2026-11-03: Cloudways Flexible on a DigitalOcean 2 GB server, PHP 8.4** (ADR 0005). It is the site the Vercel front end reads and revalidates against. Deploys happen only from CI on `main` after the CMS gate passes, by rsync over SSH from `wp-content/plugins/resource-hub-wp` in this repository into the same path on the host (one directory name in the repository, wp-env and the host, so the plugin basename matches everywhere). Five repository secrets feed the job: `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_KNOWN_HOSTS`. The CMS's configuration constants are `define()`d in the host's `wp-config.php`.
- **Deploy order, decided 2026-11-04: the CMS first, then the front end.** The CMS deploy `needs` only the CMS gate, so a front-end failure can never block a CMS deploy or a rollback. The front end goes live after the CMS it reads: in slice 3 a new job deploys it to Vercel production through a deploy hook (repository secret `VERCEL_DEPLOY_HOOK_URL`), needing both the CMS deploy and the `web` job. On Vercel, the Root Directory is `apps/web`, automatic production deploys from Git are off and preview deploys for pull requests stay on (issue #12). Additive contract changes are what make this order safe.
