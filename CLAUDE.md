# Resource Hub

A headless WordPress demo in one repository (ADR 0033): a WordPress plugin, a Next.js front end, and the contract package they share. This file holds what every session needs. Each part has a `CLAUDE.md` beside it with the rules for edits there: `wp-content/plugins/resource-hub-wp/CLAUDE.md` for the plugin and `apps/web/CLAUDE.md` for the front end. Rules for one area (revalidation, caching and redirects, the contract, ADRs) live in `.claude/rules/` and load on their own when a matching file is read or edited. Read this file and the one for the part you are changing.

## Standards to build to

Headless WordPress with Next.js over REST (GraphQL as a stretch); React and TypeScript; custom Gutenberg blocks and modular plugins to WordPress Coding Standards and PSR-12; Composer; CI in GitHub Actions' workflow syntax, run on Depot CI; PHPUnit and Playwright; WordPress VIP habits (no direct DB assumptions, object cache, no filesystem writes); WCAG and Core Web Vitals. The reference shape is a headless WordPress site on Next.js and Vercel with ISR and on-demand revalidation from the CMS; this should look like a small, clean instance of that shape. Ambition here means depth, not feature count: a small system where every decision has a one-sentence reason, and a front end that is fast, accessible and tested.

## Hard constraints

- **Fresh, generic code only.** Nothing here may be copied or adapted from any prior employer's codebase or packages. Generic WordPress and Next.js patterns only; when in doubt, write it the textbook way and record the choice.
- **Never describe this as production code.** It is a demonstration of a pattern, written fresh.
- **No secrets in git.** On the CMS side, the revalidation secret and front-end URL live in `.env` (gitignored) and in wp-env's `config` or `define()` overrides; on the front end, `REVALIDATE_SECRET` and `WP_API_URL` live in `apps/web/.env.local` (gitignored) and in Vercel project settings. Never in a committed file.

## What it is

A filterable resources library: WordPress models it and pushes changes, Next.js renders it and rebuilds pages on demand.

- **The plugin**, `resource-hub`, at `wp-content/plugins/resource-hub-wp/`: the `resource` post type and its taxonomies and meta, the resolve, page, related and search REST routes, the revalidation hook, the lockdown that keeps the CMS's theme pages for logged-in users, the settings status page, and the settings of Relevanssi (the free search plugin, installed and pinned by Composer from wpackagist in `site-plugins/`, gitignored where it lands in `wp-content/plugins/relevanssi/`) held in code, with `wp resource-hub search-index` to build its index; the plugin works without it. Registered in the plugin, not a theme. It runs in a `wp-env` environment configured at the repository root and is deployed to the hosted CMS. Slice 4 is built: the related route and `related_picks` with the editor's picker for them, the `resource-hub/related-resources` block (registered from `build/`; its render callback writes the contract's marker with card rows inside), and on the front end the resource page's related section and the swap of the block's marker for its own list.
- **The front end**, a Next.js App Router app in TypeScript at `apps/web/`, deployed on Vercel: it renders the library, the CMS's static front page at `/` and every published page at its path from the WordPress REST API, always on its own server, and revalidates on demand when the CMS says so.
- **The contract package**, `@colbitron/resource-hub-ui` at `packages/ui/`: the JSON Schemas both sides check themselves against (ADR 0010) and the stylesheets and the one typeface both render with (`tokens.css`, `card.css`, `fonts/`), the type-accent table both mark resource types from (`type-accents.json`), consumed through the pnpm workspace and never published (ADR 0033).
- **The CMS theme**, `resource-hub`, at `wp-content/themes/resource-hub/`: a block theme for editors and logged-in previews only; anonymous visitors get the lockdown's 404 (ADR 0031), rendered with this theme's 404 template in wp-env, and on the hosted CMS only once a later slice-5 pull request deploys the theme. Slice 5 has built its skeleton (header, footer, `index` and `404` templates) and its assets (the `packages/ui` tokens, Figtree with its fallback faces and the lockup's CSS, copied into the theme's gitignored `build/` by `pnpm build` and loaded by `theme.json` and `functions.php`), and the wp-env sites run it as the active theme; the remaining templates, the System / Light / Dark control and its deploy are planned. Its spec is issue #89 and its rules are in its `README.md`.
- **Documentation:** `README.md` at the root with the architecture diagram and the layout; one ADR per hard-to-reverse decision under `docs/adr/`; topic pages under `docs/architecture/`; procedures under `docs/runbooks/`.

## The contract between the CMS and the front end

`packages/ui/README.md` is the contract's only full statement; the JSON Schemas in `packages/ui/schemas/` are its source of truth (ADR 0010). Change a schema and its fixtures first, then that README, then the code on both sides. In one paragraph: the front end reads the core REST API and four custom routes (resolve by slug, page by path, related by ID, search by query) on its server only, never in the browser, and rewrites every CMS URL it renders; WordPress POSTs a bearer-authenticated batch of 1 to 25 resource, term and page events to `{FRONTEND_URL}/api/revalidate/` from a cron request after the save, and the front end clears the union of each event's current and previous state. Public URLs are the same on both sites, always with a trailing slash; `topic` and `page` are reserved. Contract changes land in one pull request that touches both sides and the schemas, and stay additive, so the front end never breaks against a CMS one deploy behind.

## Standards and workflow

- Each part's language and framework standards are in its own `CLAUDE.md`.
- Agent-first build. The code is written by agents and reviewed by a human: the critical paths get read line by line before merge (on the CMS, the revalidation hook, auth and permission callbacks, and the sanitizers; on the front end, the revalidate route and the data layer's parsing); the rest goes through the gate. The gate is PHPCS, PHPUnit and Playwright for the plugin; typecheck, lint, unit tests, Playwright with axe, the specimen's screenshots and Lighthouse CI for the front end; the schema test for `packages/ui`; and a reviewer agent on a different model than the implementer. Nothing merges until all of it passes. Lighthouse CI runs only on `main`, never on a pull request, and a budget miss there does not hold the deploy back until issue #76 calibrates it; any other Lighthouse failure does. So the local gate before a push (review, fix, local gate, push once) includes, for a pull request that changes `apps/` other than Markdown or `packages/ui/`, `pnpm web:test:lighthouse:quick` with its medians read: one run per URL, `RH_LIGHTHOUSE_URLS` for a one-page change, the full five-run `pnpm web:test:lighthouse` for a big one. It is a smell test on the author's machine, not a gate; a laptop's numbers differ from CI's 2-vCPU sandboxes, and `main`'s run is the measurement of record (`apps/web/e2e/README.md`, "Lighthouse CI").
- Work on branches and open pull requests so the review has a diff to read. Small PRs, one concern each. Commit messages say what and why.
- **Write an ADR only for a decision that is expensive to undo** (data model, contract, hosting, repository shape, caching model, deploy pipeline), **constrains later work across the system, and had real alternatives worth recording.** One decision per record, with the rejected options and the costs, under `docs/adr/` at the next free number. A timeout, a tag list or tag map, a header value, a required block attribute, a tool version or a CSS choice is not an ADR, even when it matters; it goes in a docblock, a README or a topic page. When in doubt, don't write one. Everything else goes beside what it describes: part-level standards in that part's `CLAUDE.md` or README; contract semantics in `packages/ui/README.md`; how a subsystem works in `docs/architecture/`; a procedure in `docs/runbooks/`; the reasoning for one piece of code in its docblock or test name; an unbuilt spec or an open question in an issue. **No agent creates, amends, supersedes or deletes an ADR without Colby's explicit approval, given in the agent's own conversation or relayed by the orchestrator that briefed it, quoted and scoped to one change and never passed on again**; what counts as a relay, how records change, the `adr-approved` label and the guards on it are in `.claude/rules/adr.md`.
- **wp-env is the one environment** (ADR 0033), locally and in CI, and its containers are the source of truth for test results. There is no PHP, Composer or WP-CLI on the host, so PHP tooling runs through the root's `pnpm` wrappers (`pnpm composer`, `pnpm lint`, `pnpm test:php`). Setup, ports and the other commands are in the root `README.md` and the plugin's `README.md`.
- **Deploys run only from CI on `main`, on Depot CI: the CMS first, then the front end** (ADRs 0005, 0051, 0053). The front end never goes live ahead of the CMS it reads, which is why contract changes stay additive. Secrets, rollback and rotation are in `docs/runbooks/deploy.md`.
