# Resource Hub: WordPress side

The CMS half of a headless WordPress demo. Since ADR 0033 the repository is a monorepo: this plugin lives at `wp-content/plugins/resource-hub-wp/`, the Next.js front end at `apps/web/` (it has its own `CLAUDE.md`, which still describes this side as a sibling repository until the two files are merged in a follow-up), and the contract package at `packages/ui/`. Read both CLAUDE.md files before changing the contract in either.

## Standards to build to

Headless WordPress with Next.js over REST (GraphQL as a stretch); custom Gutenberg blocks and modular plugins to WordPress Coding Standards and PSR-12; Composer; GitHub Actions; PHPUnit and Playwright; WordPress VIP habits (no direct DB assumptions, object cache, no filesystem writes); WCAG and Core Web Vitals. Ambition here means depth, not feature count: a small system where every decision has a one-sentence reason.

## Hard constraints

- **No secrets in git.** The revalidation secret and front-end URL live in `.env` (gitignored) and in wp-env's `config` or `define()` overrides, never in a committed file.

## What it is

A WordPress plugin, `resource-hub`, at `wp-content/plugins/resource-hub-wp/`, plus a `wp-env` development environment at the repository root, that models a filterable resources library and pushes changes to a Next.js front end.

**Core:**
1. Custom post type `resource` with taxonomies `resource_topic` (flat, open like tags), `resource_type` (hierarchical, a fixed list editors manage; exactly one per resource, validated on save, radio buttons in the editor; never the reserved slugs `topic` or `page`, which WordPress refuses on create and edit with an admin error) and `resource_flag` (hierarchical, code-managed; its one term is `featured`), all `show_in_rest`, REST base `resources`. Permalinks are `/resources/{type}/{slug}/` through the rewrite slug `resources/%resource_type%` and a `post_type_link` filter, mirroring the front end's paths (ADRs 0007, 0009, 0024). Registered in the plugin, not a theme. The CMS's own theme pages (single resources, archives, feeds, core sitemaps, author and search pages, every route the theme renders) answer anonymous visitors with a 404 and never redirect; logged-in users and previews see them, oEmbed discovery links are removed, the REST API stays public, `robots.txt` disallows everything, and CMS responses carry meta robots and `X-Robots-Tag: noindex` (ADR 0031).
2. Post meta registered for REST with `register_post_meta` and sanitize and auth callbacks: `summary` (string), `source_url` (URL), and `related_picks` (ordered array of post IDs: positive integers, deduplicated, never the resource itself, at most 10; auth `MetaRules::can_edit_post`; in the REST `edit` context only; read by the editor's picker and the related route, never by the front end, ADR 0030). Featured is the `resource_flag` term, not meta (ADR 0009).
3. Two custom REST routes, both with a public `permission_callback`, argument validation, and core's `WP_Error` shape for 400 and 404:
   - `GET /resource-hub/v1/related/{id}?count=n`: `count` 1 to 10, default 3; 404 unless `id` is a published resource. Editor picks first (published ones only, first `count` win, no duplicates), then the newest published resources sharing a topic, never the resource itself; a resource with no topics returns its picks alone, with no fill. The merging happens here, in one PHPUnit-tested place, not on the front end (ADR 0030). Returns IDs only, `{ "items": [ { "id", "source": "pick" | "topic" } ] }` (ADRs 0020, 0021). Cached in the object cache under group `resource_hub`, key `related:{id}:{count}`, salted with the plugin's `resource_hub` and core's `terms` `last_changed`, one-day expiry (ADR 0022).
   - `GET /resource-hub/v1/resolve?slug=…`: a current or old slug to `{ "id", "type", "slug" }` of a published resource, through core's `_wp_old_slug` data and the private `_find_post_by_old_slug()`, guarded by `function_exists` and a PHPUnit test (ADR 0029).
   Anonymous responses from these routes, `/wp/v2/resources` and the three taxonomy endpoints carry `Cache-Control: no-cache, must-revalidate, max-age=0`, so the front end's data cache is the only HTTP cache (ADR 0023).
4. One dynamic Gutenberg block, `resource-hub/related-resources`, registered from `block.json` with a PHP `render_callback`. Attributes: `topic` (required, an integer term ID chosen from a `SelectControl`), `count` (1 to 10, default 3, clamped in PHP too), and `heading` (an editable `<h2>`, default "More on {Topic name}"). It lists the newest `count` published resources in that topic, excluding the current post, with no picks, on any post type; with no topic or a deleted term it renders nothing and the editor shows a placeholder or a warning (ADR 0027). Server-rendered so the same HTML serves the editor preview and the CMS's own pages; the output is a `data-rh-block` marker around a fallback list, which the front end swaps for its own component on its server; the marker carries `data-count`, `data-topic` (the term's current slug, for the cache tag), `data-topic-id` (for the REST filter) and `data-exclude` (the current post's ID) (ADR 0026). Styles come from the shared package, loaded through `block.json` only where the block is used (ADR 0028).
5. The revalidation hook: `wp_after_insert_post`, filtered to `resource`, deriving the event from the `$post_before` status and the new one, plus `before_delete_post` for published resources (ADR 0011); and `edit_terms` with `created_`, `edited_` and `delete_{taxonomy}` for `resource_topic` and `resource_type` (ADR 0017). Events are queued per PHP request and, at `shutdown`, scheduled as one WP-Cron single event with an immediate `spawn_cron()`, the full payload built at schedule time and passed as the event's arguments (ADRs 0012, 0014). The cron callback POSTs to the front end's `/api/revalidate` per the contract below with a 3-second timeout (the VIP sniff's cap; ADR 0013) and no retries; the editor saves again to retry. Handle every response code; store the result in post meta (term meta for term events) `_rh_last_revalidation` on every resource in the batch, each noting it was sent with N other changes (status `pending` → `sent` or `failed`, code, event, time, body cut to about 1 KB), expose it as a read-only `edit`-context REST field, and surface it in the block editor by polling after a non-autosave save, in a Resources list column hidden by default, and as a notice on the term edit screen (ADR 0018). The same cron job also sends every result to PostHog as a server-side event (`wp_remote_post`, 3 s, failures ignored, never retried), when `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST` are defined; that is the only record of force-delete and term-delete results, and without it they are only printed under WP-CLI. Under WP-CLI the batch is sent synchronously at `shutdown` instead of through cron, and the result is printed (ADR 0012). No `error_log()` (ADR 0032).
6. Tests and gates: PHPUnit (wp-env test suite) for the meta sanitizers, the REST route, the block render, and the revalidation payload and response handling (HTTP mocked); PHPCS on WordPress Coding Standards, the WordPress VIP Minimum ruleset, plus PSR-12; a Playwright smoke test against wp-env (create a resource, see the block render). All of it in GitHub Actions on every pull request and every push to `main`.
7. `composer.json` at the repo root managing PHPCS, the WordPress standards, PHPUnit, and the plugin's autoloader (PSR-4 under `src/`).
8. `README.md` with an architecture diagram and a decisions section; one ADR per real decision under `docs/adr/`.

**Stretch, in order, only once core is green:**
1. WPGraphQL alongside REST on the same types, so "which and why" has a live comparison.
2. Draft preview: a signed, expiring preview token the front end can exchange for draft content.
3. A second block using InnerBlocks.

## The contract with the front end

Change this only by changing both repos in the same sitting. The JSON Schemas in `packages/ui/schemas/` (`@colbitron/resource-hub-ui`, ADR 0010) are the source of truth and `packages/ui/README.md` holds the semantics a schema cannot express; this section summarises them. Change a schema and its fixtures first, then this section and the front end's.

- **Server side only:** the front end makes every CMS request on the Next.js server, with the CMS URL in a server-only environment variable (never `NEXT_PUBLIC_`), so the CMS's address never reaches the browser. WordPress emits absolute CMS URLs everywhere (`get_permalink()`, `content.rendered`, `_embed` media); the front end rewrites them: links lose the CMS domain, and images, including `<img src>` and `srcset` in `content.rendered`, become `/media/…`, served by a Next.js rewrite of `/media/:path*` to the CMS's uploads directory. This reduces exposure; it is not a security boundary.
- **Content read:** the front end reads `GET /wp-json/wp/v2/resources?_embed&per_page=…&page=…&resource_topic=…&resource_type=…&resource_flag=…`, `GET /wp-json/wp/v2/resources/{id}` (and `?slug=`), and the taxonomy endpoints `/wp-json/wp/v2/resource_topic`, `/wp-json/wp/v2/resource_type`, and `/wp-json/wp/v2/resource_flag`. Meta is `summary` and `source_url`, under `meta` because of `show_in_rest`; the front end never reads `related_picks`. Featured is the `resource_flag` term `featured`, not meta.
- **Related:** `GET /wp-json/resource-hub/v1/related/{id}?count=3` (1 to 10) returns `{ "items": [ { "id": 12, "source": "pick" | "topic" } ] }`, at most `count` items, picks first, already merged; the front end calls it once and does no merging of its own. The front end then reads the objects with `GET /wp-json/wp/v2/resources?include={ids}&orderby=include&_embed`.
- **Resolve:** `GET /wp-json/resource-hub/v1/resolve?slug=…` returns `{ "id": 12, "type": "webinar", "slug": "current-slug" }` for a published resource found by its current or an old slug, or a 404. The front end calls it only when the current-slug lookup misses.
- **Errors from both routes:** core's `WP_Error` shape, `{ "code", "message", "data": { "status" } }`, for 400 and 404.
- **Revalidation request** (WordPress to front end): `POST {FRONTEND_URL}/api/revalidate`, header `Authorization: Bearer {REVALIDATE_SECRET}`, header `Content-Type: application/json`, body a batch of 1 to 25 events. One PHP request is one batch; events are deduplicated per resource ID for resource events and per (taxonomy, term ID) for term events (earliest `previous`, latest state); more than 25 are split into several requests.
  ```json
  { "version": 1, "events": [
    { "type": "resource", "event": "publish" | "update" | "unpublish" | "trash" | "delete", "id": 123, "slug": "example", "rest_url": "https://cms.example/wp-json/wp/v2/resources/123", "types": ["type-slug"], "topics": ["topic-slug"], "previous": { "slug": "old-example", "types": ["type-slug"], "topics": ["topic-slug"] } | null },
    { "type": "term", "taxonomy": "resource_topic" | "resource_type", "event": "create" | "update" | "delete", "id": 45, "slug": "topic-slug", "name": "Topic name", "previous": { "slug": "old-slug", "name": "Old name" } | null }
  ] }
  ```
  `types` has exactly one element. The top-level fields are the public state the event concerns: after the save for `publish` and `update`, the last public state (`$post_before`) for `unpublish`, `trash` and `delete`. `previous` is set on `update` only, with every field filled, and is `null` otherwise. The front end refreshes on `publish` and `update`, removes on the other three, and revalidates the union of the current and previous state. Restoring from the trash sends nothing. `resource_flag` sends no term events.
- **Revalidation response:** `200 { "revalidated": ["/resources/", "/resources/webinar/example/"] }`; `400 { "error": "…" }` for a malformed body; `401 { "error": "unauthorized" }` for a bad or missing bearer; `500 { "error": "…" }` when the front end fails. The plugin records status and body and shows them to the editor.
- **Public URLs**, the same on both sites, always with a trailing slash: `/resources/`, `/resources/[type]/`, `/resources/topic/[topic]/`, `/resources/[type]/topic/[topic]/`, `/resources/[type]/[slug]/`, and `…/page/[n]/` on every listing. `topic` and `page` are reserved and never type slugs. The slug is the identity; a wrong type segment, or an old slug found through resolve, redirects with a computed single-hop 308 and `Cache-Control: no-store`; never send a permanent redirect without a cache header (ADR 0025). Those redirects are the front end's; the CMS redirects no one, and its theme pages are a 404 for anonymous visitors (ADR 0031). `get_permalink()` stays absolute; the front end strips the CMS domain from every link in the HTML it renders. Cache tags on the front end are `resources`, `resource:{slug}`, `topic:{slug}` and `type:{slug}`.
- **Block marker:** the related-resources block renders `<div data-rh-block="related-resources" data-count="3" data-topic="topic-slug" data-topic-id="45" data-exclude="123">` with its `<h2>` heading and a fallback `<ul>` of links. The front end parses `content.rendered` on its server, never in the browser, and swaps the wrapper for its `<RelatedResources>` server component, in the same pass that strips link domains and rewrites images to `/media/`. `data-topic` is the term's current slug, resolved at render time from the stored term ID, and names the `topic:{slug}` cache tag; `data-topic-id` is that ID, for the `resource_topic` REST filter; `data-exclude` is the ID of the post the block sits in, left out of the list.
- **Shared styles:** `@colbitron/resource-hub-ui` (`packages/ui/` here) holds `tokens.css`, `related.css` and `card.css`; the class names (`.rh-related`, `.rh-card…`) and tokens are part of the contract. WordPress builds from the workspace source; the front end installs a pinned version from GitHub Packages through Vercel's `NPM_RC`. It is private because a public npm package would be discoverable as a general-use package; if the `NPM_RC` spike fails, the owner decides the delivery route again, with no automatic public fallback (ADR 0028). No shared JavaScript.
- **Configuration on this side:** `RESOURCE_HUB_FRONTEND_URL` and `RESOURCE_HUB_REVALIDATE_SECRET` as PHP constants (wp-config or wp-env `config`), falling back to options. Optional `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST` constants turn on results logging (ADR 0032); unset, it is skipped. None of them is ever committed. The settings page is a status page: it shows which source is active, never displays the secret, and has a "Send test revalidation" button that sends a real `update` event for the most recently modified published resource or one chosen in a searchable picker, is disabled when nothing is published, and records its result like any real event, in that resource's `_rh_last_revalidation` and in PostHog when configured, plus a non-autoloaded option the status page reads (ADR 0019).

## Standards and workflow

- PHP 8.4, matching the host (see ADR 0005). WordPress 6.9 or newer, because the related cache uses `wp_cache_get_salted()` and `wp_cache_set_salted()`, which arrived in 6.9 (ADR 0022). WordPress Coding Standards, the WordPress VIP Minimum ruleset, and PSR-12 via PHPCS; fix, don't silence. Escape on output, sanitize on input, nonces and capability checks everywhere, `$wpdb->prepare` if raw SQL is ever justified (it should not be here). Object cache for the related query; no transients as storage; no filesystem writes at runtime.
- Agent-first build. The human reviews rather than writes: the critical paths (the revalidation hook, auth and permission callbacks, the sanitizers) get read line by line before merge; the rest goes through the gate. The gate is PHPCS, PHPUnit, Playwright, and a reviewer agent on a different model than the implementer. Nothing merges until all of it passes.
- Work on branches and open pull requests so the review has a diff to read. Small PRs, one concern each. Commit messages say what and why.
- Record each real decision as an ADR as it is made, one decision per record, with rejected options where some were considered.
- **Local environment, decided 2026-11-03: `@wordpress/env` on Docker is the canonical environment.** `.wp-env.json` at the repository root is committed and mounts `wp-content/plugins/resource-hub-wp`; the same `wp-env` commands run the PHPUnit suite locally and in GitHub Actions. LocalWP is not used; a second environment would mean a second test setup to keep in step. Host toolchain as of 2026-11-03: Node 24 and pnpm present; Docker installed (start it first); no PHP, Composer, or WP-CLI on the host. Composer ships in the wp-env cli containers, so all PHP tooling runs there with no host install: `pnpm composer`, `pnpm lint`, `pnpm test:php` from the repository root (see the root `package.json`; `composer.json`, `phpcs.xml.dist` and `phpunit.xml.dist` are in the plugin directory). The JavaScript toolchain (wp-scripts, Playwright) is a dependency of the plugin package, `wp-content/plugins/resource-hub-wp/package.json`; the root's `pnpm build`, `pnpm lint:js` and `pnpm test:e2e` delegate to it with `pnpm --filter`, and `pnpm web:lint`, `web:typecheck` and `web:build` do the same for `apps/web`. The container is the source of truth for test results.
- **Hosted CMS, decided 2026-11-03: Cloudways Flexible on a DigitalOcean 2 GB server, PHP 8.4** (ADR 0005). It is the site the Vercel front end reads and revalidates against. Deploys happen only from CI on `main` after the gate and the web job pass, by rsync over SSH from `wp-content/plugins/resource-hub-wp` in this repository into the same path on the host (one directory name in the repository, wp-env and the host, so the plugin basename matches everywhere). Five repository secrets feed the job: `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_KNOWN_HOSTS`. The two configuration constants are `define()`d in the host's `wp-config.php`.
- **PHPUnit resets the tests site.** The WordPress test bootstrap drops and reinstalls the tests database (port 8889) on every run, which deactivates every plugin there. The dev site (port 8888) is untouched. Every Playwright spec therefore activates the plugin itself in a `beforeAll` via `requestUtils.activatePlugin( 'resource-hub' )` and never assumes prior state; share that from a fixture once there is more than one spec. CI runs PHPUnit before Playwright for the same reason.
