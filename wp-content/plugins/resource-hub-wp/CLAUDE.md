# Resource Hub: WordPress plugin

The CMS half of the project: the `resource-hub` plugin in this directory, mounted into wp-env from the repository root and deployed to the hosted CMS. The root `CLAUDE.md` holds what applies to the whole project, including the hard constraints, the workflow, the deploy order and the contract with the front end, in one copy; read it first. This file holds what applies only to the plugin.

## What it is

A WordPress plugin that models a filterable resources library and pushes changes to the Next.js front end in `apps/web/`.

**Core:**
1. Custom post type `resource` with taxonomies `resource_topic` (flat, open like tags), `resource_type` (hierarchical, a fixed list editors manage; exactly one per resource, enforced on REST saves (the block editor's only save path); Quick and Bulk Edit cannot change the type (hidden from both, and its terms dropped from a Bulk Edit request) and cannot publish or schedule a resource that does not have exactly one type (Quick Edit refuses with a message; Bulk Edit keeps that resource's status and names it in a notice), while a resource already published or scheduled keeps its status there; radio buttons in the editor; and a type resources still have cannot be deleted from the Types screen, its bulk delete included, or over REST; the classic `post.php` form submission, XML-RPC, WP-CLI and PHP calls (the seeder among them) are not guarded, and the revalidation hook never sends an event whose top-level `types` isn't exactly one element, so the front end never receives an invalid state from any of them; never the reserved slugs `topic` or `page`, which WordPress refuses on create and edit with an admin error) and `resource_flag` (hierarchical, code-managed; its one term is `featured`), all `show_in_rest`, REST base `resources`. Permalinks are `/resources/{type}/{slug}/` through the rewrite slug `resources/%resource_type%` and a `post_type_link` filter, mirroring the front end's paths (ADRs 0007, 0009, 0024). Registered in the plugin, not a theme. The CMS's own theme pages (single resources, archives, feeds, core sitemaps, author and search pages, every route the theme renders) answer anonymous visitors with a 404 and never redirect; logged-in users and previews see them, oEmbed discovery links are removed, the REST API stays public, `robots.txt` disallows everything, and CMS responses carry meta robots and `X-Robots-Tag: noindex` (ADR 0031).
2. Post meta registered for REST with `register_post_meta` and sanitize and auth callbacks: `summary` (string), `source_url` (URL), and `related_picks` (ordered array of post IDs: positive integers, deduplicated, never the resource itself, at most 10; auth `MetaRules::can_edit_post`; in the REST `edit` context only; read by the editor's picker and the related route, never by the front end, ADR 0030). Featured is the `resource_flag` term, not meta (ADR 0009).
3. Two custom REST routes, both with a public `permission_callback`, argument validation, and core's `WP_Error` shape for 400 and 404:
   - `GET /resource-hub/v1/related/{id}?count=n`: `count` 1 to 10, default 3; 404 unless `id` is a published resource. Editor picks first (published ones only, first `count` win, no duplicates), then the newest published resources sharing a topic, never the resource itself; a resource with no topics returns its picks alone, with no fill. The merging happens here, in one PHPUnit-tested place, not on the front end (ADR 0030). Returns IDs only, `{ "items": [ { "id", "source": "pick" | "topic" } ] }` (ADRs 0020, 0021). Cached in the object cache under group `resource_hub`, key `related:{id}:{count}`, salted with the plugin's `resource_hub` and core's `terms` `last_changed`, one-day expiry (ADR 0022).
   - `GET /resource-hub/v1/resolve?slug=…`: a current or old slug to `{ "id", "type", "slug" }` of a published resource, through core's `_wp_old_slug` data and the private `_find_post_by_old_slug()`, guarded by `function_exists` (without it, only current slugs resolve) and a PHPUnit test (ADR 0029). `slug` is required, at most 200 bytes as sent, and run through `sanitize_title()`; empty once sanitized is a 400. The cap keeps an ASCII slug from being shortened before the lookup; it does not stop `sanitize_title()` cutting a percent-encoded non-ASCII slug to 200 characters, which is harmless because stored slugs are cut the same way and the front end redirects to the canonical one. When an unpublished and a published resource both once had a slug, core's single match can be the unpublished one, and the slug is a 404 (ADR 0029). The current slug is looked up first. A resource without exactly one type, or with a reserved one, is a 404, because the schema would reject the body. In `src/Rest/ResolveRoute.php`.
   Anonymous responses from these routes, `/wp/v2/resources` and the three taxonomy endpoints carry `Cache-Control: no-cache, must-revalidate, max-age=0`, so the front end's data cache is the only HTTP cache (ADR 0023).
4. One dynamic Gutenberg block, `resource-hub/related-resources`, registered from `block.json` with a PHP `render_callback`. Attributes: `topic` (required, an integer term ID chosen from a `SelectControl`), `count` (1 to 10, default 3, clamped in PHP too), and `heading` (an editable `<h2>`, default "More on {Topic name}"). It lists the newest `count` published resources in that topic, excluding the current post, with no picks, on any post type; with no topic or a deleted term it renders nothing and the editor shows a placeholder or a warning (ADR 0027). Server-rendered so the same HTML serves the editor preview and the CMS's own pages; the output is a `data-rh-block` marker around a fallback list, which the front end swaps for its own component on its server; the marker carries `data-count`, `data-topic` (the term's current slug, for the cache tag), `data-topic-id` (for the REST filter) and `data-exclude` (the current post's ID) (ADR 0026). Styles come from the shared package through the workspace, loaded through `block.json` only where the block is used (ADR 0041).
5. The revalidation hook: `wp_after_insert_post`, filtered to `resource`, deriving the event from the `$post_before` status and the new one, plus `before_delete_post` for published resources (ADR 0011); and `edit_terms` with `created_`, `edited_` and `delete_{taxonomy}` for `resource_topic` and `resource_type` (ADR 0017). Events are queued per PHP request, deduplicated, and, at `shutdown`, scheduled as one WP-Cron single event per batch of at most 25 with an immediate `spawn_cron()`, the full payload built at schedule time and passed, with a batch ID, as the event's arguments (ADRs 0012, 0014). The public state of a `publish` or `update` event is read again from the post at `shutdown` (ADR 0011). A resource event whose `types` is not exactly one element is never sent: it is held back and recorded on that resource as `failed` with a plain message, because the schema would reject the whole batch; when nothing is configured, nothing is scheduled and the "not configured" result is recorded at once. The cron callback POSTs to the front end's `/api/revalidate` per the contract in the root `CLAUDE.md` with a 3-second timeout (the VIP sniff's cap; ADR 0013) and no retries; the editor saves again to retry. Handle every response code; store the result in post meta (term meta for term events) `_rh_last_revalidation` on every resource in the batch, each noting it was sent with N other changes (status `pending` → `sent` or `failed`, code, event, time, body cut to about 1 KB), expose it as a read-only `edit`-context REST field, and surface it in the block editor by polling after a non-autosave save, in a Resources list column hidden by default, and as a notice on the term edit screen (ADR 0018). The same cron job also sends every result to PostHog as a server-side event (`wp_remote_post`, 3 s, failures ignored, never retried), when `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST` are defined; that is the only record of force-delete and term-delete results, and without it they are only printed under WP-CLI. Under WP-CLI the batch is sent synchronously at `shutdown` instead of through cron, and the result is printed (ADR 0012). No `error_log()` (ADR 0032).
6. Tests and gates: PHPUnit (wp-env test suite) for the meta sanitizers, the REST route, the block render, and the revalidation payload and response handling (HTTP mocked); PHPCS on WordPress Coding Standards, the WordPress VIP Minimum ruleset, plus PSR-12; a Playwright smoke test against wp-env (create a resource, see the block render). All of it in GitHub Actions on every pull request and every push to `main`.
7. `composer.json` in this directory, managing PHPCS, the WordPress standards, PHPUnit, and the plugin's autoloader (PSR-4 under `src/`).

## Standards

- PHP 8.4, matching the host (see ADR 0005). WordPress 6.9 or newer, because the related cache uses `wp_cache_get_salted()` and `wp_cache_set_salted()`, which arrived in 6.9 (ADR 0022). WordPress Coding Standards, the WordPress VIP Minimum ruleset, and PSR-12 via PHPCS; fix, don't silence. Escape on output, sanitize on input, nonces and capability checks everywhere, `$wpdb->prepare` if raw SQL is ever justified (it should not be here). Object cache for the related query; no transients as storage; no filesystem writes at runtime.
- Tooling lives in this directory: `composer.json`, `phpcs.xml.dist` and `phpunit.xml.dist` for PHP, run inside the wp-env containers through the root's `pnpm composer`, `pnpm lint` and `pnpm test:php`; and the JavaScript toolchain (wp-scripts, Playwright) in this directory's `package.json`, which the root's `pnpm build`, `pnpm lint:js` and `pnpm test:e2e` call with `pnpm --filter`.
- **PHPUnit resets the tests site.** The WordPress test bootstrap drops and reinstalls the tests database (port 8889) on every run, which deactivates every plugin there. The dev site (port 8888) is untouched. Every Playwright spec therefore imports `test` from the shared worker-scoped fixture in `tests/e2e/fixtures.js`, which activates the plugin with `requestUtils.activatePlugin( 'resource-hub' )` before any spec runs, and never assumes prior state. CI runs PHPUnit before Playwright for the same reason.
