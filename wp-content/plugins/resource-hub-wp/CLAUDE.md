# Resource Hub: WordPress plugin

The CMS half of the project: the `resource-hub` plugin in this directory, mounted into wp-env from the repository root and deployed to the hosted CMS. The root `CLAUDE.md` holds what applies to the whole project; read it first. This file holds the rules for every edit in the plugin. How to run and test it is in `README.md` beside this file; how revalidation works end to end is in `docs/architecture/revalidation.md`; the contract is in `packages/ui/README.md`; and each class's docblock holds the reasoning for its own rules. Read the docblock before changing a class.

## What it is

A WordPress plugin that models a filterable resources library and pushes changes to the Next.js front end in `apps/web/`.

**Core:**
1. **Content model** (`src/ContentModel/`): the post type `resource` with `resource_topic` (flat, open like tags), `resource_type` (hierarchical, a fixed list editors manage) and `resource_flag` (hierarchical, code-managed; its one term is `featured`), all `show_in_rest`, REST base `resources`; permalinks `/resources/{type}/{slug}/` through the rewrite slug `resources/%resource_type%` and a `post_type_link` filter (ADRs 0007, 0024). Rules on every edit:
   - A resource has exactly one type once it is public. `OneType` enforces it on the save paths the editor uses and `UsedTypes` keeps a type that resources still have from being deleted; the docblocks name the unguarded paths. The revalidation hook never sends a state that breaks it.
   - `topic` and `page` are never type slugs (`ReservedTypeSlugs`); `resources`, `api`, `media` and `_next` are never top-level page slugs (`ReservedPageSlugs`).
   - No `resource` post slug or term slug in the three taxonomies stores a percent escape the front end's router decodes (`SlugEscapes`); `wp resource-hub decode-slugs` repairs slugs stored before the rule.
   - `hierarchical` on `resource_type` and `resource_flag` is the capability boundary, not a UI choice: changing it is a security change (ADR 0007).
   - The CMS's theme pages answer anonymous visitors with a 404 and never redirect (`src/Lockdown/`, ADR 0031); the REST API, the admin, login, cron and uploads are untouched.
2. **Post meta** registered for REST with `register_post_meta`, with sanitize and auth callbacks: `summary` (string) and `source_url` (URL), each with a rule in `MetaRules` stated clause by clause and tested the same way (ADR 0008). Featured is the `resource_flag` term, not meta. `related_picks` is slice 4 (issue #50).
3. **Two custom REST routes** (`src/Rest/`), each with a public `permission_callback`, argument validation and core's `WP_Error` shape for 400 and 404: `GET /resource-hub/v1/resolve?slug=…` (`ResolveRoute`) and `GET /resource-hub/v1/page?path=…` (`PageRoute`, with the path rules in `src/Pages/PagePath.php`). The related route is slice 4. `NoCacheHeader` sends the contract's no-cache header; its rule is in `.claude/rules/caching-and-redirects.md`.
4. **The block** `resource-hub/related-resources` in `blocks/related-resources/` is an editor scaffold with no PHP registration. Its render callback, attributes and marker are specified in issue #50 and the contract's "Block marker" section; do not describe them as built.
5. **The revalidation hook** (`src/Revalidation/`, with its screens in `src/Admin/` and `src/Editor/`): its rules are in `.claude/rules/revalidation.md`, which loads when you touch those files, and how it works end to end is in `docs/architecture/revalidation.md`.
6. **Tests and gates:** PHPUnit, PHPCS and Playwright, all in GitHub Actions on every pull request and every push to `main`; what each covers is in `README.md` beside this file.
7. `composer.json` in this directory, managing PHPCS, the WordPress standards, PHPUnit, the schema validator and the plugin's autoloader (PSR-4 under `src/`).

## Standards

- PHP 8.4 in wp-env, CI and on the host (ADR 0005); the declared floor is 8.2 and is not exercised by CI. WordPress 6.9 or newer (`Requires at least`). WordPress Coding Standards as the base, the WordPress VIP Minimum ruleset on top (not VIP-Go, whose relaxations assume VIP's infrastructure), and the PSR-12 sniffs that do not conflict; where WordPress and PSR-12 disagree, WordPress wins, and each exclusion in `phpcs.xml.dist` names the conflict. Warnings fail the gate: fix, don't silence. Escape on output, sanitize on input, nonces and capability checks everywhere, `$wpdb->prepare` if raw SQL is ever justified (it should not be here). Includes use `__DIR__`, because the VIP ruleset flags variable includes. Object cache, not transients, for anything cached; no filesystem writes at runtime; no `error_log()`.
- PHPUnit stays on 9.6 because the WordPress core test library's `yoast/phpunit-polyfills` 1.x tops out there. Tests are written against polyfills 4.x, but `phpunit.xml.dist` uses PHPUnit 9 names (`convertDeprecationsToExceptions`, `<coverage>`), so moving the pin also needs the PHPUnit 10+ configuration migration. The schema validator is `opis/json-schema`, reading `packages/ui/schemas/` through the mapping in `.wp-env.json` (`tests/phpunit/Revalidation/SchemaValidator.php`).
- Tooling lives in this directory: `composer.json`, `phpcs.xml.dist` and `phpunit.xml.dist` for PHP, run inside the wp-env containers through the root's `pnpm composer`, `pnpm lint` and `pnpm test:php`; and the JavaScript toolchain (wp-scripts, Playwright) in this directory's `package.json`, which the root's `pnpm build`, `pnpm lint:js` and `pnpm test:e2e` call with `pnpm --filter`.
- **PHPUnit resets the tests site.** The bootstrap drops and reinstalls the tests database (port 8889), which deactivates every plugin there. Every Playwright spec imports `test` from the worker-scoped fixture in `tests/e2e/fixtures.js`, which activates the plugin before any spec runs, and never assumes prior state. CI runs PHPUnit before Playwright for the same reason.
- XML-RPC is off (`src/Security/XmlRpc.php`): no client uses it, and it was an unguarded save path for the one-type rule.
