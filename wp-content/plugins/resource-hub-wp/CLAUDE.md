# Resource Hub: WordPress plugin

The CMS half of the project: the `resource-hub` plugin in this directory, mounted into wp-env from the repository root and deployed to the hosted CMS. The root `CLAUDE.md` holds what applies to the whole project; read it first. This file holds the rules for every edit in the plugin. How to run and test it is in `README.md` beside this file; how revalidation works end to end is in `docs/architecture/revalidation.md`; the contract is in `packages/ui/README.md`; and each class's docblock holds the reasoning for its own rules. Read the docblock before changing a class.

## What it is

A WordPress plugin that models a filterable resources library and pushes changes to the Next.js front end in `apps/web/`.

**Core:**
1. **Content model** (`src/ContentModel/`): the post type `resource` with `resource_topic` (flat, open like tags), `resource_type` (hierarchical, a fixed list editors manage) and `resource_flag` (hierarchical, code-managed; its one term is `featured`), all `show_in_rest`, REST base `resources`; permalinks `/resources/{type}/{slug}/` through the rewrite slug `resources/%resource_type%` and a `post_type_link` filter (ADRs 0007, 0024). Rules on every edit:
   - A resource has exactly one type once it is public. `OneType` enforces it on the save paths the editor uses (an autosave that would publish a stored draft is judged by `RequiredFields::check_autosave()` with OneType's rule on the stored types, because core's autosaves route ignores `rest_pre_insert_resource` errors and never stores terms) and `UsedTypes` keeps a type that resources still have from being deleted; OneType's docblock names the paths it does not guard (`post.php`, WP-CLI and PHP calls). The revalidation hook never sends a state that breaks it.
   - A resource also has a title, at least one topic and a summary once it is public, because the front end shows "Untitled resource", no topic listing and an empty card without them. `RequiredFields` refuses a REST save, an autosave that would write a public status onto a stored draft (recognised by the handler core matched, not the URL, since core matches routes without regard to case), or a Quick Edit that would publish, or keep published, a resource lacking one, judging each field from the request when it carries it and from storage when it does not; Quick Edit of a resource already public is judged "no worse", as OneType's is. Blank is what the front end would show nothing for: a title is blank once tags are stripped, entities decoded and whitespace, no-break spaces and zero-width characters removed; a summary is judged as `MetaRules::sanitize_summary()` would store it and is blank once those characters are removed, with no decoding, because the front end shows it verbatim (a typed `&nbsp;` is text). A draft may lack all of them and unpublishing is never refused, so no work is lost. The editor plugin in `editor/required-fields/` is the convenience in front of that check: one persistent notice that names what is missing and focuses the control, "Required" states in the Types, Topics and Resource details panels that their controls are described by (`aria-describedby`, `aria-required`, `aria-invalid` while the edited status is `publish` or `future` or the pre-publish sidebar is open), a pre-publish checklist, and the editor's saving lock held only while a required field is missing and the edited status is `publish` or `future` or the pre-publish sidebar is open, so drafts and unpublishing always save. RequiredFields' docblock names what it does not guard: Bulk Edit, revision restore (it can blank a published title), deleting a topic (it can leave a published or scheduled resource with none, and cron then publishes the scheduled one unchecked; guarding it is Colby's product call, not built), cron publishing, `post.php`, WP-CLI and PHP calls. The README has the WP-CLI line that lists resources published without one.
   - `topic` and `page` are never type slugs (`ReservedTypeSlugs`); `resources`, `api`, `media`, `_next` and `search` are never top-level page slugs (`ReservedPageSlugs`).
   - No `resource` post slug or term slug in the three taxonomies stores a percent escape the front end's router decodes (`SlugEscapes`); `wp resource-hub decode-slugs` repairs slugs stored before the rule.
   - `hierarchical` on `resource_type` and `resource_flag` is the capability boundary, not a UI choice: changing it is a security change (ADR 0007).
   - The CMS's theme pages answer anonymous visitors with a 404 and never redirect (`src/Lockdown/`, ADR 0031); the REST API, the admin, login, cron and uploads are untouched. For everyone, the posts page under a static front page is a 404 too (`src/Pages/PostsPage.php`, on `pre_handle_404` after the lockdown), because the front end's page route never serves it.
   - The front end's listing paths the CMS answers too (`src/Collections/`): core's rules give the library and a type's first page, and `Routes` adds `/resources/topic/{topic}/`, `/resources/{type}/topic/{topic}/` and the `/page/{n}/` forms of those and of a type, at the top of the rules, mapped to the taxonomies' query vars. `CollectionQuery` makes a collection's main query the front end's: twelve to a page, the lead's row out of the library's first page with the count unchanged, and a 404 for a type or topic that names no term. `PaginationNumbers` windows core's pagination numbers on a collection as the front end's `pageWindow()` does (`PageWindow`, held with the front end to `packages/ui/fixtures/pagination/page-window.json`). Every rule's reason is in the class docblocks.
2. **Post meta** registered for REST with `register_post_meta`, with sanitize and auth callbacks: `summary` (string, required once the resource is public, see `RequiredFields`), `source_url` (URL) and `related_picks` (an ordered list of post IDs the related route puts first, in the REST `edit` context only so anonymous reads never see it), each with a rule in `MetaRules` stated clause by clause and tested the same way (ADR 0008). Featured is the `resource_flag` term, not meta. The editor's control for `related_picks` is `editor/resource-details/related-picks.js`, in the Resource details panel: a search over published resources, filtered by type and topic, and an ordered list with move and remove buttons; it mirrors the server's cap and keeps a pick that is no longer published in the list with a note, as the meta does.
3. **Four custom REST routes** (`src/Rest/`), each with a public `permission_callback`, argument validation and core's `WP_Error` shape for 400 and 404: `GET /resource-hub/v1/resolve?slug=…` (`ResolveRoute`), `GET /resource-hub/v1/page?path=…` (`PageRoute`, with the path rules in `src/Pages/PagePath.php`), `GET /resource-hub/v1/related/{id}?count=n` (`RelatedRoute`, the HTTP shape around `RelatedItems`, which merges picks and topic matches in PHP and keeps each list in `RelatedCache`, a salted object-cache entry; the front end's related section reads the route, and the theme's `related` block renders the same selection from the same entry) and `GET /resource-hub/v1/search?q=…&page=n` (`SearchRoute`, one `WP_Query` for published resource and page IDs with `'relevanssi' => true`, 12 to a page and at most 10 pages, each page kept in `SearchCache` under RelatedCache's salt plus a search-only stamp; its PHPUnit tests assert membership, counts and paging, never order, so they pass with Relevanssi active or core's search answering). `NoCacheHeader` sends the contract's no-cache header; its rule is in `.claude/rules/caching-and-redirects.md`. `RouteMatch` tells the content-model REST guards which route and handler a request reached, by the pattern and the callback core matched, never by the URL's spelling (core matches paths without regard to case).
4. **The block** `resource-hub/related-resources`: the editor source in `blocks/related-resources/`, the registration and the render callback in `src/Blocks/RelatedResourcesBlock.php`. It is registered from its compiled copy in `build/`, which the deploy carries and `blocks/` is not, so `pnpm build` comes before PHPUnit and Playwright, as in CI. It renders the contract's marker (`packages/ui/README.md`, "Block marker") around an `<h2>` and `card.css` rows (titles at `h3`, the type's mark in its accent from the shared type-accent table, which the build copies into `build/type-accents.json` and `TypeAccents` reads, or `neutral`): the newest published resources in one `resource_topic` term stored by ID, the host post left out, `count` clamped to 1–10 in PHP. A resource with an empty plain-text title (the front end's `cardTitle()` test) or without exactly one type is dropped, never shown as "Untitled resource" or without its type; the query over-fetches `SLACK` rows so a few drops do not shorten the list. Only a PHP caller can break the one-type rule, but an editor can publish a blank title. The class docblock has every rule and why the rows are the card's markup. Its stylesheets are two shared handles, loaded through `block.json` only where the block is used: `resource-hub-tokens`, which it shares with the CMS theme (`src/Blocks/SharedTokens.php`: the theme registers it first, and the plugin registers its own byte-for-byte copy in `build/shared/` when no theme has), so a page with the block loads `tokens.css` once; and `resource-hub-card` (`src/Blocks/SharedCard.php`), the package's `card.css` copied byte for byte into `build/shared/` with the `card-labels.css` it imports, which the `resource-card` block shares, so a page with both loads the row's rules once. The front end swaps a valid marker for its own `<RelatedResources>` list and keeps the card rows inside it as the fallback; the row markup it keeps is part of the contract, so a change to it is a contract change. Eight more blocks, built and registered the same way, write the front end's markup for the CMS theme's templates, each with no wrapper attributes and each rendering nothing for a resource without exactly one type, and the card and the related section nothing for one that is not published, while the article's meta, summary and source blocks also render an unpublished resource for a user who may `read_post` it, for logged-in previews (`ContextResource`; the related block never hands an unpublished host to `RelatedItems`, whose cache entry the public route serves): `resource-hub/resource-card` (`ResourceCardBlock`), one listing row for the post a `core/post-template` gives it; for `single-resource.html`, `resource-hub/resource-meta` (`ResourceMetaBlock`), the resource page's meta line, `resource-hub/resource-summary` (`ResourceSummaryBlock`), its lead paragraph, `resource-hub/resource-source` (`ResourceSourceBlock`), its source line, and `resource-hub/related` (`RelatedBlock`), its related section, the heading and `card.css` rows at `h3` from `RelatedItems` at the front end's count, a row the front end drops dropped and nothing when none is left; and for the collection templates, reading the main query through `src/Collections/`, `resource-hub/collection-head` (`CollectionHeadBlock`, the collection's `h1`, count and filter rows), `resource-hub/featured-lead` (`FeaturedLeadBlock`, the library's lead section) and `resource-hub/collection-empty` (`CollectionEmptyBlock`, the empty state), each nothing off a collection. The rows, the article's lines and the lead render through `ResourceCardMarkup`, the one PHP copy of the front end's card and article markup, and the contract's markup fixtures (`packages/ui/fixtures/markup/`) hold it and the head to the front end's `ResourceCard`, `ResourceArticle`, `RelatedList`, `FeaturedSection` and `CollectionHead`: a change to that markup changes the fixtures, `MarkupParityTest` and the front end's `markup-parity.test.tsx` in the same pull request. The blocks' stylesheets are the shared handles for what they write (the tokens, `card.css` for rows, `card-labels.css` inlined for the meta line); what the template renders around them (`resource.css`, `related.css`, `listing.css`, `lead.css`, `search.css`) is the theme's. Three more write the theme's search page (`search.html`) over core's main search query, read through `src/Search/SearchRequest.php`: `resource-hub/search-head` (`SearchHeadBlock`, the `h1`, the form with the reader's words and the count line), `resource-hub/search-empty` (`SearchEmptyBlock`, the sentence for each state that lists nothing) and `resource-hub/page-card` (`PageCardBlock`, a published page as the front end's `PageCard`, through `ResourceCardMarkup::page_row()`), held to the front end's `SearchPage` and `PageCard` by the contract's `search/` scenes and `page/` samples.
5. **The revalidation hook** (`src/Revalidation/`, with its screens in `src/Admin/` and `src/Editor/`): its rules are in `.claude/rules/revalidation.md`, which loads when you touch those files, and how it works end to end is in `docs/architecture/revalidation.md`.
6. **Tests and gates:** PHPUnit, PHPCS and Playwright, all in CI on Depot CI (`.depot/workflows/ci.yml`) on every push to `main` and every pull request that changes `wp-content/` or a shared path (`docs/runbooks/deploy.md`, "Which jobs a pull request runs"); what each covers is in `README.md` beside this file.
7. **Search** (`src/Search/`): Relevanssi (free), installed beside the plugin from `site-plugins/`, configured in code by `RelevanssiConfig`: every option that decides what is indexed or whether a search writes is pinned in `PINNED` through `pre_option_*` filters (logging and admin search off; resources and pages; the `summary` meta; topic and type names; no comments, author, excerpt or shortcodes), so no setting is stored, and the rest that affect the index are in `FINGERPRINTED`; Relevanssi's own filters keep a search Relevanssi does not answer on core's search (`relevanssi_prevent_default_request`), index only published posts (`relevanssi_valid_status`) and never render the related-resources block into a post's index (`relevanssi_block_to_render`); `RelevanssiFoundPosts` restores Relevanssi's `found_posts`, which core overwrites for `fields => ids`; `RelevanssiPostCache` drops Relevanssi's in-request copy of a post when core cleans its cache; `SearchIndex` rebuilds the index for `wp resource-hub search-index` only when the stamp of Relevanssi's version, its tables' version and `RelevanssiConfig::fingerprint()` changed (`--force` always), upgrading the tables first, because a rebuild empties the index while it runs; `TermReindex` re-indexes the published resources of a renamed or deleted topic or type from cron. A new option that changes what is indexed goes into `PINNED` or `FINGERPRINTED`, and a change to one of `RelevanssiConfig`'s filters raises `INDEX_LOGIC`. `PINNED_OUTPUT` pins Relevanssi's snippets, highlighting and its "(Search hits: …)" line off, so a result shows its stored text; none is fingerprinted. The CMS theme's search page lives here too: `SearchPath` puts core's search at `/search/` and `/search/page/{n}/` with core's `s`, `SearchRequest` reads the main query into the front end's request kinds, and `MainSearchQuery` gives the main search query `SearchRoute::scope()` and the route's normalised words (keeping the typed ones for the form), answers a request that is not a search, and any anonymous visitor's search, which the lockdown 404s, with no posts, keeps the count and the pages the front end's on a later page, hides the pagination past the last page and never lets a search be a 404; a change to what the route searches changes `scope()`, and both queries with it. The plugin must work without Relevanssi: no Relevanssi function is called outside `src/Search/`, each call there checks Relevanssi is loaded first, and there is no `Requires Plugins` header. Relevanssi stays off in the REST API (Relevanssi's default; the classes' docblocks say why); a query asks for it with `'relevanssi' => true`.
8. `composer.json` in this directory, managing PHPCS, the WordPress standards, PHPUnit, the schema validator and the plugin's autoloader (PSR-4 under `src/`).

## Standards

- PHP 8.4 in wp-env, CI and on the host (ADR 0005), and 8.4 is also the declared floor (`Requires PHP`, `composer.json`, PHPCS `testVersion`), so CI tests the floor; to move it, change all three declarations and re-lock with `composer update --lock` (Composer only warns about a stale lock hash), together with the pin in `.wp-env.json`, the deploy job's `php-version` in `.depot/workflows/ci.yml` and the host. WordPress 6.9 or newer (`Requires at least`). WordPress Coding Standards as the base, the WordPress VIP Minimum ruleset on top (not VIP-Go, whose relaxations assume VIP's infrastructure), and the PSR-12 sniffs that do not conflict; where WordPress and PSR-12 disagree, WordPress wins, and each exclusion in `phpcs.xml.dist` names the conflict. Warnings fail the gate: fix, don't silence. Escape on output, sanitize on input, nonces and capability checks everywhere, `$wpdb->prepare` if raw SQL is ever justified (it should not be here). Includes use `__DIR__`, because the VIP ruleset flags variable includes. Object cache, not transients, for anything cached; no filesystem writes at runtime; no `error_log()`.
- PHPUnit stays on 9.6 because the WordPress core test library's `yoast/phpunit-polyfills` 1.x tops out there. Tests are written against polyfills 4.x, but `phpunit.xml.dist` uses PHPUnit 9 names (`convertDeprecationsToExceptions`, `<coverage>`), so moving the pin also needs the PHPUnit 10+ configuration migration. The schema validator is `opis/json-schema`, reading `packages/ui/schemas/` through the mapping in `.wp-env.json` (`tests/phpunit/Revalidation/SchemaValidator.php`).
- Tooling lives in this directory: `composer.json`, `phpcs.xml.dist` and `phpunit.xml.dist` for PHP, run inside the wp-env containers through the root's `pnpm composer`, `pnpm lint` and `pnpm test:php`; and the JavaScript toolchain (wp-scripts, Playwright) in this directory's `package.json`, which the root's `pnpm build`, `pnpm lint:js` and `pnpm test:e2e` call with `pnpm --filter`.
- **PHPUnit resets the tests site.** The bootstrap drops and reinstalls the tests database (port 8889), which deactivates every plugin there and leaves it on core's test theme, `default`. Every Playwright spec imports `test` from the worker-scoped fixture in `tests/e2e/fixtures.js`, which activates the plugin, Relevanssi and the `resource-hub` theme before any spec runs, and never assumes prior state. CI runs PHPUnit before Playwright for the same reason.
- **A test that publishes a resource gives it all four fields.** A PHPUnit test that saves through REST, and every Playwright spec, sends or stores a title, one type, a topic and a summary when it publishes (`OneType`, `RequiredFields`); the test library also unregisters every meta key after each test, so a PHPUnit test that needs REST to store meta registers it again in `set_up()`, as `MetaTest` does. Factory-made posts bypass both rules.
- XML-RPC is off (`src/Security/XmlRpc.php`): no client uses it, and it was an unguarded save path for the one-type rule.
- Incoming trackbacks and pingbacks are off for every post type (`src/Security/Pings.php`): `pings_open` is filtered to false, so a post stored with `ping_status` open is closed at runtime, with no data migration and no reliance on the host's `default_ping_status`. `wp-trackback.php` is a separate entry point from XML-RPC, so the XML-RPC switch alone does not stop trackbacks.
- The CMS sends no pings (`src/Security/OutgoingPings.php`): core's `_publish_post_hook` is removed from `publish_post`, so publishing a `post` queues no `_pingme`, `_encloseme` or `_trackbackme` meta and no `do_pings` event, and core's four senders are removed from `do_all_pings`, so `generic_ping` (which needs no queue) and any queue stored before the switch send nothing. Enclosure fetches go too: they are outbound requests to URLs in the content, and the `enclosure` meta they store is read only by core's feeds and XML-RPC; the front end does not read it, XML-RPC is off and the lockdown answers feeds with a 404 for anonymous visitors. One code path for WordPress 6.9 to 7.1; core's `wp_should_disable_pings_for_environment` is 7.1 only and acts on three senders at send time, so it is not used. Resources and pages never queued pings: core hooks the queue to `publish_post` alone.
