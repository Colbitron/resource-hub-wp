# Resource Hub: WordPress plugin

For a contributor new to the plugin: how to run it, test it and find your way around. The rules an agent follows on every edit are in [`CLAUDE.md`](CLAUDE.md) beside this file; the project's architecture, contract and decisions are in the [root README](../../../README.md).

The plugin models a filterable resources library for a headless front end: the `resource` post type with its taxonomies and meta, four custom REST routes (resolve a slug, a page by path, the resources related to one, and a search of resources and pages), the revalidation hook that tells the Next.js front end what changed, the lockdown that keeps the CMS's own pages for logged-in users, the admin screens that show what happened, and the settings of Relevanssi, the search engine installed beside it from [`site-plugins/`](../../../site-plugins/README.md). It is a demonstration of a pattern, written fresh, not production code.

## Running it

Requirements on the host machine: Docker, Node 24 and pnpm. PHP, Composer and WP-CLI run inside the wp-env containers; there is no host PHP. Everything runs from the repository root, where `.wp-env.json` is:

```sh
pnpm install               # the whole workspace
pnpm env:start             # WordPress at http://localhost:8888, the tests site at :8889
pnpm composer install      # inside the container; vendor/ lands in this directory
pnpm build                 # compiles blocks/, editor/ and admin/ into build/ (not committed), with the type-accent table; the block is registered from there
pnpm wp resource-hub seed  # optional sample content
pnpm wp resource-hub search-index --force  # rebuilds Relevanssi's index, since the seeder sets terms after saving
```

`pnpm env:start` also installs Relevanssi from `site-plugins/` and activates it on both sites; it builds the search index too once this plugin's `vendor/` exists, so on the first start, before `pnpm composer install`, it prints that it skipped it.

Log in at `http://localhost:8888/wp-admin` with `admin` / `password`. Activating the plugin deletes the stored rewrite rules so `/resources/…` permalinks work without a visit to Settings > Permalinks; `flush_rewrite_rules()` itself is forbidden by the VIP ruleset. If the URLs 404 later, `pnpm wp rewrite flush` is the manual equivalent.

The revalidation settings come from the `RESOURCE_HUB_FRONTEND_URL` and `RESOURCE_HUB_REVALIDATE_SECRET` constants, with `RESOURCE_HUB_POSTHOG_KEY` and `RESOURCE_HUB_POSTHOG_HOST` optional. Locally, define them in a gitignored `.wp-env.override.json` under `config`. Without them nothing is sent and every save records "not configured". The block editor shows each save's result in a notice on resources and pages; edit pages there, since a page saved in the Site Editor revalidates and records its result but shows no notice (`tests/e2e/site-editor-revalidation.spec.js`). Settings > Resource Hub shows which source is in force and has a test button; [`docs/architecture/revalidation.md`](../../../docs/architecture/revalidation.md) explains the rest.

`.wp-env.json` also maps `packages/ui` into the containers at the same path relative to the WordPress root, which is how PHPUnit reads the contract schemas. A change to `.wp-env.json` needs `pnpm env:start` again.

## WP-CLI commands

Each runs through `pnpm wp` (the dev site) or `pnpm wp:tests` (the tests site).

- `wp resource-hub seed [--count=<n>]` seeds the five types, the topics and `--count` fictional resources (default `Seeder::DEFAULT_COUNT`, 12; the catalogue holds 16). Safe to rerun.
- Not a command of the plugin's, but the one-liner for the host after the required-fields rule: every published or scheduled resource that lacks a title, a topic or a summary (`RequiredFields::missing_stored()`), as ID and title, and nothing written. The editor keeps such a resource's Update button off until someone fills the gap.

  ```sh
  wp eval 'foreach ( get_posts( array( "post_type" => "resource", "post_status" => array( "publish", "future" ), "posts_per_page" => -1, "fields" => "ids" ) ) as $id ) { if ( ResourceHub\ContentModel\RequiredFields::missing_stored( $id ) ) { WP_CLI::line( $id . "\t" . get_post( $id )->post_title ); } }'
  ```

- `wp resource-hub search-index [--force]` rebuilds Relevanssi's search index if it is out of date, and otherwise changes nothing: it empties the index, then indexes every published resource and page with its title, content, `summary` and topic and type names, the set `src/Search/RelevanssiConfig.php` selects. `--force` rebuilds a current index too. Fails when Relevanssi is not active. See [The search index](#the-search-index).
- `wp resource-hub decode-slugs [--apply]` lists every `resource` post and every term in the three taxonomies whose stored slug still holds a percent escape the front end's router decodes (one of `A-Z a-z 0-9 - _ . ! ~ * ' ( )`), with the decoded slug and anything already holding it. A dry run unless given `--apply`, which saves each through core (`wp_update_post()`, `wp_update_term()`), so the old slug is kept in `_wp_old_slug` and the front end is revalidated as on any save. A term whose decoded slug another term has is skipped and reported: core refuses it, and an editor must type a new slug. Slugs saved since the `SlugEscapes` rule need no repair; only a cron publish of a scheduled resource bypasses it, because it writes the status alone.

## The search index

Search runs on [Relevanssi](https://wordpress.org/plugins/relevanssi/), the free version, installed and pinned in [`site-plugins/`](../../../site-plugins/README.md). The plugin works without it: nothing in it needs Relevanssi, and `pnpm test:php` passes with it absent (below). Its settings live in code, in `src/Search/RelevanssiConfig.php`. The ones that decide what is indexed or whether a search writes are pinned with `pre_option_*` filters, so nothing is stored and Relevanssi's settings screen shows them but cannot change them: search logging off, admin searches left to core, only resources and pages indexed, the `summary` meta and the topic and type names indexed, no comments, author or excerpt, no shortcodes run at index time, Relevanssi's default word length and punctuation. The stopword list and a few settings that cannot matter here are left to the screen, and a change to them makes the next `search-index` rebuild. Through Relevanssi's own filters: every search query Relevanssi does not answer, the REST API's included, is left to core's search, and the related-resources block is never rendered into the index of the page that holds it, so a page that lists a resource does not match searches for that resource. A query asks for it with `'relevanssi' => true` beside `s`; `src/Search/RelevanssiFoundPosts.php` keeps such a query's `found_posts` right, which Relevanssi alone gets wrong for `fields => ids`.

Only published posts are indexed: a draft, pending, private or scheduled resource or page never reaches Relevanssi's tables, so a query against the index cannot return one by mistake. Relevanssi applies the same rule on every save, so publishing adds a post, and unpublishing, trashing or deleting it takes it out.

The index holds what those settings selected when it was built. `wp resource-hub search-index` compares a stamp of Relevanssi's version, its database version, the version its tables are at, those settings and the plugin's own index-logic version (`RelevanssiConfig::INDEX_LOGIC`, raised when a filter changes what is indexed), stored in the `resource_hub_search_index_stamp` option at the last complete build, and rebuilds only when it differs, Relevanssi has no complete index, or its tables are behind; it upgrades the tables first, as Relevanssi itself does only on an admin page load. The stamp is deleted when a rebuild starts and written when it completes, so an interrupted rebuild reads as stale. A rebuild empties the index first, so live search finds nothing or part of the library while it runs, which is why the deploy, which runs the command on every merge, must not rebuild a current index. Relevanssi has no full rebuild that skips the truncate (`src/Search/SearchIndex.php`). In practice:

1. **After Relevanssi is first activated** its tables are empty and it reports no complete index, so the next run rebuilds. `pnpm env:start` runs it on both wp-env sites; the deploy runs it on the host.
2. **After changing `RelevanssiConfig` (raise `INDEX_LOGIC` if the change is to a filter), or upgrading Relevanssi**, the stamp differs, so the next run rebuilds: locally `pnpm wp resource-hub search-index`, on the host the deploy that ships the change.
3. **After activating or deactivating Relevanssi or this plugin**, the stamp is deleted, since saves made meanwhile were indexed on Relevanssi's defaults or not at all, so the next run rebuilds.
4. **After renaming or deleting a topic or type**, nothing to do: `src/Search/TermReindex.php` re-indexes that term's published resources from WP-Cron, in sorted events of at most 50 a minute apart, or at once under WP-CLI.
5. **After a script assigns terms to posts it saved earlier**, as the seeder does, run `search-index --force`: Relevanssi re-indexes a post on save, not on a later term assignment.

The whole command took under a second for the 17 seeded resources and published page, WP-CLI's start-up included. Relevanssi keeps its index in its own tables (`wp_relevanssi` and two more); it writes no files. It also keeps a copy of each post it reads for the rest of the request and never refreshes it, so `src/Search/RelevanssiPostCache.php` drops a post's copy whenever core cleans its own cache; without that, a post published in the same request it was read in as a draft stays out of that request's searches.

## Testing

Three gates, all run by CI on Depot CI (`.depot/workflows/ci.yml`, the `gate` job) on every push to `main` and every pull request that changes `wp-content/` or a shared path (`docs/runbooks/deploy.md`, "Which jobs a pull request runs"), and all run locally from the root:

| Command | Runs |
|---|---|
| `pnpm lint` / `pnpm lint:fix` | PHPCS / PHPCBF on WordPress Coding Standards as the base, the WordPress VIP Minimum ruleset on top, and the PSR-12 sniffs that do not conflict. Where WordPress and PSR-12 disagree, WordPress wins, and each exclusion in `phpcs.xml.dist` names the conflict. Warnings fail the gate: fix, do not silence. |
| `pnpm test:php` | PHPUnit 9.6 inside the WordPress core test library that wp-env provides. The pin follows that library: as of WordPress 7.1 it depends on `yoast/phpunit-polyfills` 1.x, whose ceiling is PHPUnit 9. Tests are written against polyfills 4.x, but `phpunit.xml.dist` uses PHPUnit 9 names (`convertDeprecationsToExceptions`, `<coverage>`), so when core raises its ceiling, moving the pin also needs the PHPUnit 10+ configuration migration. |
| `pnpm test:e2e` / `test:e2e:debug` | Playwright against the tests site on port 8889, with the WordPress e2e utilities. Needs Docker beside wp-env: `theme-screenshots.spec.js` starts Chromium in the front end's pinned Playwright image for the CMS theme's pixel baselines, and a missing baseline fails in CI. WordPress is not pinned (wp-env runs the latest release, as the host does), so a WordPress release can move those baselines, as a Playwright upgrade can; the failure says so. Look at the diff, then regenerate with `WP_BASE_URL=<the tests site> pnpm test:e2e -- --update-snapshots` and commit the images (the theme's README, "Assets"). |
| `pnpm lint:js` / `pnpm format` | ESLint and Prettier with the WordPress presets on `admin/`, `blocks/`, `editor/` and `tests/e2e/`, and on the CMS theme's `scripts/` (`lint:js:theme`, `format:theme`, run from the repository root so the workspace keeps one `@wordpress/scripts`). |
| `pnpm test:schemas` | The contract's own test in `packages/ui`: Ajv compiles every schema in strict mode and checks every fixture. |

Things to know:

- **PHPUnit reinstalls the tests site.** The bootstrap drops and reinstalls the tests database, which deactivates every plugin there. CI runs PHPUnit before Playwright, and every Playwright spec imports `test` from `tests/e2e/fixtures.js`, a worker-scoped fixture that activates the plugin, Relevanssi and the `resource-hub` theme before any spec runs. The dev site on 8888 is untouched.
- **PHPUnit loads Relevanssi.** The bootstrap loads it beside the plugin and creates its tables once the database is reinstalled, so the search tests in `tests/phpunit/Search/` run against the version `site-plugins/` installed, and fail if it is missing. To show the plugin works without it, run `pnpm exec wp-env run tests-cli --env-cwd=wp-content/plugins/resource-hub-wp env RESOURCE_HUB_TESTS_WITHOUT_RELEVANSSI=1 composer test`: the search tests skip and everything else passes. The index build truncates and analyzes its table, which would commit a test's transaction, so the search tests swap those two statements for transaction-safe ones (the test's docblock).
- **Publishing in a test takes all four fields.** A public resource needs a title, one type, a topic and a summary (`OneType`, `RequiredFields`), so a PHPUnit test that publishes through REST, and every Playwright spec that publishes, sends or stores them; `tests/e2e/required-fields.spec.js` covers the editor's notice, lock and checklist, with an axe scan of the sidebar through `@axe-core/playwright`, the workspace's accessibility scanner.
- **Payloads are validated against the shared schemas.** `tests/phpunit/Revalidation/SchemaValidator.php` registers every schema in `packages/ui/schemas/` under its `$id` with `opis/json-schema` (draft 2020-12, cross-file `$ref`s) and checks every payload a test builds. `SchemaTest` runs the package's `revalidate-request.*.json` fixtures through the PHP validator, so the two validators agree on the request schema. No PHP test runs the other schemas' fixtures, and Ajv's strict compile runs only under `pnpm test:schemas`. `opis/json-schema` is a dev dependency and is never shipped.
- **The collection routes and blocks.** The CMS theme's collection templates render the front end's library, type, topic and type-within-topic pages from the main query (`wp-content/themes/resource-hub/README.md`, "The collections"). `src/Collections/Routes.php` adds the five rewrite rules core does not write, at the top of the rules: `/resources/topic/{topic}/` and `/resources/{type}/topic/{topic}/`, each with `/page/{n}/`, mapped to the taxonomies' own query vars, and `/resources/{type}/page/{n}/`, which the single resource's rule otherwise took as a resource named `page`; `Plugin::activate()` and the deploy's `wp rewrite flush` pick them up (`pnpm wp rewrite flush` locally). `Collection` reads the request (the terms, the page, `found_posts`), `Lead` picks the newest featured resource with exactly one type for the library's first page, and `CollectionQuery` sets twelve to a page, drops the lead's row from under it while the count and the pages stay the CMS's, heads the inheriting Query Loop "Latest" with its rows one level down when a lead shows, and answers a type or topic that names no term with a 404, as the front end does; `PageWindow` is the front end's `pageWindow()` in PHP and `PaginationNumbers` applies it to core's pagination block on a collection's main query through `paginate_links_output`, keeping core's markup, so the two sites list the same page numbers, held to one table in the contract package (`packages/ui/README.md`, "Page-window fixture"). Three dynamic blocks write the front end's markup from that: `resource-hub/collection-head` (the `h1`, the count and the type and topic filter rows, every link a listing path, `aria-current` on the current term or "All"), `resource-hub/featured-lead` (the "Featured" heading and the lead with its image box, nothing anywhere but the library's first page) and `resource-hub/collection-empty` (the empty state's sentence and its link back to the library, for a `core/query-no-results`). They read the main query, so their editor previews are placeholders, and they name no theme stylesheet handle (core would enqueue it on the editor's admin page with its dependencies): the theme's `functions.php` loads `listing.css` and `lead.css` on the collection templates. The contract's fixtures hold the head and the lead to the front end's (`packages/ui/README.md`, "Markup fixtures"); `RoutesTest`, `CollectionQueryTest`, `PaginationNumbersTest`, `CollectionHeadBlockTest`, `FeaturedLeadBlockTest`, `CollectionEmptyBlockTest` and `MarkupParityTest` cover them, and the theme's `theme-parity.spec.js` and `theme-screenshots.spec.js` the rendered pages.
- **The search page.** The CMS theme's `search.html` renders the front end's search page over core's main search query. `src/Search/SearchPath.php` puts core's search at the front end's path with two rewrite rules, `/search/?s=…` and `/search/page/{n}/?s=…` (core's `/?s=…` still answers, and the tests site, on plain permalinks, uses it), with core's query var `s` where the front end's is `q`; `SearchRequest` reads the main query into the front end's request kinds (`none`, `invalid`, `too-short`, `too-long`, `search`, `no-such-page`, by the search route's normalisation and bounds); and `MainSearchQuery` gives the main search query `SearchRoute::scope()`, the route's own arguments (published resources and pages, no password, never the posts page, twelve to a page), answers a request that is not a search with no posts and no SQL and tells Relevanssi not to search, takes the true count from `SearchRoute::total()` on an empty later page and caps the pages at the route's ten, hides core's pagination past the last page, and keeps a search from core's paged 404, so every state is a 200 as on the front end. `PaginationNumbers` windows the search page's numbers too. Three blocks write the page: `resource-hub/search-head` (the `h1`, the form showing the reader's words with the front end's `aria-describedby` and `aria-invalid` states, and the count line, "1 result for “q”" or "{n} results for “q”" with the sentence about the first 120), `resource-hub/search-empty` (the front end's sentence for each state that lists nothing, in a Query Loop's no-results block) and `resource-hub/page-card` (a page as the front end's `PageCard`: the label "Page", the title and the excerpt as the REST API renders it, beside `resource-card` in the post template, each block rendering its own post type). `RelevanssiConfig::PINNED_OUTPUT` pins Relevanssi's snippets and highlighting off, so a page's row shows the stored excerpt; neither is fingerprinted. Tests: `SearchPathTest`, `SearchRequestTest`, `MainSearchQueryTest`, the three blocks' tests, `MarkupParityTest`'s search scenes and page samples, `ThemeTemplatesTest`, `ThemeSearchStylesTest`, and in Playwright the search page's computed styles and baseline.
- **The template blocks.** Five dynamic blocks write the front end's markup for the CMS theme's templates, each for the post its context names (`postId`, `postType`, set by `core/post-template` for each post it lists, by `render_block()` from the global post in a single template, and by the editor's preview endpoint from the post being edited), each with no block wrapper attributes, so each writes the front end's markup and nothing else, and each rendering nothing for a resource without exactly one type, which the front end never renders. The card and the related section render only for a published resource, the only kind the front end lists; the meta line, the summary and the source line also render a resource that is not published for a user who may read it (`read_post`), so a logged-in preview of a draft or scheduled resource, and the editor's preview of it, is the article it will become, and a visitor or a subscriber gets nothing (`ContextResource`). The related section stays published-only even then, because its selection is cached in the public related route's entry. `resource-hub/resource-card` is the front end's listing row, `ResourceCard`: "Untitled resource" for an empty title and a `level` attribute of 2 to 4 for the title's heading; it may only be inserted inside a post template (`ancestor`), and a template that wants the front end's list puts `rh-card-grid` on the post template. The other four are the resource page's, `ResourceArticle` and `RelatedSection`, for `single-resource.html`: `resource-hub/resource-meta`, the meta line (the type with its mark, linked to `/resources/{type}/`, the date, and the topics, each linked to `/resources/topic/{topic}/`, on the CMS's origin); `resource-hub/resource-summary`, the summary as the lead paragraph with the page's whitespace collapse, or nothing when nothing is left; `resource-hub/resource-source`, the source line, "Source:" and a link shown by its host, or by its file name for an upload, under the front end's `sourceLink()` rules (`ResourceCardMarkup`'s docblock), or nothing; and `resource-hub/related`, the related section, `RelatedList`'s heading and id over `card.css` rows at `h3`, the editor's picks first and then the newest sharing a topic, from `RelatedItems`, the same selection and cache entry the related route serves at the count the front end asks for, with a row the front end would drop (an empty title, no one type, unpublished since) left out and nothing at all when no row is left. Their editor previews are ServerSideRender sent the context's post as `post_id`, and a placeholder where the server renders nothing. Each has a test of its own (`ResourceCardBlockTest`, `ResourceMetaBlockTest`, `ResourceSummaryBlockTest`, `ResourceSourceBlockTest`, `RelatedBlockTest`), `MarkupParityTest` holds the row, the meta line, the summary and the related section to the contract's fixtures, `ThemeTemplatesTest` renders them in the template, and `tests/e2e/resource-card-block.spec.js` checks the rows of a Query Loop on a CMS page and in the editor, `theme-parity.spec.js` and `theme-screenshots.spec.js` the resource page.
- **`build/` is not committed.** CI builds it before the gate runs; locally, run `pnpm build` (or `pnpm start` to watch) after `pnpm env:start`. `webpack.config.js` extends the `@wordpress/scripts` config with the non-block entries under `editor/` and `admin/`.
- **The block is registered from `build/`, not `blocks/`.** The deploy syncs `src/`, `build/` and `vendor/` and leaves `blocks/` behind, so `RelatedResourcesBlock` reads `build/related-resources/block.json`; without a build the block is not registered, and `RelatedResourcesBlockTest` fails on its first assertion. Run `pnpm build` before `pnpm test:php` and `pnpm test:e2e`, as CI does. The block has no stylesheet of its own: the compiled `block.json` names two shared handles as its `style`, `resource-hub-tokens` and then `resource-hub-card`, so core enqueues the tokens and the row only where the block is used. `resource-hub-card` is the shared package's `card.css` (`@colbitron/resource-hub-ui`, a workspace dev dependency of the plugin), which `webpack.config.js` copies byte for byte into `build/shared/` with the `card-labels.css` it imports beside it, and `SharedCard` registers at `SharedTokens`' priority, only when nothing has, as a `<link>`, never inlined, because the relative `@import` must resolve against the file; its version is the hash of both files. The `resource-card` block names the same two handles, so a page with both blocks loads `card.css` once (`resource-card-block.spec.js` counts it). The tokens handle is shared with the CMS theme, so a page with the block on the theme loads `tokens.css` once: the theme registers it, and `SharedTokens` registers the plugin's own copy, `build/shared/tokens.css` (which `webpack.config.js` copies from the package byte for byte), at a later `init` priority only when no theme has. The template blocks are built and registered the same way, from `build/resource-card/`, `build/resource-meta/`, `build/resource-summary/`, `build/resource-source/` and `build/related/`; `resource-meta` names the tokens handle and then its own `style-index.css`, the package's `card-labels.css` inlined by the build; `related` names the two shared handles for its rows and leaves `related.css` to the theme, which loads it on every resource page; `resource-summary` and `resource-source` name no stylesheet, since `resource.css`, the theme's, draws them (see "The template blocks" above). On the CMS's own pages, WordPress 7.1.4 enqueues the style only where an instance renders something: a block whose callback renders nothing (no topic, or a deleted one) brings no block CSS, as measured on wp-env. In the editor core loads every registered block's style regardless.
- **PHP 8.4 in wp-env, CI and on the host, and 8.4 is the declared floor** (`Requires PHP`, `composer.json`, PHPCS `testVersion`), so the floor is the version CI tests. The floor was 8.2 until the locked dev toolchain needed 8.4 (ADR 0005, amended 2026-11-07).
- **WordPress 6.9 or newer** (`Requires at least`). The salted object-cache helpers behind the related route's cache (`wp_cache_set_salted()`, `wp_cache_get_salted()`) arrived in 6.9.

## What is not built yet

The template blocks for the CMS theme are built: `resource-hub/resource-card`, one listing row for a Query Loop's post template, and the single resource page's four, `resource-hub/resource-meta`, `resource-hub/resource-summary`, `resource-hub/resource-source` and `resource-hub/related`, all written by `ResourceCardMarkup`, the renderer the related-resources block's rows share, and held to the front end's markup by the contract's markup fixtures (`packages/ui/README.md`, "Markup fixtures"; `tests/phpunit/Blocks/MarkupParityTest.php`). The theme's `single-resource.html` renders the four, and its collection templates render `resource-card` with the three collection blocks, `resource-hub/collection-head`, `resource-hub/featured-lead` and `resource-hub/collection-empty`, over the collection routes and query rules in `src/Collections/` ("The collection routes and blocks" above). The related resources are built: the related route (`GET /resource-hub/v1/related/{id}?count=n`), answered from `RelatedItems`, the selection the theme's related block renders too, and the `related_picks` meta, the editor's control for the picks in the Resource details panel, and the `resource-hub/related-resources` block, whose render callback writes the contract's marker (`packages/ui/README.md`, "Block marker") with card rows inside; the front end reads the route for its related section and swaps the marker for its own list. The CMS block theme is at `wp-content/themes/resource-hub/`, every template built and shipped and activated by every `main` deploy, and this plugin's PHPUnit and Playwright suites check its files, its 404, its copies of the contract package's assets, its `theme.json` presets against the tokens, its table and image filters (`TableRegionTest`, `ImageLightboxTest`), which template core renders for each request and that the resource template renders the blocks in the article's order (`ThemeTemplatesTest`), that `related.css` loads on a page, a post or an archive whose body holds the related-resources block and on every resource and nowhere else (`ThemeRelatedStylesTest`), its footer's System / Light / Dark control against the contract's `theme-control.html` fixture and its inline script on a page and on the 404 (`ThemeControlTest`; `theme-control.spec.js` checks the control's behaviour logged in, the first paint, JavaScript off, forced colours, axe, the anonymous 404 and the editor canvas), its stylesheets on a page with the block, a CMS page's, a seeded resource page's and the collections' computed styles against the declarations the package's rules make, written into the spec by hand and resolved from the tokens (`theme-parity.spec.js`), and a page, that resource, the library, a topic and the 404 against pixel baselines drawn in the front end's pinned Playwright image, which `theme-screenshots.spec.js` starts in Docker itself; regenerate those with `pnpm test:e2e -- --update-snapshots` and commit the images in `tests/e2e/__snapshots__/` with the change. Search is built on the plugin's side ([issue #115](https://github.com/Colbitron/resource-hub-wp/issues/115)): Relevanssi is installed, configured and indexed, and the search route queries it; the front end's search page at `/search/` reads it.
