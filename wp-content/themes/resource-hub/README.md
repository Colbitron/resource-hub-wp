# Resource Hub: CMS block theme

The CMS's own theme, for editors and logged-in previews only. The front end in `apps/web/` is the only public site, so anonymous visitors never see this theme's pages: the plugin's lockdown (`wp-content/plugins/resource-hub-wp/src/Lockdown/`, [ADR 0031](../../../docs/adr/0031-cms-theme-pages-are-for-logged-in-users.md)) answers them with a 404, and that 404 is rendered with this theme's `templates/404.html`. It is a demonstration of a pattern, written fresh, not production code.

## What is here

```
style.css            theme header only
theme.json           schema version 3: Figtree, the presets and the editor's base styles on the --rh-
                     tokens, and the header and footer template parts
functions.php        registers the stylesheets in build/ and enqueues them per template, in order
inc/table-region.php a table block's table in the front end's scroll region, on the theme's pages
templates/page.html  a page, and a static front page: the front end's PageArticle in the shell
templates/home.html  `/` while the front page shows posts: the front end's welcome page in the shell
templates/index.html everything else a logged-in user sees: the main query, each post as the article
templates/404.html   the lockdown's 404: a heading and one sentence in rh-not-found's column
parts/header.html    the header's row: the Resource Hub lockup (the mark and the wordmark, one link to
                     /resources/), alone; the mark is a copy of packages/ui/brand/mark.svg, held to it
                     by BrandMarkTest
parts/footer.html    the footer's row: the publisher line and the sentence the front end's footer has
package.json         the theme's build, a pnpm workspace package
scripts/build.mjs    copies the contract package's files into build/
figtree.sha256       the SHA-256 of the Figtree file the theme ships, in `shasum -a 256` form
build/               gitignored; written by `pnpm build`
```

A block theme gives editors the Site Editor (Appearance > Editor), whose Pages section can edit pages too. Edit pages in the post editor instead: a Site Editor save still revalidates the front end and records its result, but shows no revalidation notice (issue #89's third note, settled; `docs/architecture/revalidation.md`, "Reading results").

The lockup links to the CMS's own `/resources/` rather than to the front end: editors see the resource archive there, and anonymous visitors get the lockdown's 404. ADR 0031 rejects redirecting to the front end because each redirect is a link from the CMS domain to it, and the lockup follows the same reasoning.

## The two rules from issue #89

The 404 is the one page of this theme every anonymous visitor gets, so:

1. **It lists no pages.** The 404 template and the parts it includes hold no `core/navigation`, `core/page-list`, query or any other block that lists posts, pages or terms. A navigation block with no menu falls back to listing every published page, which would show anonymous visitors what exists.
2. **It prints no `<link rel="pingback">`.** A classic or compat `header.php` prints one itself; a block theme has no `header.php`, and no file it renders from mentions pingbacks. The plugin removes core's `X-Pingback` header (`src/Security/XmlRpc.php`).

`tests/phpunit/Theme/ThemeFilesTest.php` in the plugin checks the files: the 404 template and its parts may use only an allow list of fixed-content blocks, and no file it renders from (templates, parts, PHP, JSON, CSS, JavaScript) mentions pingbacks. `tests/e2e/theme-404.spec.js` checks the rendered 404 as an anonymous visitor: no navigation, no page or post titles, no pingback link or header. Neither stops an editor from adding a navigation block to the header in the Site Editor, which stores its own copy of the part in the database; the Playwright spec would catch it only on a site where that copy exists.

## Layout and templates

The owner chose full parity: a logged-in preview looks like the front end. So every template renders the front end's markup with the contract package's classes, beside the block classes core adds, and loads the package's stylesheets for them:

- **The shell** (`shell.css`). Each template is one group, `rh-shell`, holding the header part as `header.rh-header`, a `main.rh-shell__inner.rh-main` with the id `main`, and the footer part as `footer.rh-footer`; the parts' rows are `rh-shell__inner rh-header__inner` and `rh-shell__inner rh-footer__inner`. So the header, `main` and the footer sit in one column of `--rh-measure-wide`, centred, with the 16 px gutter, as the front end's `Shell` lays them out. The footer has the front end's two lines and no theme control yet. The groups use core's default flow layout, never `constrained`: core's constrained layout puts `layout.contentSize` on each child, measured in that child's own `ch`, where the front end puts the measure on one wrapper. Core's skip link is kept: core inserts it before the shell and points it at `main`, where the front end's is `.rh-skip`.
- **A page** (`page.html`, `page.css` and `prose.css`): `article.rh-page`, the title as `h1.rh-page__title` in `header.rh-page__header`, and the post content as `rh-page__body rh-prose`, the front end's `PageArticle`. A static front page uses it too: core looks for `front-page.html` first, finds none, and falls through to the page hierarchy, as the front end renders its front page with `PageArticle`.
- **The welcome** (`home.html`, `welcome.css` beside `page.css`): core uses `home.html` for `/` while Settings > Reading shows posts, the state of wp-env and the host today, which is when the front end shows its welcome page; the template is the same heading, sentence and link. There is no `front-page.html`, because core would use it for `/` in both states, so it could not be both the page and the welcome. Two edges differ from the front end: the posts page under a static front page also gets `home.html`, where the front end answers a 404, and `show_on_front` set to `page` with no page chosen gets `index.html`, where the front end shows the welcome.
- **Everything else** (`index.html`, `page.css` and `prose.css`): the main query, each post as the article with its title linked, until the single-resource and collection templates land.
- **The 404** (`404.html`, `not-found.css`): the heading and the theme's own sentence in `.rh-not-found`'s column. It leaves out the front end's "Browse all resources" link: an anonymous visitor would follow it to another 404.
- **Tables** (`inc/table-region.php`). A `render_block_core/table` filter puts each table block's `<table>` in a `div.rh-table-scroll` with `role="region"`, `tabindex="0"` and an `aria-label` from its caption or figcaption, the region the front end's content pass adds (`tableRegion` in `apps/web/lib/content/render.tsx`) and `prose.css` draws as the table's box. It is presentation, so it is the theme's, and `functions.php` adds it on `template_redirect`, so only pages core renders with a template get it: REST's `content.rendered`, which the front end reads, stays core's markup, and the contract does not change. Only table blocks are wrapped, not a raw `<table>` in a Custom HTML block. The file's docblock has the rest.

## Assets

The theme draws with the contract package, `@colbitron/resource-hub-ui` (`packages/ui/DESIGN.md`, "Consumers and loading"). The host never sees the pnpm workspace, so `scripts/build.mjs` copies what the theme loads into `build/`, byte for byte: `tokens.css`, `brand.css` (the lockup's classes), `fonts/figtree-latin-wght-normal.woff2` with `fonts/LICENSE-Figtree.txt` beside it, `fonts/figtree-fallback.css`, and the document, the shell and the components the templates render: `base.css`, `shell.css`, `prose.css`, `page.css`, `welcome.css` and `not-found.css`. It also writes `build/assets.php`, each copy's SHA-256, which `functions.php` takes the stylesheets' versions from. The root's `pnpm build` runs it alongside the plugin's build (pnpm runs the two packages' builds concurrently; neither reads the other's output), and CI's plugin gate runs `pnpm build` before PHPUnit and Playwright, as for the block.

- **`theme.json`** registers Figtree with `fontFace` from `file:./build/fonts/…`, under the plain name `Figtree`, with the front end's `font-display: swap`; it leaves `--rh-font-figtree` unset, so `--rh-font-sans` falls back to that name. The one font-family preset is `"Figtree", var(--rh-font-sans)`: core names the `@font-face` after the first family in the preset, and the rest is the token's stack with its fallback faces. The palette is every `--rh-color-*` token, the font sizes every `--rh-text-*` one, the spacing sizes every `--rh-space-*` one, and `layout.contentSize` and `wideSize` are `--rh-measure` and `--rh-measure-wide`, each written as `var(--rh-…)`, never as a value, so a value changes only in `tokens.css`. A slug is the token's suffix as core spells it in a custom property (`2xl` is `2-xl`). The five mark accents are not in the palette, since they are for small marks only, never text. Custom colours, gradients, duotones and font sizes are off, and core's default palette, gradients, duotones, font sizes and spacing sizes are hidden from the editor's pickers, so an editor picks only from the tokens. Hidden, not removed: core still prints those defaults' custom properties and their `.has-*` classes. Core's default shadows and aspect ratios are not hidden. The base styles set the body's colours, Figtree, the body size and leading, the link colour, the headings' weight, tracking and leading, and the sizes of `h1`, `h2` and `h3` from the tokens: a mirror of `base.css` for the editor canvas, which does not load it (below).
- **`functions.php`** registers a handle for each stylesheet on `init`. It enqueues `resource-hub-tokens`, `resource-hub-figtree-fallback` and `resource-hub-brand` on `enqueue_block_assets`, which reaches the CMS's own pages and the iframed editor canvas, and not the editor's admin page around the canvas. `tokens.css` sets `color-scheme: light dark` and writes every colour with `light-dark()`, so the pages and the canvas follow the reader's system preference, as the front end does by default.
- **The load order.** On the CMS's own pages, `functions.php` enqueues `resource-hub-base` and `resource-hub-shell`, then the template's components (`resource-hub-prose` and `resource-hub-page`, `resource-hub-welcome`, or `resource-hub-not-found`), on `wp_enqueue_scripts` at priority 20. Core enqueues its global styles there at 10, so the package's files print after `global-styles-inline-css`. `base.css` styles `body`, `a` and the headings at the same specificity as `theme.json`'s base styles, so the later one wins a tie: the package's, and a page computes what the front end computes from the same file. The values agree anyway; the order decides when they part, as after a Styles change saved in the Site Editor, which the front end never sees either. In the editor canvas only `theme.json`'s mirror applies: its base styles give the body, links and `h1` to `h3` the type, sizes and colours `base.css` gives them, and core keeps its own layout, spacing and focus styles there, so an editor's content reads in the site's type and colours, in the editor's column. Core's block styles for the table, code and separator blocks draw over `prose.css` (a border on every cell's side and a fixed table layout, code as a block in the body's font, a 2 px rule), and the front end loads none of core's CSS, so `functions.php` dequeues those three on the CMS's own pages; the canvas keeps them. The docblock of `resource_hub_theme_enqueue_page_styles()` has the reasoning.
- **One copy of the tokens.** The plugin's related-resources block names the same `resource-hub-tokens` handle in its `block.json`, and WordPress prints a handle once, so a page with the block loads `tokens.css` once. The theme registers the handle first; the plugin registers its own copy (`build/shared/tokens.css`) at a later `init` priority only when no theme has, so the block keeps its tokens in any theme (`src/Blocks/SharedTokens.php` in the plugin).

The plugin's suites hold all of it to the package and to the front end. `tests/phpunit/Theme/ThemeAssetsTest.php` fails when a copy in `build/` is not the package's file byte for byte, when `build/assets.php` holds a stale hash, or when the package's Figtree is not the file `figtree.sha256` records, so a new font file means changing the record with it; `tests/phpunit/Theme/ThemeTokensTest.php` fails when the presets are not exactly the tokens, in order, when `theme.json` writes a raw colour or length, or names a token that does not exist. `TableRegionTest.php` checks the table filter. Playwright's `tests/e2e/theme-assets.spec.js` counts the token declarations on a page with the block, on the CMS's page and in the editor canvas, and checks Figtree, the lockup and both schemes. The two parity checks the owner chose are `theme-parity.spec.js`, which compares a CMS page's computed styles (the body, the headings, a link, a paragraph's measure, the shell's column and gutter, the header's row, the article's column, the table's region) with the package's rules resolved from the tokens on the same page, and `theme-screenshots.spec.js`, pixel baselines of a page, logged in with the admin bar hidden, and of the anonymous 404, at 1280 and 360 px in both schemes, drawn by Chromium in the Linux image the front end's screenshot gate pins. That spec starts the container itself with the front end's `apps/web/e2e/browser-container.mts`, so it runs in the plugin's ordinary `pnpm test:e2e`, here and in CI. A design change regenerates the CMS baselines with `pnpm test:e2e -- --update-snapshots` (with `WP_BASE_URL` set to the tests site), and the images in `tests/e2e/__snapshots__/` are looked at and committed with the change. PHPCS lints this directory's PHP with the plugin's ruleset (`phpcs.xml.dist`), and the root's `pnpm lint:js`, which CI's plugin gate runs, lints and checks the formatting of `scripts/` through the plugin's `lint:js:theme`: the plugin's one `@wordpress/scripts`, run from the repository root, because ESLint reads no file outside the directory it runs in (`pnpm format` formats it the same way, through `format:theme`).

## Running it

`.wp-env.json` at the repository root mounts this directory into both wp-env sites. wp-env mounts a mapped theme but never activates it, on a new environment or an existing one, so its `afterStart` script runs `wp theme activate resource-hub` on the dev and tests sites after every `pnpm env:start`. The script calls `wp-env run`, so it needs `wp-env` on `PATH`; `pnpm env:start` puts the workspace's copy there, while a bare `wp-env start` from a shell without it fails at that step. The PHPUnit bootstrap then reinstalls the tests site on core's test theme, `default`, so the Playwright fixture in `tests/e2e/fixtures.js` activates the theme again before any spec runs. Run `pnpm build` once before loading a page: without `build/`, `functions.php` registers nothing, Figtree's file is missing, and the pages render in the browser's defaults.

- **The remaining component stylesheets.** The block brings `card.css` where it is used; `theme-toggle.css`, `listing.css`, `lead.css`, `resource.css` and `related.css` wait in the contract package for the templates that render them, which copy them into `build/` and enqueue them as they land (`packages/ui/README.md`, "Stylesheets").
- **The plugin's blocks** for the resource row, the resource's meta line, the collection head and the related list, which those templates render.
- **The remaining templates:** the single resource and the collection pages (archives and taxonomies); `index.html` stands in for them.
- **The System / Light / Dark control** the front end has in its footer, in `rh-footer__theme`. Until it lands, the CMS follows the system preference only.
- **The editor canvas's column.** `layout.contentSize` is `--rh-measure`, `65ch`, which core applies to each child of the canvas's constrained root, so a heading's column there is measured in its own, larger `ch` and is wider than the paragraphs'. The theme's pages put the measure on a wrapper, as the front end does; the canvas is core's layout.
- **Deploy:** CI syncs only the plugin to the host, so this theme is not on the hosted CMS yet, and the hosted 404 is still rendered with the host's current theme. The deploy must carry `build/` and may leave `package.json`, `scripts/` and `node_modules/` behind.

Issue #89's third note, the Site Editor revalidation notice, is settled: page editing stays in the post editor, and the Site Editor gets no notice (above).
