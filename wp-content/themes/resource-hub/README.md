# Resource Hub: CMS block theme

The CMS's own theme, for editors and logged-in previews only. The front end in `apps/web/` is the only public site, so anonymous visitors never see this theme's pages: the plugin's lockdown (`wp-content/plugins/resource-hub-wp/src/Lockdown/`, [ADR 0031](../../../docs/adr/0031-cms-theme-pages-are-for-logged-in-users.md)) answers them with a 404, and that 404 is rendered with this theme's `templates/404.html`. It is a demonstration of a pattern, written fresh, not production code.

## What is here

```
style.css            theme header only
theme.json           schema version 3: Figtree, the presets and the editor's base styles on the --rh-
                     tokens, and the header and footer template parts
functions.php        registers the stylesheets in build/assets.php and enqueues them per template,
                     in order, with the shell's admin-bar height and the core block styles left out
inc/table-region.php a table block's tables in the front end's scroll region, on the theme's pages
inc/image-lightbox.php image blocks without their lightbox, on the theme's pages
templates/page.html  a page, and a static front page: the front end's PageArticle in the shell
templates/singular.html a single post: the same article
templates/single-resource.html a resource: the front end's ResourceArticle and its related section,
                     through the plugin's meta, summary, source and related blocks
templates/home.html  `/` while the front page shows posts: the front end's welcome page in the shell
templates/index.html archives and search: their title as the h1, then each post as the article
templates/404.html   the lockdown's 404: a heading and one sentence in rh-not-found's column
parts/header.html    the header's row: the Resource Hub lockup (the mark and the wordmark, one link to
                     /resources/), without the front end's search control yet; the mark is a copy of
                     packages/ui/brand/mark.svg, held to it by BrandMarkTest
parts/footer.html    the footer's row: the publisher line and the sentence the front end's footer has
package.json         the theme's build, a pnpm workspace package
scripts/build.mjs    the theme's one list of its assets: copies them from the contract package into
                     build/ and writes build/assets.php, the manifest functions.php registers from
figtree.sha256       the SHA-256 of the Figtree file the theme ships, in `shasum -a 256` form
build/               gitignored; written by `pnpm build`
```

A block theme gives editors the Site Editor (Appearance > Editor), whose Pages section can edit pages too. Edit pages in the post editor instead: a Site Editor save still revalidates the front end and records its result, but shows no revalidation notice (issue #89's third note, settled; `docs/architecture/revalidation.md`, "Reading results").

The lockup links to the CMS's own `/resources/` rather than to the front end: editors see the resource archive there, and anonymous visitors get the lockdown's 404. ADR 0031 rejects redirecting to the front end because each redirect is a link from the CMS domain to it, and the lockup follows the same reasoning.

## The two rules from issue #89

The 404 is the one page of this theme every anonymous visitor gets, so:

1. **It lists no pages.** The 404 template and the parts it includes hold no `core/navigation`, `core/page-list`, query or any other block that lists posts, pages or terms. A navigation block with no menu falls back to listing every published page, which would show anonymous visitors what exists.
2. **It prints no `<link rel="pingback">`.** A classic or compat `header.php` prints one itself; a block theme has no `header.php`, and no file it renders from mentions pingbacks. The plugin removes core's `X-Pingback` header (`src/Security/XmlRpc.php`).

`tests/phpunit/Theme/ThemeFilesTest.php` in the plugin checks the files: the 404 template and its parts may use only an allow list of fixed-content blocks, and no file it renders from (templates, parts, PHP, JSON, CSS, JavaScript) mentions pingbacks. `tests/e2e/theme-404.spec.js` checks the rendered 404 as an anonymous visitor: no navigation, no page or post titles, no pingback link or header. Neither stops an editor from adding a navigation block to the header in the Site Editor, which stores its own copy of the part in the database; the Playwright spec would catch it only on a site where that copy exists.

## Layout and templates

The owner chose full parity: a logged-in preview looks like the front end. So every template renders the front end's markup with the contract package's classes, beside the block classes core adds, and loads the package's stylesheets for them:

- **The shell** (`shell.css`). Each template is one group, `rh-shell`, holding the header part as `header.rh-header`, a `main.rh-shell__inner.rh-main` with the id `main`, and the footer part as `footer.rh-footer`; the parts' rows are `rh-shell__inner rh-header__inner` and `rh-shell__inner rh-footer__inner`. So the header, `main` and the footer sit in one column of `--rh-measure-wide`, centred, with the 16 px gutter, as the front end's `Shell` lays them out. The header's row is the front end's but for its search control: the front end puts that control (`header-search.css`) at the end of the row, after the lockup, drawn into the row's padding so the row keeps the lockup's height; the theme's row holds the lockup alone, at the same height and position, until the control lands. The footer has the front end's two lines and no theme control yet. Under the admin bar, which only the CMS has, the shell's minimum height is the viewport less the bar's (core's `--wp-admin--admin-bar--height`), a rule `functions.php` adds inline after `shell.css`, so a short logged-in page does not scroll. The groups use core's default flow layout, never `constrained`: core's constrained layout puts `layout.contentSize` on each child, measured in that child's own `ch`, where the front end puts the measure on one wrapper. Core's skip link is kept: core inserts it before the shell and points it at `main`, where the front end's is `.rh-skip`.
- **A page** (`page.html`, `page.css` and `prose.css`): `article.rh-page`, the title as `h1.rh-page__title` in `header.rh-page__header`, and the post content as `rh-page__body rh-prose`, the front end's `PageArticle`. A static front page uses it too: core looks for `front-page.html` first, finds none, and falls through to the page hierarchy, as the front end renders its front page with `PageArticle`. `singular.html` is the same article for a single post, so it has the page's one `h1`.
- **A resource** (`single-resource.html`, `resource.css`, `prose.css` and `related.css`): the front end's `ResourceArticle` with its `RelatedSection`, in the article's order. `article.rh-resource` holds `header.rh-resource__header` with the title as `h1.rh-resource__title` and the plugin's `resource-hub/resource-meta` block (the type with its mark, the date and the topics, each linked to its listing); core's featured-image block at the `large` size with the class `rh-resource__media` (a `figure` where the front end writes a `div`, with core's `srcset` and `sizes`; `resource.css` draws the image the same from the class, at the column's width with the article's corners on the raised plate); the `resource-hub/resource-summary` block, the summary as the lead paragraph or nothing; the post content as `rh-resource__body rh-prose`; the `resource-hub/resource-source` block, "Source:" and a link shown by its host or file name, or nothing; and the `resource-hub/related` block, the related section with the editor's picks first and then the newest sharing a topic, from the same selection and cache the related route serves, or nothing when nothing is related. The four blocks are the plugin's (`wp-content/plugins/resource-hub-wp/README.md`, "The template blocks"), each the front end's markup with no wrapper, and render only for a published resource with exactly one type, which is the only kind the front end renders; the template itself is the shell, the article's wrapper and core's title, image and content blocks. The meta line's topic links go to `/resources/topic/{topic}/`, the front end's path, which the CMS does not answer yet: they are 404s on the CMS until the collection-templates pull request adds that path. The two things the front end does not have here: core's `wp-block-*` and layout classes beside the contract's, as on every template, and the image's `sizes` is core's rather than the front end's `CONTENT_SIZES`, which changes which file a browser picks, never the box it draws.
- **The welcome** (`home.html`, `welcome.css` beside `page.css`): core uses `home.html` for `/` while Settings > Reading shows posts, the state of wp-env and the host today, which is when the front end shows its welcome page; the template is the same heading, sentence and link. There is no `front-page.html`, because core would use it for `/` in both states, so it could not be both the page and the welcome. `show_on_front` set to `page` with no page chosen gets `home.html` too, as the front end shows its welcome then. One edge differs: the posts page under a static front page also gets `home.html`, where the front end answers a 404. The welcome's sentence and link, and the footer's two lines, are a copy of the front end's (`WelcomePage.tsx` and `Shell.tsx`): a known duplicate, kept by hand until the copy has one home.
- **Everything else** (`index.html`, `page.css` and `prose.css`): archives and search, under the archive's or the search's title as the page's one `h1` (core's `query-title`, which prints nothing on any other request), then the main query, each post as the article with its title an `h2` link, until the collection templates land. `ThemeTemplatesTest` pins which template core resolves for each kind of request, that each has one `h1`, and that a typed resource renders its four blocks in the article's order.
- **The 404** (`404.html`, `not-found.css`): the heading and the theme's own sentence in `.rh-not-found`'s column. It leaves out the front end's "Browse all resources" link: an anonymous visitor would follow it to another 404.
- **Tables** (`inc/table-region.php`). A `render_block_core/table` filter puts each table block's `<table>` in a `div.rh-table-scroll` with `role="region"`, `tabindex="0"` and an `aria-label` from its caption or figcaption, the region the front end's content pass adds (`tableRegion` in `apps/web/lib/content/render.tsx`) and `prose.css` draws as the table's box. It is presentation, so it is the theme's, and `functions.php` adds it on `template_redirect`, so only pages core renders with a template get it: REST's `content.rendered`, which the front end reads, stays core's markup, and the contract does not change. Every table directly in the block's figure is wrapped, each named as the front end names it (its own caption, else the figure's, else "Table", from the text the front end renders, cut to 150 UTF-16 code units at a word), but for two gaps the docblock explains: the theme also drops zero-width characters, and keeps words naming the CMS's own address, which the front end drops; only table blocks are, not a raw `<table>` in a Custom HTML block. The file's docblock has the rest.
- **Images** (`inc/image-lightbox.php`). The theme's pages leave out core's image block stylesheet (below), which is what hides an image lightbox's overlay, and the front end never shows a lightbox, so on the same pages, through the same `template_redirect` hook, every image block renders with its lightbox off.

## Assets

The theme draws with the contract package, `@colbitron/resource-hub-ui` (`packages/ui/DESIGN.md`, "Consumers and loading"). The host never sees the pnpm workspace, so `scripts/build.mjs` copies what the theme loads into `build/`, byte for byte: `tokens.css`, `brand.css` (the lockup's classes), `fonts/figtree-latin-wght-normal.woff2` with `fonts/LICENSE-Figtree.txt` beside it, `fonts/figtree-fallback.css`, and the document, the shell and the components the templates render: `base.css`, `shell.css`, `prose.css`, `page.css`, `resource.css`, `related.css`, `welcome.css` and `not-found.css`. The script's `ASSETS` is the theme's one list of them: each copy, and for a stylesheet its handle and the handles it loads after. It writes that list into `build/assets.php`, with each copy's SHA-256, and `functions.php` registers every stylesheet from the manifest, versioned by its hash; no other file lists them. The root's `pnpm build` runs it alongside the plugin's build (pnpm runs the two packages' builds concurrently; neither reads the other's output), and CI's plugin gate runs `pnpm build` before PHPUnit and Playwright, as for the block.

- **`theme.json`** registers Figtree with `fontFace` from `file:./build/fonts/…`, under the plain name `Figtree`, with the front end's `font-display: swap`; it leaves `--rh-font-figtree` unset, so `--rh-font-sans` falls back to that name. The one font-family preset is `"Figtree", var(--rh-font-sans)`: core names the `@font-face` after the first family in the preset, and the rest is the token's stack with its fallback faces. The palette is every `--rh-color-*` token, the font sizes every `--rh-text-*` one, the spacing sizes every `--rh-space-*` one, and `layout.contentSize` and `wideSize` are `--rh-measure` and `--rh-measure-wide`, each written as `var(--rh-…)`, never as a value, so a value changes only in `tokens.css`. A slug is the token's suffix as core spells it in a custom property (`2xl` is `2-xl`). The five mark accents are not in the palette, since they are for small marks only, never text. Custom colours, gradients, duotones and font sizes are off, and core's default palette, gradients, duotones, font sizes and spacing sizes are hidden from the editor's pickers, so an editor picks only from the tokens. Hidden, not removed: core still prints those defaults' custom properties and their `.has-*` classes. Core's default shadows and aspect ratios are not hidden. The base styles set the body's colours, Figtree, the body size and leading, the link colour, the headings' weight, tracking and leading, and the sizes of `h1`, `h2` and `h3` from the tokens: a mirror of `base.css` for the editor canvas, which does not load it (below).
- **`functions.php`** registers a handle for each stylesheet in the manifest on `init`. It enqueues `resource-hub-tokens`, `resource-hub-figtree-fallback` and `resource-hub-brand` on `enqueue_block_assets`, which reaches the CMS's own pages and the iframed editor canvas, and not the editor's admin page around the canvas. `tokens.css` sets `color-scheme: light dark` and writes every colour with `light-dark()`, so the pages and the canvas follow the reader's system preference, as the front end does by default.
- **The load order.** On the CMS's own pages, `functions.php` enqueues `resource-hub-base` and `resource-hub-shell`, then the template's components (`resource-hub-prose` and `resource-hub-page`; `resource-hub-prose`, `resource-hub-resource` and `resource-hub-related` on a single resource; `resource-hub-welcome`; or `resource-hub-not-found`), on `wp_enqueue_scripts` at priority 20. Core enqueues its global styles there at 10, so the package's files print after `global-styles-inline-css`. `base.css` styles `body`, `a` and the headings at the same specificity as `theme.json`'s base styles, so the later one wins a tie: the package's, and a page computes what the front end computes from the same file. The values agree anyway; the order decides when they part, as after a Styles change saved in the Site Editor, which the front end never sees either. In the editor canvas only `theme.json`'s mirror applies: its base styles give the body, links and `h1` to `h3` the type, sizes and colours `base.css` gives them, and core keeps its own layout, spacing and focus styles there, so an editor's content reads in the site's type and colours, in the editor's column. Core's block styles for five blocks draw over `prose.css`, and the front end loads none of core's CSS, so `functions.php` dequeues them on the CMS's own pages, and the canvas keeps them: the table's (a border on every cell's side, a 3 px rule under the head, a fixed table layout), the code block's (its code set as a block that breaks spaces), the separator's (its dots style, three dots in place of the rule), the quote's (its large style's padding, italic and right-aligned citation) and the image's (a margin under the caption, alignment and sizing rules, and the lightbox's, see above). Core's button look is not a block stylesheet but core's default `theme.json` element style, which the canvas shares, so it stays (below). The docblock of `resource_hub_theme_enqueue_page_styles()` has the reasoning.
- **One copy of the tokens.** The plugin's blocks name the same `resource-hub-tokens` handle in their `block.json`, and WordPress prints a handle once, so a page with a block loads `tokens.css` once. The theme registers the handle first; the plugin registers its own copy (`build/shared/tokens.css`) at a later `init` priority only when no theme has, so the blocks keep their tokens in any theme (`src/Blocks/SharedTokens.php` in the plugin).
- **The resource page's stylesheets have two owners.** The theme owns what the template renders: `resource.css` and `related.css`, registered from the manifest and enqueued on every single resource, `related.css` whether or not the related block renders anything, because the front end's resource route always carries it and the same file draws the heading of a related-resources block in the body, which only the theme can load for the page. The plugin's blocks own what they write: the rows' `card.css` comes with the related block under the shared `resource-hub-card` handle (`src/Blocks/SharedCard.php`), and the meta line's labels, `card-labels.css`, with the meta block, each only where the block renders something. So the theme keeps no copy of `card.css`, and the plugin none of `related.css`: the shared-handle fallback exists for the blocks that live in post bodies on any theme, and the related block lives in this template alone.

The plugin's suites hold all of it to the package and to the front end. The markup the plugin's blocks write for the resource page is held to the front end's by the contract's markup fixtures (`packages/ui/README.md`, "Markup fixtures"): the meta line, the summary and the related section each have a fixture both sides' tests render and compare. `tests/phpunit/Theme/ThemeAssetsTest.php` reads the manifest and fails when a copy in `build/` is not the package's file byte for byte, when it holds a stale hash, when a copied stylesheet has no handle or a handle no copy, when `functions.php` enqueues a handle the manifest does not register, or when the package's Figtree is not the file `figtree.sha256` records, so a new font file means changing the record with it; `tests/phpunit/Theme/ThemeTokensTest.php` fails when the presets are not exactly the tokens, in order, when `theme.json` writes a raw colour or length, or names a token that does not exist. `TableRegionTest.php` and `ImageLightboxTest.php` check the two block filters, and `ThemeTemplatesTest.php` which template core renders for each kind of request. Playwright's `tests/e2e/theme-assets.spec.js` counts the token declarations on a page with the block, on the CMS's page and in the editor canvas, and checks Figtree, the lockup and both schemes. The two parity checks the owner chose are `theme-parity.spec.js` and `theme-screenshots.spec.js`. The first is not a comparison with the front end's computed styles: it reads a CMS page's computed styles and holds each to the value the spec expects the package's rule to give it, written in the spec as a selector and its declarations from `prose.css`, `base.css`, `shell.css` and the rest, by hand, and resolved from the tokens on the same page by a probe element (the body, the headings, links, paragraphs, lists, quotes, code, the rule, an image and the captions, the shell's column and gutter, the header's row, the article's column, the table's region, the welcome, and a short page under the admin bar), and the same for a resource page it seeds with a featured image, a summary, a source, a pick and a topic match (`resource-page-seed.js`): the article's column, the header and the meta line with its mark and links, the image, the summary, the body, the source line and the related section's heading and rows, in both schemes and at 360 px. The second is `theme-screenshots.spec.js`, pixel baselines of a page and of that seeded resource, logged in with the admin bar hidden, and of the anonymous 404, at 1280 and 360 px in both schemes, drawn by Chromium in the Linux image the front end's screenshot gate pins. That spec starts the container itself with the front end's `apps/web/e2e/browser-container.mts`, so it runs in the plugin's ordinary `pnpm test:e2e`, here and in CI. A design change regenerates the CMS baselines with `pnpm test:e2e -- --update-snapshots` (with `WP_BASE_URL` set to the tests site), and the images in `tests/e2e/__snapshots__/` are looked at and committed with the change. So does an update that moves pixels without a design change: WordPress is not pinned, so wp-env and CI run the latest release, as the host does with major updates on, and a release that changes core's markup or CSS can shift the baselines; a Playwright upgrade, which moves the pinned image (`apps/web/e2e/playwright-image.mts`), can too. A failed comparison says so in its message. Look at the diff in the run's artifacts first: when it is core's or the browser's change and the page still matches the design, regenerate. PHPCS lints this directory's PHP with the plugin's ruleset (`phpcs.xml.dist`), and the root's `pnpm lint:js`, which CI's plugin gate runs, lints and checks the formatting of `scripts/` through the plugin's `lint:js:theme`: the plugin's one `@wordpress/scripts`, run from the repository root, because ESLint reads no file outside the directory it runs in (`pnpm format` formats it the same way, through `format:theme`).

## Running it

`.wp-env.json` at the repository root mounts this directory into both wp-env sites. wp-env mounts a mapped theme but never activates it, on a new environment or an existing one, so its `afterStart` script runs `wp theme activate resource-hub` on the dev and tests sites after every `pnpm env:start`. The script calls `wp-env run`, so it needs `wp-env` on `PATH`; `pnpm env:start` puts the workspace's copy there, while a bare `wp-env start` from a shell without it fails at that step. The PHPUnit bootstrap then reinstalls the tests site on core's test theme, `default`, so the Playwright fixture in `tests/e2e/fixtures.js` activates the theme again before any spec runs. Run `pnpm build` once before loading a page: without `build/`, `functions.php` registers nothing, Figtree's file is missing, and the pages render in the browser's defaults.

## Not built yet

Slice 5 continues in [issue #89](https://github.com/Colbitron/resource-hub-wp/issues/89):

- **The remaining component stylesheets.** The plugin's row blocks bring `card.css` where they are used, under the shared `resource-hub-card` handle, which a theme that registers it first at `init` would provide instead (`src/Blocks/SharedCard.php` in the plugin); `theme-toggle.css`, `listing.css` and `lead.css` wait in the contract package for the templates that render them, which copy them into `build/` and enqueue them as they land (`packages/ui/README.md`, "Stylesheets").
- **The plugin's block** for the collection head, which the collection templates render. The row block is built, `resource-hub/resource-card`, a listing row for a Query Loop's post template (the post template carries `rh-card-grid`), as are the resource page's four (the plugin's `README.md`, "The template blocks"). The meta line links each topic to `/resources/topic/{topic}/`, the front end's path, which the CMS does not answer yet, so those links 404 on the CMS until the collection templates add it.
- **The remaining templates:** the collection pages (archives and taxonomies); `index.html` stands in for them.
- **The header's search control** the front end has at the end of its header row (`header-search.css` and `header-search-bar.css` in the contract package), which issue #128 redesigns before the theme renders it.
- **The System / Light / Dark control** the front end has in its footer, in `rh-footer__theme`. Until it lands, the CMS follows the system preference only.
- **Buttons.** A button block is a filled button on the CMS and a plain link on the front end, whose content pass renders its markup with no core CSS. The look is core's default `theme.json` element style, printed in the global styles the pages and the editor canvas share, so the theme cannot drop it on its pages alone; matching the front end would mean styling buttons as links in the canvas too, or filtering core's `theme.json` data per request.
- **The editor canvas's column.** `layout.contentSize` is `--rh-measure`, `65ch`, which core applies to each child of the canvas's constrained root, so a heading's column there is measured in its own, larger `ch` and is wider than the paragraphs'. The theme's pages put the measure on a wrapper, as the front end does; the canvas is core's layout.
- **Deploy:** CI syncs only the plugin to the host, so this theme is not on the hosted CMS yet, and the hosted 404 is still rendered with the host's current theme. The deploy must carry `build/` and may leave `package.json`, `scripts/` and `node_modules/` behind.

Issue #89's third note, the Site Editor revalidation notice, is settled: page editing stays in the post editor, and the Site Editor gets no notice (above).
