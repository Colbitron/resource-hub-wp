# @colbitron/resource-hub-ui

The contract between the Resource Hub WordPress plugin ([`wp-content/plugins/resource-hub-wp/`](../../wp-content/plugins/resource-hub-wp/)) and its Next.js front end ([`apps/web/`](../../apps/web/)), both in this repository, written once as JSON Schema (draft 2020-12) so both sides can check themselves against it ([ADR 0010](../../docs/adr/0010-contract-as-json-schema-in-a-shared-package.md)). PHPUnit in the plugin validates every payload it builds against these schemas; the front end proves its Zod readers against the same fixtures. When either side drifts from the schemas, its own test fails.

Every schema and every property carries a `description` that states what the value means, not only what type it is. The schemas are the contract; this file is the only full statement of the semantics a schema cannot express. Anything else that describes the contract summarises this file and links here.

Contract changes land in one pull request that touches both sides and the schemas, and they stay additive: add a field, route or event before anything relies on it, and remove the old one only after nothing does, so the front end never breaks against a CMS one deploy behind ([ADR 0033](../../docs/adr/0033-one-repository-for-the-plugin-the-front-end-and-the-contract.md)). Change a schema and its fixtures first, then this file, then the code on both sides.

## Schemas

| File | Describes |
|---|---|
| `schemas/revalidate-request.schema.json` | Body of `POST {FRONTEND_URL}/api/revalidate/`, WordPress to front end: a batch of resource, term and page events |
| `schemas/revalidate-response-ok.schema.json` | The `200` reply: the paths the front end revalidated |
| `schemas/revalidate-response-error.schema.json` | The `400`, `401` and `500` replies: `{ "error": "…" }`; `401` is exactly `unauthorized` |
| `schemas/related-response.schema.json` | `GET /wp-json/resource-hub/v1/related/{id}?count=n`: related resource IDs with the reason each was picked, merged on the CMS, for the resource page's related section (see [Related items](#related-items)) |
| `schemas/search-response.schema.json` | `GET /wp-json/resource-hub/v1/search?q=…&page=n`: one page of the published resources and pages matching a query, as IDs and kinds, with the total and the number of pages (see [Search](#search)) |
| `schemas/resolve-response.schema.json` | `GET /wp-json/resource-hub/v1/resolve?slug=…`: an old or current slug to the resource's canonical id, type and slug |
| `schemas/page-response.schema.json` | `GET /wp-json/resource-hub/v1/page?path=…`: the published page the front end serves at a public path, with its canonical path, or `null` |
| `schemas/wp-error.schema.json` | The WordPress core REST error shape the custom routes return for `400` and `404` |
| `schemas/type-accents.schema.json` | The package's type-accent table, `type-accents.json`: which brand accent marks each `resource_type` term, by term ID; data, not a payload: the front end imports it at build time, and the plugin's build copies it into `build/`, which the plugin reads per request (see [Type accents](#type-accents)) |
| `schemas/common.schema.json` | Shared `$defs` the others reference: `id`, `slug`, `typeSlug`, `topicSlug`, `typeList`, `topicList`, `path`, `pagePath` |

The bearer token on the revalidation request is a header and is not part of any schema. The stylesheets the package also holds are described under [Stylesheets](#stylesheets), and the type-accent table under [Type accents](#type-accents).

## How the two sides talk

**Server side only.** The front end makes every CMS request on the Next.js server, with the CMS's `/wp-json` base in `WP_API_URL`, a server-only environment variable (never `NEXT_PUBLIC_`), so the CMS's address never reaches the browser ([ADR 0040](../../docs/adr/0040-the-cms-url-never-reaches-the-browser.md)). WordPress emits absolute CMS URLs everywhere (`get_permalink()`, `content.rendered`, `_embed` media) and does no rewriting; the front end rewrites them while rendering: links lose the CMS domain, and images, including `<img src>` and `srcset` in `content.rendered`, become `/media/…`, which the front end rewrites to the CMS's uploads directory one to one. `/media/` is therefore part of the contract: a path under `wp-content/uploads/` is the same path under `/media/`. This reduces exposure; it is not a security boundary.

**Content reads.** `GET {WP_API_URL}/wp/v2/resources?_embed&per_page=…&page=…&resource_topic=…&resource_type=…&resource_flag=…`, `GET {WP_API_URL}/wp/v2/resources/{id}` and `?slug=`, the taxonomy endpoints `/wp/v2/resource_topic`, `/wp/v2/resource_type` and `/wp/v2/resource_flag`, and `GET {WP_API_URL}/wp/v2/pages/{id}`. Meta is `summary` and `source_url`, under `meta` because of `show_in_rest`. Featured is the `resource_flag` term `featured`, not meta: a featured resource has that term's ID in `resource_flag`. Anonymous responses from these routes and from `/resource-hub/v1/`, errors included, carry `Cache-Control: no-cache, must-revalidate, max-age=0` (the plugin's `NoCacheHeader`), so the front end's Data Cache is the only HTTP cache between the two sides.

**Custom routes.** `GET {WP_API_URL}/resource-hub/v1/resolve?slug=…`, `GET {WP_API_URL}/resource-hub/v1/page?path=…`, `GET {WP_API_URL}/resource-hub/v1/related/{id}?count=…` and `GET {WP_API_URL}/resource-hub/v1/search?q=…&page=…` (described below). All have a public permission callback and answer errors in core's `WP_Error` shape, `{ "code", "message", "data": { "status" } }`, for 400 and 404.

**Revalidation request**, WordPress to front end: `POST {FRONTEND_URL}/api/revalidate/`, with the trailing slash like every front-end path (the slashless form is a 308 the plugin's sender does not follow), header `Authorization: Bearer {REVALIDATE_SECRET}`, header `Content-Type: application/json`, body a batch of 1 to 25 events:

```json
{ "version": 1, "events": [
  { "type": "resource", "event": "publish" | "update" | "unpublish" | "trash" | "delete", "id": 123, "slug": "example", "rest_url": "https://cms.example/wp-json/wp/v2/resources/123", "types": ["type-slug"], "topics": ["topic-slug"], "previous": { "slug": "old-example", "types": ["type-slug"], "topics": ["topic-slug"] } | null },
  { "type": "term", "taxonomy": "resource_topic" | "resource_type", "event": "create" | "update" | "delete", "id": 45, "slug": "topic-slug", "name": "Topic name", "previous": { "slug": "old-slug", "name": "Old name" } | null },
  { "type": "page", "event": "publish" | "update" | "unpublish" | "trash" | "delete", "id": 7, "path": "/about/team/", "previous": { "path": "/team/" } | null }
] }
```

**Revalidation response:** `200 { "revalidated": ["/resources/", "/resources/webinar/example/"] }` listing the paths revalidated (tags are not reported); `400 { "error": "…" }` for a malformed body; `401 { "error": "unauthorized" }` for a bad or missing bearer; `500 { "error": "…" }` when the front end fails, a missing or invalid secret included. The plugin records the status and body and shows them to the editor, so every message must be plain, accurate, and never quote a value. Every response carries `Cache-Control: no-store`.

## Semantics the schemas assume

**A revalidation request is a batch.** `{ "version": 1, "events": [ … ] }`, with 1 to 25 events. One WordPress PHP request produces one batch, so a bulk edit or a bulk trash in the admin is one request to the front end, not one per post. Events within a batch are deduplicated per resource ID for resource events, per (taxonomy, term ID) for term events and per page ID for page events, so a post and a term that share a numeric ID never merge; each group becomes one event carrying the earliest `previous` and the latest current state. A group that ends in `unpublish`, `trash` or `delete` after an `update` in the same request carries, at the top level, the state from before that update (for a term, its slug and name from before a rename), because that is the state the front end can have cached; `previous` stays `null`. A batch that would exceed 25 events is split into several requests.

**Resource events describe the public state the event concerns.** The top-level `slug`, `types` and `topics` are the state after the save for `publish` and `update`, and the last public state before removal for `unpublish`, `trash` and `delete` (or, after an `update` in the same request, the state before the request). A trashed post's slug is therefore the slug readers used, never the `__trashed` form WordPress renames it to. Changes that never touch public state send nothing: editing a draft, or restoring from the trash, which restores to draft. Permanently deleting a resource already in the trash sends nothing, because its `trash` event was already sent.

**`previous` is non-null only and always on `update`.** It holds the slug, type and topics (for a term event, the slug and name; for a page event, the path) from before the save, every field filled whether or not it changed, so the front end can also revalidate the listings and URL the item just left. When the resource's earlier types were not exactly one, as on the save that gives its one type to a resource saved outside the REST API, `previous.types` carries the current type in their place, with `previous.slug` and `previous.topics` kept. For every other event it is `null`: `publish` and `create` have no earlier public state, and the removal events already describe the last public state in the top-level fields.

**Term events** cover `create`, `update` and `delete` of `resource_topic` and `resource_type` terms, because renaming or deleting a term changes pages without saving any resource. `resource_flag` terms are managed in code and send none. An edit that changes neither slug nor name sends nothing. Assigning or removing terms on a resource is an `update` of that resource, not a term event. There is no topic redirect: an old topic URL is a 404 after a re-slug.

**The front end groups events.** `publish` and `update` mean refresh; `unpublish`, `trash` and `delete` mean remove, where its refetch of the resource returns nothing and the page becomes a 404. For every event it revalidates the union of the paths and cache tags implied by the current and the `previous` state, and never diffs the two. The tags are `resources`, `terms`, `resource:{slug}`, `topic:{slug}` and `type:{slug}` for resource and term events, and `pages` for page events, with every slug in WordPress's lower-case percent-encoded form. `terms` is produced only by term events and carried by every fetch that embeds or lists terms, so a term change reaches every page that shows the term; `pages` is produced only by page events and carried by every page lookup and read.

**A page event is about a public path.** `{ "type": "page", "event", "id", "path", "previous": { "path" } | null }` describes a WordPress page (post type `page`) the front end serves ([ADR 0052](../../docs/adr/0052-the-front-end-renders-the-cms-pages.md)): `path` is the page's public path in the state the event concerns, `/` for the static front page (Settings > Reading), else its parent chain and slug with a trailing slash (`/about/team/`, the `pagePath` definition). The five event names mean what they mean for a resource, and `previous` is set on `update` only, with the path before the save: a slug or parent change, and a page becoming or ceasing to be the front page (an `update` between its own path and `/`), are updates. A password put on a served page is an `unpublish`, and one taken off a `publish`. A parent's move or rename sends no event for its children, whose paths also changed; the front end clears one `pages` tag for every page lookup and read, so they follow. Posts send no events, and the front end never serves them.

**A page lookup is answered for the current state.** `GET /wp-json/resource-hub/v1/page?path=…` answers the static front page for `/`, else the published page whose parent chain is the path, else the one published page that has the last segment as its slug now (a page moved under another parent); a page that is not published or has a password, the posts page (`page_for_posts`, only while `show_on_front` is `page`) and an ambiguous slug are `null`. The answer's `path` is the page's canonical path now, `/` for the front page, so the front end redirects when it differs from what it asked for, after looking that path up as well. A miss is a 200 with `page: null`, not a 404, so the front end's Data Cache keeps it; a segment that sanitizes to nothing is a miss too. Only a `path` that is not a string or is over 2010 bytes is a 400, and the front end treats that, and a `rest_no_route` 404 from a CMS without the route, as a miss. A top-level page is never slugged `resources`, `api`, `media`, `_next` or `search`, the front end's own first segments (`search` for its search page at `/search/?q=…`): WordPress gives such a slug a suffix on save, and the front end answers such a path with a 404 without asking.

**Resolve answers for a published resource only.** `GET /wp-json/resource-hub/v1/resolve?slug=…` returns `{ "id", "type", "slug" }` for a published resource found by its current slug first, then by an old slug through core's `_wp_old_slug` record, or a 404 (`resource_hub_not_found`). `slug` is required, at most 200 bytes as sent, and run through `sanitize_title()`; empty once sanitized is a 400. The front end calls it only when its current-slug lookup misses, and sends the 308 itself. When an unpublished and a published resource both once had a slug, core's single match can be the unpublished one and the slug is a 404; that is pinned by a test, not fixed. A resource without exactly one type, or with a reserved one, is a 404.

**A resource has exactly one type.** `types` is a one-element array because the type is a URL segment and a resource has one canonical URL. The array form keeps the field the same shape as `topics`.

**Reserved type slugs.** A `resource_type` slug is never `topic` or `page`, because the front end's routes `/resources/topic/[topic]/` and `/resources/[type]/page/[n]/` would collide with a type of that name. WordPress refuses them on save; the schemas enforce it wherever a type slug appears: a resource event's `types` and `previous.types`, a term event's `slug` and `previous.slug` when its taxonomy is `resource_type`, and the resolve response's `type`. The front end's readers are stricter than these schemas on slugs that cannot be stored or put in a path: they also reject a dot segment (one or two dots, raw or percent-encoded), a lone surrogate, a slug longer than 200 characters once percent-encoded, a percent escape of a character Next.js decodes before a page sees the segment, which is `encodeURIComponent`'s unescaped set `A-Z a-z 0-9 - _ . ! ~ * ' ( )` (`case%2dstudy`, `%41bc`, `x%7ey`, `arti%27cle`, `a%2ab`), so the slug's own URL could never be served, and a type slug that is `topic` or `page` in any case. The CMS never stores such an escape in a `resource` post slug or in a term slug of the three taxonomies: it decodes them on save.

**`rest_url` is fetched, so the front end checks its host.** The schema pins its scheme to `http` or `https`, which rejects `javascript:`, `mailto:` and the like, but it cannot know the WordPress origin. Before fetching `rest_url` the front end must check that its host matches the WordPress origin it is configured with, and refuse it otherwise. That check is the guard against server-side request forgery, and it lives on the front end. Today the revalidate route fetches nothing at all and ignores `rest_url` after validating it.

**`topics` has no `maxItems`.** An extreme batch (25 events, each with very many topics) could produce a `200` listing more paths than fit in the plugin's 64 KB response limit, and the plugin would record a truncated answer for revalidation that did happen. Not a real case; if it becomes one, `topics` gets a `maxItems` on both sides.

## Reader policy

Strict where we produce, lenient on unknown keys where we consume ([ADR 0010](../../docs/adr/0010-contract-as-json-schema-in-a-shared-package.md)). The schemas keep `additionalProperties: false`, and a side checks what it produces against them exactly: the plugin its request and route responses, the front end its replies to the revalidation request. A side that reads a payload parses it with a variant that drops keys it does not know instead of rejecting them, every rule on a known key unchanged. The reason is the deploy order: the CMS deploys first and contract changes are additive, so for the length of one deploy the CMS can send a key the front end does not know yet, and a front end that answered it with a `400` would turn an additive change into a breaking one.

On the front end the exact mirror stays under a `…Strict` export, and it is the one the conformance tests prove against these fixtures, so an extra-key fixture is still rejected; the revalidate route and the data layer parse with the reader. The policy covers unknown keys only. A new value for an existing enum (an event name, an event `type`, a term `taxonomy`) is not additive: the reader rejects the whole batch with a `400`, so the front end must ship support for it before the CMS sends it, reversing the usual deploy order for that one change. Bumping `version` is not a way round that: the front end answers a `version` it does not understand with a `400` too. Whether an unreadable event should instead trigger a broad revalidation is open in [issue #51](https://github.com/Colbitron/resource-hub-wp/issues/51).

A collection the front end reads is parsed one item at a time, and a bad item is skipped rather than failing the listing, up to a threshold; `apps/web/lib/wp/fetch.ts` holds the rule. Flag terms are currently parsed as strictly as the other taxonomies ([issue #54](https://github.com/Colbitron/resource-hub-wp/issues/54)).

## Related items

The related route and the plugin's `related_picks` post meta exist on the CMS (`RelatedRoute`, `RelatedCache` and `Meta` in the plugin's `src/`), validated against `related-response.schema.json` and its fixtures; the editor sets the picks in the Resource details panel, and the front end's related section on the resource page reads the route. The contract:

- `GET {WP_API_URL}/resource-hub/v1/related/{id}?count=3` (`count` 1 to 10, default 3) returns `{ "items": [ { "id": 12, "source": "pick" | "topic" } ] }`: at most `count` items, already merged, picks first in the editor's order, then the newest published resources sharing a topic, newest first and with no ranking by how many topics overlap, unpublished picks skipped, no duplicates, never the resource itself. A resource with no topics gets its picks alone; one with neither gets an empty list. A `count` out of range is a 400 and an ID that is not a published resource a 404, in core's `WP_Error` shape.
- **IDs only.** The front end calls it once, does no merging of its own, and reads the objects with `GET {WP_API_URL}/wp/v2/resources?include={ids}&orderby=include&_embed`, so one code path renders a resource everywhere and no permalink has to be rewritten.
- The list is cached on the CMS under a salted object-cache key that any published resource's save, delete or topic change turns over; a change of picks on a published resource reaches the route on the next request after the save. The anonymous response carries the no-cache header like every other route here.
- `related_picks` is an ordered list of at most 10 post IDs, in the REST `edit` context only, for the editor's picker; the front end never reads it, and an anonymous read of `/wp/v2/resources` never includes it. A pick that is no longer published stays in the list and is skipped by the route.

## Search

The search route exists on the CMS (`SearchRoute` and `SearchCache` in the plugin's `src/Rest/`), validated against `search-response.schema.json` and its fixtures, and the front end's data layer reads it (`searchSite` in `apps/web/lib/wp/search.ts`) for its `/search/` page ([issue #115](https://github.com/Colbitron/resource-hub-wp/issues/115)), which renders the results as `card.css`'s rows, a page's with the label `.rh-card__kind` in place of the type. The contract:

- `GET {WP_API_URL}/resource-hub/v1/search?q=webinar&page=1` returns `{ "items": [ { "id": 118, "type": "resource" | "page" } ], "total": 30, "pages": 3 }`: one page of at most 12 matches, resources and pages mixed, in the search engine's order. A match is a published resource or a published page with no password, never the posts page (`page_for_posts`, while `show_on_front` is `page`), because the front end serves neither; whoever asks, the same answer.
- **`q`.** Required and a string. Every run of whitespace, as PHP's PCRE matches `\s` in UTF mode (Unicode whitespace, U+0085 and U+180E included, U+FEFF and the zero-width characters not), becomes one space and the ends are trimmed; what is left must be 2 to 100 characters, counted as Unicode code points, and valid UTF-8. Anything else is a 400 `rest_invalid_param` (a missing `q` is core's `rest_missing_callback_param`, also a 400). Nothing else is done to it: no tags stripped and no case folded, so the front end sends the normalised form and its cache key and the CMS's are the same query.
- **`page`.** An integer from 1 to 10, default 1; anything else is a 400 `rest_invalid_param`. A page past the last one with results is a 200 with no items and the same `total` and `pages`.
- **`total` and `pages`.** `total` is every match, as the engine counts them, never capped. `pages` is `total` over 12, rounded up and capped at 10, so matches past the 120th are counted and never listed; the front end can say there are more and invite a narrower query. Both are 0 when nothing matches.
- **IDs and kinds only.** The front end calls the route once per page of results and reads the objects per kind: `GET {WP_API_URL}/wp/v2/resources?include={ids}&orderby=include&_embed` for resources, as the related section does, and `GET {WP_API_URL}/wp/v2/pages?include={ids}&orderby=include` for pages, which embed nothing the front end reads. It shows them in the route's order, and a match the collection no longer returns (unpublished between the two reads) is left out. The engine is the plugin's choice and not part of the contract: moving from one engine to another changes the order and what matches, never the shape.
- **Tags.** The route's fetch and both object reads carry `resources`, `terms` and `pages`, fixed from the request: any resource event can change what matches, the reads embed term names, and any page event can add, move or remove a page among the results.
- **Cache.** The answer is cached on the CMS under a salted object-cache key per normalised query and page that turns over on every change a search can see: any published resource's save, delete or topic change, as for the related lists, and a save or delete of any page that was or becomes public, a change to Settings > Reading, and any change to a type or topic term. The anonymous response, errors included, carries the no-cache header like every other route here, so the front end's Data Cache is the only HTTP cache in front of it.
- A CMS without the route answers core's 404 `rest_no_route`; the front end reads that as no search at all, never as an error, so a front end a deploy ahead keeps working.

## Block marker

The `resource-hub/related-resources` block's render callback (`wp-content/plugins/resource-hub-wp/src/Blocks/RelatedResourcesBlock.php`) writes the marker below with card rows inside it, and the front end's content pass (`apps/web/lib/content/render.tsx`) swaps a valid marker for its own `<RelatedResources>` list (`apps/web/components/RelatedResources.tsx`). The rows the CMS writes are the fallback the front end shows when it does not swap, so the markup inside the marker is part of the contract too. The contract:

- The block renders `<div data-rh-block="related-resources" data-count="3" data-topic="topic-slug" data-topic-id="45" data-exclude="123">` around its `<h2>` heading and the resources as card rows in `card.css`'s markup, titles at `h3` and linked with `get_permalink()`, the type's mark carrying `data-accent` from the type-accent table as the front end's `ResourceCard` writes it (see [Type accents](#type-accents)), the title and the type and topic names as plain text and the summary as stored, each escaped as React escapes text, so a row reads as the front end's `ResourceCard` does; a one-line `<p>` takes the rows' place when the topic has no other published resource that gets a row. A resource gets no row when its title is empty as plain text (nothing left once whitespace and zero-width characters are removed, the front end's `cardTitle()` test) or it does not have exactly one type; the block over-fetches a few rows so `count` stays filled, and can list fewer when more than a few of the newest are dropped. Only a PHP caller can publish a resource without exactly one type, but an editor can publish one with a blank title. The wrapper carries the `rh-related` class. With no topic chosen, or a topic that no longer exists, the block renders nothing at all.
- `data-topic` is the term's current slug, resolved at render time from the stored term ID, and names the `topic:{slug}` cache tag; `data-topic-id` is that ID, for the `resource_topic` filter on `/wp/v2/resources`; `data-exclude` is the ID of the post the block sits in, left out of the list (`0` when the block renders outside any post, which the front end treats as an invalid marker); `data-count` is 1 to 10, clamped on the CMS.
- **The row markup.** Inside the wrapper: `<ul class="rh-card-grid" role="list">`, and per resource an `<li>` holding `<article class="rh-card">` with `<p class="rh-card__meta">` (`<span class="rh-card__type" data-accent="…">` and a `<time datetime>`), then `<div class="rh-card__body">` with `<h3 class="rh-card__title">` around `<a class="rh-card__link">`, `<p class="rh-card__summary">` when there is a summary, and `<ul class="rh-card__topics" role="list" aria-label="Topics">` of `<li class="rh-card__topic">` when there are topics. Of all the body's markup, the front end's sanitiser (`CARD_CLASSES` and `listProps` in `apps/web/lib/content/render.tsx`) keeps exactly three things more inside the wrapper of a marker whose `data-*` attributes are valid, and only there: the `<article>` element; the `rh-card*` classes, each on its own element alone (`rh-card-grid` on a `<ul>` or `<ol>`, `rh-card` on an `<article>`, `rh-card__meta` and `rh-card__summary` on a `<p>`, `rh-card__type` on a `<span>`, `rh-card__body` on a `<div>`, `rh-card__title` on an `<h2>` to `<h6>`, `rh-card__link` on an `<a>`, `rh-card__topics` on a `<ul>`, `rh-card__topic` on an `<li>`), all but `rh-card-grid` and `rh-card` only inside a row, an `<article>` of the same marker that kept `rh-card`; and `role="list"` on any `<ul>` or `<ol>` there, with `aria-label="Topics"`, exactly, only on a `<ul>` that kept `rh-card__topics`. Anything else falls back to the body's rules: another `rh-` class, any other role or label, `data-accent`, and a class on the wrong element or outside a row are dropped, so a fallback row's mark is the neutral ink on the front end; an `<article>` outside a valid marker is unwrapped, and one without `rh-card` is kept but is not a row. A marker whose `data-*` attributes are not valid gets none of the three, and the wrapper of every marker, a marker nested in another's rows included, gets the body's rules with `rh-related` its one class, so a nested marker is judged by its own attributes alone. Renaming a class, moving one to another element, or changing the role or the label is a contract change on both sides.
- The front end parses `content.rendered` on its server, never in the browser, in the same pass that strips link domains and rewrites images to `/media/`, and replaces a valid wrapper with its own `<RelatedResources>` server component: the newest `count` published resources in the topic, the host post left out, fetched with the `topic:{slug}` tag, under the marker's heading at the level the body's outline gives it. It renders the wrapper's own heading and rows, with their URLs rewritten, as the fallback for a marker with an invalid attribute, one inside a link, one past the first five in a body, and one whose fetch fails. The marker never reaches the browser.
- The marker's attributes, the heading, the row markup above and the shared class names are part of the contract. No shared JavaScript.

## Type accents

`type-accents.json` is the table of which brand accent marks each resource type, and both sides read this one file; `schemas/type-accents.schema.json` is its shape. Each row is a `resource_type` term's ID, the slug that ID is expected to carry, and one of the five accents; no two rows share an ID, a slug or an accent (the package's `test/type-accents.test.js`). The IDs are the same on the hosted CMS, the local wp-env and the mock CMS's seed, and the front end's unit test checks every row against the seed. How the marks look, and the table in prose, are in [`DESIGN.md`](DESIGN.md) ("Colors").

- **The rule both sides apply.** A type term gets its row's accent when the table has a row for its ID and the term's slug is the row's; any other term, a renamed one included, gets `neutral`. Either way the value goes in `data-accent` on `.rh-card__type`, so `card-labels.css` paints the dot in the accent or, for `neutral` (which matches none of its rules), in the ink. Adding a type is a development change: its row ships in the same pull request and deploy as the term, so a new type is never coloured by accident.
- **The front end** imports the file (`apps/web/lib/type-accents.ts`, `typeAccent()`), at build time, through the workspace.
- **The plugin** cannot read the workspace on the host, which receives only the plugin's `build/`, `src/`, `vendor/` and main file. Its webpack build (`webpack.config.js`) emits the file unchanged as `build/type-accents.json`, and `ResourceHub\Blocks\TypeAccents` reads that copy for the related-resources block's rows. PHPUnit fails when the copy in `build/` differs from this file, so a stale build cannot pass the gate.
- **Additive.** The table adds an attribute to the block's rows; nothing reads it from the CMS's HTML, since the front end drops `data-accent` from a marker's fallback rows (see [Block marker](#block-marker)). A changed row reaches each side with that side's deploy, the CMS first, so for the length of one deploy the CMS's own pages can mark a new type while the front end still shows it neutral.

## Configuration

Names on each side, and the one rule both share. None of them is ever committed.

| Side | Variable | Holds |
|---|---|---|
| CMS | `RESOURCE_HUB_FRONTEND_URL` | The front end's origin, with no path; the plugin appends `/api/revalidate/`. A PHP constant, falling back to the option of the same name in lower case |
| CMS | `RESOURCE_HUB_REVALIDATE_SECRET` | The shared secret. Constant, falling back to the option |
| CMS | `RESOURCE_HUB_POSTHOG_KEY`, `RESOURCE_HUB_POSTHOG_HOST` | Optional; constants only. Unset, results logging is skipped |
| Front end | `WP_API_URL` | The CMS's `/wp-json` base, server-only |
| Front end | `REVALIDATE_SECRET` | The same secret as the CMS's |
| Front end | `SITE_URL`, `WP_MEDIA_ORIGIN` | The public origin, and an optional base for `/media/`; see `apps/web/README.md` |

**The secret's rule.** `REVALIDATE_SECRET` is 32 to 256 printable ASCII characters (0x21 to 0x7E) with no whitespace and no trailing newline, used exactly as defined, never trimmed. Both sides refuse anything else: the front end answers every request with a `500` that names the problem, and the CMS treats the secret as not configured and records why.

## Public URL shape

Both sides mirror this; it is not schema-validated. Every path has a trailing slash, every listing paginates as `…/page/[n]/`, `topic` and `page` are reserved and never type slugs, and `resources`, `api`, `media`, `_next` and `search` are reserved and never top-level page slugs. `/search/` is reserved for the front end's search page, which takes its query as `?q=…`: the one public URL with a query string, because a search is not a path.

| Path | Lists |
|---|---|
| `/` | The static front page, or the front end's welcome page when none is set |
| `/[page]/…/` | A published WordPress page at its parent chain |
| `/resources/` | Everything |
| `/resources/[type]/` | One type |
| `/resources/topic/[topic]/` | One topic |
| `/resources/[type]/topic/[topic]/` | One type within one topic |
| `/resources/[type]/[slug]/` | A single resource |
| `/search/?q=…&page=n` | The front end's search page: resources and pages matching the query, at most 10 pages of 12; never a redirect or a 404 |

The slug is the identity. On the front end, a wrong type segment, an old slug found through resolve, a wrong page parent or a non-canonical form redirects with a computed single-hop 308 that a browser is never allowed to keep; the CMS redirects no one, and its theme pages are a 404 for anonymous visitors, with `robots.txt` and `noindex, nofollow` on top ([ADR 0025](../../docs/adr/0025-permanent-redirects-are-computed-and-never-kept-by-browsers.md), [ADR 0031](../../docs/adr/0031-cms-theme-pages-are-for-logged-in-users.md)). `get_permalink()` stays absolute; the front end strips the CMS domain from every link in the HTML it renders.

## Stylesheets

The package also holds the stylesheets the CMS and the front end render with, the one typeface and the brand mark's canonical drawing, so the two sides look the same from one source. The `--rh-` tokens and the `rh-` class names are part of the contract: renaming one is a contract change, made on both sides in the same pull request. The visual system itself (what each token is for, the colour scheme, the type, motion, the components, how each consumer loads the CSS and the font, and how to change it) is written up once, in [`DESIGN.md`](DESIGN.md); the values are in `tokens.css` and nowhere else.

| File | Holds |
|---|---|
| `tokens.css` | Design tokens as custom properties on `:root`, all prefixed `--rh-` and named for their role, never for their value: colour as `light-dark()` pairs, the five mark accents, type, spacing, radius and measure. Every other stylesheet builds on these and defines no colour or size of its own. |
| `card.css` | The resource row: `.rh-card` and its parts (`__meta`, `__type`, `__body`, `__title`, `__link`, `__summary`, `__topics`, `__topic`) and `.rh-card-grid`, the list the rows sit in (the name is kept from the earlier card grid, so no consumer renames anything). It imports `card-labels.css` first, with a relative `@import`, so loading `card.css` loads the whole row; ship the two files side by side. The markup it expects is in the file's header comment: the meta line is a sibling before the body, and the row carries no image (`__media` is gone; nothing rendered it on the CMS side). A CMS page in a mixed list (the search results) is the same row with `.rh-card__kind`, the small label "Page", alone in its meta line, with no type mark, no date and no topics. `.rh-card__type` takes an optional `data-accent` attribute, one of `coral`, `cobalt`, `lemon`, `mint` or `grape`, which colours the type mark drawn before the name; any other value or none gives the neutral mark. Both sides set it from the package's type-accent table (see [Type accents](#type-accents)), and write `neutral` for a type the table does not know. |
| `card-labels.css` | The row's two labels, `.rh-card__type` with its type mark (the `data-accent` rules above) and `.rh-card__topics` with `.rh-card__topic`, and their forced-colours rule: for a component that shows the labels without the row, as the front end's resource page does in its meta line, so it loads none of the row's layout. The class names are the row's; the markup is in the file's header comment. |
| `brand.css` | The lockup: `.rh-brand`, the one link that holds the mark and the wordmark, and its parts `__mark` (the inline SVG, sized from the wordmark) and `__name`. | `base.css` | The document under every component: the box model, `color-scheme` pinned by `data-theme="light"` or `"dark"` on `<html>` (no attribute is System), the body, links, `:focus-visible`, headings, paragraphs, images and video, and the skip link, `.rh-skip`. Load it after `tokens.css` and before any component stylesheet. The landmarks' layout is each consumer's own (the front end's is `apps/web/components/shell.css`). |
| `theme-toggle.css` | The System / Light / Dark control: `.rh-theme`, a fieldset of three native radios drawn as one segmented control, with `--pending`, `__legend`, `__option`, `__input`, `__label`, `__icon` and `__suffix`. | `header-search.css` | The header's search control, the button half: `.rh-header-search` at the end of the header's row after the lockup, and in it `.rh-header-search__toggle`, a 2.75rem square (a link to `/search/` without JavaScript, a disclosure button with it, named "Search" by `aria-label`), with the icon `.rh-header-search__icon`, drawn by its SVG attributes. The front end's `HeaderSearch` renders the markup in the file's header comment; the CMS theme's header is to render the same (issue #89). The form inside the bar is the consumer's own: the front end's is its search page's form (`.rh-search`, `apps/web/components/search.css`, not contract), so a CMS header that renders that markup needs that stylesheet moved here first. |
| `listing.css` | The collection pages: `.rh-listing__header`, `__count`, `__section`, `__lead`, `__latest` and `__empty`; the filters, `.rh-filters` with `__group`, `__name`, `__list` and `__link` (`aria-current` on the current one); and the pagination, `.rh-pagination` with `__list`, `__link` (`aria-current="page"`), `__gap`, `__step` and `__step--next`. The block's `block.json` loads `card.css`, inlined into its build, where the block is used, after the `resource-hub-tokens` handle it shares with the CMS block theme, so a page with both loads `tokens.css` once; the theme copies `tokens.css`, `brand.css`, the font, its licence and `fonts/figtree-fallback.css` into its own build, and the plugin's PHPUnit suite holds the copies and the theme's `theme.json` presets to this package. The front end imports each component stylesheet from the workspace at build time, from the component that renders its markup, after `tokens.css` and `base.css`; the CMS theme's templates are to load them as they land (issue #89). What only the front end renders, such as its shell's layout, its welcome page and its error boundaries, stays in `apps/web/components/` and is not contract. Adding a component stylesheet means a new `exports` entry in `package.json`, a line in `files`, and a header comment with the markup it expects. Import by file name:

```js
import '@colbitron/resource-hub-ui/tokens.css';
import '@colbitron/resource-hub-ui/fonts/figtree-fallback.css';
import '@colbitron/resource-hub-ui/base.css';
import '@colbitron/resource-hub-ui/card.css';
```

The package's tests (`pnpm --filter @colbitron/resource-hub-ui test`, or `pnpm test:schemas` from the root) also check the stylesheets: `test/contrast.test.js` resolves every colour token in both schemes and asserts WCAG AA for every text pair and 3:1 for the focus ring, `test/design-doc.test.js` fails when a token in `tokens.css` has no sentence in `DESIGN.md`, or the other way round, and `test/figtree-fallback.test.js` fails when `fonts/figtree-fallback.css` differs from what the script derives from Figtree's file, or `--rh-font-sans` lists its faces in another order. `test/package-files.test.js` fails when a stylesheet at the package's top level is missing from `files` or `exports` in `package.json`, so a new one cannot ship unimportable.

## Fixtures and test

`fixtures/valid/` and `fixtures/invalid/` hold example payloads named `<schema>.<case>.json`, where `<schema>` is the schema file name without `.schema.json`. The test in `test/` compiles every schema with Ajv in strict mode and asserts that every valid fixture passes and every invalid fixture fails, and that every payload schema has at least one of each. From the repository root:

```sh
pnpm --filter @colbitron/resource-hub-ui test
```

CI runs it in the plugin's gate on every push to `main` and every pull request that changes `wp-content/` or a shared path; `packages/` is a shared path, so a change to this package always runs it (`docs/runbooks/deploy.md`, "Which jobs a pull request runs"). The plugin's PHPUnit runs the `revalidate-request` fixtures, and only those, through its own validator, so the two validators are known to agree on the request schema.

## Using the schemas

The package belongs to this repository's pnpm workspace and is never published ([ADR 0033](../../docs/adr/0033-one-repository-for-the-plugin-the-front-end-and-the-contract.md)). A workspace package that needs it adds it to its `package.json` and runs `pnpm install` from the repository root, which links `packages/ui/` in:

```json
"dependencies": {
	"@colbitron/resource-hub-ui": "workspace:*"
}
```

The package exports `./schemas/*`, so a consumer imports a schema by file name, and `./type-accents.json`, the table (see [Type accents](#type-accents)). The import below uses import attributes (`with { type: 'json' }`), which need Node 22 or newer:

```js
import request from '@colbitron/resource-hub-ui/schemas/revalidate-request.schema.json' with { type: 'json' };
```

Register every schema with the validator under its `$id`, not only the one being checked. Schemas reference `common.schema.json` by relative `$ref`, and a `$ref` resolves against the referring schema's `$id`. Each `$id` is the file's raw URL on `main`, but it is an identifier, not a location: validators look it up among the schemas they were given and do not fetch it.

`rest_url` uses `format: uri`. Formats are not part of a draft 2020-12 validator's core: Ajv needs a formats plugin, `ajv-formats` (the test here calls `addFormats( ajv )`), and without one a validator either ignores `format` or throws on the unknown format when it compiles the schema. The `^https?://` pattern on `rest_url` holds either way.
