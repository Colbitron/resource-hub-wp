# Resource Hub design system

The one written home of the visual system shared by the Next.js front end (`apps/web/`), the WordPress plugin's block and the CMS block theme. Three things are true at once and each lives in one place: the **intent and the rules** are here; the **values** are in [`tokens.css`](tokens.css) beside this file (this document names tokens, and gives a value in prose only where it explains a rule, such as the 4 px spacing step or the 360 px phone width; where the two differ, `tokens.css` is right and this document is fixed); and the **rendered truth** is the front end's specimen page, `apps/web/app/fixtures/specimen/`, which shows every token and every component with fixture content and is captured by the screenshot gate. When the three disagree, fix the one that is wrong and rerun the gates in [Changing the system](#changing-the-system).

The section order follows Google Labs' DESIGN.md convention (Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts), with five sections of our own where that convention has nothing to say: the brand, the colour scheme, motion, how each consumer loads the system, and how to change it. A test, `test/design-doc.test.js`, fails when `tokens.css` declares a `--rh-*` token this document does not mention, when this document names one that does not exist, or when the sections drift from that order.

## Overview

Resource Hub is a filterable library of resources, published by Colbination and rendered by a headless WordPress and Next.js pair; it is a demonstration of that pattern, written fresh. It takes its look from the publisher's own site: warm paper rather than white, ink rather than black, one friendly geometric sans for everything, and five small accents of colour used sparingly, as marks and never as the voice. The two sites should read as siblings.

The tone is editorial and quiet. Text carries the page: hierarchy comes from weight, size and a few hairlines rather than from boxes, shadows or colour fields. Density is reading-first: a prose measure of about sixty-five characters, generous line height, one gutter on a phone and no horizontal scroll at 360 px. Everything is server-rendered HTML with plain CSS; the design never depends on client-side JavaScript except for the theme control described below, which degrades to the system preference without it, and the header's search bar, which degrades to a link to the search page.

The library's own name stays "Resource Hub". Colbination is its publisher: its mark sits beside the wordmark in the header, and its name is in the footer and the share image, never as a second name in the header (see [Brand](#brand)).

## Brand

Colbination publishes the site, and the site keeps its own name. The brand layer is therefore small: one mark, one wordmark, and the files a browser and a share card read.

**The mark** is Colbination's own, and not covered by the repository's GPL license (the root `README.md`, "License"): a coral rounded square with a "C" cut from it, tilted six degrees over its deep ink shadow square. It has two fixed colours of its own, coral `#ff5a4f` and the shadow's ink `#1b1436`, that are not tokens and do not change with the scheme: it is a logo, the same on paper and on ink, and the one place in the system where a colour is written outside `tokens.css`. Its one canonical drawing is `packages/ui/brand/mark.svg`. It is copied as `apps/web/app/icon.svg`, the file the browser is given as the site's icon, inline in `apps/web/components/Brand.tsx` for the header, where an inline SVG costs no request, and inline in the CMS theme's header part (`wp-content/themes/resource-hub/parts/header.html`); `apps/web/test/brand-mark.test.tsx` fails if either front-end copy differs from the canonical drawing, and the plugin's `tests/phpunit/Theme/BrandMarkTest.php` if the theme's does. The mark is decorative wherever it appears (`aria-hidden`, `focusable="false"`): the name beside it is the name, and the mark alone is never a link.

**The lockup** is the mark beside the wordmark "Resource Hub", set as a heading at `--rh-text-lg` (`--rh-weight-heading`, `--rh-tracking-heading`, `--rh-leading-tight`), the mark 1.25 em of that size and the gap between them `--rh-space-2`, so the whole lockup is one line, 1.25 em tall, and scales with the reader's text size. It is the header's one home link, to the library, with the accessible name "Resource Hub", and the header's first thing; the only other is the search control at the end of the row (see [Components](#components)), a square button drawn into the row's padding, so the header is one row, the lockup's height, at every width from 320 px up; the theme control is at the end of the footer (see [Theme and colour scheme](#theme-and-colour-scheme)). The wordmark underlines on hover, as every link does; nothing in the lockup moves.

**Clear space and minimum size.** Keep about half the mark's width (0.625 em of the wordmark, about 14 px in the header) between the lockup and any other mark, text or image, so nothing reads as part of it; the specimen draws that ideal as a dashed box. The header keeps it without an exception: the lockup's one neighbour there is the search control, at the far end of the row with the row's free space between them (about 70 px at 320 px wide, more above), and the header's padding (`--rh-space-3`, 12 px) separates it only from the header's own hairline, a frame and not another mark. That padding keeps the header to the lockup's height plus 24 px, one row at every width, so the first image sits as high as it can; the search control's 44 px square reaches into it rather than growing it (`apps/web/e2e/brand.spec.ts` fails if a second row appears, if anything but the lockup and the search control is in the row, or if the row is taller than the lockup's height plus its padding). The mark alone is never drawn under 16 px, the size at which the favicon still reads as a C; in the lockup it is never under 24 px, so the wordmark beside it stays on the type scale. The share image sets it at 200 px beside a 96 px wordmark.

**Don't** recolour the mark or draw it in a token's colour, set it straight or tilt it further, flip it, stretch it, add a shadow or a halo, place it on a photograph or on coral, use it as a bullet or a type mark, put another logo beside it, or use it alone as a link without the name.

**Icons and the share image.** The files are in `apps/web/app/` and served at Next.js's metadata convention routes, but their icon links are listed explicitly, in `apps/web/lib/site-icons.ts`:

- `icon.svg`: the mark, served as the site's icon for every browser that reads an SVG one (`sizes="any"`), so the tab shows the same drawing at any size. It is linked last, after the two 32 px files; the root layout lists the links in that order (`apps/web/lib/site-icons.ts`), because the conventions alone take the order the filesystem lists the files in.
- `icon.png` and `favicon.ico`: the mark alone at 32 × 32 on a transparent background, for a browser or crawler that reads no SVG icon and for the `/favicon.ico` some ask for without being told; the ICO holds that same PNG as its one image. Both are linked with `sizes="32x32"`, so a browser that reads SVG prefers the SVG.
- `apple-icon.png`: 180 × 180, the mark on the light paper surface with no transparency, since iOS fills transparent pixels with black; iOS rounds the corners itself.
- `opengraph-image.png` with `opengraph-image.alt.txt`: 1200 × 630, the lockup at share-card size and "Published by Colbination" under it, on the paper surface, for the light contexts share cards are shown in. It is every page's share image except a resource with a trusted featured image, whose own metadata keeps that image (`components/ResourceArticle.tsx`), so every page gets X's large card: `apps/web/lib/share-metadata.ts` writes the card type on the routes that write their own `openGraph`, Next.js derives it on the rest, and Next.js copies the image and the other fields from the Open Graph ones. Its URL always carries the file's content hash, so a re-rendered image gets a new URL and no scraper or CDN keeps the old one: a route that writes no `openGraph` gets the file convention's `/opengraph-image.png?…`, and one that writes its own names the PNG's static import, `/_next/static/media/opengraph-image.<hash>.png` (`apps/web/lib/share-image.ts`); each route carries exactly one.

The PNGs and the ICO are drawn by `apps/web/scripts/render-brand-images.mts` (`pnpm --filter resource-hub-web brand:images`) from `icon.svg`, the site's own Figtree file and the light side of the colour tokens, in Chromium inside the same digest-pinned Playwright image the screenshot gate uses, so a laptop and CI draw the same pixels, and committed. Run it after a change to the mark, the tokens or the words, look at the images and commit them. Forgetting to fails the gate: `--check` renders them again in memory and compares the decoded pixels with the committed files, allowing a handful of anti-aliased pixels per image (50 in the share image, 10 in the apple icon, 4 in each 32 px icon; a one-step change to a colour token moves thousands), and the screenshot run (`pnpm web:test:screenshots`, and CI's screenshot step) runs that check in its own container before the screenshots. They are not generated at request time with `next/og`, because Satori reads no woff2: a generated image would need a second copy of Figtree, in TTF or OTF beside a second copy of its licence, a rendering bundle of about half a megabyte in the deployment and a route of its own under the trailing-slash rule, for an image whose words never change. The trade-off is that the script is run by hand, and that a share image per resource is not possible this way; the day one is wanted, the TTF and `next/og` are the path.

## Colors

Every colour is a role, named for what it does and never for its value, and every role is a `light-dark()` pair so one declaration serves both schemes.

| Token | Role |
|---|---|
| `--rh-color-text` | Ink: body text, headings, the strong rules under the listing's section headings and over its pagination, the current filter's and the current page's underline, and the neutral mark |
| `--rh-color-text-muted` | Secondary text: meta lines, dates, summaries, topic labels, captions, the footer, hover borders |
| `--rh-color-surface` | The page: the body background, and the one surface every page is drawn on |
| `--rh-color-surface-raised` | An inset surface a step away from the page: code, the box the resource page's featured image loads into, the article's quote and its table's header row, the checked theme segment |
| `--rh-color-border` | Decorative hairlines, as translucent ink so one value sits on either surface: dividers, the rules between rows and around the filters, the edge of the article's insets, a table's rules |
| `--rh-color-border-strong` | The boundary of a control whose edge is the only thing that shows it is one (the theme control), the short rule between a row's topic labels, and the rule under a table's header row; opaque, in the ink family |
| `--rh-color-accent` | Links, and the skip link's background: cobalt, the brand's link colour |
| `--rh-color-accent-text` | Text on `--rh-color-accent` |
| `--rh-color-focus` | The focus ring: cobalt in light, lemon in dark |

**Links are cobalt**, in both schemes, underlined, never colour alone.

**The five brand accents** are tokens of their own, `--rh-mark-coral`, `--rh-mark-cobalt`, `--rh-mark-lemon`, `--rh-mark-mint` and `--rh-mark-grape`, and they are for **small marks only**: a dot beside a printed name, a brand mark, a hairline of colour (the coral bar down the left edge of a quote in an article is the one such hairline today). They are never text, never a text background and never the only thing that distinguishes two states, because in the light scheme lemon, coral and mint sit under the 3:1 non-text line against the surface, and grape under it against the raised surface (2.77:1). Cobalt, lemon and mint are lifted a step in the dark scheme so they read on ink; coral and grape have one brand value, written as a `light-dark()` pair of that value twice so that every colour token has the same shape.

**Each resource type has an accent.** The mark goes beside the type's printed name, so the name says what the colour only hints at, and a mark is never part of a link, because the cobalt dot would read as part of it: where the printed name is itself a link, on the resource page, the dot is drawn by the element around the link and sits outside the link's text and underline (see [Components](#components), "The article"). The table is the package's `type-accents.json`, keyed by the `resource_type` term's ID, which is the same on the hosted CMS, the local wp-env and the mock CMS's seed; a unit test on the front end checks every row against the seed, and both sides read the one file ([README](README.md), "Type accents").

| Term ID | Slug | Accent |
|---|---|---|
| 3 | `article` | mint |
| 4 | `ebook` | grape |
| 5 | `webinar` | coral |
| 6 | `podcast` | lemon |
| 7 | `case-study` | cobalt |

A type the table does not know, or whose ID now carries a different slug, gets a **neutral mark** in the ink (`--rh-color-text`). Adding a type is therefore a development change, not an editorial one: the term is created in the CMS and its accent row ships in the same change and the same deploy, so a new type is never coloured by accident. The front end's `toCard` (`lib/wp/cards.ts`) puts the accent on every row, on the lead and on the resource page's header as `data-accent` on `.rh-card__type`, the plugin's related-resources block puts it on its rows the same way, and `card-labels.css`, which `card.css` imports, paints the dot from it (see [Components](#components)).

**Borders are decorative or they mark a control.** The hairline, `--rh-color-border`, is decoration: it separates things that are already told apart by their text and space, so it may sit far under 3:1, and it is never the only edge of something a reader can activate. Wherever a control's edge is what shows it is a control (the theme control), that edge is `--rh-color-border-strong`, which reaches 3:1 against both surfaces (WCAG 1.4.11). The filters, the pagination and the resource page's topics have no edge at all: they are text links, told apart by their place in a labelled `nav` or list and by their underline, and the current filter by an underline in the ink. The rows between rules keep the hairline because each row's title is a link.

**Contrast is a test, not a table.** WCAG 2.2 AA: 4.5:1 for every pair of text on a background, and 3:1 for the focus ring and a control's boundary against both surfaces, in both schemes. `test/contrast.test.js` parses `tokens.css`, resolves each scheme and asserts every pair (text and muted text on the page and on the raised surface, links on both, text on the accent, the inverted current state, the focus ring and the strong border), so the ratios are never written down to go stale. Every colour token is in an asserted pair or in the test's commented list of decorative exemptions, which is the hairline and the marks; their ratios are printed, not asserted, with a translucent colour composited over the surface first. The test also refuses a token declared outside the one `:root` block, so a scoped override cannot carry a value it never measured. One open point for the owner: in the light scheme lemon is the weakest mark by far, with coral and mint under 3:1 too, and grape under it on the raised surface (2.77:1). Clearing 3:1 would mean darkening those three light values away from the brand's; the dark scheme is fine as it is.

## Theme and colour scheme

The reader's system preference is the default. `tokens.css` sets `color-scheme: light dark` on `:root` and writes every colour with `light-dark()`, so the browser picks the side; there is no `prefers-color-scheme` media query and no second copy of the values.

**The System / Light / Dark control** lets a reader override that. The default is System. The choice is stored in the browser only, in `localStorage` under `rh-theme` as `light` or `dark` (System removes the key), never in a cookie and never read on a server, so every page stays static and ISR-cached. It is applied as `data-theme` on `<html>`, which `base.css` maps to `color-scheme: light` or `dark`; every `light-dark()` token follows at once, with no transition, and removing the attribute hands the choice back to the system preference. A media query could not have been overridden this way, which is why the tokens use `light-dark()` and the contrast test refuses a media query.

**Where it sits.** At the end of the front end's footer, after its text, on every page. That keeps it always available in one consistent place, the same on every page and at every width; out of the reading path, so a reader who never wants it never passes it, and it is the last Tab stop on the page rather than the first after the site's name; and it keeps the header to one row at every width, holding the lockup and the one small search button, where the theme control beside the lockup had to wrap under it on a phone. Where the footer's text and the control fit side by side, the control sits at the right; where they do not, it takes a row of its own under the text, at the left, still with its words.

**First paint.** A one-line inline script in the root layout's `<head>` (`apps/web/lib/theme.ts`, `THEME_INIT_SCRIPT`, built from the same constants the component uses) reads the key inside `try/catch` and sets the attribute as the browser parses, before anything is painted and before any bundle loads, so a stored choice never flashes the other scheme. `suppressHydrationWarning` sits on `<html>` and nowhere else, because that is the one element whose attributes the script changes; `apps/web/test/hydration-warning.test.ts` holds that in the source, since a production build never reports an attribute mismatch, and `pnpm web:test:dev` (`apps/web/e2e/theme.dev.ts`, local only, not in CI) loads the page under `next dev` with Dark stored and fails on any hydration warning. The server renders no option checked and the group invisible (`visibility: hidden`, so it keeps its space and the footer does not move when it appears); the client component (`apps/web/components/ThemeToggle.tsx`, with its store in `lib/theme-store.ts`) reads storage through `useSyncExternalStore` with a `null` server snapshot, so the hydration render agrees with the markup, and React then re-renders with the stored choice, checks the right option and shows the group. Without JavaScript the group never shows, which is right because the choice could not be applied, and the page follows the system preference; a `<noscript>` style in the root layout's `<head>` (`THEME_NOSCRIPT_STYLE`) removes the control's slot from the footer, so no empty space is kept for it. A layout effect re-applies the attribute after hydration, as a guard: the Next.js guide warns that development's Strict Mode remount can reset `<html>`; that was not reproduced on Next.js 16.4.5 with React 19.3, so the effect sets the same value again and is kept in case a later version does. The `storage` event on `localStorage` keeps other open tabs in step, and a page restored from the back/forward cache re-reads the stored value, since it missed any such event while frozen, and drops a choice storage refused, since it cannot tell whether another tab wrote meanwhile. When storage refuses a write (blocked or full), the choice still applies to the page and the control shows it; after a reload both fall back to what storage holds. `<meta name="theme-color">` is not set: a per-scheme pair would copy two values out of `tokens.css`, and it would not follow the override without script; add it when it earns that.

**The control** (`apps/web/components/ThemeFieldset.tsx` and this package's `theme-toggle.css`, classes `rh-theme…`, shared so the CMS theme's planned control draws the same) is a native `<fieldset>` with a visually hidden `<legend>`, "Theme", and three native radios with labels, in the order System, Light, Dark, each with a hand-drawn inline icon and a visible word. Native radios because the platform gives the group, the single selection, the arrow keys and the announcements, and a radio announces its own new state, so there is no live region. Each option's accessible name is "System theme", "Light theme" or "Dark theme": the visible word plus a hidden suffix inside the label, so the name stands alone where the legend is dropped (iOS VoiceOver inside a landmark, TalkBack with any group) and begins with the visible text for voice control. The words are never hidden: at narrow widths and at 400% zoom the group wraps onto its own row. The input is laid over its whole segment at `opacity: 0`, never `display: none` or a 1px clip, so touch exploration and a click find it where it is drawn. The checked segment has a raised fill and a bar of `--rh-border-width-strong` under it in the ink, so the state is a shape and not a colour; under `forced-colors: active` it takes `SelectedItem` and `SelectedItemText`, and the bar, which only the checked segment has there, is drawn in `CanvasText`, because `SelectedItemText` can match the page's `Canvas` (both are white in Chromium on Linux) and `CanvasText` on `Canvas` is the pair every forced palette keeps apart; the focus ring, a real outline because shadows vanish there, uses `Highlight`. Each segment is at least 2rem tall and sized in rem, over the 24px target minimum. The group's padding and the gap between segments are `--rh-space-2`, more than the focus ring reaches outside a segment (`--rh-focus-width` plus its 2 px offset), so the ring never overlaps the group's border or the next segment. Arrowing between the options changes the theme at each press, which is native radio behaviour and a change of content, not of context, because the switch is instant. Tab reaches the group once, on the checked option, after everything else on the page. There is no hint of what System resolves to; one could be added as separate text near the group, never by renaming the option.

**Content Security Policy.** The front end has none today. One added later must allow the head script: by its SHA-256 hash, since the script is a fixed string, which should hold on static and ISR pages where a nonce would force dynamic rendering. To be verified when a CSP is written, together with whether the App Router's own inline scripts can be hashed, which decides whether `'unsafe-inline'` is needed regardless.

**Manual check with VoiceOver and Safari on macOS.** The automated gate (`apps/web/e2e/theme.spec.ts`: axe in each state, one Tab stop and wrapping arrows, the same names at 320 and 1280 px, first paint by the script alone with every bundle blocked, hydration with no console error, JavaScript off, forced colours, no transitions, targets at 320×256, two tabs) cannot hear what a screen reader says. Once per change to the control, with VoiceOver on (Command-F5) in Safari, on any page of the site:

1. Move with VoiceOver's own navigation, VO-Right Arrow (Control-Option-Right Arrow), which is how a VoiceOver user goes through a page and the primary path to check, through the footer to the control, the last thing on the page (VO-U's landmarks menu reaches the footer, "content information", in one step). Listen for the option's name with "theme" in it, its selected state, its position and the group's name, in the order "System theme, selected, radio button, 1 of 3, Theme, group" or close to it; the words vary by version. Note whether Safari stops on the legend or on a label apart from its radio, a known Safari behaviour and not a defect of the markup.
2. Press Right Arrow. Listen for "Light theme, selected, radio button, 2 of 3", and see the page turn light at once. Right Arrow again: "Dark theme", "3 of 3", the page dark. Right Arrow again: System, the page following the system preference.
3. Then the keyboard path without VoiceOver's keys. It assumes Safari's "Press Tab to highlight each item on a webpage" is on (Safari > Settings > Advanced); with it off, Safari's Tab skips links and buttons, so press Option-Tab wherever this step says Tab. Press Tab past the page's links and the footer's: the last stop is the checked option, announced as in step 1. Tab again: focus leaves the group in one step. Shift-Tab returns to the checked option.
4. Reload. The chosen option is still selected and announced as such.

Not tested: NVDA, JAWS, VoiceOver on iOS and TalkBack. The names were built to stand alone for the last two, which may drop the legend.

The CMS block theme loads `tokens.css` on its own pages and in the editor canvas, so they follow the system preference by the same mechanism and an editor's preview looks like the front end in either scheme. The theme has no control yet; one that sets `color-scheme` on the CMS's `<html>` the same way is planned (issue #89).

## Typography

**Figtree, and only Figtree**, for body text and headings alike: one variable file on the weight axis, latin subset, in [`fonts/`](fonts/) with its SIL Open Font License beside it (`fonts/LICENSE-Figtree.txt`). The file is the official Google Fonts release, taken byte for byte from `@fontsource-variable/figtree`; nothing is ever requested from Google by a visitor's browser. There is no italic file: the few italics in a body are synthesised by the browser, and the italic face can be added beside this one if that ever shows. The faces behind it exist only for the moment before the file lands and for a consumer that has not loaded it: first size-adjusted copies of common system fonts, so that moment looks as close to Figtree as each platform can draw it, then the plain system sans.

| Token | Role |
|---|---|
| `--rh-font-sans` | The one family stack: Figtree first, through `--rh-font-figtree` (see [Consumers and loading](#consumers-and-loading)), then the size-adjusted fallback faces in `fonts/figtree-fallback.css` (see [Fallback faces](#fallback-faces)), then the system sans, which is all a consumer that loads neither gets (the plugin's block in a theme other than the CMS's) |
| `--rh-weight-heading` | Headings and the site name: heavier than body text |
| `--rh-tracking-heading` | Headings: slightly tighter than body text |
| `--rh-tracking-label` | A small upper-case label, slightly looser so the capitals breathe: a type's name beside its mark, a filter group's name |
| `--rh-text-sm`, `--rh-text-base`, `--rh-text-md`, `--rh-text-lg`, `--rh-text-xl`, `--rh-text-2xl` | The size scale: meta lines, labels and filters, body, the lead's summary and the listing's section headings, a row's title, the lead's title, `h1` |
| `--rh-leading-tight`, `--rh-leading-body` | Line height for headings and for everything else |

Body text is the regular weight; labels and strong text are semibold; headings, a row's title, the lead's title and the site name take the heading weight and tracking. The one upper-case setting is the small label (a type's name, a filter group's name), semibold at `--rh-text-sm` with `--rh-tracking-label`; it is a `text-transform`, so the DOM keeps the editor's casing and a screen reader reads a word, not initials. Headings carry their hierarchy in size and weight alone, with no colour. The page title is the page's only `h1`; a body's headings start at `h2`.

## Layout

Spacing is one scale on a 4 px step, `--rh-space-1`, `--rh-space-2`, `--rh-space-3`, `--rh-space-4`, `--rh-space-5`, `--rh-space-6`, `--rh-space-7` and `--rh-space-8`, and every margin, padding and gap in a component is one of those steps: the small ones inside a component (the gap between a row's lines, the gap between a mark and its name), `--rh-space-4` for the gutter, `--rh-space-5` for a row's padding, the large ones between sections and around `main`. There are no fixed breakpoints: things wrap. A row (`.rh-card`) and the lead (`.rh-lead`) are each two columns where both fit on one line and one column where they do not, by flex-wrap with a basis per column (the row's meta line asks for 9rem and its body for 24rem; the lead's image for 22rem and its body for 18rem), so the change happens where the content needs it and not at a width written down; the listing's lists of filters, topics and pages wrap the same way, and the two measures do the rest. `--rh-measure` is the prose line length, used by every paragraph, every summary and by the single-resource and page columns; `--rh-measure-wide` is the content width of the shell, centred, with one gutter of `--rh-space-4` on both sides at every width. The page must never scroll sideways at 320 px, and it must reflow rather than scroll at 400% zoom, which is the same width; the listing's spec, the specimen's own check and the axe scan hold that.

## Elevation & Depth

The system is flat: one page surface, `--rh-color-surface`, on which everything is drawn, with no boxes, fills or shadows around content. Depth, where it is needed, is shown by an inset and a rule: a code block, the box the featured image loads into, and in an article the quote and the table are `--rh-color-surface-raised` or edged with the hairline, and edges are `--rh-color-border` at `--rh-border-width`, or `--rh-color-border-strong` where the edge marks a control (see [Colors](#colors)). An inset is never a card: it marks a kind of content inside the reading column (a quotation, a table, code), not a thing to activate, and nothing in a list is boxed. Hierarchy on a listing comes from two weights of rule: hairlines between rows and around the filters, and a strong rule (`--rh-border-width-strong` in the ink) under the two section headings and over the pagination. A hover underlines; the current filter and the current page are underlined with the strong line and set a weight heavier, never inverted or filled. There are no shadow tokens today. If a later direction wants a resting shadow or a lift on hover, it is added as a token here and in `tokens.css` first, and stays subtle enough to vanish in the dark scheme.

## Shapes

Corners are nearly square: `--rh-radius-sm` for inline code and the theme control's segments, `--rh-radius` for images, the article's insets (the quote, the table's region, code blocks), the skip link, the theme control itself and the focus ring drawn around a row or the lead. Lines are `--rh-border-width`; a bar that marks a state (the checked theme segment, the current filter's and the current page's underline) and the strong rules on a listing are `--rh-border-width-strong`, heavier than a hairline and lighter than the focus ring. The focus ring is an outline of `--rh-focus-width` in `--rh-color-focus`, offset by two pixels so it never touches the thing it marks; on a row or the lead it is drawn around the whole thing through the stretched link's overlay. No pills anywhere: a filter, a page number and a topic are text. No fully round shapes, except a mark's dot.

## Motion

There is one motion today: the header's search bar comes in when a reader opens it, fading in and dropping a step (`--rh-space-2`) over 150 ms, through `@starting-style` (`header-search-bar.css`); closing is instant, and a browser without `@starting-style` shows the bar at once. A browser without `:has()` (Firefox before 121, Safari before 15.4) cannot anchor the bar to the header, so there the bar is not laid over the page at all: it takes a line of its own in the header's flow under the row and pushes the page down while open (the `@supports not selector(:has(*))` block in `header-search-bar.css`), visible and usable rather than placed off the screen. This is the rule it follows, and any that comes after it. Motion is CSS transitions only, on `transform`, `opacity` and colour, and nothing moves that does not respond to the reader. About 200 ms is the guide, not a rule: a hover or a focus settles in that order, and nothing runs longer than a glance. Under `prefers-reduced-motion: reduce` every transition and animation is off, with no exception for "small" ones: `apps/web/test/reduced-motion.test.ts` fails any rule in a shipped stylesheet that sets a `transition*` or `animation*` property unless a rule for the same selector in the same file sets the shorthand to `none` inside `@media (prefers-reduced-motion: reduce)`. A theme switch is instant, never cross-faded. No JavaScript animation, no scroll-driven effects, no autoplay.

## Components

The shared stylesheets are the contract: `tokens.css`, and one file per shared component, each building only on the tokens and defining no colour or size of its own. `card.css` holds the row, `.rh-card` and its parts (`__meta`, `__type`, `__body`, `__title`, `__link`, `__summary`, `__topics`, `__topic`), and `.rh-card-grid`, the list the rows sit in, with the markup it expects in its header comment. The row's two labels, `__type` with its mark and `__topics` with `__topic`, are in `card-labels.css`, which `card.css` imports first: loading `card.css` loads the whole row, and a component that shows the labels without the row, as the resource page's meta line does, loads `card-labels.css` alone and none of the row's layout. The related-resources section (slice 4, issue #50) renders the same rows, so no second list style is planned. `brand.css` holds the lockup, `.rh-brand` and its parts (`__mark`, `__name`), with its markup in its header comment: the front end's header (`components/Brand.tsx`) and the CMS theme's header part render the same link, so the lockup is shared rather than the front end's own. The header's search control is shared for the same reason, in two files: `header-search.css`, the button (`rh-header-search`, `__toggle`, `__icon`), and `header-search-bar.css`, the bar it opens (`__panel`) and the button's open state, which a consumer may load later than the button, as the front end does.

Under every component is `base.css`, the document: the box model, the colour scheme the theme choice pins through `data-theme`, the body, links, the focus ring, headings, paragraphs, media and the skip link, `.rh-skip`; it loads after the tokens and before any component. The rest of the page's components are shared too, because the owner chose full parity between the site and the CMS's logged-in previews, featured lead included (issue #89), and each file's header comment has the markup it expects: `theme-toggle.css` the theme control (`rh-theme`); `listing.css` the collection pages' header, filters, section headings, empty state and pagination (`rh-listing`, `rh-filters`, `rh-pagination`); `lead.css` the featured lead (`rh-lead`); `resource.css` the article (`rh-resource`); `prose.css` an editor's body (`rh-prose`); `page.css` a CMS page (`rh-page`); `related.css` the related list (`rh-related`); and `not-found.css` the 404 page (`rh-not-found`). The front end consumes them from the workspace at build time, and the CMS theme's templates load the ones they render (the page, the welcome, the 404 and the body so far), the rest as their templates land. `shell.css` holds the landmarks' layout under every page (`rh-shell`, `rh-shell__inner`, `rh-header`, `rh-main`, `rh-footer`), and `welcome.css` the welcome page `/` shows when the CMS has no static front page (`rh-welcome`), both of which the front end and the CMS theme's templates render. Only what the front end alone renders is its own, not contract, in `apps/web/components/*.css`: the routes' error boundaries (`unavailable.css`, `rh-unavailable`) and the search page's form and count line (`search.css`, `rh-search`), since the CMS theme's search template renders core's search block, whose markup is WordPress's own. A class the CMS comes to render moves into this package first.

**The collection pages** (the library, a type, a topic, a type within a topic, and their later pages, all `components/ListingPage.tsx`) are one typographic list on the flat surface, in the editorial direction the owner chose on 2026-11-06: the title and the count on one line, the filters between hairlines, then the lead and the "Latest" list on the library's first page, or the list alone, and the pagination on a strong rule. The reference was a static specimen of that direction; it was built on the real components and these tokens, not copied.

**The row** (`.rh-card`, `components/ResourceCard.tsx`) is one resource in a list: a meta line in a narrow left column (the type mark, the type's name as a small upper-case label, and the date), and beside it the title at `--rh-text-lg`, the summary in the muted ink at the prose measure, and the topics as small labels separated by short rules. Rows are separated by hairlines and carry no image, no box and no fill. The meta line is a sibling before the body, so the two columns need no wrapper, and the row wraps to one column where the two do not fit (see [Layout](#layout)). The row is one link through the stretched-link pattern: the title's link is its only interactive element and its `::after` covers the row. The trade-off is that the summary and the topics cannot be selected with the mouse, accepted because the row leads to the page that holds the same text; the alternative, if selection is ever wanted, is to lift the summary above the overlay at the cost of a click on it no longer navigating. The title is a heading at the level the page gives it: `h2` under the page's `h1`, `h3` under a section heading. On the CMS, the `resource-hub/resource-card` block writes the same row for each post of a Query Loop's post template, at the level its `level` attribute gives, so a logged-in preview of a collection lists the site's rows; the contract's markup fixtures hold the two to the same HTML (`README.md`, "Markup fixtures").

**A page in a mixed list** (the search results, `components/PageCard.tsx`) is the row with a page's own meta line: in place of the type and the date, the small upper-case label "Page", `.rh-card__kind` in `card.css`, which is the type's label without its mark, because the mark stands for a resource type and a page has none; no date, since a page's publish date says little about it; and no topics. The title and the excerpt are the row's title and summary, and the row is one stretched link as every row is. A resource in the same list is the ordinary row, so the two kinds are told apart by the printed label, never by colour alone.

**The search page** (`/search/`, `components/SearchPage.tsx`) is the listing's shape around a form: the `h1` in `rh-listing__header`, then the form, then a muted count line or one of the listing's empty-state sentences, the rows and the pagination. The form (`components/SearchForm.tsx`, `search.css`) is a visible label over a field and a button that wrap onto two lines where they do not fit. The field's edge is `--rh-color-border-strong`, because its edge is what shows it is a field (see [Colors](#colors)), at `--rh-radius-sm`; the button is the error boundaries' filled button in inverted ink (`unavailable.css`), so the site has one kind of button; both are at least 2.5rem tall.

**The header's search control** (`components/HeaderSearch.tsx`, `header-search.css` and `header-search-bar.css`) is a square button at the end of the header's row, 2.75rem a side (the 44 px target), with a magnifier drawn like the theme control's icons and the accessible name "Search"; its edge is `--rh-color-border-strong`, because a bare icon needs its edge to read as a control, at `--rh-radius-sm`, and the edge darkens to the ink on hover. It is drawn into the row's padding, so the header keeps its height. Without JavaScript it is a link to `/search/`; with it, a disclosure button that opens the search bar and moves focus to its field. Open, the button takes the raised fill and the ink edge and its icon becomes a cross, so the state is a shape as well as a fill. The bar is a band the width of the page under the header's hairline, laid over the page rather than pushing it down, so opening it moves nothing: the page's surface with a hairline under it, like the header, never a box or a shadow, holding the search page's own form at the shell's gutter. Escape, Tab out of it and a press outside close it. On the search page the control stays a link, to the page's own field, rather than open a second form. The word "Search" is not shown beside the icon: the header must stay one row at 320 px and at large text sizes, which the lockup and a worded button do not both fit; the name is the word, for screen readers and voice control.

**The type mark** is a dot of the type's accent, `--rh-space-2` across, before the printed type name, as the `::before` of `.rh-card__type` painted from its `data-accent` attribute (`coral`, `cobalt`, `lemon`, `mint`, `grape`; anything else, or no attribute, is the neutral ink). It is always beside the name and never part of a link, and under forced colours every dot takes the system text colour. The row, the lead and the resource page's header all carry it through that one class, so there is one mark and not three.

**The lead** (`.rh-lead`, `components/FeaturedLead.tsx` and `lead.css`) is the newest featured resource, large, at the top of the library: its image in a 16:9 box beside the meta line, the title at `--rh-text-xl`, the summary at `--rh-text-md` and the topics, the meta line and the topics being the row's own parts. Rules, decided here and held by `e2e/listings.spec.ts`: the lead appears on the first page of the unfiltered library only, when a resource carries the `featured` flag, and nowhere else; a filtered listing answers the filter with its list, and a later page is not the front. There is never an empty slot: with nothing featured the list stands alone, and a featured resource with no trusted image renders its text at the full width with no box. The lead is left out of the rows under it when it falls on the same page, so a resource is linked once per page, while the count and the pagination stay the CMS's; a lead whose own place is on a later page appears there as a row. With a lead the list sits under a "Latest" heading and its rows take `h3`; without one the rows sit under the `h1` as `h2`s. The lead's image is the page's only image and its LCP candidate, so it is loaded eagerly at high priority and preloaded from the head, with its dimensions on the `<img>` and a reserved box, so nothing moves when it lands.

**The filters** (`rh-filters`, `components/FilterNav.tsx`) are two rows of text links between hairlines, each row a list named by a small upper-case label ("Type", "Topic"), inside one `nav` named "Filter resources". A link is a 2rem-tall flex box, over the 24 px target of WCAG 2.5.8 whatever the text; it underlines on hover with the hairline weight, and the current one carries `aria-current` and is underlined with the strong line and set semibold, so the state is a shape as well as a weight. No chip, border or fill.

**The pagination** (`rh-pagination`, `components/Pagination.tsx`) is Previous, the page numbers and Next as text links on a strong rule, inside a `nav` named "Pagination", each at least 2.5rem square; the current number carries `aria-current="page"`, the heading weight and the strong underline. Previous and Next are left out at the ends, never disabled.

**The article** (`rh-resource`, `components/ResourceArticle.tsx` and `resource.css`) is the single resource page, in the direction the owner chose on 2026-11-06: the collection pages' flat surface, and on it the article of the "paper" specimen, built on the real components and these tokens rather than copied. It is one reading column of `--rh-measure`, centred in the shell's width, so the image is never wider than the text under it and a page that is all text does not hang off the left edge of a wide screen. In order: the title, the page's only `h1`; the meta line, the type's name as a small upper-case label with the type mark before it, the date, and the topics as the row's small labels separated by short rules, each a link to its listing (`.rh-card__type` and `.rh-card__topics` from `card-labels.css`, so the page says the type and the topics as the row does; on the CMS, the `resource-hub/resource-meta` block writes the same line for the single-resource template); the featured image at the column's width with `--rh-radius` corners, loading into the raised surface, with its dimensions on the `<img>` so nothing moves when it lands, eager, preloaded and at high fetch priority, since it is the page's largest contentful paint; the summary as the lead paragraph, at `--rh-text-md` in the muted ink; the body; and the source line, "Source:" and a link shown by its host, in small muted text under a hairline. The welcome page, the CMS's pages (`rh-page`, `page.css`), the 404 page (`rh-not-found`, `not-found.css`) and the routes' error boundaries use the same centred column and the same lead size for their one sentence, so every page that is not a list reads as the same kind of page. No chip anywhere on it: the topics are underlined text.

*The type's name stays a link* to its listing, decided here with the redesign. The page has no filter bar, so the meta line is the one place a reader can go from a resource to everything of its type, as they can from it to everything on each of its topics; a printed name beside linked topics would be the one thing in the row that looked like a link and was not. The dot's rule still holds: the mark is the `::before` of the span around the link, painted from `data-accent`, so it sits outside the link's text and its underline, with the gap `card-labels.css` gives it, and a cobalt dot beside a case study never reads as the start of the link. The link keeps the label's ink rather than taking the link colour, so the mark and the name stay the row's pair, and is underlined at the hairline weight, set low under the capitals, thickening to the strong line on hover: an underline rather than colour is what says it is a link.

*The body* (`rh-prose`, `prose.css`, shared with the CMS's pages) styles the editor's HTML by element after the sanitising pass (`lib/content/render.tsx`): headings from `h2` down, with the page's title the only `h1` and every body heading shown a level down when the editor wrote one (the pass's outline rule); paragraphs and lists at the body size with muted markers; links in the link colour, underlined at the hairline weight and thickened on hover. Three things are insets, boxed on the raised surface or edged with the hairline at `--rh-radius`, so a reader can tell them from the prose without colour: *the quote*, a step larger than the body, with a bar of `--rh-mark-coral` at `--rh-border-width-strong` down its left edge (twice that under forced colours, where it takes the box edge's colour and only its width tells it apart), the one hairline of brand colour in the article, and its `cite` as a small muted line; *the table*, whose box is the pass's scroll region (`.rh-table-scroll`, a focusable landmark named by the caption or "Table", so a wide table scrolls sideways inside the column, by keyboard too, and the page never does), with the header row a band of the raised surface under a strong rule in `--rh-color-border-strong`, hairlines between rows, including above a footer, and none under the box's last row, which the box's edge closes; and *code*, a `pre` on the raised surface that wraps rather than scrolls (a scrollable region would need a tab stop the sanitiser cannot give it), with inline code on the same surface at `--rh-radius-sm`. *Figures and images* take the featured image's corners but not its loading surface, which would show as a plate behind a transparent PNG or SVG (the image's own width and height reserve its box, so nothing moves without it), with the caption small and muted under them; a body image goes through `next/image` with the same `sizes` as the featured image, `CONTENT_SIZES` in the pass, which is `--rh-measure` written out as a length, and the viewport less the two gutters below it, because `sizes` cannot read a variable or a `ch` (the pass's docblock has the measurement and the rule: it never understates the rendered width, and the resource page's spec measures the image against it).

*The related list* (`.rh-related`) is one shape in three places: the resource page's related section under the article, the front end's `<RelatedResources>` in place of the `resource-hub/related-resources` marker in a body, and the marker's fallback, the CMS's own rendering of the block, which the pass marks with the same class and shows when the block's read fails. All three are a small collection in the listing's shape: a heading at `--rh-text-md` over a strong rule in the ink, and under it the rows of `card.css`, each row the listing's row with its title one level under the heading. The CMS block (`RelatedResourcesBlock` in the plugin) writes the same row markup inside the marker, with `role="list"` on its two lists and each row's `data-accent` from the shared type-accent table, so the editor preview and the CMS's own pages mark each type as the site does; the pass keeps that markup, and only it, inside a valid marker, without `data-accent`, so a fallback row's mark on the front end is the neutral ink; a marker that still holds a plain list of links, the block's first shape, renders each link on a row between hairlines, in the ink, semibold and underlined. In a body, `prose.css` keeps the body's heading, list, paragraph and link rules off the rows; outside one, `related.css` draws the heading's rule. A row that would say "Untitled resource", or names no type, is left out of a related list everywhere, on the CMS's side as on the front end's: a related row is a recommendation.

States are the same everywhere: `:focus-visible` draws the ring; links underline on hover, with the offset set once; the current filter and page use `aria-current` and the strong underline, and under forced colours an outline on top of it; the checked theme option has its fill and bar as described under [Theme and colour scheme](#theme-and-colour-scheme).

## Consumers and loading

Every consumer takes the package through the pnpm workspace as `@colbitron/resource-hub-ui`; it is never published. `tokens.css` is loaded before any component stylesheet, and each stylesheet is loaded only where its markup is rendered, except where a route's module graph imports it for markup the route may render (CMS pages, for the related-resources block; see below).

- **The front end.** `components/Shell.tsx` imports `tokens.css`, `base.css` and `shell.css`, in that order, and the root layout renders the shell around every page; no stylesheet is imported from `layout.tsx`, and each component imports its own CSS, from this package or, for what only the front end renders, from beside it in `apps/web/components/` (`ResourceCard` imports `card.css`; `ResourceArticle` imports `card-labels.css` alone, for its meta line, the resource page gets `card.css` from its related section's rows, and every CMS page gets it, with `related.css`, from the related-resources block's renderer, which `PageArticle` imports whether or not the body has a marker). The font is loaded by `app/fonts.ts` with `next/font/local`: the file from `fonts/` is served from the app's static assets under a hashed name, preloaded on every route, with `font-display: swap` and a size-adjusted Arial fallback face; [Font display](#font-display-swap) has the reasoning and the measurements. `components/Shell.tsx` also imports `fonts/figtree-fallback.css` beside the tokens, the package's own size-adjusted faces for systems without Arial, which `--rh-font-sans` lists after next/font's two names ([Fallback faces](#fallback-faces)). The loader sets `--rh-font-figtree` on `<html>` to its two generated family names, and `--rh-font-sans` in `tokens.css` reads that variable first, so no stylesheet needs to know the generated names; the layout applies that one class, because a variable read on `:root` has to be set on `<html>`.
- **The block.** The plugin's `resource-hub/related-resources` block has no stylesheet of its own: its compiled `block.json` lists two shared handles in `style`, `resource-hub-tokens` and then `resource-hub-card`, so core enqueues the tokens, then the row, in the editor and on the CMS's own pages only where the block is used. `resource-hub-card` is `card.css`, which the plugin's build copies from this package byte for byte into `build/shared/`, with the `card-labels.css` it imports beside it, so the two ship together, and which `src/Blocks/SharedCard.php` registers as a `<link>` (never inlined, so the relative `@import` resolves against the file); the deploy's sync of `build/` carries them. The handle is shared with the block theme, which enqueues it too, and WordPress prints a handle once, so a page with the block on the theme loads `tokens.css` once. The theme registers it first; the plugin registers its own copy, `build/shared/tokens.css`, which its build copies from this package byte for byte, at a later `init` priority only when nothing has, so the block keeps its tokens in any theme (`src/Blocks/SharedTokens.php`). The block's own output is the contract's heading over rows in `card.css`'s markup, the same rows `ResourceCard` renders, with titles at `h3` and the type's mark in its accent from `type-accents.json`, which the plugin's build copies into `build/type-accents.json` beside the stylesheets; so the editor preview and the CMS's own pages show the front end's rows. The front end never loads the block's stylesheet: it swaps the marker for its own `<RelatedResources>` list, and the fallback it shows when it cannot keeps the block's rows but styles them with its own CSS, so readers of the site are not affected. Figtree comes from the theme, not the plugin, so in another theme the block gets the system fallback in `--rh-font-sans`. Two more plugin blocks write the front end's markup for the CMS theme's templates, with the same renderer as the block's rows and the same loading: `resource-hub/resource-card`, one row for a Query Loop's post template, whose `block.json` lists the same two handles, so a page with both blocks loads `card.css` once; and `resource-hub/resource-meta`, the resource page's meta line, which loads the tokens handle and `card-labels.css` alone (`build/resource-meta/style-index.css`), as `ResourceArticle` imports it for that line, and leaves the line's layout to `resource.css`, which the template that renders the article loads. A page with the meta line and rows (a resource with its related list) declares the labels' rules twice, once in the meta block's file and once from `card.css`'s import: the same rules, so nothing changes but about a kilobyte.
- **The block theme.** `wp-content/themes/resource-hub/` is a workspace package whose build (`scripts/build.mjs`, run by the root's `pnpm build`) copies `tokens.css`, `brand.css`, the font file with `LICENSE-Figtree.txt` beside it, as the licence requires, and `fonts/figtree-fallback.css` into the theme's gitignored `build/`, byte for byte, since the host never sees the workspace and `theme.json` resolves `file:./` relative to itself. `theme.json` registers Figtree from that copy with `fontFace`, under the plain family name `Figtree`, with `font-display: swap`, and leaves `--rh-font-figtree` unset, so `--rh-font-sans` falls back to that name; its one font-family preset is `"Figtree", var(--rh-font-sans)`, because core names the face after the preset's first family. Its palette is the colour role tokens (not the mark accents, which are never text), its font sizes the size scale and its spacing sizes the spacing scale, and `layout.contentSize` and `wideSize` are `--rh-measure` and `--rh-measure-wide`, each written as a `var()` of its token and never as a value. `functions.php` enqueues `tokens.css` (the shared handle), `fonts/figtree-fallback.css` and `brand.css` on the CMS's own pages and in the iframed editor canvas, so an editor's page drawn before the font file lands gets the same fallback faces as the front end, and the header part's lockup is the front end's. ### Font display: `swap`

The front end loads Figtree with `font-display: swap`. The owner settled the choice on 2026-11-06, on the measurements below.

The preloaded file is 20 KB, and on a slow first visit it arrives at about the moment of the first paint. With `optional` the browser gives the file a very short block period and, if the file misses it, keeps the fallback face for the whole document. An App Router navigation keeps the document, so a reader who arrives over a slow connection reads every page of that visit in the fallback; only a full page load takes Figtree from the cache. With `swap` the page is drawn in the fallback until the file lands and in Figtree from then on.

Measured on cold visits (an empty cache) to a production build at 360 px, with Chromium's network emulation, ten runs per cell (three for Fast 4G); "Figtree on first paint" counts the runs whose first paint was drawn in Figtree, and the LCP figures are medians in milliseconds:

| Profile | Page | `optional`: Figtree on first paint | `swap`: Figtree on first paint | LCP, `optional` / `swap` | CLS, worst run |
|---|---|---|---|---|---|
| Fast 3G | resource | 0/10 | 9/10 | 1316 / 1312 | 0 |
| Fast 3G | listing | 5/10 | 10/10 | 1324 / 1316 | 0 |
| Slow 4G | resource | 5/10 | 10/10 | 488 / 476 | 0 |
| Slow 4G | listing | 10/10 | 10/10 | 476 / 472 | 0 |
| Fast 4G | both | 6/6 | 6/6 | about 385 | 0 |

The file landed between 5 and 35 ms before the first paint, a race that `optional` loses on slow first visits; `swap` does not depend on it, since a file that misses the first paint is still used once it lands. So `swap` put the brand face on the first paint of 39 of 40 cold loads on the two slow profiles, while `optional` dropped it on 15 of 20 cold Fast 3G loads, with the same LCP and no measured layout shift under either.

What the measurement does not cover: the server was local, with no TLS, and the emulation adds its latency to each response (CDP's `Network.emulateNetworkConditions`) rather than to each round trip, so it has no TLS handshake and no TCP slow start. The file's arrival relative to the first paint, which decides the race, may differ on a real connection in either direction. Field data from real visits would settle it.

The risk `swap` accepts is a file that lands after the first paint. Titles are bold, and the fallback face is size-adjusted against Figtree at the regular weight, so a bold title in the fallback is not quite the width it will be in Figtree, and a line can re-wrap when the face changes and push what follows down. With the file held back two seconds, two card titles below the fold on a listing at 360 px went from one line to two when Figtree arrived; CLS counts only what moves in the viewport, so it scored 0.0002, but the same re-wrap in the viewport would count. `apps/web/e2e/font-swap.spec.ts` holds the file back two seconds on the resource page and on a listing, each with a long title, checks that the first paint was in the fallback and that Figtree draws the title once the file has landed, and keeps the shift from the first paint until after the swap within CLS 0.05; and checks, by CDP's `familyName`, that the first paint was drawn in a font one of the size-adjusted fallback faces below covers, which on Linux, where Arial is absent, means one of the package's fonts; it cannot prove the face's size-adjust was applied, because Chromium reports `isCustomFont: false` for a `local()` face. A hand-tuned bold fallback face would narrow the width difference without removing it, and was not built. `optional` was the alternative turned down: nothing can move after the first paint under it, at the cost of the brand face on slow first visits.

### Fallback faces

The fallback face next/font generates matches `local("Arial")` alone, so a system without Arial skipped it and drew the first paint in whatever its fonts gave the next family in the stack, unadjusted: in Playwright's Linux image, which the screenshot gate runs in, that was WenQuanYi Zen Hei, through `system-ui`. `fonts/figtree-fallback.css` adds four faces, which `--rh-font-sans` lists after next/font's two names, in this order, so a common platform draws the first paint in a face sized like Figtree whatever fonts it has:

| Face | Fonts it matches (`local()`) | Where it is the fallback | `size-adjust` | Ascent / descent / line gap |
|---|---|---|---|---|
| `Figtree Fallback Arial` | Arial, Liberation Sans, Arimo | Most Linux systems (Liberation Sans), Playwright's image and CI's runner (`fonts-liberation`), ChromeOS (Arimo); on macOS and Windows next/font's own face, with the same numbers, comes first | 99.94% | 95.06% / 25.02% / 0% |
| `Figtree Fallback DejaVu Sans` | DejaVu Sans | Debian and Ubuntu without Liberation | 90.00%, measured (calculated: 87.26%) | 105.56% / 27.78% / 0% |
| `Figtree Fallback Noto Sans` | Noto Sans | Fedora | 96.00%, measured (calculated: 93.87%) | 98.96% / 26.04% / 0% |
| `Figtree Fallback Roboto` | Roboto | Android | 99.57% | 95.41% / 25.11% / 0% |

`scripts/figtree-fallback.mjs` derives the numbers and prints the stylesheet, and `test/figtree-fallback.test.js` fails when the two differ. The calculation is next/font's: `size-adjust` is Figtree's average advance width over the fallback's, both over next/font's frequency-weighted sample string, and each override is Figtree's own line metric divided by that `size-adjust`, so every face has Figtree's ascent, descent and line gap and only its width calibration differs. Liberation Sans and Arimo have Arial's advance widths and line metrics exactly, so one face serves the three. DejaVu Sans and Noto Sans are hinted, and Chromium on Linux, the one platform where they are the fallback, draws a hinted font at a whole pixel size and rounds each advance to a pixel, so their width there moves in steps. At the calculated values Chromium drew the site's 14 px text 5% narrower than Figtree, enough for the listing's topic filters at 360 px to fit on one line fewer and move the lead below them when Figtree landed. Their `size-adjust` is instead the value at which Chromium in Playwright's Linux image drew the first 1,500 words of this file closest to Figtree's width at 14 and 16 px. The script's comment has the figures.

Measured on 2026-11-06 with `apps/web/e2e/font-swap.spec.ts`'s two late-font tests (the file held back two seconds, CLS from the first paint until after the swap), in Chromium on macOS and in Playwright's pinned Linux image on `linux/arm64`. "Before" is the build without these faces. For the three single-font rows, Ubuntu's `fonts-dejavu-core`, `fonts-noto-core` and `fonts-roboto` were added to the image and every other candidate font removed:

| Platform, the font of the first paint | Resource page, 360 px | Listing, 360 px | Resource page, 1280 px | Listing, 1280 px |
|---|---|---|---|---|
| macOS, Arial (next/font's face), before and after | 0.0000 | 0.0005 | 0.0038 | 0.0003 |
| Linux image, before: WenQuanYi Zen Hei | 0.0001 | 0.1752 | 0.0002 | 0.0006 |

With the calculated `size-adjust`, DejaVu Sans and Noto Sans moved the 360 px listing by 0.1742 and 0.1753, and with no face at all (`system-ui` giving them unadjusted) by 0.0399 and 0.0436; the measured values brought both to the row above. Each face is the regular weight, and the browser synthesises bold from it, as from next/font's: a bold title in any fallback is about 4% narrower than in Figtree, and the listing's lead title still goes from one line to two at 360 px when Figtree lands, low enough in the viewport that it scores as above. A bold face per font, calibrated on Figtree's bold, would close that, and was not built. Glyphs Figtree's Latin subset lacks (Cyrillic, Greek, some symbols) now fall to the first fallback face that has them, at that face's `size-adjust`, so on a system with DejaVu Sans alone they draw about 10% smaller than they would unadjusted; that is accepted as rare and cosmetic.

## Do's and Don'ts

- **Do** build on tokens; **don't** write a colour, size or space as a raw value in a component stylesheet.
- **Do** import a stylesheet from the component that renders its markup; **don't** import one from `layout.tsx`.
- **Do** print the type's name beside its mark, with the dot before the name and outside its link where the name is one; **don't** use a mark as text, as a text background or as part of a link, and **don't** draw an accent as a line except the quote's coral bar.
- **Do** underline links; **don't** rely on colour alone for any state.
- **Do** keep every list typographic, on the one surface, with rules for structure; **don't** box, fill or pill a row, a filter, a page number or a topic.
- **Do** box a quote, a table and a code block inside an article as insets, so they read as what they are; **don't** box anything a reader activates, and **don't** put a photograph, a fill or a shadow behind the page.
- **Do** write every colour as a `light-dark()` pair; **don't** add a `prefers-color-scheme` media query.
- **Do** keep Figtree the only typeface; **don't** add a web font, and **don't** let a browser request anything from Google.
- **Do** draw the mark from `icon.svg` or `Brand.tsx`, in its own colours; **don't** recolour it, and **don't** use it alone as a link.
- **Do** keep motion to short CSS transitions, all off under reduced motion; **don't** animate with JavaScript.
- **Do** keep plain CSS with BEM-ish class names under the `rh-` prefix; **don't** add a framework, a preprocessor, CSS-in-JS or shared JavaScript. Utility frameworks and CSS Modules generate or rewrite class names at build time, and the markup WordPress renders in PHP could not share them, so the contract's class names stay plain.
- **Do** treat a token or class rename as a contract change made on both sides in one pull request.

## Changing the system

1. Change the value in `tokens.css`, or add the token there. A new token goes into the specimen's list (`apps/web/app/fixtures/specimen/tokens.ts`) and onto the page; `apps/web/test/specimen-tokens.test.ts` fails until it does.
2. Say what it is for in this document; `test/design-doc.test.js` fails until it does.
3. Run the package's tests from the repository root, `pnpm test:schemas`, which now also runs the contrast and design-doc tests, and the front end's `pnpm web:test`.
4. Regenerate the specimen baselines with `pnpm web:test:screenshots:update` and read the diff images like code: every design change shows its cost there.
5. Run the rest of the gate: `pnpm web:typecheck`, `pnpm web:lint`, `pnpm web:test:e2e` (which includes the axe scan of every template in both schemes), `pnpm web:test:screenshots` and `pnpm web:test:lighthouse` (mobile; performance at least 0.95, accessibility 1, LCP at most 2500 ms, CLS at most 0.05, TBT at most 200 ms). A budget or a rule that fails is a finding to fix in the design, never a threshold to loosen.

A change to a component stylesheet here is a change to every consumer that loads it: the front end's gate above covers the site, and the CMS theme's pages change with it once its templates load the file. A rename of a token or a class is a contract change: both sides in one pull request, and additive where a consumer could be a deploy behind. A decision that changes the direction of the system (a new typeface, a different scheme mechanism) is recorded as an ADR; everything else is recorded here.
